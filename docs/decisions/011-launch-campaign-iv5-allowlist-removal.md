# 011. Remove the `launch-campaign` IV-5 test-send domain allowlist

**Status:** Accepted
**Date:** 2026-05-11
**Linear:** [BC-7599](https://linear.app/brite-nites/issue/BC-7599)
**Related issues:** [BC-6785](https://linear.app/brite-nites/issue/BC-6785) (round-5 dogfood that surfaced the issue), [BC-5826](https://linear.app/brite-nites/issue/BC-5826) (original `launch-campaign` skill build that introduced IV-5)
**Affected files:** [`plugins/marketing/commands/launch-campaign.md`](../../plugins/marketing/commands/launch-campaign.md) § Input validation § IV-5; [`docs/marketing-context.md`](../marketing-context.md) (deleted)

## Context

`/marketing:launch-campaign` Phase 10 Mode 2 (`--test-send <email>`) calls Email Bison's `POST /api/campaigns/sequence-steps/{step_id}/test-email` endpoint to deliver a single real email to an operator-supplied inbox for end-to-end pipeline verification. Originally, Input validation rule IV-5 layered three checks before the call:

1. **Regex validation** of `--test-send <email>` for malformed input.
2. **Structured JSON construction** of the `call_api` body (never string concatenation of operator input).
3. **Domain allowlist check** against `docs/marketing-context.md § test_send_allowlist`. The recipient's domain had to appear in this allowlist or Mode 2 would hard-halt. No `--allow-external-test-send` override existed.

The threat IV-5 (3) was designed against: operator types a recipient that is NOT their own inbox but believes they are test-sending to themselves — typo on own domain, copy-paste from CRM, autocomplete misfire — and a half-baked test email reaches a real customer.

The BC-6785 round-5 dogfood walk hit the friction shape of this design directly. A fresh worktree had no `docs/marketing-context.md`. Mode 2 hard-halted at IV-5 even though the recipient was `corinne+bc-6785-r5@britenites.com` — the operator's own inbox at the company's own domain. The round-5 mitigation was to manually create a `marketing-context.md` stub with `## test_send_allowlist` listing `britenites.com`. Workable, but logged as a follow-up (F-IV-5) because every fresh worktree, every new repo using the plugin, and every operator onboarding hit the same friction.

BC-7599 was filed as the design issue. Five resolution shapes were considered (auto-detect from `git config user.email`, ship a default stub at plugin install, an explicit `--allow-operator-self-send` flag, combinations, and a refined "git-config fallback when allowlist absent/empty" variant). All five preserved the allowlist concept and tried to fix its bootstrap friction. None of them re-examined whether the allowlist itself was earning its keep.

## Decision Drivers

- **Threat-to-friction proportionality.** IV-5's allowlist only gates `--test-send` — a single email at a time, manually typed by the operator. Real campaign activation (Phase 9 sequence creation + Phase 11 resume) sends to a CSV-sourced lead list of arbitrary size and has **no equivalent allowlist gate**. The current design applies tighter friction to the lower-blast-radius case.
- **Existing per-send safety surface.** Phase 10 Mode 2 step 4 already prompts the operator with the exact recipient address before the `call_api` fires (`Send real test email to {test-send email}? [Y/n]`). The allowlist is an upstream policy layer; the operator-confirm prompt is the actual per-send check.
- **Realistic failure mode.** The operator who clicks through the recipient-confirm prompt without reading would also have manually-authored the allowlist without reading — the allowlist does not catch the realistic clickthrough failure that the operator-confirm prompt also misses.
- **Recurring bootstrap friction.** Every fresh worktree, every operator onboarding, every potential plugin install in a new repo hits the same halt-with-no-recovery-path. The "fix" (manually author `marketing-context.md`) is documentable but is a tax paid forever.
- **Source-of-truth canon.** `docs/marketing-context.md` is the canonical artifact generated by the `product-marketing-context` skill. Stubbing it from `launch-campaign` for the narrow allowlist purpose created a parallel "stub-it-from-here" path that competed with `product-marketing-context`'s ownership.

## Decision

**Remove IV-5's domain allowlist check. Retain IV-5's email-format regex and structured-JSON construction.**

Mode 2's per-send safety relies on:

1. **Email-format regex** (IV-5, retained) — catches malformed `--test-send` values.
2. **Structured JSON construction** (IV-5, retained) — ensures operator input is JSON-serialized, never string-concatenated into the `call_api` body.
3. **Phase 10 Mode 2 step 4 operator confirmation prompt** (already present, unchanged) — displays the exact recipient address and requires explicit Y/n affirmation before the `call_api` fires.

The `docs/marketing-context.md` stub created during BC-6785 round-5 is deleted. The file had a single consumer (IV-5's allowlist check) and was explicitly labeled as a stub awaiting replacement by the `product-marketing-context` skill. With IV-5's allowlist gone, the stub serves no purpose, and other marketing skills that read `marketing-context.md` already have a "warn-and-proceed-with-reduced-context" standing policy for the absent-file case (see `plugins/marketing/skills/product-marketing-context/SKILL.md` line 142).

## Alternatives Considered

### A. Auto-allowlist via `git config user.email` domain match (the original BC-7599 candidate)

Read `git config user.email` at IV-5 evaluation time and treat the operator's own domain as implicitly allowlisted. Zero workspace setup; generalizes across orgs.

**Why rejected:** Preserves the underlying allowlist concept. If the allowlist itself isn't proportionate to the threat, adding an auto-detection fallback is treating the symptom (bootstrap friction) rather than the cause (the allowlist's value relative to its friction). The auto-detection also creates a silent-policy behavior — operators wouldn't know when the auto-allowlist fired vs. when the file's explicit allowlist fired.

### B. Ship a pre-filled `marketing-context.md` stub at plugin install

Bundle a starter `marketing-context.md` with `britenites.com` pre-populated as part of the marketing plugin install.

**Why rejected:** Plugins writing files into operator-owned repos is anti-pattern. Hardcodes `britenites.com` into a plugin meant to generalize. Competes with the `product-marketing-context` skill, which is the canonical "create marketing-context.md" surface.

### C. Add `--allow-operator-self-send` flag

Explicit command-line opt-in flag bypassing IV-5 for the operator-self-send use case.

**Why rejected:** Moves the friction from "remember to author a file" to "remember to type a flag" without removing the underlying allowlist mechanism. The realistic failure mode (clickthrough without reading) is unaffected. Operator alias-habituation defeats the explicit-authorization property.

### D. A + B combined

Auto-detect via `git config` plus a shipped stub.

**Why rejected:** Inherits both B's anti-pattern flaws and A's silent-policy concerns. Maximal complexity for a layer that itself isn't earning its keep.

### E. Skill offers to create the file on first run

Skill prompts the operator to create `marketing-context.md` when missing.

**Why rejected:** Duplicates the `product-marketing-context` skill's job from inside `launch-campaign`. Two surfaces for "create the file" create coordination drift.

### F. Refined A — git-config fallback only when allowlist absent/empty

Use git-config domain as fallback only when `marketing-context.md` is missing or has an empty allowlist; file remains authoritative when present.

**Why rejected:** Initial analysis preferred this option because it preserved the "file as source of truth when present" property. Reviewing the threat model surfaced that the allowlist as a layer is itself disproportionate to the threat — the operator-confirm prompt at Mode 2 step 4 already does the actual per-send safety work. Removing the layer entirely is cleaner than building a fallback for a layer that wasn't pulling its weight.

## Consequences

### Positive

- Fresh worktrees and new repos that install the marketing plugin can immediately run `--test-send` without authoring any marketing-context artifact.
- The single per-send safety surface (Mode 2 step 4 operator-confirm prompt) is now the unambiguous "before the email fires" gate. No layered confusion about which check stopped a send.
- `marketing-context.md` ownership simplifies: `product-marketing-context` is the sole creator; no skill stubs the file from a side path.
- ADR documents that the threat model was re-examined and the allowlist layer was found disproportionate — future contributors who consider re-adding a domain allowlist have the rationale on file.

### Negative

- Loses the (weak) typed-policy artifact that an audit could point to as "we sanctioned these test-send domains." Audit value was already weak — the allowlist was operator-self-authored in a working stub, not a centrally-managed policy.
- Slightly increases the surface where operator clickthrough of the Mode 2 step 4 prompt could send a test email to a wrong domain. Mitigation: the prompt displays the full recipient address; the operator typed the address; the cognitive load of one address in one prompt is low.

### Out of scope

- The `product-marketing-context` skill's broader purpose (brand voice, ICPs, sender info) is unchanged. Other marketing skills continue to read `marketing-context.md` under the existing warn-and-proceed-when-absent policy.
- Production campaign activation (Phase 9 sequence creation, Phase 11 resume) is unaffected. Those phases were never gated by IV-5's allowlist.

## Verification

A future BC-6554-style live-walk of `launch-campaign` in a fresh worktree should confirm Mode 2 with `--test-send <operator-email>` proceeds without an `marketing-context.md` artifact present.
