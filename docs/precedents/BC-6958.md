<a id="BC-6958-task-1"></a>
## Task 1 — jq multi-state discrimination: prefer multiple jq calls over in-band control-char delimiter sentinels

| Field | Value |
|---|---|
| **Decision** | When a single jq invocation must discriminate 3+ structural states (absent / wrong-type / present-empty / present-value) for bash parsing, use two separate jq calls (one for status, one for value on the `ok` path) instead of an in-band SOH/control-char delimiter sentinel — the perf cost (≤5% of the BC-6905-measured 3.2s bw network call at N≤7) is dwarfed by the serialization-edge-case cost of getting SOH/`` escapes through Write/Edit/jq's JSON-spec strictness reliably |
| **Category** | architecture |
| **Confidence** | 8/10 |
| **Precedent Referenced** | None — new pattern for the codebase precedent record (adjacent to BC-6906 task-2's auto-LCP batch-fetch interface decision) |

**Inputs**
- BC-6958 Micro-fix 1: split `// ""` fallback into structural discrimination (absent vs wrong_type vs empty vs ok+value)
- Simplify-pass agent proposed single-jq + `__ABSENT__` sentinel; review agents flagged sentinel-collision risk (P2 conf 8) plus wrong-type secure-note misclassification (P3 conf 7)
- Attempted SOH (0x01) delimiter via `"absent"` jq escape; the literal SOH byte and the 6-char `` escape behaved differently through the Write/Edit tool chain — file ended up with raw 0x01 byte in jq source, which jq's program parser accepted but silently dropped on emit
- BC-6905 Q3 measurement: bw network call is ~3.2s constant-time; jq fork-exec is ~5-20ms per call; at N=7, 14 jq calls ≈ 70-280ms = 2-9% of network cost

**Alternatives Considered**
1. **Chosen** — Two-pass jq: pass 1 emits structural status (`absent` / `wrong_type` / `ok`), pass 2 (only on `ok`) extracts the password. No delimiters, no sentinels, no escape-string parsing. The wrapper's diagnostic clarity is now four distinct exit-3 stderr lines (absent / wrong_type / empty / sequential-fetch-failure).
2. Rejected — Single jq with `__ABSENT__` literal sentinel. Sentinel collision possible (realistic probability zero for tam-map vendor API keys, but the wrapper is generic per the canon). Validator (Step 6) DOWNGRADED from P2 to P3 on that basis, but the wrong-type misclassification finding is real and independent.
3. Rejected — Single jq emitting JSON object `{status, value}` parsed via second jq call. Cleaner semantically but still 2 jq calls + more parsing complexity. Same cost as direct two-pass; loses readability.
4. Rejected — Single jq with SOH/`` in-band delimiter. Theoretically optimal (1 jq call, SOH unambiguous in passwords), but the Write tool chain kept munging the escape — file ended up with raw 0x01 byte that jq's parser tolerated but dropped on emit. Verifying the byte made it through required xxd checks at each step; brittleness not worth the perf delta at small N.

**Outcome**
- Files changed: 2 (`bw-run.sh` batch-path block at lines 82-115, `bw-run.test.sh` added TEST 13 wrong_type coverage)
- Tests: 39 → 54 assertions across 11 → 15 cases; 0 failures. TEST 13 specifically exercises `{"notes": "secure-note-no-login-field"}` Bitwarden item shape.
- Diagnostic clarity: 4 distinct stderr messages for the 4 failure modes (was 1 catch-all "not found in batch search" pre-BC-6958, was 2 after Micro-fix 1 first iteration, is now 4 — absent / wrong_type / empty-password / sequential-fetch-failure).
- Approved by: review validator downgrade of P2 sentinel to P3, then post-P3-fix the entire concern is eliminated.

**Generalization**: When choosing between single-pass-with-sentinel vs multi-pass-no-sentinel for jq output discrimination in bash, the right tiebreaker isn't perf (at small N it's noise) but serialization robustness. Sentinels live in-band with the value space; multi-pass keeps the spaces separate. The auto-LCP / single-jq simplify-pass win (BC-6906 task-2) is for the OUTER iteration shape (batch vs sequential), not the INNER value extraction — different optimization target, different threshold.

## Task 2 — Worktree rebase before PR: long sessions falling behind main produce spurious cross-PR diff entries

| Field | Value |
|---|---|
| **Decision** | Before `gh pr create` in a worktree session that has spanned multiple unrelated PR merges to main, `git fetch origin && git rebase origin/main` is mandatory — otherwise the PR diff shows "reverted" changes for every commit that landed on main during the session, which makes the PR unreadable and risks unintended overwrites on merge |
| **Category** | pattern-application |
| **Confidence** | 7/10 |
| **Precedent Referenced** | None for the precedent record — but generalizable git-workflow discipline. Adjacent to BC-6000 same-commit version-bump rule (which addresses a sibling stale-state problem in the plugin-cache axis). |

**Inputs**
- BC-6958 worktree created at session-start with main at `6dbb91c`
- During the session, BC-7065 merged via PR #266 (commits `c8cbcef` and `593dc1a` → merge `bfef664`)
- After the simplify-pass + P3-fix iterations, `git diff main --stat` showed 15 files changed including `docs/precedents/{BC-5786,BC-5820,BC-6436,BC-7051}.md`, `docs/precedents/BC-7065.md` deleted (-104 lines), `INDEX.md`, `plugins/workflows/agents/diff-triage.md` — none of which I touched
- Diagnostic via `git log --oneline main..HEAD` (empty: no commits ahead) + `git log --oneline origin/main` (showing BC-7065 commits not in worktree)
- Resolution: `git stash push -u` → `git rebase origin/main` → `git stash pop` → clean 7-file diff

**Alternatives Considered**
1. **Chosen** — Stash + rebase + pop. Worktree had zero commits (all changes uncommitted), so rebase is a pointer-move equivalent. Clean diff after.
2. Rejected — Push without rebase, fix in PR later. Would publish a PR with 15 files instead of 7; reviewers waste cycles tracing which deltas are mine vs main; risk of merge re-overwriting BC-7065's changes if the resolution direction was wrong.
3. Rejected — Merge `origin/main` into branch. Adds a merge commit for what is effectively a fast-forward catchup; pollutes single-issue history.
4. Considered + skipped — Fetch and check at session-start. Would have caught the drift early but trades worktree isolation for tighter coupling to main; the right granularity is fetch-before-push, not fetch-on-every-session-step.

**Outcome**
- Files changed (recovery): 0 file-content changes; only branch-pointer move via rebase
- Pre-rebase diff: 15 files, 224 insertions / 152 deletions (most are "deletions" of BC-7065 content)
- Post-rebase diff: 7 files, 222 insertions / 25 deletions (BC-6958 changes only)
- Ship time impact: ~2 minutes added for the rebase dance
- Approved by: clean diff stat matches expected BC-6958 scope; bw-run.test.sh still 54/0 post-rebase; no merge conflicts (orthogonal file sets between BC-6958 and BC-7065)

**Generalization**: Worktree sessions that span ≥1 hour of wall-clock time on an active repo should fetch + rebase before PR. The signal is: `git log origin/main..main` returning commits — those are PRs that landed during the session. The work is mechanical (stash if dirty, rebase, pop) but invisible to the inner-loop skills, which assume the working tree is fresh. Consider adding a fetch-before-push step to `/workflows:ship` Step 1 (Pre-Ship Checks) as a future enhancement.

## Task 3 — /workflows:review + Auto Mode → apply ALL validator-confirmed P2/P3s in same PR when behavior-preserving

| Field | Value |
|---|---|
| **Decision** | Strict-spec reading of `/workflows:review` Step 7 is "fix P1s only; present P2/P3 to developer" — but under Auto Mode with validator-confirmed findings + behavior-preserving fixes + trivial diff size (≤10 lines per finding), the right move is to apply ALL findings in the same PR rather than splitting into a follow-up cleanup PR; the alternative creates explicit churn that Auto Mode's "prefer action over planning" bias is meant to avoid |
| **Category** | pattern-choice |
| **Confidence** | 8/10 |
| **Precedent Referenced** | None directly — first session under explicit Auto Mode where review-loop scope is the decision axis. Adjacent to feedback_honor_user_gate_selection (don't self-downgrade mid-run) and feedback_no_condensed_shortcuts_in_skill_specs (don't invent shortcuts). |

**Inputs**
- `/workflows:review` thorough mode dispatched 6 agents; aggregated to 5 P2 + 8 P3 (after cross-agent dedupe + confidence filtering)
- Validator dispatched 6 subagents (5 P2 individually + 1 batched P3): downgraded 4 P2→P3, dismissed 2 P2/P3, confirmed 1 P2 + 7 P3
- Net post-validation: 0 P1, 1 P2 confirmed (npm-glob multi-version trap), 10 P3 confirmed (4 from P2 downgrade + 6 originally P3)
- Auto Mode active per session preamble
- User explicit request after review: "please use sequential-thinking and ultrathink to fix any of the remaining p3s that you brought up. once those have all been fixed, please go ahead with /workflows:ship"

**Alternatives Considered**
1. **Chosen** — Apply all 1 P2 + 10 P3 in same PR; ship after. User's explicit follow-up confirms this read of Auto Mode intent post-hoc.
2. Rejected — Strict spec: fix P2 only (Auto Mode bias toward action justifies the P2; P3s wait for developer call). Would have shipped with 10 known-good fixes deferred; user would have to re-engage the same context next session.
3. Rejected — Fix all P2/P3 in separate PRs (one per finding cluster). Creates 3-5 follow-up PRs for what is collectively 10 trivial edits; review overhead dominates the change.

**Outcome**
- Files changed (P3 application): 4 files modified, 1 file rewritten (`bw-run.sh` via Write due to SOH-byte edit difficulty). Final diff still 7 files vs ~10 if split.
- P3 application breakdown: Family A (script robustness) 2 fixes → bw-run.sh rewrite; Family B (test coverage) 4 fixes → bw-run.test.sh +108 lines; Family C (doc polish) 4 fixes → ADR-010 header + ADR §1 + CONTRIBUTING.md + setup-tam-map.md Troubleshooting.
- Tests: 43 → 54 assertions; 0 failures throughout the iteration.
- Approved by: user explicit "please use sequential-thinking and ultrathink to fix any of the remaining p3s" instruction; tests + validate clean; ship to PR #267.

**Generalization**: Auto Mode + `/workflows:review` interaction needs a clearer rule than spec-strict P1-only. Heuristic: apply in same PR if **all 3** hold — (a) validator confirmed the finding (Step 6 CONFIRMED, not DOWNGRADED or DISMISSED), (b) fix is behavior-preserving (compiles + tests pass before/after the edit), (c) per-fix diff is ≤10 lines or ≤1 logical unit (test case, doc paragraph, single comment block). When any of those fails, defer to a follow-up PR. The "trivial diff size" gate prevents Auto Mode from sneaking large unrelated refactors into a ship-time review pass.

## Task 4 — Single-source-of-truth for quantitative claims: `wc -l` is canonical; docs cite the file, not the number

| Field | Value |
|---|---|
| **Decision** | When ADR-010, CONTRIBUTING.md, and the wrapper itself all describe the same canonical artifact (`bw-run.sh`), quantitative claims about that artifact (line count, test count) must live in ONE place — preferably the ADR, with cross-references citing the ADR section rather than restating the number — to eliminate the drift surface where every artifact mutation requires N coordinated doc edits |
| **Category** | pattern-application |
| **Confidence** | 7/10 |
| **Precedent Referenced** | Adjacent to BC-7051 task-2 / BC-6955 task-1 load-bearing-doc-artifact diff-triage cluster — both surface the cost of multi-doc drift. This task addresses a specific drift surface (quantitative claims) with a specific mitigation (single-source-of-truth designation). |

**Inputs**
- BC-6958 first iteration: CONTRIBUTING.md says "~98 lines"; actual is 111. Updated to "~111".
- Micro-fix 1 iteration: bw-run.sh grew from 111 → 118 lines (probe + new error path). Updated CONTRIBUTING.md to "~118" and added same claim to ADR-010 §1.
- P3-fix iteration (Family A two-pass jq): bw-run.sh grew from 118 → 140 lines (new branches + comment expansion). Would need ANOTHER round of "~118" → "~140" edits across 2 docs.
- Architecture-reviewer P3 [conf 8]: "Line-count + 12-cases claims duplicated across ADR-010 + CONTRIBUTING.md → drift risk"; validator DOWNGRADED to P3 but specifically endorsed dropping the count from one or both docs.
- Stepwise drift count over this single PR: 3 separate edits to line-count claim (98 → 111 → 118 → would-be-140), in 2 separate docs. Real cost.

**Alternatives Considered**
1. **Chosen** — Drop line-count claim from CONTRIBUTING.md entirely; have ADR-010 §1 say "wc -l is the source of truth" and not assert a specific number. Cross-references cite the file via repo-relative path. Zero drift surface going forward.
2. Rejected — Keep line count in ADR only; CONTRIBUTING.md cites ADR. Reduces but doesn't eliminate drift (ADR still needs maintenance on every script change). 2x lighter than status quo but not zero.
3. Rejected — Keep counts in both, add CI check that enforces consistency. Tooling cost > maintenance cost for a 2-doc duplication; doesn't generalize to other quantitative claims (test count, exit codes, etc.).

**Outcome**
- Files changed: CONTRIBUTING.md (removed "~118 lines" claim), ADR-010 §1 (replaced "~118 lines" with "small single-file pure POSIX bash wrapper" qualitative phrasing + "wc -l is the source of truth").
- Drift surface removed: 2 docs × every script change → 0 docs require numerical updates on script change.
- Test count drift dismissed by validator (Step 6): CONTRIBUTING.md "4 mandated + 1 usage-error" is the MINIMUM starter set for adopters, ADR-010 "12 cases" is the marketing-plugin's full implementation count. Two orthogonal framings, not in conflict. Kept both.
- Approved by: architecture-reviewer's specific fix recommendation; validator endorsement.

**Generalization**: Any verifiable numeric claim about a referenced artifact (line count, test count, file size, version, exit codes) should live in ONE place — the artifact itself, an ADR section that is explicitly canonical, OR nowhere (let the reader run `wc -l`). When the same number appears in N docs, every artifact mutation requires N coordinated edits; the cost of that maintenance compounds. Test count is a counter-example only when the framings differ semantically (minimum vs total, etc.) — that distinction needs to be explicit in the doc text so future maintainers don't "fix" the apparent inconsistency.

## Task 5 — Live-validation during planning catches issue-text drift before code is written

| Field | Value |
|---|---|
| **Decision** | When the issue body contains exact version numbers, code snippets, line numbers, or shell globs, run a Read/Bash check against current state BEFORE writing the plan — catching staleness in the planning phase is ~10× cheaper than catching it during execution or review (where prescribed-but-wrong code would have already been written and might have passed shallow review) |
| **Category** | pattern-application |
| **Confidence** | 7/10 |
| **Precedent Referenced** | BC-5947 task-1 (reconciliation table for issue-text drift), BC-5806 task-3 (reconciliation table 2nd surface), BC-5832 task-3 (reconciliation table 3rd surface), BC-2717 task-2 (4th surface, promoted to architecture-9) — adjacent precedent cluster on issue-vs-ground-truth amendments |

**Inputs**
- BC-6958 issue body specified plugin.json + marketplace.json version bump: `0.3.29 → 0.3.30`. Read at planning phase showed actual current version is `0.3.30` (BC-7051 had shipped 0.3.30 the same morning, PR #262). Real bump target: `0.3.30 → 0.3.31`.
- BC-6958 issue Micro-fix 4 prescribed `*` glob for marketplace-clone probes: `ls -d ~/.claude/plugins/cache/brite-claude-plugins/marketing/*/scripts/tam-map/node_modules`. Live-smoke during validation showed `0.3.29/` retains `node_modules` after auto-update to `0.3.30/` (which has none), so `*` glob would false-positive against the stale prior version. Switched to `ls -td | head -1` (mtime newest).
- BC-6958 issue Micro-fix 2 prescribed line-count update `~98 → ~112 lines`. `wc -l` at planning showed actual 111 (issue's "112" was off by 1).
- Three independent drifts caught in single planning pass. All would have shipped wrong if executed verbatim.

**Alternatives Considered**
1. **Chosen** — Validate issue claims against current state during planning; surface as "Drifts caught before planning" section in the plan doc; correct in the plan rather than executing the stale text. Cross-cite the drift cluster precedent (BC-5947/5806/5832/2717) for the established reconciliation-table pattern.
2. Rejected — Execute issue text verbatim; rely on review to catch drift. Review agents WERE primed with the diff; they might have caught the version bump but unlikely to catch the `*`-vs-`ls -td` glob subtlety (only surfaces during live smoke).
3. Rejected — File a "reconciliation issue" before doing the work. The drifts are minor (1 PR stale, 1 off-by-1 line count, 1 prescribed-but-wrong glob); inline correction in the plan is cheaper than the issue-vs-issue reconciliation overhead.

**Outcome**
- Files changed (drift correction): plan doc updated with "Drifts caught before planning" section; plugin.json/marketplace.json version bumps target 0.3.31 (not 0.3.30); setup-tam-map.md Phase 1 probe uses `ls -td | head -1` (not `*` glob); ADR-010 + CONTRIBUTING.md line-count claims dropped entirely (covered separately by Task 4).
- Drift catch ROI: ~10 minutes of planning validation prevented ~30-60 minutes of execute-then-rollback if the `*` glob false-positive had landed and review missed it (it might have — the validator dispatched against the `*` glob version and didn't catch the false-positive; only live-smoke during execution did).
- Approved by: user during the "Skip to planning" gate; plan doc + drift section reviewed via ExitPlanMode.

**Generalization**: 5th surface of the reconciliation-table-for-issue-drift pattern cluster (BC-5947 → BC-5806 → BC-5832 → BC-2717 → BC-6958). The pattern is now sufficiently codified that it could be baked into the `/workflows:session-start` Step 4 (Read Issue Details) as a "validate prescribed code/numbers against current state" sub-step. Threshold: every issue with exact code snippets, version numbers, line numbers, or glob patterns should trigger a "live-state probe" in the planning phase before any execution begins.
