## task-1 — Precedent-fix scope: when sibling artifacts share a code path, fix both in the discovering PR

**Pattern type:** pattern-choice (NEW — 1st surface)

**Confidence:** 9/10

**Context.** Iteration 1 of `/workflows:review thorough` on BC-6963 surfaced a P1 (conf 10): the Phase 1 bash dispatch to `flow-resume-breadcrumb.sh` used `--mode --current-phase --completed-phases --status` flags that don't exist on the BC-6956 helper. The helper takes a positional `<path>` and reads JSON from stdin — verified by reading the helper script before applying the fix (cribbed from BC-6962 task-1's "validators must consult upstream" discipline). The same broken bash snippet existed in BC-6962's just-merged `start-project.md` (shipped 2 sessions ago at PR #275, before either orchestrator had been dogfooded end-to-end).

**Decision.** Fix BOTH orchestrators in this PR rather than file a follow-up Linear issue for the BC-6962 sibling. Rationale:
1. The bug literally won't run end-to-end on either orchestrator's first dogfood — fixing both ahead of Brand Hub dogfood (BC-6998, v1.0 acceptance gate per Q40 sub-decision 4) prevents two cascading dogfood failures.
2. BC-7446 task-2 meta-precedent: "cross-document references need ground-truth fetch at authorship; encode protocol into review-agent prompt, not into author memory." Generalizes to: "when the protocol layer is wrong, fix at the protocol layer, not document-by-document." Filing a follow-up issue would defer + atomize the fix.
3. The fix is line-for-line identical between siblings (same python heredoc, same `last_updated` rename) — zero additional risk from including the precedent-fix in the same PR. The diff scope creep is ~46 lines on start-project.md vs ~78 net on retrofit-project.md.
4. The user's `/workflows:review … fix them` instruction was permissive on scope; nothing in the issue body or session memory said "retrofit only."

**Rejected alternatives:**
- File-and-defer: would have closed BC-6963 with a known dogfood-fail in the sibling. Net cost: 1 extra Linear issue created + 1 extra PR cycle in the next session.
- Hot-patch BC-6962's PR retroactively: BC-6962 already merged; amending closed PRs isn't standard. Would have required reopening or filing a new PR anyway — strictly worse than including in BC-6963's PR.
- Open a separate sibling PR from this session: doubles the review/CI burden for a single semantic fix.

**How to apply.** When `/workflows:review` surfaces a defect in artifact X that the reviewer notes "also exists in sibling Y" (especially when the cause is shared upstream contract drift or helper-signature drift), include sibling Y's fix in the same PR if:
(a) the sibling is in the same plugin/directory and untouched by other in-flight PRs,
(b) the fix is line-for-line identical (zero divergence risk),
(c) the sibling's defect blocks the same downstream dogfood / acceptance gate as the primary artifact.
If any of (a)/(b)/(c) is violated — e.g., sibling fix requires deeper refactor, or sibling is owned by a different feature branch — file a follow-up issue instead.

**Telemetry watch.** Look for this pattern to surface in BC-6964 (`/flow:add-domain` orchestrator), BC-6965 (`/flow:add-sub-flow`), and BC-6996 (plugin CLAUDE.md) as they ship — each of those may discover sibling bugs in already-merged orchestrators and have the same decision point. ## task-2 — Independent post-PR review pass is non-redundant with in-loop review

**Pattern type:** pattern-application (NEW — 1st surface)

**Confidence:** 8/10

**Context.** The user instructed (verbatim): "after the PR is open, run one more independent review agent against that PR. if it comes back clean, proceed with merging." The in-loop `/workflows:review thorough` had already run twice and converged on 0 P1 / 0 P2 (with all simplify-pass nits ship-as-is). The user's post-PR pass appeared on its face redundant.

**Decision.** Dispatched one independent code-reviewer agent against the open PR with a fresh prompt explicitly listing 10 cross-check claims for the agent to re-verify against the helper script + the Q37 lock + the issue body's acceptance criteria. The agent found 1 conf-9 P3 (placeholder drift `<retrofit>` vs `<retrofit-slug>` in resume contract rows 3-4) that BOTH in-loop iterations had missed. The drift was real: every other reference in the file used the canonical `<retrofit-slug>` placeholder per the slugification contract; only those two table cells had the bare form. Fix was 2 chars × 2 lines, applied + pushed in a 3rd commit, then merged.

**Rejected alternatives:**
- Skip the independent pass: user explicitly asked for it; instruction was unambiguous.
- Treat the independent agent as just-another-iteration of `/workflows:review`: that would have lumped it into the same convergent-loop dynamic that already declared "clean" at iteration 2. The independent pass's value comes from (a) fresh context (no recall of the iteration-1/iteration-2 false-negatives), (b) explicit cross-check list (forces re-verification against helper script line numbers, not just re-reading the diff), (c) being post-PR-creation (the agent reads the actual GitHub PR view + diff, not just the worktree state).

**Why the in-loop reviews missed this.** Iteration 1 was dominated by the P1 fix-loop; iteration 2's code-reviewer cited resume contract rows 3-4 by line number ("retrofit-project.md:129") but didn't notice the bare `<retrofit>` form because it was scanning for state-machine semantics, not placeholder consistency. The independent pass, prompted with cross-check claim #8 about the slug contract specifically, did a cross-file `grep <retrofit` and saw the drift.

**How to apply.** When the user requests a post-PR independent review pass, build the prompt by (a) listing 5-10 specific cross-check claims that the in-loop reviews validated, with file:line citations the agent must re-verify, and (b) asking for explicit "VERDICT: CLEAN — safe to merge" language. Do NOT pass the in-loop review summary as context — the agent must derive its conclusions independently to add value. The cross-check claims are the value-add over just re-running `/workflows:review`.

**Telemetry watch.** This pattern surfaces whenever a multi-iteration review-loop converges to "clean" but the user is uncertain. Look for surfaces in future ship sessions where the user explicitly asks for "one more pass" — promotion candidate after 3 surfaces if the independent pass consistently catches conf-7+ findings the in-loop missed.
