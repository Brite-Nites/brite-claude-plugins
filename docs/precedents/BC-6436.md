## Trace 1 — pattern-application — 3-agent simplify-pass convergence as confidence amplifier

**Confidence**: 8/10
**Tags**: simplify-pass, agent-convergence, confidence-threshold
**Precedent Referenced**: 1st surface (NEW)

### Decision

When 3 simplify-pass agents independently flag the same finding at conf 5-6/10 each, treat the convergence as signal — apply the fix even though no individual agent crosses the conf-7 threshold the review-pass downstream uses.

### Why

In this session the 3 simplify agents (code-reuse, code-quality, efficiency) all independently flagged that `sf-deploy/SKILL.md` line 33 (early-body cue) and lines 246-254 (Orchestration Commands section) duplicated the same gate-list and raw-CLI fallback caveat. Each individually rated the redundancy at conf 5-6/10. None hit the conf-7 review threshold individually. But:

- The 3 agents had **different specializations** (reuse-detection vs quality vs efficiency) and converged on the same fix from different framings.
- The convergent suggestion was **textually similar** (tighten the cue to a routing pointer; let the section carry detail) — they hadn't agreed by template, they'd agreed by analysis.
- The fix was **provably behavior-preserving** (validate.sh confirmed clean) and produced **measurable token savings** (~50-80 tokens per skill activation).

The conf-7 threshold exists to filter individual-agent noise. Cross-agent convergence is a different signal class — multiple independent priors aligning on the same conclusion. The product of 3 independent 60% confidences is much higher than any single 60%.

### How to apply

In simplify-pass aggregation: count agents flagging the same `file:line` or same logical issue. If ≥3 distinct agents converge on the same finding (even at conf <7 individually), promote it to "apply" rather than "suggest". Verify behavior preservation via the project's verifier (validate.sh, test suite, lint) before keeping. Revert if the verifier breaks.

### Counter-evidence to watch

If applying converged-but-low-conf simplify findings starts breaking verifiers more often than it lands clean (>20% revert rate), the rule is too aggressive. Currently at 1-of-1 clean-application rate — needs more data.

### Promotion path

3rd surface → architecture-9. Adjacent observation: this is the inverse of BC-2717 task-1 fix-pass-regression-check, which says "non-trivial fix-passes hide regressions". That one says be more cautious; this one says be more confident on convergent low-conf findings. The two compose naturally.

## Trace 2 — pattern-application — explicit precedent context-priming makes diff-triage agents apply prior precedents reliably

**Confidence**: 8/10
**Tags**: diff-triage, precedent-application, doc-artifact, BC-5786, BC-5820
**Precedent Referenced**: BC-5786 task-1 (1st surface), BC-5820 task-1 (2nd surface, promoted to architecture-9 in chain BC-5786→BC-5820)

### Decision

When dispatching diff-triage on a doc-artifact change (skill body, ADR, design doc, plan, precedent), include the load-bearing-doc-artifact precedent in the prompt explicitly. The triage agent reliably votes NON-TRIVIAL when primed with the precedent; without priming, it has historically defaulted to TRIVIAL on small line-count diffs.

### Why

In this session the diff was 3 files, 18 lines net change — well within typical TRIVIAL territory. Diff-triage was prompted with: *"in this repo, doc-artifact changes under `docs/{decisions,research,designs,precedents}/` AND skill body content under `plugins/<plugin>/skills/<skill>/SKILL.md` are load-bearing routing artifacts — they shape model behavior at runtime. The triage has historically (precedents BC-5786 task-1, BC-5820 task-1) underweighted these as TRIVIAL when they were actually load-bearing. Factor that in."*

Triage voted NON-TRIVIAL with a rationale that explicitly cited the load-bearing nature: "Skill body routing change adds early-text recommendation cue and flips orchestration commands from 'planned' to 'live,' altering model behavior at invoke time despite only 18-line total diff."

This is the 3rd surface of the precedent — but a different *application* surface. BC-5786 was the original observation (override TRIVIAL after-the-fact). BC-5820 was retrospective confirmation (also overrode TRIVIAL after-the-fact, on a doc artifact). BC-6436 is **preventative application** — priming the triage with the precedent up-front and getting the right verdict on first call. The pattern works both ways: as a downstream override AND as upstream priming.

### How to apply

Whenever invoking the diff-triage agent on a diff that touches `plugins/<plugin>/skills/<skill>/SKILL.md`, `commands/<cmd>.md`, `agents/<agent>.md`, `docs/decisions/`, `docs/designs/`, `docs/precedents/`, or `docs/research/`:

- Include in the diff-triage prompt: a one-line summary of what the change semantically does (not just the line count), AND a citation of BC-5786/BC-5820 task-1 precedent calling out load-bearing-doc-artifact reasoning.
- Trust the triage's verdict. If it still votes TRIVIAL after priming, that's a stronger signal of actual triviality.

### Counter-evidence to watch

If priming the triage results in NON-TRIVIAL votes on diffs that genuinely warrant TRIVIAL (small typo fixes, comment-only changes, frontmatter-only updates), the priming is too aggressive — refine the prompt to distinguish "load-bearing" (routing prose, decision text, contract documentation) from "incidental" (typos, formatting, comments).

### Adjacent cluster

BC-5786 task-1 + BC-5820 task-1 + BC-6436 task-2 — at 3 surfaces, "load-bearing-doc-artifact diff-triage priming" is durable enough to bake into the diff-triage agent's default prompt or into `/workflows:review` Step 2 directly. Worth tracking as a candidate workflow change (separate issue).

## Trace 3 — architecture — cross-repo factual drift in skills (cross-REPO inverse of BC-2717 task-3 cross-skill reciprocal-sync)

**Confidence**: 7/10
**Tags**: cross-repo, factual-drift, reciprocal-sync, BC-2717
**Precedent Referenced**: BC-2717 task-3 (cross-skill keep-in-sync reciprocal annotation, architecture-8, 2nd surface)

### Decision

Skills that cite specific factual claims sourced from another repo's `CLAUDE.md` (cron expressions, named entities, API versions, count claims) are vulnerable to silent drift. The cross-skill reciprocal-sync pattern from BC-2717 task-3 maps to the cross-REPO case but the mechanism is heavier — there's no shared session, no shared agent, no co-located file. Worth tracking as a separate problem class.

### Why

cdr-compliance-reviewer flagged in this session (P3, conf 6/10, lines 156-170 of `sf-deploy/SKILL.md`):

- L156: cron `0 0 6 1 1 ?` for `DisqualifiedRecycleScheduler` (Apex job)
- L157: NC `Slack_Webform_Alerts` (single named NC)
- L170: "4 active ECAs" with names (counted claim)
- L70/L109: 90% / 100% / 75% Apex coverage gates
- L44: API version `65.0`

All sourced from `brite-salesforce/CLAUDE.md` per the file's stated convention. If any drifts upstream, this skill silently lags. No drift-detection mechanism exists. The cross-skill version (BC-2717 task-3) handles this for skills sharing a repo: a reciprocal annotation in both files calling out the dependency. Cross-REPO has no analogous lightweight mechanism.

### How to apply

Three options, all heavier than the cross-skill case:

1. **Reciprocal annotation in both repos** — `sf-deploy/SKILL.md` adds a "verify against brite-salesforce/CLAUDE.md L<N>" footer; `brite-salesforce/CLAUDE.md` adds a "consumed by britenites-claude-plugins/.../sf-deploy/SKILL.md" footer. Both annotations must be remembered and updated on every relevant change. Manual, fragile.

2. **Periodic drift-check command** — A `/workflows:cross-repo-drift-check` or `/cadence:weekly` step that diffs the cited claims against the source repo's current state. Heavier but automated.

3. **Move the canonical claim to a single source** — replace verbatim quotes with `gh api` fetches at skill-activation time. Adds runtime latency; requires gh-availability.

This trace files the problem class. Solution selection deferred to a follow-up issue.

### Counter-evidence to watch

If the claims in lines 156-170 don't actually drift over the next 4 weeks, the problem is theoretical. File a follow-up to do a 4-week look-back: have any of those values changed in `brite-salesforce`? If yes, drift is real. If no, leave alone.

### Promotion path

This is 1st surface as an explicit problem class, but it's an extension of BC-2717 task-3 (architecture-8, 2nd surface). Promotion path: file 1 follow-up issue to track the look-back. If drift is empirically observed, escalate to a 2nd-surface companion to BC-2717 task-3 covering cross-REPO; consider option 2 (drift-check command). If no drift observed in 4 weeks, archive.
