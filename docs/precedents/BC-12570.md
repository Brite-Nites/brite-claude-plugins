# BC-12570 — marketing-context.md creation (labs entity, ADR-024 Input 1)

<a id="BC-12570-task-1"></a>

## Task 1 — Populate exactly one entity section when a context doc feeds a count-keyed auto-detect

**Date:** 2026-06-04
**Category:** pattern-choice
**Confidence:** 8/10
**Tags:** context-skill, auto-detect, entity-resolution, tam-mapping, bc-1966

### Decision

When a context doc feeds a downstream auto-detect mechanism keyed on **how many entities are populated** (tam-mapping "Before Starting": 1 populated → silent use; 2+ → AskUserQuestion every run), populate **exactly one entity section** at creation time and make the count machine-legible with an explicit `## Entity Status` table. Broader multi-entity material (company overview, flywheel, shared voice) goes in a clearly-shared preamble, never as entity *sections*.

### Inputs

- BC-12570 asked for "at minimum the labs entity — nites/supply can follow incrementally."
- The `product-marketing-context` SKILL.md embeds authoritative brand context for **all four** entities — the path of least resistance was to populate all of them from the embedded baseline.
- `tam-mapping` SKILL.md `Before Starting` table: "exists with one entity populated → Use it. Print `Using entity=<X> ...`. Proceed." vs. "multiple entities populated → AskUserQuestion."
- Acceptance criterion ③ ("entity auto-detect resolves without `--entity`") is only cleanly satisfied on the single-entity path — the multi-entity path technically "resolves" but reintroduces a per-run interaction tax, which is the exact tax the issue was filed to remove.

### Alternatives Considered

1. **Labs-only entity section + Entity Status table** *(chosen)* — auto-detect stays silent; the table makes "populated" unambiguous for both humans and the detection heuristic; incremental population has an obvious slot to fill.
2. **Populate all 4 entities from the SKILL.md baseline** — more "complete" on day one, but flips every future tam-mapping run to an AskUserQuestion and waters down acceptance ③ from "resolves silently" to "resolves after a prompt." Rejected: completeness here is a regression.
3. **Labs-only, no status table** — same runtime behavior, but "is nites populated?" becomes an inference over prose; future incremental sessions (and the auto-detect itself) have to guess. Rejected for ~5 lines of cost.

### Why durable

The general shape recurs anywhere a config/context artifact drives a "count the populated things" dispatch: one populated → silent default; many → interactive disambiguation. "Fill in everything you know" is the natural-but-wrong instinct when the source material (here, SKILL.md's all-entity brand context) covers more than the consumer wants populated. The discriminator is: **does downstream behavior change with the count?** If yes, population level is an interface decision, not a completeness decision — choose it from the consumer's dispatch table, and make the count explicit rather than inferable.

Secondary tooling note from the same session: `britelabs.io` 403s plain `WebFetch`; `mcp__plugin_marketing_spider__spider_scrape` with `request: chrome` + `return_format: markdown` got the full page for ~$0.0016 — the in-plugin fallback order for marketing-skill site reads.
