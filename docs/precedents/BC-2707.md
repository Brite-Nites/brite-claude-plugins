# BC-2707: Two-call MCP confirmation gate blocks same-turn auto-confirm, not affirmative vocabulary

**Date:** 2026-04-20
**Category:** pattern-choice
**Confidence:** 8/10

## Decision

When a skill documents a two-call MCP confirmation-gate pattern, the guarantee being enforced is that **the model must yield to the user between the two calls** — not that the user's response must match a narrow set of phrases. Accept any clear affirmative scoped to the operation ("yes", "approved", "go ahead", "proceed", "do it"); block only the anti-pattern where the model issues both calls in the same turn without a real user response in between. Ambiguous responses ("maybe", "what are my options", silence, off-topic) still stop and re-prompt.

## Context

BC-2707's email-bison skill documented the two-call pattern for the 8 Email Bison MCP gated tools (`resume_campaign`, `unsubscribe_lead`, `remove_email_from_blocklist`, etc.). The initial draft wrote the gate as: *"On explicit user approval, second call. On any other user response — including 'proceed', 'yes do it', or silence — stop and ask for a clearer confirmation."*

Review (code-reviewer, P2 [8/10]) flagged this as internally contradictory: "yes do it" is, by any reasonable reading, explicit approval. Listing it as a response that should *not* be treated as approval would make the skill refuse to proceed when a user had clearly consented, forcing an awkward re-prompt loop.

The root confusion: the author was trying to prevent the LLM from *auto-confirming without a user turn*, but wrote the rule as if the danger lived in the vocabulary of affirmatives. The actual anti-pattern is the skill issuing both MCP calls in a single turn (no user response in between), which is a turn-structure property, not a word-choice property.

## Alternatives Considered

1. **Keep the original "block any affirmative vocabulary except 'approved'" rule.** Rejected: produces false-refusal UX, contradicts itself (the rule says "explicit approval required" then lists common approvals as insufficient), and does not map to the real MCP-gate contract — the vendor MCP returns a prompt and accepts any second call with `confirmation: true`; it doesn't check the user's exact words.
2. **Drop the gate entirely and trust the vendor MCP's first-call prompt-return behavior.** Rejected: the vendor gate only blocks tools that happen to be gated, and `/workflows:review` earlier in the session flagged this as a P3 — a future sibling skill could accept a terser wording from its own prompt template. The skill-level gate is defense in depth.
3. **Rephrase the rule to target same-turn auto-confirm, accept any clear affirmative (chosen).** Preserves the defense-in-depth layer, eliminates the contradictory wording, and maps to what the vendor actually checks. The skill now says: *"The user responds. If the response is clear affirmative consent scoped to this operation ('yes', 'approved', 'go ahead', 'proceed', 'do it'), make the second call. If ambiguous ('maybe', silence, off-topic), stop and re-ask. The anti-pattern this gate blocks is the skill issuing both calls in the same turn without a real user response between them — not the wording of the affirmative."*

## Outcome

SKILL.md Workflow 4 step 4 rewritten. Anti-Slop Guardrails bullet updated: *"Do not auto-confirm MCP confirmation gates. Every gated tool requires two calls with an explicit user turn between them; relay the vendor prompt verbatim."* (Note the shift from "explicit user approval" to "explicit user turn.")

**Reusable beyond this case.** Every future skill that implements a two-call gate pattern — BC-2718 (campaign-orchestration, `resume_campaign`/`archive_campaign`/`import_leads_to_campaign`), BC-2720 (reply-processing, `unsubscribe_lead`/`blacklist_lead`), BC-2719 (deliverability-audit, `enable_warmup`), and any future `workflows:*` or `revops:*` command that wraps destructive MCP calls — inherits this rule. When writing the gate instruction, target *turn structure*, not *vocabulary*.

**Related side-finding.** The same review pass caught a second pattern worth remembering: LLMs fabricate rate limits from naming conventions. `bulk_add_to_blocklist` was tagged with a fictional "500-per-call cap" because two *other* bulk tools (`bulk_create_leads`, `upsert_multiple_leads`) are documented at 500. The fix is to always cite the integration guide's §Rate-limits or `discover_tools` output, never infer from tool-name prefix. This is a lighter-weight rule than the main decision but applies to every skill that references rate limits or batch sizes.

**Precedent Referenced:** none (new pattern — the skill-tool-integration pattern guide's "availability check" rule is adjacent but distinct).
