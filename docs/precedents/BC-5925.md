# BC-5925: FLS-deferred-to-consuming-skills when narrowing a service account permset

**Date:** 2026-04-24
**Category:** pattern-choice
**Confidence:** 7/10

## Decision

When porting a service account from broad profile-level access (e.g., `System Administrator`) to a narrow-scope permission set, scope the initial tightening PR to **object-level Read only** and **defer `<fieldPermissions>` grants to the consuming-skill PRs that land afterward**. Each consuming skill owns its own field access list. Don't pre-aggregate FLS grants in the narrowing PR "just in case" — the object-level tightening is the major risk reduction, and FLS becomes an incremental per-skill add.

## Context

BC-5925 tightened `Marketing_Claude_MCP` service user from `System Administrator` profile + 6 permsets to `Minimum Access - Salesforce` + 1 narrow `Marketing_MCP_Read_Only` permset. The narrow permset grants `ApiEnabled` + object Read on 13 objects, with **no** `<fieldPermissions>` entries.

At plan time, there was a real scope decision: include FLS grants for all standard + custom fields the planned 5 skills might query, OR defer them. The planned skills (BC-2717 list-building, BC-2720 reply-processing, BC-2725 lead-routing, BC-2727 data-enrichment, BC-2728 crm-hygiene) weren't built yet — their exact field lists were speculative. Aggregating would have meant:

- Guessing which fields each future skill queries
- Producing a large PR with hundreds of `<fieldPermissions>` entries
- Reviewing each field grant without concrete skill context
- Revisiting on every skill PR anyway (when specific field needs surface)

Deferring meant:
- Smaller, focused permset PR (127 lines, 13 `<objectPermissions>` blocks, 1 `<userPermissions>` block)
- Each skill's PR owns and justifies its own `<fieldPermissions>` additions
- Downstream cost: on first skill ship, standard-field reads may fail post-downgrade until FLS is added

## Alternatives Considered

1. **Pre-aggregate all expected FLS in the narrowing PR.** Rejected — speculative field list, review burden, and redundant revisit on each consuming-skill PR. The 80% use case (standard fields like `Lead.Email`) shouldn't require a new permset PR each time someone wants to ship a skill.
2. **Skip the narrowing until at least one consuming skill has its field list pinned.** Rejected — service user sat on `System Administrator` with `Modify All Data`. Every day of delay was a day of unnecessary blast radius for a live integration user.
3. **Defer FLS to consuming-skill PRs (chosen).** Object-level Read lands immediately; field-level grants land when the skill that needs them lands.

## Outcome

BC-5925 shipped a 127-line permset + 7-step post-merge sequence. Predicted cost materialized exactly at T8: `SELECT Id, Email, Status FROM Lead LIMIT 1` (standard-field query via the service user) failed with `No such column 'Email' on entity 'Lead'` — FLS-invisible-field behavior. BC-2717 list-building (next to ship) adds `Lead.Email` + `Lead.Status` `<fieldPermissions>` as part of its own PR.

**The predicted cost showing up concretely validates the decision.** If the cost had been unexpectedly high (e.g., if every skill required a new permset deploy cycle or the rollback of a shipped skill), the decision would have been wrong. The cost was exactly one `<fieldPermissions>` block per affected field, added to each consuming skill's existing PR — which is the definition of "incremental per-skill add."

**Reusable beyond Salesforce.** The same pattern applies to any "narrow a service account" operation against any permission-model where capability-grant and data-scope are separable axes:

- AWS IAM: start with service/resource ARNs in the role, defer field-level `Condition` constraints
- Postgres roles: start with table-level `SELECT`, defer column-level grants
- Google Cloud IAM: start with resource-level role bindings, defer conditional bindings

The shared principle: the first-order blast-radius reduction (kill the wildcard access) is independent of second-order field/column restriction. Shipping them together couples two scopes that don't need to be coupled; splitting them respects the "smallest reviewable change" principle.

**Adjacent decision: staged post-merge sequencing.** BC-5925's runbook also chose staged (additive → cut-over → cleanup) over all-at-once. The staged shape gave the smoke-test between cut-over and cleanup a place to live. In practice step 4 (profile change) smoke passed cleanly and no rollback was used — so the staging didn't save anything on this run — but the gate structure made the plan legible to the user and kept the explicit-approval surface small per decision. Lower-confidence precedent (6/10) since not stressed; noting here rather than its own file.
