## Task 1 — Plain-language reframe rescues a brainstorm stuck on issue-body design-shape labels

**Category:** pattern-choice
**Confidence:** 7/10
**Tags:** pattern-choice, brainstorming, plain-language, issue-body-framing, user-comprehension

### Decision

Reframe the brainstorm in plain language when the issue body's design-shape labels don't track. The BC-6307 issue body framed three options (replace ESP / augment ESP / toggle ESP) for the email-type axis. When I (parent agent) opened the brainstorm with those three labels and a fourth I'd derived from precedents (pre-filter), the user said: "what is happening? i am definitely not following. can we back it up and just explain exactly what this issue is addressing before we get into the details."

Pivoted to a plain-language reframe — described what the user actually experiences ("Phase 2 looks at each lead's email and asks one question — whose mail server hosts this domain"), what's missing ("teach Phase 2 to notice the difference between professional, personal, and role addresses"), and what the proposed behavior would look like end-to-end. Once the user agreed on that frame, the design-shape labels became a follow-up choice that took 1 round to resolve, not a 4-option upfront question.

### Alternatives considered

1. **CHOSEN.** Reframe in plain user-experience language; defer the design-shape labels until the underlying behavior is agreed. Outcome: brainstorm converged in ~10 turns; design doc landed cleanly; user explicitly confirmed comprehension ("yes okay that is how i match it").

2. Push harder on the design-shape options with more diagrams/comparison tables. Rejected — user signal "I am definitely not following" indicated the abstraction layer was wrong, not the explanation depth. Adding more detail at the wrong abstraction would have widened the gap.

3. Skip brainstorm and write the plan directly with my recommended shape (pre-filter) flagged for review. Rejected — user pacing preference is collaborative scoping at design-decision points; pre-empting would have skipped exactly the consultation the issue's 4 design questions warranted.

### Rule derived

**When issue-body framing uses domain-shape labels (replace/augment/toggle/etc.) and the user doesn't track, abandon the labels and reframe in user-experience plain language.** Once the underlying behavior is agreed, design-shape labels become a 1-question follow-up rather than the entry point. Trigger signals: "I'm not following," "what does this entail," reverting to questions about basic mechanics, requesting plain-language gist before plan-write. The user's `feedback_jargon` memory codifies the trigger pattern; this trace adds the *response* pattern.

### Promotion note

1st surface for "design-shape-label reframe" specifically. The broader pattern (plain-language gist before plan-write, BC-6302 task-1) is already at 2nd surface. Watch for 3rd surface to consolidate as a single CLAUDE.md gotcha: "When user signals 'I'm not following,' drop the label layer and re-anchor on user-experience plain language."

## Task 2 — Post-edit re-read catches own-output logical flaws review would've found

**Category:** bug-resolution
**Confidence:** 6/10
**Tags:** bug-resolution, self-review, post-edit-verification, execution-discipline, gate-2-design

### Decision

After landing Tasks 1-3 of the plan, the user asked to "Yeah go ahead and read it first" before continuing. Doing the read end-to-end caught three real problems my forward-only edits had introduced:

1. A flag (`--skip-email-type-filter`) referenced in the "Skip if" prose that was never defined elsewhere.
2. A stale "Steps 2–6" reference in Phase 2 Purpose after renumbering had shrunk it to 5.
3. A logical inversion: I wrote step 5's sidecar-write *before* gate 2 fired, but the sidecar can only be written after the operator decides at gate 2 what gets skipped.

Each of these would have surfaced in `/workflows:review` and consumed a review-fix cycle. Catching them via self-review post-edit cost ~5 minutes and one re-edit; review-fix would've cost a P1 finding + a separate commit + the validation latency.

The third issue (sidecar before gate 2) was the substantive one. I surfaced it explicitly to the user as a real correctness issue with two reconciliation options (Option A: classify ESP for all leads then filter at step 5; Option B: classify only post-filter, more limited gate-2 preview). User chose A; I applied the fix.

### Alternatives considered

1. **CHOSEN.** Read the rendered Phase 2 block end-to-end immediately after writing it; surface logical flaws to the user before continuing. Outcome: 3 issues caught, 1 substantive correctness question raised + resolved with user input, mechanical fixes applied without re-spawning subagent. The review pipeline later flagged different issues — not these three — confirming the self-review caught a distinct class.

2. Skip self-review and rely on `/workflows:review` to catch these. Rejected — the review pipeline is broader-and-shallower (5 agents looking at the whole diff) and has 30-min latency; self-review is narrower-and-deeper (parent-agent re-reading own output in fresh context).

3. Use `verification-before-completion` skill at every task checkpoint. Rejected — overkill for spec-only edits where the only test is `validate.sh`; the skill is designed for code with build/test/integration layers.

### Rule derived

**Read your own output end-to-end before declaring a checkpoint complete on spec edits.** Forward-only writing accumulates internal-consistency drift (stale cross-refs, undefined flags, ordering inversions) that the writer doesn't see while writing but a cold reader catches in seconds. This is distinct from `/workflows:review` (broader, agent-driven) and from `verification-before-completion` (test-suite-driven) — it's a 5-minute self-read for the prose-only case where the writer is the only fast feedback loop available.

### Promotion note

1st surface for "post-edit self-read for spec-only PRs." Watch for repeats. Borderline: if ~50% of spec-only PRs benefit from this, promote to a hook (post-Edit narrate "re-read before continuing?"). If <30%, leave as a session-discipline note.

## Task 3 — Auto-rebase resolves marketplace.json conflict when origin/main advances mid-session

**Category:** pattern-choice
**Confidence:** 7/10
**Tags:** pattern-choice, mid-session-rebase, marketplace-json-conflict, version-bump-discipline, ship-time-rebase

### Decision

At ship-time pre-flight, `git fetch origin main` revealed origin had advanced from `5b36154` to `1a92509` — Holden had merged BC-6434 (PR #236) while BC-6307 was in review. Files touched: revops + workflows plugin versions, INDEX.md, CLAUDE.md, and crucially `.claude-plugin/marketplace.json` (which BC-6307 also touches with the marketing version bump).

Ran `git rebase origin/main` — git's 3-way merge resolved the marketplace.json conflict cleanly without manual intervention, because each PR's edit was on a different table row (workflows row vs marketing row). The post-rebase file correctly contained both bumps: `workflows: 3.29.4`, `revops: 0.2.5` (Holden's), `marketing: 0.3.18` (mine).

Validate.sh ran post-rebase: 0 errors. Anchor sweep + asymmetry test: still passing. Pushed the rebased branch with `git push -u origin HEAD` (no force needed — the branch had never been pushed before).

### Alternatives considered

1. **CHOSEN.** Rebase silently when the conflict is mechanical and on different table rows. Outcome: clean linear history; PR #237 bases on the latest main; no merge commit polluting the BC-6307 commits.

2. Merge `origin/main` into the branch instead of rebase. Rejected — would have created a merge commit on a feature branch, breaking the linear-history convention this repo uses (verified via `git log --oneline` of recent merges — all squash-merged). Also makes the precedent traces harder to read.

3. Pause and ask the user how to handle the conflict. Rejected — marketplace.json conflicts on different rows are known mechanical and routinely auto-resolved. Pausing would have added latency without surfacing a real decision point.

4. Force-push with `--force-with-lease` to rewrite the local feature branch and replace origin's. Rejected by the security hook — destructive flag tripped the dangerous-pattern check. Plain `git push -u origin HEAD` (first push) worked.

### Rule derived

**When `git fetch origin main` shows advance during a ship-time session, rebase silently if (a) the conflict is mechanical, (b) edits are on different rows/sections of the same file, and (c) the branch hasn't been pushed yet (so plain push will work post-rebase). Pause and surface only if the conflict is on overlapping content, or if the branch is already on origin (force-push concern).**

### Promotion note

1st surface for ship-time-rebase. The marketplace.json conflict pattern will recur every time two PRs touch different plugin version rows simultaneously — that's most multi-stream sessions. Watch for 3rd surface to promote as a CLAUDE.md gotcha or a hook ("on `git fetch origin` showing advance, attempt auto-rebase silently before continuing").

## Task 4 — When validators time out at infrastructure level, pivot to direct validation rather than re-dispatch

**Category:** pattern-choice
**Confidence:** 6/10
**Tags:** pattern-choice, validator-timeout, review-pipeline, infrastructure-failure, fallback-discipline

### Decision

`/workflows:review` Step 6 dispatched 3 Opus validators in parallel, one per P1. Validator #1 returned in 18 seconds with CONFIRMED. Validator #2 stalled with "Agent stalled: no progress for 600s (stream watchdog did not recover)". Validator #3 returned "API Error: Stream idle timeout - partial response received" after 763 seconds.

Two of three validators failed at the infrastructure layer (stream timeout, watchdog kill), not the agent layer (no progress on the actual task). Re-dispatching parallel validators would have likely repeated the failure pattern.

Pivoted to direct self-validation against source: re-read the cited file/lines, verified the claim independently. P1 #2 (step ordering paradox) — confirmed by reading lines 285-301 of launch-campaign.md. P1 #3 (dig-all-leads efficiency) — verified spec/design-doc contradiction is real, but downgraded to P2 because the operator had consciously chosen the unfiltered path mid-execution with bounded cost (12 extra DNS lookups). Both judgments documented in the review report; user notified the validation pivoted from agent-driven to direct.

### Alternatives considered

1. **CHOSEN.** Direct self-validation when validators time out at the infrastructure layer (≥600s with no agent progress). Outcome: 2 P1 findings validated in <2 min of parent-agent reading; review pipeline continued to Step 7 (fix loop) without further delay; fixes landed in commit 2.

2. Re-dispatch the failed validators sequentially (not parallel). Rejected — same infrastructure issue would likely recur; serial dispatch only saves on cross-agent timeout interaction, not the watchdog itself. Plus 2× more wall-clock.

3. Use error recovery's "Retry failed agent" path. Rejected — same as #2; the retry button doesn't address the root cause (stream timeout, not retry-recoverable).

4. Use error recovery's "Stop review" path. Rejected — would have left 2 P1s unvalidated and blocked the ship-pipeline. Direct validation is faster than aborting and re-running the whole review.

### Rule derived

**When 2+ Step-6 validators time out at the infrastructure layer (≥600s with no agent progress, watchdog kills, stream-idle timeouts), pivot to direct parent-agent self-validation rather than re-dispatching.** Direct validation is appropriate when the parent has the source files in context and the finding is a concrete claim about a specific file:line. Pivot threshold: 2 of N validators failing infrastructurally signals a session-wide issue, not a per-validator one. Re-dispatch when a single validator times out (transient).

### Promotion note

1st surface. This pattern has only appeared once (this session). If the next 2-3 ship sessions don't see validator timeouts, leave as a per-trace note. If they do, escalate to a `/workflows:review` Step 6 fallback rule: "after 1 validator timeout, attempt direct self-validation for the remaining P1s in parallel with the re-dispatched validator."
