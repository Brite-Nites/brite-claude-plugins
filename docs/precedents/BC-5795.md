# BC-5795: Revert-and-reship beats forward-fix when review catches P1 factual errors post-merge in a load-bearing agent-invoked skill

**Date:** 2026-04-20
**Category:** pattern-choice
**Confidence:** 9/10

## Decision

When `/workflows:review` runs post-merge against an already-shipped skill PR and confirms P1-severity factual errors in the skill body — content that future agents will auto-invoke and follow — revert the merge commit on main and re-ship a corrected version on a new branch, rather than opening a forward-only fix PR that leaves the incorrect guidance live in the interim.

The gate is the combination of (1) agent-invoked skill (not docs, not code comments), (2) factual errors in load-bearing rules, (3) errors CONFIRMED by independent validators. Any of those three absent, a forward-only fix is the right tool.

## Context

PR #147 (BC-5795 v1) shipped a customization of `plugins/revops/skills/sf-connected-apps/SKILL.md` adding `## Brite Context` + `## Brite ECA Conventions` sections on top of the MIT-licensed upstream skill. The PR was merged before `/workflows:review` ran.

Review (comprehensive, all tier 1+2+3 agents including cdr-compliance) surfaced 11 findings — all 11 CONFIRMED by per-finding independent validators, zero dismissed. Two were P1-severity factual errors:

- **P1.1** `CI_Deploy` described as the live GitHub Actions refresh-token path. Ground truth in `docs/research/salesforce-mcp-findings.md:393, 412`: `CI_Deploy` is committed-but-inactive; CI actually uses `SFDX_AUTH_URL` under Salesforce's built-in `PlatformCLI` Connected App. Rule #6 (and § Brite Context) built their "CI vs runtime auth separation" argument on a hypothetical live ECA.
- **P1.2** `Outbound_Sales_Ops` classified as one of "four ECAs are live today." Ground truth in `findings.md:50, 390`: it's a legacy ConnectedApp auto-wrapped with an ECA settings file during the Spring '26 migration. `Marketing_Claude_MCP` is Brite's **first** pure ECA.

Both errors are inherited by every future SF OAuth task in any Brite repo because the skill auto-invokes on the matching triggers. That's different in kind from a bug in a runtime path (which fails visibly) or docs (which a reader evaluates) — durable misguidance compounds silently.

## Alternatives Considered

1. **Forward-only fix PR.** Open a new PR on top of #147's merge that corrects the rules + frontmatter. Rejected: leaves `789cd77` live on main with incorrect guidance until the fix merges. Any SF OAuth work landing in that window would reference the wrong conventions; no automated signal would flag the drift.

2. **P1-only follow-up PR, defer P2/P3.** A minimal forward fix for the two P1s, with P2+P3 deferred to a separate issue. Rejected: same live-misguidance window as #1, and the P2.1 (frontmatter drift from sibling-zero template — missing `upstream:` key + truncated `author:` field) is a provenance contract violation that is cheaper to fix now than in a third PR later.

3. **Hold — don't act.** Document findings, leave merge as-is. Rejected: user explicitly authorized revert when the P1s surfaced; holding would defeat the point of running post-merge review.

4. **Revert + re-ship on new branch (chosen).** New branch `holden/bc-5795-v2` from `origin/main`. `git revert 789cd77` → clean revert commit. Apply corrected SKILL.md + updated plan doc as a second commit. Open PR #149 with both commits. When merged, main moves from "shipped-with-P1s" directly to "shipped-corrected" with the revert in history as an explicit audit marker.

## Outcome

`holden/bc-5795-v2` → two commits (`4475be4` revert, `06b685f` corrected content). PR #149 opened + reviewed + merged as `706d890`. End-state on main: corrected SKILL.md v1.1.0-brite.2, plan doc with post-merge corrections log, upstream-table override banner, all 7 conventions factually grounded in `salesforce-mcp-findings.md`.

Total rework: ~25 minutes agent time from P1 confirmation to merged fix. No SF OAuth work landed in the bad-guidance window (checked `git log main --since` during the interim).

**Reusable beyond this case.** This is the second instance of `/workflows:review` running post-merge in recent sessions — the previous instance was BC-5794 (pre-merge, caught P1s before merge). The pattern that matters is **pre-merge review is cheap, post-merge review on agent-invoked content requires an explicit decision framework for revert vs forward-fix**. The three-gate filter (agent-invoked + P1-factual + CONFIRMED-by-validators) reliably identifies cases where revert is worth the history noise.

**Secondary observation: factual-content reviewers on SKILL.md bodies have real teeth.** Previous memory (`Review Agent False Positives`) flagged that code-reviewer often flags structural non-issues. This session is counter-evidence: 11/11 CONFIRMED after independent validation, zero dismissed, zero downgraded. The per-finding Opus verifier subagent pattern (Step 6 of `/workflows:review`) earned its cost here — without independent verification, the two P1s might have been rationalized away, especially since one was built on a plausible-sounding (but wrong) narrative.

**Tertiary observation: sibling-zero template is now actually two templates.** BC-5793 (sf-deploy) places Brite sections AFTER `## When This Skill Owns the Task`; BC-5794 (sf-permissions) + BC-5795 (sf-connected-apps) place them BEFORE. Worth an explicit precedent-trace note so sibling-two-onward can pick either with a documented reason, rather than re-deriving.
