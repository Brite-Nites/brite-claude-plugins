## Task 1 — Plain-language gist must scrub project-acronyms (refinement of BC-6302 task-1)

**Date:** 2026-05-01
**Category:** pattern-choice
**Confidence:** 7/10
**Tags:** plain-language-gist, jargon-bridge, plan-gate, communication-discipline, acronym-scrub, BC-6302-extension

### Decision

When applying the BC-6302 task-1 pre-plan plain-language gist rule, the gist itself must contain ZERO project-acronyms. No `BC-NNNN`, no `R-Nxa`, no `Tnn`, no `Sx-N`, no `Phase N step N`. Use only common nouns the user already recognizes: "the campaign-launching command," "the email," "merge fields." If a project-acronym is load-bearing to the gist, the gist isn't plain-language — rewrite it.

This extends BC-6302 task-1 with the second-instance evidence the original trace's promotion candidate explicitly named.

### Inputs

- BC-6548 plan-write was preceded by a proactive 2-paragraph gist per BC-6302 task-1. The gist read: *"EB only resolves UPPERCASE merge tokens like `{FIRST_NAME}`. Lowercase ones like `{first_name}` render as the literal text 'first_name' in the email — a silent broken send with no diagnostic. We use UPPERCASE everywhere already, but if anyone drifts (hand-edit, port from another tool), the email goes out broken with no warning. This plan locks the rule by adding a hard validation step before campaign launch + clear 'always UPPERCASE' notes in the skill that writes copy and the EB reference doc, plus a refresh of two 'unverified' markers that BC-6308 round-3 has now resolved."*
- The gist mentioned `BC-6308 round-3` as the verification source. That single acronym carried back the same density the gist was supposed to relieve.
- Plan-write was attempted; user interrupted with *"can you just tell me in plain brief terms what this issue is addressing"*. Tool use was rejected.
- The retry that landed dropped ALL acronyms: *"In Email Bison, merge tokens like `{FIRST_NAME}` only work when they're typed in ALL CAPS. If someone writes `{first_name}` (lowercase) by accident, EB doesn't replace it — the email goes out with the literal text 'first_name' sitting in the middle of the sentence."* User responded *"got it okay"* and approved plan-write.
- The diff between rejected gist and accepted gist is exactly one feature: zero project-acronyms.

### Alternatives Considered

1. **Mandate acronym-scrub in plain-language gists** *(chosen)* — costs nothing more than the gist already cost; eliminates the failure mode where a single in-line acronym re-imports the density the gist was relieving. The accepted retry proves the user-side bar is "common nouns only," not "common nouns + 1-2 internal labels."
2. **Allow internal acronyms if they're hyperlinked** — rejected. User's correction wasn't about lookup-cost; it was about cognitive register. A hyperlink doesn't help if the user has already paused to ask the question.
3. **Acronym-scrub only on the first sentence** — rejected. The rejected gist's BC-acronym was in the closing paragraph, not the opening; the failure was global, not positional.

### Outcome

- **Files changed:** `feedback_jargon.md` (auto-memory) extended with the acronym-scrub bullet under "How to apply"
- **Tests:** N/A (workflow discipline)
- **Approved by:** user *"got it okay"* + *"yes"* to proceed with plan-write after the acronym-free gist landed

### Precedent Referenced

- BC-6302 task-1 (proactive plain-language gist before plan-write) — direct parent. This trace narrows the *form* requirement BC-6302 left implicit.
- `feedback_jargon.md` (auto-memory) — base preference for plain-language; both traces operationalize it at different points.

### Promotion candidate

2nd instance. **The BC-6302 task-1 trace explicitly named a 2nd-instance trigger: "any session where the user pauses or rejects a plan-write to ask 'what does this do' / 'explain this plainly' / equivalent. At 2nd instance, promote to a `writing-plans` skill amendment: add a Pre-plan gist step…"** This session is that 2nd instance. Per `feedback_user_delegation_scope`, the actual skill amendment is project-level (out of in-session scope) and is deferred for the user to advance via `/workflows:promote-precedent` whenever they choose. Recording the trigger here so the path is open.
