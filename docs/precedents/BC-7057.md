## task-1 — 3-iteration convergence floor extends to 3-4 iterations when iter-1 finding-count is wide (≥10 findings ≥ confidence 7)

**Pattern type:** pattern-application (3rd surface of BC-6965 task-5; extension axis: finding-count vs iteration-budget relationship)

**Confidence:** 9/10

**Context.** BC-6965 task-5 locked the precedent "iterative review-loop convergence: 3-iteration floor for 'loop until clean' — iter 2 fold-in commonly introduces 0-2 new defects caught by iter 3" (sample: BC-6965 surfaced 1 new defect in iter 2, caught by iter 3 fresh-context). BC-6964 was the 2nd surface (sample size 2; iter-2 fold-in landed 0 new defects, but the 3-iteration floor still held). BC-7057 is the 3rd surface AND a counter-example to the strict "3-iteration floor" wording: with iter 1 surfacing **15 findings ≥ confidence 7 (2 P1, 9 P2, 4 P3)** — substantially wider than BC-6965's iter 1 (1 P2 + 5 P3) and BC-6964's iter 1 (5 P2 + 7 P3) — **iteration 4 was required to reach clean.** Iter 3 had 1 P2 [8/10] remaining (fixture `npm run lint` + `npm test` not asserted; iter-3 fix expanded build-only loop to build/lint/test loop); iter 4 confirmed clean across all 7 agents.

**Decision.** Extend the precedent text from "3-iteration floor" to "3-4 iteration convergence floor; iter-4 needed when iter-1 surface is wide (≥10 findings ≥ confidence 7)." Reasons:
1. Iter-1 finding-count is a strong predictor: BC-6965 iter-1 = 6 findings → converged iter 3; BC-6964 iter-1 = 12 findings → converged iter 3; BC-7057 iter-1 = 15 findings → converged iter 4. Linear scaling.
2. Iter-2 fold-in defect injection is independent of finding-count: BC-7057 iter-2 introduced 1 inconsistency (LINEAR_ISSUE_COUNT=9 branch error-handling mismatch vs =0/=10) caught by iter-3 — matches BC-6965 pattern exactly. The iter-3 catch of iter-2 fold-in defects holds; the iter-3-clean assumption breaks when finding-count is wide enough that a meaningful coverage gap (the build-only assertion) survives the iter-1 surface.
3. With 3 surfaces (BC-6965 / BC-6964 / BC-7057), the pattern is **eligible for promotion** to org-level handbook per the promotion threshold ≥ 3 surfaces.

**Rejected alternatives:**
- Hold the wording at "3-iteration floor" + treat BC-7057 as anomaly: would underestimate iteration budget for future wide-surface PRs and risk premature ship.
- Bump floor universally to 4: would over-budget narrow PRs where iter 3 has reliably converged twice.
- Tie iteration budget to PR size in lines: less predictive than iter-1 finding-count; correlated but not causal.

**How to apply.** When running `/workflows:review` with intent "loop until clean":
- Iter 1: surfaces baseline findings. If ≥10 findings ≥ confidence 7, **plan for 4 iterations** (not 3).
- Iter 2: applies fixes; fold-in commonly introduces 0-2 new defects.
- Iter 3: fresh-context review catches iter-2 fold-in defects + any iter-1 gaps that survived the iter-1 surface (e.g., coverage gaps where iter-1 agents focused elsewhere).
- Iter 4: confirms clean when iter-3 still surfaces findings; this is the convergence iteration for wide-surface PRs.

Counter-example flag: if iter 4 still surfaces ≥ 1 P2 ≥ confidence 7, the loop is not converging and the cause is likely a misclassification (an agent flagging an intentional decision repeatedly) — escalate to user judgment rather than iter 5.

## task-2 — Q55 sub-decision 4 ("filesystem is source of truth; don't pin top-level counts in body text") extends from plugin CLAUDE.md surface counts to test-report assertion counts

**Pattern type:** pattern-choice (NEW pattern — Q55 sub-decision 4 extension)

**Confidence:** 8/10

**Context.** Plugin `plugins/flow-architecture/CLAUDE.md` § Surface map enforces Q55 sub-decision 4: "Drift-tolerant per Q55 sub-decision 4 — categorical prose for commands and sub-skills, literal MATRIX for agent dispatch. Source of truth is the filesystem; do not assert top-level counts in body text." Originally locked at the plugin-CLAUDE.md scope to prevent surface-count drift between plugin docs and `commands/` / `skills/` / `agents/` directories. BC-7057 iter-2 simplify pass flagged `vslice-report.md` for the same drift class: line 7 said "37 hard assertions" then iter-1 fixes bumped to 63, then iter-3 fix bumped to 65. Each iteration would have required hand-syncing the count.

**Decision.** Apply Q55 sub-decision 4 verbatim to `plugins/flow-architecture/tests/vslice-report.md`. Replaced pinned counts at line 7 + line 57 + line 67 with phrasing like "the exact hard-assertion count is emitted by the harness summary at runtime (source of truth — FDA Q55 sub-decision 4 says don't pin top-level counts in body text)." The harness's `printf '... %d pass / %d fail ...'` runtime emission is the canonical count; the doc defers to runtime. Coverage history table retains versioned rows but omits literal counts per row.

**Rejected alternatives:**
- Keep literal count + add a "stale-by-version" disclaimer: still requires hand-sync every iteration; cleaning text in 2 places vs cleaning text in 1 place is a wash.
- Auto-generate the doc from the harness via `--emit-report-row` flag: bigger plumbing for marginal value at v0.2.10; consider if a 3rd consumer of the count materializes (e.g., dashboards, telemetry).
- Limit Q55.4 to plugin CLAUDE.md only: arbitrary scope-cap that ignores the same drift mechanism in adjacent docs.

**How to apply.** When authoring a project-internal doc that describes filesystem-derived or runtime-emitted totals (commands per plugin, assertions per test, sub-flows per domain, etc.):
1. Identify whether the count has a deterministic runtime emission (`./test.sh` summary, `ls dir | wc -l`, `git log --oneline | wc -l`).
2. If yes: phrase the doc text to defer to the runtime emission with an explicit cross-reference to the canonical line.
3. If no (e.g., target shape that doesn't yet exist on disk): mark explicitly as "Planned: ...; v0.X.Y harness asserts none of these — domain-level coverage activates as <issue> sub-skill PR lands."
4. In coverage-history tables, version the row but elide the literal count; the version + scope description is the load-bearing axis.

This rule applies recursively as docs proliferate. The originating Q55 sub-decision 4 lock should be cited verbatim each application (already amended in this PR via vslice-report.md content).

## task-3 — Strict-loop below-threshold P3 application: apply during iter 2 when 4-iteration convergence is likely (2nd surface of BC-6964 task-3, with 4-iteration extension)

**Pattern type:** pattern-application (2nd surface of BC-6964 task-3; extension axis: which iteration to apply below-threshold nits)

**Confidence:** 8/10

**Context.** BC-6964 task-3 established "strict 'loop until clean': apply below-threshold P3 nits when agent marks 'not a defect' + edits are trivial single-line + iter-3 verify is cheap." The pattern was 1st-surfaced at iter 3 of BC-6964 (3-iteration convergence) where 1 P3 conf 6 below-threshold finding (Section 5b honesty re-check verbatim message) was applied defensively to converge clean. BC-7057 is the 2nd surface AND a finding about which iteration to apply.

**Decision.** Apply below-threshold P3 nits at **iter 2** rather than iter 3 when:
1. Iter 1 surface is wide (≥ 10 findings ≥ confidence 7) — indicates 4-iteration convergence is more likely.
2. The below-threshold nits cluster around a single fix (stderr-leakage in MODE_* captures, in BC-7057's case — 3 P3s at confidence 4-5 all addressing the same `2>&1` → `2>/dev/null` switch in 3 places).
3. The fix is mechanical and cheap to verify in the next iteration (single-line `2>&1` → `2>/dev/null` swap; same `if VAR="$(...)"; then` shape preserved).

BC-7057 applied 3 below-threshold P3s in iter 2 (stderr-leakage cluster + 1 documentation-comment back-reference). Iter 3 surfaced 0 of the iter-2-applied nits as new findings, and the 1 P2 it did surface (npm lint/test coverage gap) was a wider coverage extension that iter-1+iter-2 agents had not flagged. This confirms that iter-2 application of below-threshold nits doesn't introduce new defects when constrained to cluster-fix-then-verify.

**Rejected alternatives:**
- Hold below-threshold nits until iter 3 (BC-6964 task-3's original rule): would have left the stderr-leakage cluster latent through iter 3; iter 3 would still need to surface and fix them, lengthening the loop.
- Apply ALL below-threshold P3s without filter: risks defensive-action chains that introduce defects (each "nit fix" is a chance to inject a new defect; bound applies).
- Defer below-threshold P3s to a follow-up PR: contradicts user's "loop until clean" directive; below-threshold ≠ not-a-finding.

**How to apply.** During iter 2 of a wide-surface `/workflows:review` loop:
1. Identify which P3 below-threshold findings are mechanical single-line edits (high confidence about the fix shape).
2. Identify which cluster around a common root cause (3 P3s addressing the same `2>&1` → `2>/dev/null` are 1 fix, not 3).
3. Apply the cluster as a single fix-block in iter 2 alongside the high-confidence findings.
4. Iter 3 verify: confirm the cluster fix didn't introduce new defects + check whether iter-3 agents surface any new P2/P3 in the same neighborhood (would indicate the fix shape was wrong).
5. If iter 3 surfaces a coverage gap that's wider than the iter-2 cluster fix (BC-7057's npm lint/test case), it's a separate axis — apply in iter 3, expect iter 4 clean.

Iter 4 convergence target remains: 0 findings ≥ confidence 7 across all 7 review agents.
