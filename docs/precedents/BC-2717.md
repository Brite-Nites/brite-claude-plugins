## Task 1 — Fix-pass regression check is load-bearing on non-trivial fix-passes (≥5 fixes)

**Category:** architecture
**Confidence:** 8/10
**Tags:** architecture, review-fix-pass, regression-check, single-author-blindspot, 30-minute-window

### Decision

`/workflows:review thorough` first pass on this PR produced 35 raw findings → 13 fixes applied under "fix all + ultrathink." Validation passed on every fix. User asked "should we run another review before merging?" — running a focused 3-agent second pass on the fix-pass output **caught two real regressions the first fix-pass introduced and would have shipped silently**:

1. **RR2 — internal contradiction**: A Source-1 staleness gate fix (P3.7 from first pass) said "default = re-run Workflow 2" while contradicting two other rules in the same file — the per-source EB-exclusion routing table ("Always SKIP") and the Anti-Slop guardrail ("Always SKIP") that the same fix-pass had also edited.

2. **RR3 — security asymmetry**: The same staleness gate's mtime check used shell-interpolated `--input-dir`, reopening the path-injection class the first fix-pass had just closed for `--audience-view-name`. Half-class fix that left the other half as the new attack surface.

Both bugs were in code I had written 30 minutes earlier. Neither could have been caught by the same author re-reading their own work — they are the kind of error that requires fresh perspective on the fix-pass output as a coherent whole. `validate.sh` couldn't catch either (it only verifies structural validity).

### Alternatives considered

1. **Run a focused 3-agent second pass before merging** — Chosen. Cost: ~3 minutes vs the alternative cost of shipping a regression that needs a follow-up PR. Bounded scope ("what could the fix-pass have broken?") makes the agents more efficient than full review. Hit rate on real regressions justified the cost: 100% on actionable findings (8/8 confirmed + 4 absorbed + 1 follow-up + 1 dismissed false positive).

2. **Rely on first-pass validation + `validate.sh`** — Rejected after the user prompted reflection. `validate.sh` is structural-only; first-pass validation re-verified the 2 P1 fixes but not the 11 P2/P3 fix-pass-introduced changes. The single-author 30-minute window is too tight for fresh perspective on one's own writing.

3. **Wait for PR review by humans** — Rejected as the sole defense. PR review is asynchronous and may take days; meanwhile the bugs would sit in the diff. The fix-pass regression check is a same-session safety net.

### Rule derived

**After applying ≥5 fixes to a SKILL/spec/markdown file in a single fix-pass, run a focused regression-check review (2-3 agents, bounded scope) before declaring done.** Skip the simplify pass + skip the full Tier-2/Tier-3 selection — the focused agents only need to verify "what could the fix-pass have broken?" against the diff-of-the-diff. The agent prompts should call out specific risk areas the fix-pass touched (cross-section consistency, security-class asymmetry, schema/step-numbering off-by-one).

The single-author blindspot is the load-bearing factor: the same person who wrote a fix has lost the structural distance needed to spot inter-fix contradictions in the same session.

### Promotion note

**Reinforces and extends BC-5832 task-2** ("cross-skill contract integration → review hit rate ~100% vs single-skill polish ~20%; calibrate review-fix budget by workload type"). BC-5832 task-2 established that review-validation hit rate is workload-dependent. This trace adds that **fix-pass-regression-check hit rate is also workload-dependent — non-trivial fix-passes (≥5 fixes) have a 100% real-regression rate in the n=1 sample here.**

1st surface for the specific "fix-pass regression check" pattern. At 2nd surface (any future PR where re-reviewing a fix-pass catches ≥1 real regression), promote to 9/10 architecture and recommend updating the `/workflows:review` skill itself to suggest a re-pass after non-trivial fix-passes by default.

Adjacent patterns: BC-5832 task-1 (independent re-read of cited authority) — both rely on fresh perspective being the load-bearing factor.

## Task 2 — 3rd surface for issue-vs-ground-truth amendments table at plan-doc top — promotes to architecture-9

**Category:** pattern-application
**Confidence:** 9/10
**Tags:** pattern-application, plan-doc-shape, amendments-table, issue-drift, third-surface, architecture-promotion

### Decision

This PR's plan doc (`docs/plans/BC-2717-plan.md`) opens with a 6-row "Issue-vs-ground-truth amendments" table. Each row maps:

| issue says | plan does | why | optional follow-up issue link |

This is the **3rd surface** for the pattern — preceded by BC-5947 (1st instance) and BC-5832 task-3 (2nd surface). Per the established promotion convention (3rd surface → architecture-9), this trace records the pattern's promotion to durable architecture-9 status.

The pattern stays valuable across surfaces because issue bodies in Linear are write-once (Prosemirror save mangles edits per `gotcha_linear_markdown_mangling.md`); the plan doc is the only place where the delta between issue-as-filed and reality-as-shippable can be recorded losslessly. The amendments table at the TOP (not in an appendix) ensures every reviewer encounters the deltas before reading the tasks themselves.

### Alternatives considered

1. **Amendments table at top of plan doc** — Chosen. 3rd successful surface confirms shape: 5-column table (#, issue says, plan does, why, optional follow-up). Reviewers acknowledge resolved deltas before reading tasks.

2. **Amend the Linear issue body** — Rejected (BC-5832 task-3 precedent already recorded this rejection). Linear's Prosemirror save mangles list patterns and drops numbered lists in new sections; the plan doc is safer.

3. **Amendments scattered as inline plan-doc notes** — Rejected (BC-5947 originally tried this; reviewers missed the deltas). The top-of-doc table is the consolidated, scannable form.

### Rule derived

**Any plan doc whose source issue has drifted from ground truth MUST record the delta in a 5-column amendments table at the top of the plan doc, BEFORE the task list.** Each amendment row optionally links to a follow-up issue tracking the unresolved gap (BC-2717 amendment rows 1 + 3 demonstrate). Reviewers + future plan-readers see resolved scope deviations on first read; no buried surprises.

### Promotion note

**Promotes to architecture-9 (durable, cross-cutting).** BC-5947 1st surface, BC-5832 task-3 2nd surface, BC-2717 task-2 3rd surface. Pattern is now ratified.

Recommended next moves: (1) add a one-line note to the writing-plans skill itself recommending the amendments table when issue drift is detected; (2) cross-link this trace from BC-5947 + BC-5832 task-3 + future plan docs as the canonical pattern source.

## Task 3 — Cross-skill keep-in-sync reciprocal cross-reference (2nd surface)

**Category:** pattern-application
**Confidence:** 8/10
**Tags:** pattern-application, cross-skill-mirror, keep-in-sync, reciprocal-annotation, anti-drift

### Decision

This PR's list-building skill mirrors the EB-exclusion procedure from tam-mapping § 3 Phase 4.5. The plan committed (amendment row 4) to adding a "Keep in sync — when one changes, audit the other" annotation on **both** sides of the mirror. The first commit landed the list-building-side note but not the tam-mapping-side note — the architecture-reviewer caught the asymmetry (RR2 from second pass) and the fix-pass added the reciprocal.

This is the **2nd surface** for the cross-skill keep-in-sync reciprocal-annotation pattern. BC-5832 was the 1st surface (tam-mapping ↔ icp-scoring delegation contract).

The asymmetry-failure mode is well-defined: a future editor changing the canonical side (here, tam-mapping § 3 Phase 4.5) sees no signal that another skill duplicates the procedure → silent drift → the mirror skill (here, list-building § Workflow 2) keeps running an out-of-date version of the procedure until someone notices at runtime.

### Alternatives considered

1. **Add reciprocal "Keep in sync" notes on both sides** — Chosen (plan amendment row 4 committed to this; first commit forgot the tam-mapping side; second-pass review caught it; fix-pass corrected). The mutual annotation closes the silent-drift loop.

2. **Factor the procedure into a shared reference doc** — Rejected (plan brainstorm decision 3, validated by second-pass review). Each skill self-contained = readable end-to-end. Factoring forces editing the just-shipped sibling (scope creep).

3. **One-way annotation (only the mirror skill cites the canonical)** — Rejected. Asymmetric annotations were the actual bug.

### Rule derived

**When one skill mirrors a procedure from another, BOTH sides MUST carry a "Keep in sync — when one changes, audit the other" annotation pointing at the other.** Plan amendment rows that commit to mirror patterns MUST explicitly say "both sides" so the reviewer can audit. The asymmetry test is mechanical: after PR commit, grep for the annotation in both files; if only one has it, the mirror has already half-broken.

### Promotion note

2nd surface (BC-5832 → BC-2717). At 3rd surface, promote to architecture-9 and consider adding a `/workflows:review` agent-prompt template specifically for "verify reciprocal cross-references when plan amendments commit to mirror patterns."

## Task 4 — Security-class half-fix in same fix-pass = adjacent input becomes new attack surface

**Category:** pattern-choice
**Confidence:** 7/10
**Tags:** pattern-choice, security-fix-pass, half-class-fix, path-validation, asymmetry-attack-surface

### Decision

The first fix-pass added regex validation (`^[a-z0-9_]+$`) to `--audience-view-name` (closing P2.4 — gh-api path injection). The same fix-pass ALSO added a Source-1 staleness gate that used `stat $INPUT_DIR` (shell-interpolated) on user-controlled `--input-dir`. **The fix-pass closed the path-injection class for one input flag while reopening it for an adjacent input flag in the same edits.**

Second-pass security review caught this as RR3. Resolution (RR3 fix): unified path-validation step in Workflow 1 step 0 covering ALL 6 path-bearing flags (`--output-dir`, `--input-dir`, `--input-csv`, `--audience-csv`, `--criteria-file`, `--sfdx-project-dir`) via Python `os.path.realpath` (argv-passed, no shell interpolation). Single edit absorbed RR9-RR12 (realpath portability, criteria-file load step, `$BRITE_DATA_PLATFORM` workflow binding, --input-csv/--audience-csv asymmetry).

### Alternatives considered

1. **Unified path-validation step covering all 6 path inputs in one step** — Chosen. Closes the asymmetry by treating all path inputs as a single class. Future path-bearing flags added to the skill MUST be added to this list — single grep-able source of truth.

2. **Per-flag validation in each Workflow step that uses the flag** — Rejected. Spread-out validation creates the exact asymmetry pattern this fix is closing — easy to forget when adding a new flag.

3. **Document the validation in Anti-Slop only, no workflow step** — Rejected. Anti-Slop is a guardrail-of-last-resort; workflow-step enforcement is the load-bearing surface. (Both Anti-Slop AND workflow step are now in place after the fix-pass.)

### Rule derived

**When a fix-pass closes a security class for one input, scan ALL adjacent inputs of the same shape in the same fix-pass and either fix them in the same edit OR explicitly document why they're out of scope.** The pattern matters for fix-passes specifically because adjacent edits in the same session create a "if you fix half a class, the other half becomes the new attack surface" failure mode. Security review (specialty agent) is well-suited to catching this because security reviewers reason about input classes, not per-flag specifics.

### Promotion note

1st surface for this specific anti-pattern. Adjacent precedents: BC-5832 task-1 (independent re-read of cited authority — same fresh-perspective principle). At 2nd surface (any future fix-pass where security reviewer catches a half-class fix), promote and add a security-reviewer agent-prompt template hint.

This trace is also evidence FOR Task 1 (fix-pass regression check is load-bearing) — without the second-pass security review, RR3 would have shipped silently.

## Task 5 — Cross-skill schema rename caught by architecture-reviewer reading downstream contract independently

**Category:** architecture
**Confidence:** 8/10
**Tags:** architecture, cross-skill-contract, schema-rename, independent-contract-read, downstream-consumer

### Decision

The first commit of this PR named the SMTP catch-all column `smtp_catch_all` in the `enriched_leads.csv` schema. The downstream consumer skill (icp-scoring) `--rubric abc` mode requires a top-level column literally named `catch_all` and HALTs with `missing required column 'catch_all' for --rubric abc` if absent.

The first-pass `architecture-reviewer` agent caught this as P1 (conf 9) by **reading icp-scoring's documented contract independently** and comparing against list-building's documented schema. The `code-reviewer` agent did NOT catch this — it verified the producer's schema row against the SKILL.md prose but did not cross-reference the downstream consumer's contract. **Specialty agent split was load-bearing**: architecture-reviewer's instinct to re-read cross-skill contracts independently is what surfaced the contract break.

This reinforces **BC-5832 task-1** (independent re-read of icp-scoring delegation contract caught a P1 in tam-mapping). Same agent, same skill (icp-scoring), same failure mode (downstream contract break). **2nd surface for the "architecture-reviewer independent contract re-read" pattern** — promote to architecture-9 candidate.

### Alternatives considered

1. **Rename column to `catch_all` + add explicit reshape note** — Chosen. Cites the literal failure mode (`missing required column 'catch_all' for --rubric abc`) and explains the JSONL-to-flat-CSV reshape pattern that mirrors tam-mapping § 3 Phase 7.

2. **Keep `smtp_catch_all` and document a downstream reshape requirement** — Rejected. Pushes the reshape burden onto every downstream consumer; icp-scoring `abc` would still HALT on first invocation.

3. **Modify icp-scoring contract to accept `smtp_catch_all`** — Rejected (out of scope; icp-scoring just shipped per BC-5831; cross-skill contract changes warrant a fresh ADR).

### Rule derived

**Cross-skill contract reviews need an agent that re-reads the consumer's input contract from scratch, not just verifies the producer's emit shape against documentation.** The architecture-reviewer specialty does this naturally; code-reviewer does not. When a SKILL emits an artifact consumed by another SKILL via documented contract, the review pipeline MUST include architecture-reviewer (Tier 3 conditional, but include explicitly via CLAUDE.md `## Review Agents` override if not auto-triggered).

### Promotion note

**2nd surface for "architecture-reviewer independent contract re-read catches downstream consumer contract break."** BC-5832 task-1 was the 1st surface (catch_all reshape from tam-mapping → icp-scoring). BC-2717 is the 2nd surface, also against icp-scoring's `--rubric abc` contract. At 3rd surface, promote to architecture-9 and add a recommendation that `/workflows:review` always include architecture-reviewer when the diff touches a SKILL.md emitting artifacts consumed by another SKILL.

Adjacent precedents: BC-5832 task-2 (review-validation hit rate is workload-dependent — cross-skill integration is high-hit-rate workload). Both reinforce that the cross-skill contract surface is where review investment pays off most.
