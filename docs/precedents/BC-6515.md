## Task 1 — Live-verify before enshrining doc claims that trace to narrative-only artifacts

**Date:** 2026-05-01
**Category:** pattern-choice
**Confidence:** 8/10
**Tags:** pattern-choice, verification-discipline, dogfood-transcript, raw-evidence-vs-narrative, plan-gate, factual-anchor-recipe

### Decision

When about to write a permanent doc claim that traces back to a dogfood transcript section (or any narrative artifact) rather than a raw API/output capture, pause before plan-write and verify the claim live. The trigger is structural: if the cited evidence is a one-sentence operator narrative (e.g., "Lead UUIDs returned (newer than round-2's response shape)") and a grep against the artifact directory produces zero raw-payload matches for the field/behavior in question, the claim has not been verified — it has only been reported. Live-verify (live MCP call, fresh CLI run, etc.) before enshrining; capture the raw response in the plan file as durable evidence.

For BC-6515: the issue body cited round-3 transcript § Phase 4 UPLOAD as evidence that EB now returns `uuid` on lead-create. Transcript line 284 was a single-sentence operator note ("Lead UUIDs returned…"); `grep -rn "uuid" docs/dogfood/bc-6308/` returned only that line and zero raw-response captures. User flagged the gap pre-plan ("can we confirm the API now adds a uuid field? like i want to see it with my own eyes"). Live `POST /api/leads/multiple` call to `emailbison-personal` workspace 13 captured raw response with `uuid: "a1ad8f8d-2e14-45e7-b78a-4593983613fd"`; lead 14723 deleted via DELETE endpoint; raw response pasted into `docs/plans/BC-6515-plan.md`.

### Inputs

- Issue BC-6515 § Sources cited transcript section + plan file as evidence
- `docs/dogfood/bc-6308/round-3-transcript.md` line 284: operator narrative one-liner, no raw JSON
- `grep -rn "uuid" docs/dogfood/bc-6308/`: 0 matches
- `cat docs/dogfood/bc-6308/launch-metadata.json`: `lead_ids_returned: [...]` only — no field-level response capture
- `search_api_spec(POST /api/leads/multiple)` documented response example: lists `id` only, no `uuid` (spec docs lag runtime — verification side-finding)
- Live `POST /api/leads/multiple` call: response carried `uuid` field; cleanup via DELETE successful

### Alternatives Considered

1. **Live POST + capture raw JSON** *(chosen)* — definitive proof the field exists today (2026-05-01), creates citable evidence in the plan file, side effect is one dogfood-flavored test lead in workspace 13 (cleaned up via DELETE).
2. **Spec read only** — rejected. `search_api_spec` doesn't list `uuid` in the response schema, so a spec read alone would have falsified the claim — but in this case the spec is wrong, not the claim. Spec-only reads can produce the opposite false-confirmation: "spec doesn't list the field, so the claim must be wrong" when reality is "spec just lags."
3. **Trust the transcript narrative** — rejected. Operator narratives are the lowest-evidence artifact in the dogfood-walk hierarchy: raw response > metadata.json > transcript narrative. Enshrining a doc claim from a one-line narrative would have left the doc citing prose-of-prose without a verifiable trail.
