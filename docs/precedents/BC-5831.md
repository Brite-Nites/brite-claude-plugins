## Task 1 — Review-pipeline validation step is load-bearing (~80% downgrade rate)

**Category:** pattern-choice
**Confidence:** 7/10 (ambient pattern across many sessions; this session is a clear exemplar but not the first)
**Tags:** pattern-choice, review-validation, severity-inflation, false-positives, validation-subagents, load-bearing-step
**Precedent Referenced:** none (this is a meta-observation about the /workflows:review pipeline itself; not extending a specific prior architecture trace)

### Decision

When running `/workflows:review` thorough mode against a substantial new artifact (e.g., a 400+ line SKILL.md spec), Step 6 validation is **the** authoritative severity pass — not Step 4 review agents. Empirical pattern: 5 review agents produced 35 raw findings (5 P1 + 14 P2 + 16 P3); after confidence filtering (≥7) 17 remained (5 P1 + 10 P2 + 2 P3); after Step 6 validation, **0 P1s confirmed** (1 dismissed as false positive, 4 downgraded to P3) and **9 of 10 P2s downgraded to P3** (only 1 P2 confirmed, both P3s confirmed). Net: ~80% of the ≥7-confidence findings were over-classified by the originating reviewer.

This means Step 6 validation **must not be skipped** for non-trivial diffs, and review-step output cannot be treated as a final severity verdict. Validation subagents — which read the cited file:line independently and apply the severity rubric without seeing the originating reviewer's narrative — catch false positives that the reviewer agent's own writeup buries under confident prose.

### Surface in this session

Concrete examples of severity collapse during BC-5831 review:

- **P1 (cdr-compliance, conf 8) "Missing free-email-provider rejection rule"** → DOWNGRADED to P3. Verifier checked the upstream references (`fit-scoring.md`, `icp-definition.md`, `UPSTREAM.md`) and found NO "Operational Rule 1" in the worktree to inherit. The cdr-compliance reviewer hallucinated a CDR claim from the BC-5832 issue addendum text. The verifier's independent read caught it.
- **P1 (code-reviewer, conf 9) "marketing-context.md schema mismatch"** → DISMISSED. Verifier read `product-marketing-context/SKILL.md` (the canonical generator) and found no documented output template that contradicts icp-scoring's expected `## Brite <X> ICP` headers. The reviewer inferred a contract that wasn't asserted.
- **P1 (performance-reviewer, conf 7) "Per-record model invocations not batched"** → DOWNGRADED to P3. Verifier confirmed per-row is the prescribed upstream contract (verbatim `fit-scoring.md` prompt) with cost gates as the protective mechanism. Batching would break the upstream prompt and per-row reasoning fidelity.
- **P2 (code-reviewer, conf 9) "`--max-records` semantic contradiction"** → DOWNGRADED to P3. Flag table at L43 governs the unset case; anti-slop at L332 governs the set case. Different inputs, not contradictory. Reviewer treated them as the same input case.

### Pattern

Review agents are tuned to flag generously (high recall, lower precision); validation subagents are the precision pass. Both are necessary. **Skipping validation = shipping false-positive fixes** — wasted fix-loop attempts on non-bugs, churn against working code, and the more dangerous case of "fixing" a non-bug in a way that introduces a real one.

The pattern compounds with diff size: the larger the artifact, the more reviewer findings, the more validation matters. For BC-5831 (864 new lines), the 17 ≥7-confidence findings would have produced ~3-4 hours of futile fix-loop work without Step 6.

Inverse pattern (when validation can be safely skipped): when the diff is **trivial** (≤4 mostly-cosmetic line changes) AND the orchestrator can directly inspect each finding's claim against the file in <30 seconds. BC-5901 task-4 codified this as "Step 6 may be skipped when 100% of findings are factually-confirmable by direct inspection." That carve-out does NOT apply to non-trivial diffs.

### Applies when

- Running `/workflows:review` against any non-trivial diff (≥1 new file >100 lines, or ≥10 modified lines)
- Considering whether Step 6 validation is worth the agent-dispatch overhead (answer: yes, almost always, for non-trivial)
- Reading review output and tempted to act on a P1/P2 before validation runs (don't — wait for Step 6, or read the cited code yourself first)
- Designing future review-pipeline tooling: validation IS the authoritative pass; review agents are a generator, not a verdict

### Doesn't apply when

- Trivial diff per BC-5901 task-4 carve-out (orchestrator-direct-inspection sufficient)
- Single-line changes where reviewer findings are obviously off-target (orchestrator can dismiss with a one-line note)

## Task 2 — Brainstorm scope-amendments table in plan doc enables grep-verifiable acceptance

**Category:** architecture
**Confidence:** 7/10 (concrete rule with grep-verifiable acceptance; first instance for marketing skill ports)
**Tags:** architecture, plan-doc-shape, brainstorm-amendments, grep-verifiable-acceptance, scope-divergence, decision-traceability
**Precedent Referenced:** none directly (related to BC-5871 task-2 verification-as-discovery surface, but this trace is about plan-doc structure not verification)

### Decision

When `/workflows:session-start` brainstorming surfaces decisions that **amend** the issue spec (rather than just elaborating it), record each amendment in an explicit table in `docs/plans/BC-XXXX-plan.md` with three columns: **Question**, **Decision**, **Rationale**. Then add a `### Scope amendments vs issue` subsection naming each amendment as a delta (`Replaces ...`, `Adds ...`). Every amendment must have a grep-verifiable acceptance criterion in the verification checklist.

This makes scope drift between issue spec and shipped artifact auditable: a future reader can grep both the plan doc and the SKILL.md to confirm the encoded decision matches the recorded amendment, and the issue spec's stale clause can't accidentally be re-introduced during execution because the verification checklist would fail.

### Surface in this session

BC-5831 brainstormed 4 decisions, 2 of which amended the issue spec:

1. **Cost-cap UX** — issue spec said "`--max-records 10000` hard limit" (Tam-map addendum § Added scope item 5). Amendment: replaced with `AskUserQuestion` gate at thresholds (no hard refuse).
2. **Missing-marketing-context.md fallback** — issue spec said "warn user" but didn't define recovery. Amendment: added explicit 3-way `AskUserQuestion` (run /marketing:product-marketing-context, pick entity inline, or cancel).

The plan doc encoded both as a 4-row "Brainstorm decisions (recorded 2026-04-26)" table and a "Scope amendments vs issue" subsection. Verification checklist included grep-verifiable items: `grep "no hard cap"` must find the SKILL.md line; `grep -E "(hard limit 10000|max-records 10000 hard)"` must find nothing. Both grep tests passed during fix-up.

### Pattern

The plan doc is the contract between brainstorm and execution. When brainstorm amends the issue, the plan doc's table is the authoritative record (the issue body is read-only history). Without an explicit amendment table, scope drift becomes invisible: the implementer follows the brainstorm decisions, but a reviewer reading the issue and comparing to the diff sees apparent contradiction with no recorded resolution.

The grep-verifiable acceptance criterion is what makes the table operational rather than decorative. "No hard refuse documented anywhere in SKILL.md" is grep-checkable; "the spec is consistent" is not.

### Applies when

- Brainstorming surfaces a decision that contradicts or refines an existing issue clause (not just elaborates a placeholder)
- Plan doc is being written for any non-trivial issue (multi-task plan, ≥3 tasks)
- Verification checklist is being authored — every amendment must have a corresponding grep-verifiable line item

### Doesn't apply when

- Brainstorm decisions are pure elaboration of issue spec (no amendments)
- Issue spec was authored AFTER the brainstorm (i.e., the plan IS the issue)
- Trivial fix where the brainstorm/plan/execute steps are skipped entirely

## Task 3 — Cross-skill "Receives from" insertion needs consumer's input-contract verification

**Category:** bug-resolution
**Confidence:** 7/10 (real bug introduced + caught + fixed in this session; concrete rule with verification path)
**Tags:** bug-resolution, cross-skill-link, input-contract, consumer-verification, code-reviewer-catch, indirect-upstream
**Precedent Referenced:** none (new pattern class — cross-skill-link factual-correctness surface, distinct from prior cross-skill verification traces about boundary scope)

### Decision

When adding a "Receives from" entry to a sibling skill's cross-skill boundaries section, **read the consumer's §2 Before Starting AND §6 Operational Runbook before authoring the line**. The new line must accurately describe what the consumer actually iterates over — direct CSV consumption, per-prospect artifact consumption, optional input vs required, etc. Don't assume "qualified list → consumer skill" implies direct CSV iteration; some consumers operate per-prospect on a different artifact shape.

When the data flow is two hops (e.g., A produces CSV → B operates on per-prospect derivatives of that CSV), the cross-link must be framed as **indirect upstream**, naming the intermediary skill that bridges the data-shape gap.

### Surface in this session

During Phase C cross-link insertion for BC-5831, I added this line to `plugins/marketing/skills/email-copywriting/SKILL.md` line 206:

> **Receives from:** ..., `icp-scoring` (BC-5831 — qualified prospect list as `*_qualified.csv` from `score_0_100` mode or `tier-a.csv` / `tier-b.csv` from `abc` mode; the qualified list becomes the prospect input for sequence drafting).

The /workflows:review code-reviewer flagged this as **P2 conf 8**, and the validation subagent CONFIRMED. Reading email-copywriting's actual §2 + §6: the skill consumes a **per-prospect situation-mining artifact** (or a scratch-path interview), not a CSV. The qualified CSV is consumed by `/marketing:launch-campaign`, not by email-copywriting directly. The real chain is two hops: `icp-scoring qualified.csv` → per-prospect `situation-mining` runs → `email-copywriting` per situation artifact.

The fixed line frames the relationship as **indirect upstream**:

> ..., `icp-scoring` (BC-5831 — *indirect upstream*: the qualified prospect list ... is the population from which per-prospect `situation-mining` runs feed this skill — icp-scoring's CSV is consumed by `/marketing:launch-campaign`, not directly by this skill).

### Pattern

Cross-skill links carry implicit data-flow claims that are easy to get wrong when the chain is multi-hop. The pattern most likely to misfire: "skill A produces CSV X; skill B is downstream → therefore B consumes X directly." If B's actual input is a per-prospect derivative of X (e.g., a research artifact extracted per row), the cross-link wording is wrong even though the directional claim ("A is upstream of B") is right.

Verification rule: read the consumer's §2 Before Starting (which lists required inputs) and §6 Operational Runbook (which shows actual flow). If the consumer's flow doesn't iterate the producer's output directly, the cross-link is indirect — frame it that way.

### Applies when

- Adding any "Receives from" cross-link to a sibling skill's cross-skill-boundaries section
- Cross-link spans skills where the data shape changes between producer and consumer (CSV vs per-prospect, list vs single-record, raw vs enriched)
- Reviewing a PR that touches another skill's cross-skill section without modifying that skill's actual inputs

### Doesn't apply when

- Both skills operate on the same artifact shape (CSV → CSV with added columns)
- The cross-link is unidirectional and the consumer explicitly documents the producer as a required input
