# BC-5794: Second-of-N session confirms the sibling-zero template generalizes

**Date:** 2026-04-20
**Category:** pattern-choice
**Confidence:** 8/10

## Decision

A first-of-N session (BC-5793) that does the work of locking a template is only worth that investment if session two can pick it up mechanically. Execute the second instance of a templated pattern ("sibling-one") entirely from the first session's departures + convention sources — do not re-derive decisions or re-open conflicts the first session closed. If the template does not pick up cleanly, the first-of-N did not do its job and the precedent should be downgraded, not the template relitigated.

## Context

BC-5794 was the second Phase 3 RevOps skill customization, following BC-5793 (the first-of-N / sibling-zero). The three issue-body conflicts that BC-5793 resolved at Plan gate (rename-vs-keep name, attribution wording, no `git mv`) re-appeared identically in BC-5794's issue body because both issues were filed before ADR-007 §3.6 locked the naming convention.

The template held. All three overrides from BC-5793 applied verbatim to BC-5794:
- Issue T1/T3 paths `brite-permissions` → override to `sf-permissions`
- Attribution: canonical `Adapted from Jaganpro/sf-skills@ff1ab74 (MIT)` form
- Execute step 1 `git mv` → no-op

No new convention drift surfaced. `UPSTREAM.md` (updated by BC-5793) needed zero additional edits. The plan doc, commit message, PR body, and Linear comment all mirrored BC-5793's 3-location audit trail.

## Alternatives Considered

1. **Re-derive the overrides at Plan gate in BC-5794.** Rejected — BC-5793 precedent exists precisely to skip this. Re-deriving would cost 3 AskUserQuestion turns and risk producing a different answer (attribution wording especially).
2. **Batch BC-5794 with BC-5795–5805 as a single megadiff.** Rejected — 11 skills × 7 conventions each is too much to review together; sibling-one is the right unit to confirm the template before fanning out.
3. **Apply BC-5793's overrides verbatim, document them once at Plan gate, ship (chosen).** Plan file cites BC-5793 as the sole source for the override block; verification table re-points T1/T3 paths; commit + PR + Linear comment each reference "per BC-5793 precedent". 1 AskUserQuestion for plan approval, zero for the overrides themselves.

## Outcome

Delivered `plugins/revops/skills/sf-permissions/` customization — one SKILL.md edit adding attribution + Brite Context + 7-subsection Brite Permission Conventions (mirroring brite-salesforce/CLAUDE.md lines 164–173 verbatim) + frontmatter version bump to `1.2.0-brite.1`. All 9 verify tests (T1–T5, T8, T9) passed locally; T6/T7 cross-repo deferred post-merge same as BC-5793.

`/workflows:review` verdict: NON-TRIVIAL. Across 3 simplify agents + 4 review agents (code, security, performance, cdr-compliance): 0 P1s, 0 P2s applied, 6 simplify + 3 P3 polish fixes applied as a second commit. 1 P2 (description length, confidence 6) deferred — sibling-zero consistency ruled against trimming.

**Reusable beyond this case.** Sibling-one is the inflection point for template validation. If sibling-one ships with novel plan-gate decisions that sibling-zero didn't cover, the first-of-N was incomplete and the precedent should be amended before the remaining N−2 siblings start. If sibling-one ships mechanically (as here), the template is confirmed durable and the remaining siblings can fan out in parallel without re-reading the first-of-N precedent in full.

**Secondary observation:** cdr-compliance-reviewer caught a path-consistency issue (HTML attribution comment missing `brite-salesforce/` prefix) that code-reviewer, security-reviewer, and performance-reviewer all missed. On skill-customization diffs where cross-repo references are load-bearing, the CDR agent earns its slot — the value isn't just CDR coverage but provenance-path auditing.

**Strengthens** BC-5793 (first-of-N). The BC-5793 precedent should be read as "ratified by BC-5794" on the attribution-wording and keep-upstream-name decisions.

**Precedent Referenced:** BC-5793
