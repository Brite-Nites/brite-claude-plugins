## task-1 — Spec-heavy command `/workflows:review` thorough-loop ceiling: 5 iterations (refining BC-5761/BC-6965 prediction upward)

**Pattern type:** pattern-choice (refines the iteration-budget precedent from BC-5761 / BC-5762 / BC-6965 task-5)

**Confidence:** 9/10

**Context.** BC-5761 / BC-5762 locked "fix-review loops for markdown-spec PRs converge in 4-5 iterations; budget accordingly, cap at 5". BC-6965 task-5 sharpened the floor: "3-iteration floor for 'loop until clean' — iter 2 fold-in commonly introduces 0-2 new defects (citation drift, schema drift) caught by iter 3". This session ran the explicit "loop until clean" instruction on a 370-line load-bearing spec file with 5 reviewers in parallel. Trajectory:

- iter 1: 0 P1 / **4 P2 / 8 P3** (initial draft surfaces real contract gaps)
- iter 2: 0 P1 / 0 P2 / **5 P3** (iter-1 fold-in introduces 5 minor contracts that iter-2 reviewers refine)
- iter 3: 0 P1 / 0 P2 / **3 P3** (iter-2 fold-in introduces 3 more minor framing nits)
- iter 4: 0 P1 / 0 P2 / **1 P3** (iter-3 fold-in self-introduced 1 contract gap — `stale: indeterminate` had no `--json` representation)
- iter 5: **0/0/0 — CONVERGED**

The trajectory is **monotonically decreasing AND P1/P2 stay at zero from iter 2 onward**, but P3-tail takes 5 iterations to fully drain on a spec-heavy artifact. BC-6965's 3-iteration floor was correct for an orchestrator with locked Q-decisions; **this session adds: spec-heavy commands (especially those introducing NEW spec contracts beyond the locked Q-decisions) need 5-iteration ceiling**, not 3.

**Decision.** When invoking `/workflows:review` with explicit "loop until clean" on a spec-heavy artifact (>300 lines of new prose), budget for 5 iterations and 5 reviewers in parallel. The convergence shape: P1/P2 drop to zero at iter 2; P3-tail takes 3 more iterations to drain. Stop conditions:

1. **Iter ≥3 returns 0/0/0** across all selected reviewers — converged, ship.
2. **Iter ≥3 returns only "scale-awareness notes"** (perf-style speculative concerns, not actionable) — converged for shipping purposes; reviewer recommendation typically explicit ("CONVERGED. Ship").
3. **Iter ≥5 still returns P3s** — accept remaining P3s as v1.1 parking-lot candidates and ship; further iteration introduces more contracts than it fixes. (BC-5761's "cap at 5" hard-stop applies.)

**Rejected alternatives:**
- Use BC-6965 task-5's 3-iteration floor as a hard rule: would have shipped at iter 3 with 3 P3s carrying forward — including a real `--json` contract gap (the iter-3 stale-tri-state) that iter 4 caught. Cost of skipping = 1 v1.1 amendment we now don't need.
- Cap at 4 iterations: would have caught the iter-3 contract gap at iter 4 (correctly) but missed iter-5's confirmation that iter-4 fix didn't introduce new drift. The iter 5 0/0/0 is the convergence proof, not noise.
- Re-litigate at iter 5 with full 5-reviewer fan-out: by iter 5 most reviewers have converged earlier (CDR-clean iter 2; security-clean iter 2; arch-clean iter 3; perf "CONVERGED. Ship" iter 4). Selective dispatch (only the still-active reviewer) at iter 5 was the right call.

**How to apply.** For spec-heavy artifacts (new commands, new SKILL.md files, new agent definitions >300 lines):
1. Set the iteration budget to 5; commit count expected at 5 (1 implementation + 4 review-loop fix-ups).
2. Iter 1 should fan out to all 5 reviewers (code, security, performance, architecture, CDR-compliance).
3. Iter ≥2 dispatches selectively — only re-launch reviewers that produced findings in the prior iter; reviewers that returned 0/0/0 stay clean unless a structural section they own was rewritten.
4. Treat reviewer language ("CONVERGED. Ship", "Verdict: Ship") as a strong stop signal at any iteration; combined with 0/0/0 from at least one reviewer it's converged.
5. After ship, the precedent trace counts iterations as a quality signal — fewer is better but plateauing at 4-5 on a spec-heavy artifact is healthy, not concerning.

**Telemetry watch.** Track per-PR iteration count for `/workflows:review thorough` invocations on spec-heavy artifacts. Hypothesis: median converges at 4 iterations on locked-Q-decision orchestrators (BC-6965 was 3); 5 on spec-heavy commands introducing new contracts (BC-6969); higher on commands that span multiple Q-locks (untested — predict 6+). Joint promotion candidate with BC-5761 + BC-5762 + BC-6965 task-5 — promote the tier-stratified iteration-budget rule when 2+ more spec-heavy commands surface this exact 5-iteration shape.

## task-2 — 3rd surface of BC-6955 task-3: line-anchor verification at canon source-of-truth (counter 3/N toward promotion)

**Pattern type:** pattern-application (BC-6955 task-3 — line-anchor verification, surfaced 3rd time across BC-6955 / BC-6965 / BC-6969)

**Confidence:** 10/10

**Context.** Iteration 1 of `/workflows:review thorough` surfaced architecture-reviewer P1 (conf 10): the audit.md spec cited Q38 lock at `plugins/flow-architecture/docs/design-rationale/project_fda_plugin_interview.md:700`, refinement audit trail at `:716`, sub-decision 4 deferred at `:730`, Q29.7 at `:272`. **Actual canon line anchors: Q38 = `:713`, refinement audit = `:729`, sub-decision 4 = `:743`, Q29.7 = `:273`. All four anchors were off — Q38 by 13 lines, the others by 13 / 13 / 1 lines.**

This is a faithful-echo violation against canon — the same class as BC-6955 task-3 (1st surface: BC-6955 author-time miss caught by code-reviewer; led to Q29 amendment 1 + the BC-6955 task-3 precedent itself), BC-6965 task-1 (2nd surface: BC-6965 author-time miss caught by /workflows:review iter 1; led to Q47 amendment 1 + Q23 amendment 1). **BC-6969 is the 3rd consecutive surface** in 4 weeks of FDA-plugin work.

**Distinguishing feature this surface.** Unlike BC-6955 (1 anchor off) and BC-6965 (1 amendment + 1 citation), BC-6969 had **4 anchors off in a single author-time miss**. The author-time error mode is "cite the issue body's referenced line numbers without re-grepping the canon file when the canon file has been edited" — both BC-6965 + BC-6969 sessions referenced canon line numbers from the issue body without re-verification. The Q-lock canon file accumulates amendments over time; the issue body's pinned line numbers grow stale faster than the issue gets re-edited.

**Decision.** Apply the BC-6955 task-3 precedent unchanged: fix the derivative (audit.md) AND re-verify all line anchors at the canon source-of-truth at the same time, in the same PR. Single commit (the iter-1 fix-up). No separate canon-amendment needed for the line numbers themselves — the canon line numbers were always correct; only the derivative drifted.

**Rejected alternatives:**
- File a Q38 amendment for the line-anchor drift: incorrect — the canon Q-lock body text was correct; the derivative cited stale line numbers. No canon change is warranted.
- Fix only the most-cited anchor (Q38 lock `:713`): would have left 3 of 4 anchors broken, perpetuating the same fail-mode for the next reader.
- Defer to a follow-up issue: line-anchor drift is a faithful-echo defect, not a feature scope question; same-commit fix is the only correct disposition.

**How to apply.** The rule has not changed since BC-6955 task-3, but the 3rd surface confirms it as load-bearing:

> **Before authoring any FDA-plugin command/skill/agent that cites canon Q-lock line numbers, run a grep against the actual canon file FIRST to confirm each cited line number resolves to the cited content.** Re-verify EVERY anchor in EVERY draft, even if the issue body provides line numbers — the issue body's anchors grow stale as canon amendments land. The cost of running 4-5 `grep -n "^**Q[0-9]" canon.md` calls per draft is sub-second; the cost of shipping 4 wrong anchors is a P1 from architecture-reviewer.

**Telemetry watch.** **Promotion candidate.** BC-6955 task-3 promotion threshold was implicit (3 surfaces); BC-6969 is the 3rd surface. Joint promotion candidates with BC-6955 task-3 + BC-6965 task-1 (canon-amendment-in-same-PR is the correct mechanical when the fix is at canon; line-anchor verification is the correct mechanical when the fix is at the derivative — same load-bearing principle, two correctional mechanics). Recommend promotion to organization-level CLAUDE.md as a process-discipline rule for any plugin maintainer authoring against an interview-memory canon. Counter: BC-6955 task-3 (1st) + BC-6965 task-1 (2nd) + BC-6969 task-2 (3rd) = **3/3 surfaces in 30 days; promote**.

## task-3 — Canon-described MCP-tool signature can drift from actual MCP-tool registration

**Pattern type:** pattern-choice (NEW — 1st surface; sibling to BC-6955 task-3 line-anchor pattern but with a distinct fix mechanic)

**Confidence:** 8/10

**Context.** Iter-1 code-reviewer surfaced a P2 (conf 7): the audit.md spec proposed `list_issues({labels: ["domain:<slug>"]})` per the canonical Q38 sub-decision 3 + Q29.3 description (memory:706 + memory:262). **The actual workflows-plugin Linear MCP `list_issues` tool registration takes `label` as a singular string, not `labels` as a list.** The canon Q-lock description was authored from a stale view of the MCP tool registration; the derivative faithfully echoed the canon description; both diverged from the actual MCP signature.

This is **distinct from BC-6955 task-3** (line-anchor drift in faithful-echo): there, the canon source was correct and the derivative drifted. Here, **the canon source itself is stale against an external dependency** (the workflows-plugin MCP tool registration), and the derivative correctly executes faithful-echo against the canon.

The fix mechanics differ:
- **Line-anchor drift (BC-6955 task-3):** fix the derivative; canon stays unchanged.
- **Canon-vs-MCP-signature drift (BC-6969 task-3):** fix the derivative AND flag the canon for amendment.

**Decision.** Apply a **two-part fix**:
1. Correct the derivative to use the actual MCP signature (`label: "domain:<slug>"` singular).
2. Add an explicit "Q38 amendment 2 candidate if the divergence persists past Brand Hub dogfood" forward-pointer in the derivative, citing canon's older `labels: [...]` form descriptively. Do NOT amend canon in the same PR — Brand Hub dogfood (BC-6998) will reveal whether the derivative-only correction is sufficient or whether the canon needs to be re-anchored to the actual MCP signature.

**Rejected alternatives:**
- Fix only the derivative without the forward-pointer: would lose the canon-drift signal for future readers; next derivative might re-derive `labels: [...]` from canon and hit the same bug.
- Amend canon in the same PR (Q38 amendment 2): premature — we don't yet know whether the workflows MCP signature is stable or in flux. Waiting for Brand Hub dogfood signal is the cheaper-information policy.
- File a follow-up Linear issue for canon-amendment: same as above; the forward-pointer in the derivative is the lower-friction parking-lot mechanism since canon amendments require explicit user lock.
- Treat as a non-issue (just fix the spec): would leave canon as a future fail-mode source.

**How to apply.** When `/workflows:review` surfaces a defect where:
(a) the derivative faithfully echoes a canon Q-lock description, AND
(b) the canon description specifies an external dependency's API shape (MCP tool signature, library API, GraphQL schema, etc.), AND
(c) the actual external dependency's shape differs from canon's description,

then the correct fix is **derivative-only correction PLUS a forward-pointer to the canon amendment as a v1.X candidate**. Canon amendment is deferred to the next consumer that proves the divergence is structural (not transitional). The derivative carries the actual signature with an explicit "track as Q<N> amendment <M> candidate" tag.

**Telemetry watch.** Surface again on the next FDA derivative that calls a workflows-plugin MCP tool (BC-6977 `/flow:ship` clone, BC-6961 `/flow:plan-{discipline}` parent, BC-6964 `/flow:add-domain`). If 2+ of those surface the same `labels:` vs `label:` divergence, promote canon amendment from "candidate" to "required" — the divergence is structural, not transitional. Joint sibling to BC-6955 task-3 (both patterns address canon-source drift but with opposite fix-mechanics — same parent precedent class, two distinct load-bearing children).

## task-4 — APFS case-insensitive `.gitignore` matches silently swallow new files

**Pattern type:** bug-resolution (NEW — gotcha-class durable learning)

**Confidence:** 9/10

**Context.** After authoring `plugins/flow-architecture/commands/audit.md` (310 lines, with Phase A / Phase B / Phase C content), the file appeared on disk via `ls -la` (26670 bytes) but `git status` showed it as **untracked-and-invisible** (not even `??`). Investigation: `.gitignore` line 2 has `AUDIT.md` (intent: ignore audit-artifact files at any depth). On macOS APFS (case-insensitive by default), git's gitignore matching is case-insensitive when the underlying filesystem is — so `AUDIT.md` matched `audit.md` silently. `git check-ignore -v plugins/flow-architecture/commands/audit.md` revealed the matching pattern: `.gitignore:2:AUDIT.md ⟶ plugins/flow-architecture/commands/audit.md`.

Fix: add an explicit negation rule `!plugins/flow-architecture/commands/audit.md` immediately after the `AUDIT.md` line, with a comment explaining the APFS interaction.

**Decision.** Document the APFS-case-insensitive gitignore matching gotcha as a durable learning. Always run `git check-ignore -v <new_file_path>` after `Write` for any new file in a directory that touches a top-level gitignore pattern, BEFORE assuming `git status` will show the file. Do not rely on git's silence to confirm tracking — silence on macOS APFS can mean "matched a case-insensitive ignore rule".

**Rejected alternatives:**
- Rename the FDA command to something that doesn't case-overlap (`flow-audit.md` etc.): would diverge from the FDA `/flow:audit` slash-command convention (commands match `<slug>.md`); cosmetic + breaks the convention.
- Change the existing `AUDIT.md` rule to a more anchored form (`/AUDIT.md` for repo-root only, or `/AUDIT_*.md` for prefix-scoped): risks breaking the original intent of catching `AUDIT.md` audit-artifact files anywhere in the tree; surgical negation is the safer change.
- Use a `core.ignorecase=false` git config: requires per-clone configuration; doesn't survive fresh checkouts; addresses the symptom not the cause.

**How to apply.** Add to plugin / project CLAUDE.md gotchas:

> **APFS case-insensitive `.gitignore` matching:** macOS APFS is case-insensitive by default; git's gitignore matching follows the filesystem's case-sensitivity. A top-level `AUDIT.md` rule will silently match `audit.md`, `Audit.md`, etc. After writing any new file whose name case-insensitively overlaps an existing gitignore pattern, run `git check-ignore -v <path>` to confirm; add an explicit `!path/to/file.md` negation rule when needed. Do not assume `git status` is the source of truth on macOS — silence can mean "matched and hidden", not "tracked".

**Telemetry watch.** Likely-low-frequency gotcha (most plugin file names don't case-overlap with existing ignore patterns), but high-impact-when-it-fires (a load-bearing artifact silently absent from git is a P1 ship blocker). If 1+ more sessions surface this within 30 days, promote to project CLAUDE.md gotcha section. Single-surface for now; durable-learning-but-not-precedent-promotion candidate.
