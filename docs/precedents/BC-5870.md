## Task 1 — First-principles reframing surfaces a better option, but user pick from the original gate governs what ships

**Category:** pattern-application
**Confidence:** 8/10
**Tags:** pattern-application, gate-respect, first-principles-reframe, recommendation-vs-pick, architecture-9-promotion
**Precedent Referenced:** BC-5866 (gate-respect contract, original), BC-5864/5865 (1st surface — spec-cascade self-downgrade), BC-5872 (2nd surface — `###` subsection cascade), BC-5869 task-1 (3rd surface — skill-invocation-shape escape hatch; flagged architecture-9 promotion at next novel surface)

### Decision

When the user asks for a first-principles recommendation on a binary A/B gate, it is legitimate to articulate a **third option A'** that the issue body did not name. That articulation does not redefine the gate. If the user then picks from the **original binary** ("proceed with A"), ship A as written — never silently substitute the articulated A' because "it's what I'd recommend anyway."

**Specific instance this session.** BC-5870 issue body framed two options: A (threshold aggregation at 10 flags) vs B (post-synthesis opt-in `AskUserQuestion`). User asked "what do you recommend? think about it from first principles." I reframed the choice around what § 1.6 is actually for (Gate #1 cycle-shape judgment, not data display) and recommended **A' — always aggregate, no threshold** — as cleaner than A's threshold or B's opt-in, grounded in BC-5869's "render at decision-relevant granularity" pattern.

User replied "proceed with A." I shipped A verbatim — the 10-flag threshold, not always-aggregate. The A' recommendation was captured in the conversation but did not leak into the spec edit.

### Alternatives considered

1. **Ship A' since it's what the recommendation converged on.** Treat "proceed with A" as roughly equivalent to "proceed with the recommendation." **Rejected.** "A" is a literal token the user typed after reading a specific definition of A in the issue body. Substituting A' because the orchestrator prefers it is the silent-self-downgrade failure BC-5866 codifies, moved to a new surface (recommendation substitution).

2. **Re-prompt before shipping A.** "You picked A, but my recommendation was A' — are you sure about A?" **Rejected.** Re-prompting with orchestrator opinion embedded pressures the user toward a different path. If a new gate is genuinely needed, it should be neutral — but in this case no new gate was needed. The pick was unambiguous.

3. **Embed A'-flavored hedges into the A implementation.** E.g., ship A with a `TODO: revisit always-aggregate` comment or a lower threshold (e.g., 5 instead of 10) that starts drifting toward A'. **Rejected.** That is precisely the surface this precedent exists to prevent — the orchestrator biasing the execution toward its preferred option through implementation choices the user did not authorize.

### Rule derived

**The orchestrator's first-principles analysis can surface a legitimately better option, but the user's gate pick binds the execution to the **named** option they picked, not the option the orchestrator would have picked.** The two moves — *reframing the decision space* and *executing the pick* — are separable. The first is a legitimate part of recommendation; the second is governed by the gate-respect contract regardless of recommendation strength.

### Promotion note

**4th distinct surface-class for BC-5866 — architecture-9 threshold crossed.** Per BC-5869 task-1: "Architecture-9 promotion candidate at next novel surface." Surfaces so far: spec-cascade self-downgrade · `###` subsection cascade · skill-invocation-shape escape hatch · **first-principles-reframe recommendation-substitution**. The gate-respect contract now crosses the 4-surface threshold and is due for promotion to `plugins/cadence/skills/_shared/gate-respect.md` as a **surface-agnostic rule** rather than a per-surface application pattern. Follow-up work item: rewrite `gate-respect.md` to name the abstract invariant ("the named option the user picks binds execution regardless of orchestrator-side synthesis") and list the surfaces as examples, not as the definition.

## Task 2 — Verification-discovered adjacent bugs stay out of the current PR; file a sibling issue with verification-origin framing

**Category:** scope-change
**Confidence:** 6/10
**Tags:** scope-change, atomic-pr-discipline, verification-side-effects, sibling-issue-framing, dogfood-chain
**Precedent Referenced:** None primary. Adjacent to `memory/feedback_atomic_issues_for_agents.md` (atomic issues); adjacent to BC-5869 secondary observation on BC-6000 cache-fix verification.

### Decision

When seeded verification for an in-flight issue uncovers an **adjacent bug** in a different layer of the same system, do not absorb the fix into the current PR. Ship the current issue at its original scope; file a sibling issue that (a) cites the verification step as the origin, (b) documents the shape of the discovery, and (c) explicitly states why the current issue is not blocked.

**Specific instance this session.** BC-5870 plan included seeded verification against W17's real `audit.json`. That verification revealed the `project-audit` subagent was persisting `quality_gate_flags_count` (int) with `quality_gate_flags: []` empty — a spec departure from `agents/project-audit.md:42`, which declares the full `{issue_id, check, message}` list. The discovery had a measurable downstream impact on BC-5870's own Option A rule: the "by check" half of the aggregation line could not be rendered against W17's real data.

The tempting move was to widen BC-5870 to include the agent-side fix, producing one PR that both codifies the render rule AND fixes the persistence. Rejected. Filed BC-6052 (project-audit spec departure) as a sibling with BC-5870 as its `relatedTo` and BC-5763 (W17 dogfood) as parent. BC-5870 shipped at original scope; BC-6052 remains independently testable.

### Alternatives considered

1. **Absorb the agent fix into BC-5870.** Update `agents/project-audit.md` emission alongside the spec edit. **Rejected.** The issues live in different layers (spec-layer render rule vs. agent-layer output schema) and have different review surfaces. Bundling them would have widened the PR review scope, delayed BC-5870 by one round of agent fixup, and muddled the precedent trace (is this a spec-codification precedent or an agent-fix precedent?).

2. **Hold BC-5870 ship until the agent fix lands, so the Option A rule can be fully seeded-tested against real W17 data.** **Rejected.** The spec rule itself is correct (AC #1, #2, #4 all covered). The render-against-real-data story is a downstream integration concern; the rule is unit-correct and will integration-pass once BC-6052 lands. Holding would conflate spec correctness with downstream integration — which violates atomic-PR discipline.

3. **Skip the seeded verification entirely, ship BC-5870 from the synthetic fragments only.** **Rejected in the other direction.** The W17 verification is where BC-6052 surfaced; skipping it would have buried the spec departure for another dogfood cycle.

### Rule derived

**Seeded verification is a discovery surface; discoveries it produces are filed as siblings, not absorbed.** The framing in the sibling issue's Context section should explicitly name the verification step as origin — this preserves the dogfood→cluster→fix chain in the issue graph without requiring readers to reconstruct it from commit history.

### Observation

BC-5763 (W17 dogfood) has now surfaced three sibling fixes in this cluster: BC-5869 (§ 1.6 drift bullets / zero-activity footer), BC-5870 (§ 1.6 quality-flags threshold), BC-6052 (project-audit persistence). The "§ 1.6 synthesis is doing too much at 26 projects" diagnosis continues to expand its blast radius — the cluster may still hold more findings. Worth re-reading W17 `dogfood-notes.md` against the current spec once BC-6052 lands, in case a 4th sibling surfaces.
