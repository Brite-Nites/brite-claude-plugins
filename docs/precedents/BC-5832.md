## Task 1 — userConfig must omit `default` to honor an ADR's "unset → auto-detect" resolution order

**Category:** architecture
**Confidence:** 8/10
**Tags:** architecture, plugin-json-schema, adr-008, auto-detect, userconfig-pattern

### Decision

ADR-008 (`docs/decisions/008-tam-mapping-enrichment-pluggability.md` § "Unset resolution order") specifies a 3-step probe-fallback chain when `enrichment_provider` is **not configured**: probe `brite_mcp` → probe `brite_cli` → fall through to `blitz_waterfall`. The ADR's correctness depends on the userConfig field actually being capable of being "unset."

The first commit of this PR set `"default": "blitz_waterfall"` in plugin.json's `userConfig.enrichment_provider`. The architecture-reviewer caught this in /workflows:review thorough mode at **P2 [7/10]**: with a default value, the userConfig is never unset, so the probe chain is unreachable code — every existing user is silently pinned to `blitz_waterfall`, and the BC-5538 cutover would require a manual userConfig flip per user instead of being automatic.

The fix (commit `0e2b257`) was to drop the `default` key entirely from plugin.json and add an explicit 3-step auto-detect resolution order to SKILL.md §Before Starting → Enrichment-provider selection (matching the ADR text). The trimmed userConfig description now reads `"Unset → auto-detect per ADR-008 (probe brite_mcp → brite_cli → blitz_waterfall)."`

### Alternatives considered

1. **Drop the `default` field; document auto-detect in SKILL.md** — Chosen. Honors the ADR contract; future BC-5538 cutover happens automatically the moment the brite-enrichment MCP registers (no userConfig surgery needed per user).

2. **Keep `default: blitz_waterfall`; amend ADR-008 to record that the explicit default supersedes auto-detect** — Rejected. The ADR was deliberately structured so unset = auto-detect because the plugin's primary distribution model is "ship and have it Just Work." A hardcoded default forces every install to update userConfig at MCP-cutover time, defeating ADR-008's "ship now, swap later" rationale. The right move was honoring the ADR, not bending it.

3. **Set `default: null`** — Considered. Some JSON schema libraries treat null and unset as equivalent; Claude Code's userConfig substitution does not. Cleaner to omit the key entirely.

### Rule derived

**When an ADR specifies "unset → auto-detect" resolution, the corresponding plugin.json `userConfig` field MUST NOT specify a `default`.** A default value makes the unset state unreachable, silently disabling the auto-detect path the ADR was written to enable. This applies generically to any future userConfig field paired with an ADR-defined fallback chain.

Pattern is general enough to belong in CLAUDE.md gotchas — added there in this PR alongside the existing strict-schema gotcha.

### Promotion note

First surface for this specific gotcha (userConfig + ADR auto-detect interaction). Filed as architecture (not pattern-choice) because it's a generic plugin.json schema rule, not a per-skill judgment call. At the 2nd surface (any future ADR specifying an unset-fallback chain that gets the same treatment) bump to 9/10 architecture and promote to a CLAUDE.md gotcha cross-link from this trace.

The userConfig-as-routing-layer pattern (declared field used by skills via `${user_config.*}`) is itself a 1st-class architectural mechanism — this trace records the first observed gotcha against it. Adjacent precedents: BC-6000 same-commit version-bump rule (cache-keyed-by-version interacts with userConfig in similar "the schema is load-bearing, treat carefully" ways).

## Task 2 — Cross-skill contract integrations have higher review-validation hit rate than single-skill spec authoring

**Category:** pattern-application
**Confidence:** 8/10
**Tags:** pattern-application, review-validation, hit-rate, cross-skill-contract, workload-dependency

### Decision

BC-5832 is the **2nd surface** for the "Step 6 review-validation is workload-dependent" observation. The 1st surface (BC-5831 task-1, 7/10) recorded a ~80% downgrade rate where review agents over-classified spec-refinement findings. BC-5832 recorded the opposite extreme: **5/5 = 100% confirmation rate** on the 5 above-threshold findings (1 P1 + 4 P2 with confidence ≥7).

The difference is the *nature of the work*, not the rigor of the review:

- **BC-5831 (low validation rate):** iterative refinement of a single skill (icp-scoring) where most P1/P2 findings were stylistic boundary calls — the work was already grounded in earlier shipped artifacts, so reviewers' independent re-derivations had high overlap with intentional choices and got DOWNGRADED/DISMISSED.

- **BC-5832 (high validation rate):** first-instance integration of a cross-skill contract (Phase 7 reshape per icp-scoring's `--rubric abc` delegation contract) plus first-time interaction with a userConfig + ADR resolution-order pattern (ADR-008). Reviewers' independent reads of the icp-scoring SKILL.md delegation-contract section and the ADR-008 §"Unset resolution order" section produced findings the orchestrator's planning hadn't fully internalized. Real contract violations, not style.

Promoted to 8/10 because the rule has now surfaced from both directions (low + high) — establishes the bracket and gives the orchestrator a calibration anchor: when the work is a contract integration with a previously-shipped sibling, expect higher hit rate; when it's spec polish on a single artifact, expect ~80% downgrade.

### Alternatives considered

1. **Treat 100% confirmation as luck** — Rejected. The findings were independently validated by direct grep on source artifacts (icp-scoring SKILL.md text, icypeas_client.py argparse, ADR-008 prose) — orthogonal to reviewer rhetoric. The hit rate is real, not accidental.

2. **Conclude review agents are unreliable in general** — Rejected by counter-example. BC-5832's reviews delivered durable contract-level fixes (Phase 7 reshape would have halted on first Labs invocation; userConfig default would have silently disabled ADR-008's auto-detect). The agents earn their cost on integration work.

3. **Conclude the validation step is redundant** — Rejected. Step 6's value at high-validation-rate workloads is *low* (validators just confirm CONFIRMED), but its value at low-validation-rate workloads is *high* (catches the false positives). Without doing validation, you can't know which regime you're in until after the fixes ship.

### Rule derived

**Review-validation hit rate is workload-dependent — high for first-instance cross-skill contract integrations, low for single-skill spec refinement.** Orchestrator should still always run Step 6 validation (you don't know which regime you're in until you see the validator outputs), but anchor expectations: if the PR adds a contract surface against an already-shipped consumer, expect ≥70% confirmation; if the PR refines a single artifact in isolation, expect ≤30% confirmation.

Calibration value: the orchestrator can budget review-fix effort more accurately. Cross-skill contract PRs should expect 1+ commit of review-fixes; single-skill polish PRs may need 0–1.

### Promotion note

2nd surface — promotes BC-5831 task-1 from 7/10 to 8/10. At 3rd surface (next time the orchestrator can record a hit rate against the workload type) promote to architecture-9 unified rule.

Adjacent precedents: BC-5901 task-4 (Step 6 may be skipped for factually-confirmable findings) covers the orchestrator-shortcut path; this trace covers when the full Step 6 dispatch is worth running.

## Task 3 — 2nd surface for issue-vs-ground-truth amendments table at top of plan doc

**Category:** pattern-application
**Confidence:** 8/10
**Tags:** pattern-application, plan-doc-shape, amendments-table, issue-drift, scope-divergence

### Decision

BC-5832's plan doc opens with a 5-row issue-vs-ground-truth amendments table (Tool Surface, plugin.json userConfig, enum naming, vertical-playbook filename, phase numbering) that codifies the deltas between the Linear issue body and on-disk reality before T1 starts. The pattern was introduced in **BC-5831 task-2** (7/10) as an architecture trace; BC-5832 is the 2nd surface — promotes to 8/10.

The amendments are not optional commentary; they are the *contract* between planner and reviewer. Without the table, scope drift (e.g., this PR dropping 2 unregistered MCPs from `allowed-tools` because the issue body listed them aspirationally) would be invisible until /workflows:review surfaced it as an alleged P1, requiring a re-litigation that should have been settled at brainstorm time.

In BC-5832 the 5 rows broke down as:
1. Tool Surface — issue body had `mcp__plugin_marketing_enrichment__*` (pending BC-5538) and `mcp__plugin_marketing_github__*` (no marketing github MCP) → drop both per CLAUDE.md silent-fail gotcha.
2. plugin.json userConfig — issue didn't mention; ADR-008 demanded → add.
3. Enum naming — issue body had `blitz_prospeo_waterfall`; ADR-008 has `blitz_waterfall` → use ADR.
4. Vertical playbook filename — issue body referenced `{vertical}-icp.md`; on-disk files are `{vertical}.md` → match disk.
5. Phase numbering — issue called Phases 6-7 "NEW for Labs"; reality is Phases 1-5 universal + 6-7 Labs-only → unify numbering.

All 5 deltas surfaced naturally from brainstorm Q&A; the table just records them durably. Reviewers in Step 4 read the amendments first and don't re-flag the resolved deltas.

### Alternatives considered

1. **Document amendments inline in the plan body** — Rejected. Inline notes are skimmed past; a table at the top forces reviewers to acknowledge the deltas before reading task descriptions.

2. **Skip amendments table when delta count is small** — Rejected. Even 1 amendment is enough to confuse a reviewer; the table is cheap to write (5 rows took ~3 minutes) and free to read.

3. **Update the Linear issue description to reflect ground truth** — Rejected per `gotcha_linear_markdown_mangling.md`. The Linear Prosemirror save mangles 11 known list patterns; a re-save risks mid-document content drops. The amendments table in the plan doc is the durable record.

### Rule derived

**Plan docs for issues with known body-vs-reality drift open with a 5-column amendments table: # | Issue body says | Ground truth | Resolution in this PR | (optional citation).** Replaces inline-note style; reviewers read it first; review-time surface re-litigation drops to ~0 for scope-already-resolved deltas.

Specifically applies when:
- Issue body lists MCP servers, tool names, file paths, or version numbers (high drift surface).
- Issue body cites enum values, ADR numbers, or sibling-issue blockers from a prior planning session.
- Issue is older than the most recent ADR that scopes its domain.

### Promotion note

2nd surface — promotes BC-5831 task-2 from 7/10 to 8/10. 3rd surface (any future plan doc using this exact 5-column shape) promotes to architecture-9 durable rule. The pattern is converging fast: BC-5947 introduced reconciliation tables for tool inventory drift, BC-5806 task-3 ratified them as "reconciliation table" pattern (pattern-application 7/10), BC-5831 task-2 specialized to scope-amendments (architecture 7/10), BC-5832 confirms the specialization (this trace, 8/10).

Adjacent: BC-5806 task-3 + BC-5947 reconciliation-table pattern — same shape, different domain (tool inventory vs scope amendments). At 3rd surface for the scope-amendments specialization specifically, the unified rule could fold both back to a single "front-matter table for any issue/reality drift" pattern.
