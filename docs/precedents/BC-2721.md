# BC-2721: Sequential-thinking resolves multi-axis runbook design questions; `discover_tools` at Plan gate prevents tool-name drift

**Date:** 2026-04-21
**Category:** pattern-choice
**Confidence:** 8/10

## Decision

Three durable patterns crystallized during BC-2721 (net-new `campaign-analysis` marketing skill, 383-line SKILL.md + 165-line evals.json + 14 commits → PR #161):

1. **Sequential-thinking-tool-first for multi-axis runbook design questions.** When 2+ independent design questions surface during section authoring (e.g., "where does Gate N resolve?" + "what does Procedure M pass downstream?" + "is this runtime check circular?"), invoke `mcp__sequential-thinking` with a 10-step budget and check for cross-question interactions (do A × B, A × C, B × C compose cleanly?) before committing edits. Saves an iteration cycle versus resolving questions serially with the user.
2. **Thin routing at skill boundaries.** When a skill hands off to a consumer skill (BC-5829 MSPA in this case), pass the full contracted block with labels + priority preserved; do NOT pre-filter at the producer boundary. §4 Cross-skill boundaries is the contract; filtering there silently contradicts §4. Consumer specialists own the filter logic — that's why they exist.
3. **Deterministic skip over runtime conditional when operation is guaranteed redundant.** Procedure 1 step 4 was originally "execute §5 Phase 2 steps 1–7, skip step 1 if same workspace." The "if same workspace" check was circular (you'd call the tool to check). Rewritten to "execute §5 Phase 2 steps 2–7; step 1 is subsumed by Procedure 1 step 1, and the skill guarantees no workspace mutation between them." Same behavior, no runtime conditional, testable statically.

Plus a BC-5797 factual-anchor-recipe extension:

4. **`discover_tools` at Plan gate for any skill citing extended-tier MCP tool names.** Task 10's post-hoc audit caught `list_workspace_stats` (tool does not exist; actual name is `get_workspace_stats`). Had `discover_tools(category="workspace")` been run during Plan (Task 6 § MCP Tool Reference authoring), the wrong name would never have entered the skill body. Extends the factual-anchor recipe from 5 to 6 checks.

## Context

BC-2721 was originally scoped with "generic benchmarks / A/B / funnel / cohort / attribution" — correct but unstructured. Adapted from Revgrowth1/ai-gtm-workflows workflow 11 (MIT) into Brite's 5 Core Variables (Offer / Message / Segment / Infrastructure / Timing) + 4-phase flow (Hypothesis → Data Collection → Analysis → Recommendations) + 6-section report with verdict mapping (TOP PERFORMER / SCALE / TEST MORE / MONITOR / UNDERPERFORM).

Three runbook design questions surfaced during §6 Operational Runbook review (after commit `dfa0af5` wrote the initial runbook):

- **Q1 — Gate 4 timing:** does the "benchmark set confirmation" gate resolve fully in §2 Before Starting alongside Gates 1-3, or does §2 only surface it while the confirmation actually happens inside Procedure 4 (the per-entity benchmark switch)?
- **Q2 — MSPA input scope:** when Procedure 3 hands off to BC-5829 MSPA ITERATE mode, does it pass the full §6 §6 Next Iteration Recommendations block (5 verdict classes, priority-ordered) or pre-filter to just SCALE + TEST MORE rows (the actionable-iteration subset)?
- **Q3 — Double availability call:** Procedure 1 step 1 calls `get_active_workspace_info` for availability + Gate 2 verification. Procedure 1 step 4 (Phase 2 Data Collection) routes to §5 Phase 2 which ALSO starts with `get_active_workspace_info` as step 1. Skip the second call, always run both, or deterministically start Procedure 1 step 4 at §5 Phase 2 step 2?

The sequential-thinking tool ran a 10-step analysis applying operator-UX, contract-consistency, deterministic-execution, and narrow-first-contract principles. Each question produced a clear winner (A / D / G respectively), and the trio composed cleanly (no cross-question conflicts). Total: ~5 min including tool invocation, vs ~20+ min for serial user back-and-forth on three ambiguous design questions. Fix applied in commit `74ec4cb`.

Separately, BC-5797's factual-anchor audit (Task 10) caught the `list_workspace_stats` drift via live `discover_tools(category="workspace")`. Tool is not in the 17-tool Workspace category; actual name is `get_workspace_stats` (extended tier). Same silent-halt failure class as BC-5903's allowed-tools namespace bug (both are "skill cites X, X does not exist, MCP returns not-found, skill silently halts"). Fixed in commit `9896ea2`; sibling skill drift filed as BC-5909 for separate PR.

## Alternatives Considered

**On Q1 (Gate 4 timing):**

1. **A — Resolve fully in §2 (chosen).** All operator setup prompts cluster upfront; Procedure 4 becomes pure mechanical lookup with no runtime operator prompt. Consistent with §2 "Before Starting" label literal + BC-5761 one-question-per-field + symmetry with Gates 1-3.
2. **B — Surface in §2, confirm inside Procedure 4.** Rejected. Defers a confirmation until "right before you need it" but context-switches the operator between setup prompts and analytical prompts. The benchmark confirmation's inputs are fully known at §2 (workspace → table mapping is deterministic), so there's no information-gain argument for deferring.

**On Q2 (MSPA input scope):**

1. **D — Pass full §6 §6 block, preserve verdict labels + priority ordering (chosen).** §4 Cross-skill boundaries already contracts "the §6 §6 block is the input"; filtering at the Procedure 3 boundary would silently contradict §4. §6 §6 is ALREADY curated at generation time (verdict-tagged, priority-ordered, observational/kill markings per §3.4). Thin routing pattern: let MSPA specialize in filter logic.
2. **C — Pre-filter to SCALE + TEST MORE only at Procedure 3 boundary.** Rejected. Narrow-first principle (define minimum contract first) superficially favored this, but §4 was already written and committed with the wider contract; narrowing would drift from §4. The narrow-first principle applies to raw data, not to already-curated output — and §6 §6 is curated.

**On Q3 (Double availability call):**

1. **G — Procedure 1 step 4 starts at §5 Phase 2 step 2, deterministically (chosen).** Principle 3 applies: runtime "skip if same workspace" is circular (you'd call the tool to check). Principle 4: the skill guarantees no mutation between step 1 and step 4, so the second call is deterministically redundant. Easier to test (static assertion) than a runtime check.
2. **E — Always run both (defense in depth).** Rejected. The "defense" is meaningless against the realistic threat model (external processes don't mutate active MCP workspace for the current session in any observed case).
3. **F — "Skip if same workspace" runtime conditional.** Rejected. Self-defeating: the check IS the call. No coherent mechanism.

**On the factual-anchor extension:**

1. **Run `discover_tools` at Plan gate (chosen as forward-looking extension).** Catches wrong tool names BEFORE they enter the skill body. Post-hoc audit (Task 10) worked but cost a late-stage edit; upfront verification costs ~30 seconds and avoids the rework.
2. **Trust integration-doc as authoritative, skip live verification.** Rejected. email-bison.md's §Workspace section (before this PR) did NOT document `list_workspace_stats` or `get_workspace_stats` explicitly — so there was no factual anchor to check. Integration doc is authoritative only when it's been verified; otherwise live `discover_tools` is the ground truth.

## Outcome

Shipped as [PR #161](https://github.com/Brite-Nites/claude-plugins/pull/161) — 14 commits, 5 files changed, 838 insertions / 2 deletions. `validate.sh` 0 errors, `check-guardrails.sh` 0 violations, `evals.json` parses.

**Reusable beyond this case.**

- **Sequential-thinking activation criteria:** 2+ independent design questions + at least one that crosses skill/procedure boundaries + decisions that will compose (e.g., both affect the same runbook). Do not invoke for single-axis questions or pure mechanical choices — overhead > benefit there.
- **Thin-routing pattern for cross-skill handoffs:** when §4 Cross-skill boundaries names "the X block" as input to a consumer skill, pass X as-is. Pre-filtering in the producer creates a silent divergence from the §4 contract. This applies to the full marketing plugin's handoff graph (email-bison ↔ campaign-orchestration ↔ campaign-analysis ↔ campaign-debrief etc.).
- **Deterministic-skip rule:** if operation Y is guaranteed-redundant after operation X (same arguments, no state mutation between them), rewrite as "start from Y+1" statically rather than a runtime "skip Y if condition" check. Applies anywhere a procedure invokes another section's flow with overlapping steps.
- **`discover_tools` at Plan gate for MCP-using skills:** before any Task that writes MCP tool names into a SKILL body (typically Task 6 § MCP Tool Reference in the Outbound-Skill template), run `discover_tools(category=<category>)` on each category the skill will call. Record verified tool names directly into the Plan doc; Task 6 copies from the Plan, not from memory.

Single-audit → multi-issue-filing is a durable productivity pattern when a shipped skill has multiple same-class bugs.

Recorded in the auto-memory; not a precedent-worthy pattern on its own.
