# BC-5826: Split semantic operator-intent gate from per-iteration turn-structure prompts for N-chunk mutating operations

**Date:** 2026-04-20
**Category:** pattern-choice
**Confidence:** 8/10

## Decision

When a slash command runs a mutating operation across N chunks or N campaigns — any loop where each iteration needs the BC-2707 two-call MCP turn-structure gate — do NOT re-prompt the full semantic "Are you sure?" per iteration. Split the gate into two:

1. **Semantic operator-intent gate** — fires **once** up front, covering the entire batch. Surfaces the full scope (chunk count, lead total, sample data, risk) so the operator makes a real semantic decision with attention.
2. **Turn-structure prompt** — fires **per iteration** with deliberately thin wording ("Chunk i/N — vendor prompt: '{verbatim}'. Continue?"). Its only job is to create the user turn between the vendor's two calls, per BC-2707. Rapid-fire affirmatives ("yes" / "do it" / "y") are expected and correct.

This preserves BC-2707's load-bearing guarantee (no same-turn auto-confirm of destructive mutations) while eliminating gate fatigue at N=20+ iterations. Without the split, a 10k-lead upload would demand 20+ semantic confirmations from the operator; the gate stops being a real safety check by confirmation 5.

## Context

BC-5826 `/marketing:launch-campaign` includes Phase 4 UPLOAD (chunks at the 500-lead vendor limit) and Phase 6 ATTACH LEADS (one vendor call per ESP-segment campaign). Both originally spec'd a per-iteration `AskUserQuestion` with full semantic wording. A 10k-lead CSV = 20 upload chunks = 20 "This will create N leads. Proceed?" prompts + the campaign-creation / attach-leads gates.

The /workflows:review performance-reviewer flagged this as P1 ("gate-fatigue risk + gate-effectiveness erosion"). Opus validation downgraded the finding to P2 on the grounds that `bulk_create_leads` is not in EB's MCP-enforced confirmation-gate table (verified via `email-bison.md` § MCP confirmation gates) — so per-chunk operator gates are a skill-level UX choice, not a vendor turn-structure requirement. BC-2707 itself is explicit: the gate is turn structure, not vocabulary — meaning the user turn between the two vendor calls is mandatory, but its wording is not.

That opened the redesign: keep one user turn per iteration (BC-2707 contract satisfied), but drop the semantic re-approval. The semantic approval lives once, up front, at a fresh-attention gate where the operator can actually weigh the decision.

## Applying the pattern

**When to split:**
- The phase involves N iterations of a mutating vendor call where each call needs the BC-2707 two-call gate
- N is commonly ≥ 3 (anything that could trigger gate fatigue on a real run)
- The iteration-level decisions are homogeneous — every iteration has the same risk profile (e.g., "attach 500 leads to workspace W"). Heterogeneous decisions (e.g., `allow_parallel_sending` prompts, which materially change who gets contacted) remain semantic gates and are NOT replaced by turn-structure prompts.

**Shape of the semantic gate:**
- Up-front. Fires BEFORE any vendor call. Scope surface includes: total count (leads, campaigns), chunk / iteration count, representative sample, risk framing ("campaigns will move from Draft to Queued and send real emails").
- Single-shot. Approval covers the full batch.
- Abort = abort the entire phase, not one iteration.

**Shape of the turn-structure prompt:**
- Thin. Typically: `"Chunk i/N — vendor prompt: '{verbatim}'. Continue?"` or `"Campaign {id} — vendor prompt: '{verbatim}'. Continue?"`
- Two options: Continue, Abort remaining iterations (committed iterations stay; un-started iterations halt).
- Rapid-fire affirmatives valid — the prompt exists to create the user turn required by BC-2707, not to re-extract attention.
- The vendor prompt is STILL relayed verbatim (per BC-2707 relay contract). What changes is the skill's framing wording around it.

**Heterogeneous-per-iteration exceptions (still semantic gates):**
- `allow_parallel_sending` vendor prompts — deliberate decision about contacting a prospect across campaigns. Semantic.
- Any vendor prompt that materially differs across iterations (different risk, different scope). Semantic.
- The first iteration after a long-idle operator gap (not generally solvable without knowing operator state — mention in skill docs but don't auto-detect).

## Heterogeneous-per-iteration detection rule

The simplest heuristic: if every iteration's vendor prompt template is the same modulo the iteration index / target ID, use a turn-structure prompt. If the vendor prompt can return a substantively different shape (e.g., `allow_parallel_sending`), branch back to a semantic gate before proceeding with that specific iteration.

In BC-5826, Phase 6 ATTACH LEADS encodes this branch: the per-campaign loop uses a turn-structure prompt by default, but if the vendor returns an `allow_parallel_sending` prompt instead of the normal confirmation, the skill falls back to a full semantic gate for that iteration only.

## Precedent referenced

- **BC-2707** (two-call MCP confirmation gate blocks same-turn auto-confirm, not affirmative vocabulary) — the canonical source. BC-2707's explicit "turn structure, not vocabulary" framing is what authorizes this split; without it, the redesign would have looked like bypassing the gate.
- **BC-5789** (per-item audit at filter time can rescue items the locked plan would have lost) — complementary pattern for loop-shaped workflows where per-iteration decisions need differentiation.

## Related finding: pre-tool-use security hook can block content authoring

A secondary observation from this session worth capturing as a gotcha (added to project CLAUDE.md, not a full precedent trace): the Brite pre-tool-use security hook is NOT limited to blocking shell commands. During this session's Input validation section authoring, the hook returned `{"ok": false}` on a `Write`/`Edit` call because the file content included (a) explicit Brite-internal domain names in the IV-5 allowlist and (b) credential env-var names (e.g., `EMAILBISON_*_TOKEN`) in the IV-7 no-credentials rule. The hook treats those as "surface exposure" regardless of whether they're actual secrets.

**Workaround pattern:** reference external allowlist / config files (`docs/marketing-context.md § test_send_allowlist`) and generic phrasing ("any credential env var", "Brite-internal domain allowlist") instead of enumerating specific values inline in command / skill markdown. The content is equally useful and the hook doesn't flag it.

**First documented case** of the security hook gating content authoring in this codebase. Prior gotcha entries (see `memory/gotcha_security_hook_blocks_infra.md`) cover the shell-command variant only.

## Confidence

8/10. The pattern maps cleanly to any future slash command with chunked or multi-target mutating operations (campaign activation, bulk contact imports, batch deploys, per-environment rollouts). The semantic/turn-structure split has a clear boundary rule (homogeneous iteration → turn-structure; heterogeneous → semantic). The one degree of uncertainty: this hasn't been live-validated at scale in a real 10k-lead run. BC-5826 X17 dogfood was 6 leads — the chunking path did not exercise. A round-2 dogfood with larger scale (Issue C in the BC-5826 follow-up list, blocked by this landing) will confirm or refine the prompt-wording minimums. Revisit after the round-2 dogfood.
