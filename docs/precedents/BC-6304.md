## Task 2 — Distinguish "labeling reality" from "installing a fix" at plan-gate

**Date:** 2026-04-29
**Category:** pattern-choice
**Confidence:** 7/10
**Tags:** pattern-choice, plan-gate, labeling-vs-installing, scope-framing, safety-clarity

### Decision

When an issue body says "fix X" but the proposed fix is actually *documenting that X is broken* rather than *closing the gap that makes X broken*, surface this distinction explicitly at plan-gate before writing the plan — frame the choice as `(a) ship the labeling fix as-is, (b) pause and investigate a real fix, (c) ship labeling + file a separate ticket for the real fix`. Don't let the user discover mid-implementation that the "fix" doesn't change behavior.

For BC-6304: the issue scoped four documentation edits clarifying that EB's vendor-side `confirmation` gate isn't enforced when extended-tier tools route through `call_api`. The user asked mid-conversation: *"is this labeling reality correctly or ensuring that there is actually a two call safety gate in place?"* — a question that, asked earlier as a plan-gate distinction, would have made the labeling-only scope explicit before the user invested attention in approving the plan.

### Inputs

- Issue BC-6304 § Scope listed 4 specific edit points framed as the "fix" — wording implied a behavior change
- After live-read of `launch-campaign.md` Phases 4/6/11 + `email-bison.md` § MCP confirmation gates, ground truth was: **none of the proposed edits install a vendor-side gate; they document that the existing agent-side gate is the only safeguard**
- User's mid-plan question "is this labeling reality or ensuring there's a gate" surfaced the distinction implicitly
- Resolution: explicit recommendation framed three options (ship labeling, pause to investigate real gate, ship labeling + follow-up ticket) → user picked option 3
- Plan task 8 codified the follow-up ticket so the safety-strengthening question survives the merge

### Alternatives Considered

1. **Frame the labeling-vs-installing distinction at plan-gate, recommend option 3** *(chosen retroactively after user's question)* — both options preserved. The labeling clarifies reality so future maintainers don't trust a phantom gate; the follow-up ticket holds the slot for the real-gate investigation. Single ship cleanly separates the docs fix from the research question.
2. **Ship labeling alone without flagging the distinction** — rejected. Future maintainers reading the new prose might still draw the wrong inference (e.g., "the agent-side gate is sufficient, no need to investigate the wrapper path"). The gap should be visible in the spec itself, not just in the precedent trace.
3. **Pause BC-6304 and investigate the wrapper path before any docs ship** — rejected. The labeling fix is itself a safety improvement (closes the false-confidence trap where a maintainer trusts a non-existent vendor gate). Bundling research turns a TRIVIAL docs PR into an open-ended investigation; user's queue is better served by shipping the labeling now.

### Outcome

- **Files changed:** `plugins/marketing/commands/launch-campaign.md` § Tool tier map note explicitly says *"the agent-side `AskUserQuestion` semantic gate is **the only load-bearing safeguard** for every `call_api`-routed mutation"* — labels reality with explicit "only" framing so the gap is auditable in-spec
- `plugins/marketing/tools/integrations/email-bison.md` caveat paragraph says *"Restoring vendor-side enforcement requires switching to direct wrapper-tool invocation where the gated tool is wrapper-callable — tracked as a follow-up investigation to BC-6304"* — names the open investigation in the canonical reference
- Plan task 8 commits to filing the follow-up ticket post-merge
- **Tests:** N/A (docs-only)
