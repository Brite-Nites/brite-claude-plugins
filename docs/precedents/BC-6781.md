## Task 1 — Defer immediate-verify to downstream issue when scope collapses into the same operational step

**Date:** 2026-05-07
**Category:** scope-change
**Confidence:** 7/10
**Tags:** scope-change, scope-collapse, plan-gate, defer-to-downstream, dogfood-chain, verification-collapse

### Decision

When an issue body lists "immediate verification" and "downstream-issue verification" as **separate steps**, but on inspection both steps describe the **same operational action** at the same abstraction layer, defer the immediate verification to the downstream issue. The plan-gate scope check is: if executing the planned verification produces the same artifacts and the same operator workflow as the downstream issue's verification, the two are not separate steps — they are the same step listed in two places.

### Inputs

- BC-6781 issue body listed three required fixes: (1) rewrite test-copy-liquid.json, (2) verify against EB UI Preview Body across 3 leads, (3) round-5 (BC-6785) re-walks S-23 with corrected artifact.
- BC-6785 (round-5 dogfood parent) issue body explicitly lists S-23 re-walk as one of its convergent S-rows after all round-4 fixes (BC-6780 + BC-6781 + BC-6782) land together.
- Initial 7-task plan included the live verification with full EB workspace setup (3 leads + 1 campaign + Preview Body inspection × 3 leads + cleanup).
- User asked at plan-gate: "should we do the testing in the actual 5th round of dogfooding?" — surfacing the scope-collision question.

### Alternatives Considered

1. **Defer verification to BC-6785 round-5 walk** *(chosen)* — Plan slimmed from 7 tasks to 3 (artifact author + transcript update + commit). The closing comment on BC-6781 + the round-4 transcript follow-up table both cite the artifact path and the scope-split rationale, making the deferred-to-downstream decision durably discoverable. Cost: BC-6785 round-5 is the convergent dogfood by design — its job is to verify all round-4 fixes landing together, S-23 belongs in that walk by issue charter.
2. **Verify here in BC-6781 (issue-body literal scope)** — Strict adherence to the issue body's "Required fix" enumeration. Rejected because items 2 and 3 collapse: BC-6785 S-23 IS the same Preview Body inspection across the same 3-lead pattern (truthy + empty + populated). Doing it here would duplicate ~30 min of EB workspace setup + Preview Body × 3 leads + cleanup that round-5 would do anyway. The duplicate-work cost is concrete; the de-risk-now value is thin (canonical Pattern A + B is documented from EB vendor article 184).

### Why durable

This is a new sub-shape in the plan-gate scope-management family that complements the existing scope-expansion precedents (BC-6298 task-1, BC-6544 task-1, BC-6548 task-1, BC-6782 task-1) — those handle "issue-enumerated sites are a strict subset of grep-discoverable sites; expand scope at plan-gate." This one handles the inverse: "issue-enumerated steps are operationally redundant with a downstream-issue's already-charter-scoped steps; contract scope at plan-gate."

The detection trigger is: at plan-write, if a planned task's deliverable matches a downstream issue's deliverable at the same abstraction layer (same artifacts, same operator workflow, same Pass/Fail criterion), surface the scope-collision question to the operator before plan-write finalizes. The user's "should we do this in round 5?" question made the trigger explicit; future invocations should pre-empt by surfacing the collision proactively when planning a task whose deliverable matches a downstream-issue body.
