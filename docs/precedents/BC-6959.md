## task-2 — 6th surface for BC-6965 task-5 (3-iteration /workflows:review convergence)

<a id="BC-6959-task-2"></a>

**Decision:** /workflows:review "loop until clean" needs **4 iterations** for >=1500 LOC PRs — iter 2 and iter 3 fold-ins each commonly self-introduce 1-3 new defects caught by next iter; iter 4 converges.

**Category:** pattern-application

**Confidence:** 9/10

**Inputs:**
- Iter 1: 4 review agents → 0 P1, 3 P2 + 7 P3 (conf ≥7) caught + fixed
- Iter 2 fold-in re-review: 2 P2 + 4 P3 NEW (self-introduced by iter-1 fold-in's prose rewrites)
- Iter 3 fold-in re-review: 2 P2 + 2 P3 NEW (self-introduced by iter-2 fold-in's formula rewrites)
- Iter 4: code-reviewer + perf-reviewer both return `CONVERGED` (0 P1/P2/P3)

**Alternatives Considered:**
1. **4-iteration floor for `loop until clean` on >=1500 LOC PRs** (chosen) — matches BC-6965 task-5 prediction "iter 2 commonly introduces 0-2 new defects caught by iter 3" and extends it: at this LOC scale, iter 3 fold-in also introduces 0-2 caught by iter 4. Reason: this is the 6th surface of the pattern across BC-6957/6958/6962/6963/6965/6959 — well past the 3-surface promotion threshold.
2. Treat the user instruction "loop until clean" as 1-iteration max — rejected; iter 1 alone left 6 P2 unresolved.
3. Treat as bug in reviewer agents — rejected; each iter's findings traced to genuine prose-drift from the prior iter's fold-in commits (e.g., iter-2 introduced "(1 + 6N)" formula that contradicted its own parenthetical).

**Outcome:**

- 4 iterations converged in measurable bounded-resource budget (~5-10 min agent dispatch per iter)

**Precedent Referenced:**

## task-3 — Independent reviewer post-PR-creation catches load-bearing staleness defects

<a id="BC-6959-task-3"></a>

**Decision:** Dispatch one independent reviewer with **completely fresh context** post-PR-creation; it catches stale-branch / version-conflict / parallel-PR-drift issues that the in-flow `/workflows:review` loop is structurally blind to.

**Category:** pattern-choice

**Confidence:** 8/10

**Inputs:**
- /workflows:review (4 iters) ran against `git diff main...HEAD` cached at session start — saw no parallel-PR drift because it didn't re-fetch
- Independent reviewer ran `git fetch origin main` + `git merge-tree main HEAD` + `git diff main..HEAD --stat` from scratch
- Caught: (a) version downgrade 0.2.10 → 0.2.9 (BC-6000 violation); (b) deletion of 4 PRs of merged work; (c) hard merge conflicts on `plugin.json` + `marketplace.json`

**Alternatives Considered:**
1. **Independent fresh-context reviewer mandatory post-PR-creation** (chosen) — the in-flow review loop is correct for diff-content quality but cannot see post-session-start state drift. Reason: this session's user instruction "once the PR has been opened, run one more independent review agent against the PR, and if it comes back clean merge" turned out to be load-bearing — without it, the merge would have downgraded the plugin.
2. Re-run /workflows:review with fresh `git fetch` between iters — rejected; the in-flow loop's strength is fast iteration on the same diff. Re-fetching mid-loop changes the diff under each iter's feet.
3. Trust the in-flow loop and merge — rejected (the BLOCKER finding proves the safety margin matters).

**Outcome:**
- Files changed: 0 from the reviewer-finding itself (the finding triggered a rebase, not a code fix)
- The independent reviewer's HOLD verdict converted into a CLEAR TO MERGE verdict on re-dispatch post-rebase
- Approved by: auto-verified by the same agent on re-dispatch

**Precedent Referenced:** BC-6965 PR-flow precedent ran a similar gate but on a smaller diff (~454 lines); this is the first time the gate caught a parallel-PR-drift blocker.

**Tags:** pattern-choice, independent-review, post-pr-gate, staleness-detection, version-conflict

## task-4 — Lazy child-issue creation post-PR-open satisfies coordination-shell parent AC

<a id="BC-6959-task-4"></a>

**Decision:** For a parent issue that self-describes as a "coordination shell, not a work unit" (per Q3 hybrid granularity), create child issues **after the PR opens but before merge** — children reference the open PR URL in their bodies; their state matches parent's state ("In Review" → "Done" on merge).

**Category:** pattern-application

**Confidence:** 7/10

**Inputs:**
- BC-6959 issue body explicitly says "Children of this parent are **created lazily as work begins on each sub-skill** (Q3 hybrid granularity) — this issue is a coordination shell, not a work unit."
- BC-6959 AC5: `list_issues parentId=<this-issue-id>` returns `9` children
- 9 sub-skills implemented in a single PR (atomic batch), not 9 separate PRs

**Alternatives Considered:**
1. **Create all 9 children at PR-open, mirroring parent's status, flip with parent on merge** (chosen) — satisfies AC5 cleanly; each child documents which Q-lock it implements; status flips atomically with parent. Reason: matches the lazy-creation spec letter while batching the writes into one mutation window.
2. Create children at scoping time before the PR — rejected; Q3 explicitly says "lazily as work begins" which prevents up-front fan-out before content exists.
3. Create children only post-merge — rejected; would leave AC5 unsatisfied at merge time (the AC is read by the parent issue's own gate check).

**Outcome:**
- Files changed: 0 in the diff (all writes are Linear-side)
- 9 children created: BC-7673..BC-7681
- AC5 verified: `list_issues parentId=BC-6959` returned exactly 9 children
- Approved by: auto-verified at parent's merge-flip

**Precedent Referenced:** None — Q3 hybrid granularity is locked in `project_fda_plugin_interview.md` but this is the first time it's been operationalized at this scale (9 children in one batch).

**Tags:** pattern-application, lazy-creation, coordination-shell, parent-issue, batch-children
