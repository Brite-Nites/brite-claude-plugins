# BC-6439 — wrapper-tool invocation path investigation closure

<a id="BC-6439-task-1"></a>

## Task 1 — Update source prose, don't just comment-close, when the prose itself triggered the investigation

**Date:** 2026-04-29
**Category:** pattern-choice
**Confidence:** 8/10
**Tags:** investigation-close-out, source-prose-update, phantom-path-removal, spec-precision, comment-vs-spec

### Decision

When an investigation closes with outcome (b) "the path doesn't exist," and the *source prose* that named that path (e.g., `"tracked as a future follow-up to BC-NNNN"`) was itself the trigger for filing the investigation, close-out **must** include updating the source prose — not just dropping a Linear comment. Comment-only close leaves the phantom path in the spec, which invites a future maintainer (or future-you) to refile the same investigation.

For BC-6439: the BC-6304 prose said *"Restoring vendor-side enforcement would require switching to direct wrapper-tool invocation for the gated tools — tracked as a future follow-up to BC-6304."* That single sentence is what made me file BC-6439 in the first place. Closing BC-6439 with comment-only would mean that same sentence still sits in the spec, ready to trigger another investigation 6 months from now.

### Inputs

- BC-6439 investigation verified outcome (b): no wrapper-callable variant of `resume_campaign`, `import_leads_to_campaign`, or `bulk_create_leads` exists in the `mcp__emailbison-personal__*` namespace; the `confirmation` prose in `discover_tools` descriptions is informational, not a runtime gate
- Two paths offered to user: **Path A** (small spec tightening + close) vs **Path B** (close with comment only, leave BC-6304 prose as-is)
- User's question that surfaced the right framing: *"once we do this are we marking the issue done or what? like does action need to be taken or not?"* — checking whether comment-only would satisfy the AC
- AC inspection showed BC-6439's own acceptance criteria explicitly required *"if decision (b), `email-bison.md § MCP confirmation gates` caveat paragraph updated with the concrete reason in place of the open-ended 'tracked as a follow-up investigation' wording"* — so the AC author (me at filing time) had already foreseen this discipline
- Path A shipped: PR #234 tightened both `launch-campaign.md § Tool tier map` and `email-bison.md § MCP confirmation gates` with the BC-6439 finding inline
- Cost differential: ~5 min of extra work (tighten 1-2 sentences in two files + tiny PR) for permanent removal of the phantom-path trigger

### Alternatives Considered

1. **Path A — small spec tightening + close** *(chosen)* — matches BC-6439's own AC, removes the phantom path so it can't trigger a re-investigation, ~5 min of work. Closes the loop cleanly.
2. **Path B — comment-only close** — leaves BC-6304's "tracked as a future follow-up" wording in place. Saves ~5 min today; risks a 30-min re-investigation in 6 months when someone else reads BC-6304 and files BC-6439 again. Negative ROI on the time saved.
3. **Defer the prose tightening to a separate "polish" pass** — rejected. Polish passes are where small precision-fixes go to die. The right home is the close-out PR of the investigation that produced the finding.
