## Task 1 — A rule-landing is itself a retroactive-debt audit trigger; a later PR's bump clears accumulated pre-rule drift in a single catch-up

**Category:** architecture
**Confidence:** 7/10
**Tags:** architecture, retroactive-audit, rule-landing, version-bump-discipline, cache-invariant-extension, bc-6000-extension

### Decision

When a new rule lands that governs commit-time behavior (BC-6000: any edit under `plugins/<plugin>/{hooks,skills,commands,agents}/**` requires a plugin version bump in the same commit), commits from before the rule-landing date accumulate silent drift — clients keep serving the pre-rule cached version because no bump has fired since the baseline. The canonical remediation is **a single bump in the next rule-eligible PR**, which releases all accumulated pre-rule changes to client caches in one landing. The bump's minor-vs-patch decision should reflect the catch-up magnitude, not just the current PR's scope.

**Specific instance this session.** BC-6000 landed on 2026-04-23 (workflows plugin 3.29.1 → 3.29.2, filed precedent: "cache serves stale until version changes"). On 2026-04-24, BC-5927 edited two files under `plugins/revops/skills/**`. I initially wrote "no plugin version bump" into the plan, consistent with six prior Phase 3 ports (BC-5793, BC-5794, BC-5795, BC-5796, BC-5797, BC-5798) that had all shipped between 2026-04-20 and 2026-04-21 without bumping — because those shipped **before** BC-6000 codified the rule. When the worktree CLAUDE.md Gotchas section surfaced the rule during execute-time file reads, I paused, flagged the gap, and proposed amending the plan. User chose minor bump (`0.1.0 → 0.2.0`) rather than patch, explicitly framed as the 8-way cumulative catch-up (6 prior ports + 2 this PR) released to client caches in one landing.

### Alternatives considered

1. **Patch bump (`0.1.0 → 0.1.1`)** — Conservative semver; treats each skill customization as polish. **Rejected by user.** Minor signals the meaningful catch-up nature; patch understates the 8-way accumulated work.

2. **Skip the bump, file a separate audit issue for plugin version drift** — Defer the fix; leave cache stale longer. **Rejected.** Adds latency to the fix, and a dedicated audit PR is heavier ceremony than bundling the bump into this PR.

3. **Retroactively audit the 6 prior PRs and add a bump-missing addendum comment to each** — Thorough but silly. **Rejected.** The bump only needs to fire once for cache invalidation; re-annotating history buys nothing.

4. **Bump individually per commit (`0.1.0 → 0.1.1` commit 1, `0.1.1 → 0.1.2` commit 2)** — Strict reading of "same commit as any edit" rule. **Rejected.** Within a single PR, clients only observe the merge commit; a single bump at the first skill-edit commit is cache-sufficient.

### Rule derived

**When a rule that governs commit-time behavior lands, the rule itself acts as a retroactive-debt audit signal for the time window between the baseline and the rule-landing date. The next rule-eligible PR after the landing should:**

1. **Re-read the CLAUDE.md gotcha / rule file at execute-time**, not rely on pre-execution knowledge.
2. **Audit prior commits in the window** for rule-eligible changes that skipped the then-unwritten discipline.
3. **If drift is found, include the catch-up action (bump, permset sync, etc.) in the current PR** rather than deferring to a separate cleanup PR.
4. **Size the catch-up action to the cumulative window**, not just the current change (minor bump not patch when N prior changes accumulated).

This is a generalization of BC-6000's architecture precedent: BC-6000 states *"cache serves stale until version changes."* This precedent extends it: *"cache serving stale from pre-rule commits is released by the first post-rule bump in the plugin — time the bump as a catch-up vehicle."*

### Promotion note

First instance of the retroactive-debt extension of BC-6000. File as pattern-application extension. If a second rule-landing surface reveals the same catch-up dynamic (e.g., a future security rule that lands after N vulnerable PRs shipped), promote to architecture-8. If a third surface materializes, consider architecture-9 promotion with an abstract rule-landing-triggers-catch-up pattern.

## Task 2 — Execute-time CLAUDE.md re-read is a discovery surface distinct from pre-execution brainstorming

**Category:** pattern-choice
**Confidence:** 6/10
**Tags:** pattern-choice, execute-time-discovery, claude-md-gotcha, brainstorm-incompleteness, bc-5870-extension, discovery-surface

### Decision

The brainstorming gate is not sufficient for scope completeness on mechanical ports. Specifically, when a skill or rule file (CLAUDE.md Gotchas section) is re-loaded during execution by a tool call (Read, Edit on a file in the worktree), content in that file can surface gaps that pre-execution brainstorm missed. **Treat execute-time file-read events as a first-class discovery surface**, not merely file-loading for editing. Pause execution to flag the gap, propose an amendment, and get user approval before continuing — do not silently fold the amendment into ongoing edits.

**Specific instance this session.** User selected "Brainstorm first" at the complexity gate despite the issue body being detailed. In brainstorm, we resolved the overlap policy (restate with cross-reference). I wrote the plan including an explicit "Out of scope: plugin version bump" section, consistent with six prior Phase 3 ports. Moving to execute, I ran `Read` on the worktree copy of `plugins/revops/skills/sf-testing/SKILL.md` — and the tool result included a `<system-reminder>` block surfacing the full worktree CLAUDE.md, including the BC-6000 Gotcha. That's the moment I caught the scope gap. Not in brainstorm, not in planning — in a file Read during execute. I paused, flagged, and asked the user to amend the plan (see Task 1).

### Alternatives considered

1. **Treat the BC-6000 gotcha as in-scope-from-the-start because every session loads the same CLAUDE.md** — Pre-execution knowledge should have surfaced it. **Rejected.** Pre-execution context loading is Tier 1 CLAUDE.md + MEMORY.md, but the worktree copy of CLAUDE.md reloads at execute-time when a subdirectory file is read — that's a second, distinct load surface with its own discovery potential. Recent rules (BC-6000 landed 2026-04-23, one day before this session) may be visually present in the main-repo CLAUDE.md load but not actively pattern-matched against the current issue's plan until the worktree-repo read fires.

2. **Silently fold the bump into execution without flagging to the user** — Since BC-6000 is explicit and the remediation is mechanical. **Rejected.** This is a scope change: the plan said "no bump," execution would include a bump, and the user never gated the change. Per BC-5870 task-1's gate-respect contract, a plan change mid-execution requires re-gating.

3. **Pause and file a follow-up issue for the bump instead of amending the current plan** — Treat as sibling bug per BC-5870 task-2 "verification-discovered adjacent bugs file as siblings." **Rejected on this instance.** BC-5870 task-2 was about adjacent bugs not in the current PR's scope of responsibility. The BC-6000 rule is *coupled* to the current PR's skill edits — it defines what the PR must include to be cache-valid. A sibling issue would ship an incomplete PR first, then fix it. Better to amend the current plan.

### Rule derived

**Pre-execution brainstorming (Step 5 of session-start) is a necessary but not sufficient gate for scope completeness on mechanical ports. Execute-time file reads are a first-class discovery surface.** When a `<system-reminder>` block or a file content surfaces a rule, gotcha, or constraint during execution that contradicts the plan:

1. **Pause execution immediately** — do not continue editing.
2. **Flag the gap to the user in specific terms**: which rule, which file surfaced it, how the plan conflicts, proposed amendment.
3. **Propose amendment with concrete options** (recommended + alternatives) via `AskUserQuestion`.
4. **Update the plan doc** to reflect the amendment — including crossing out the superseded section so future readers see the correction history.
5. **Continue execution only after user approval** of the amendment.

### Promotion note

Adjacent to BC-5870 task-2 ("seeded verification is a discovery surface"), but on the execute-phase rather than verify-phase. BC-5870 task-2 concerned adjacent-bug discovery during the verify phase; this precedent concerns same-bug scope-completeness discovery during the execute phase. **Both surfaces share the meta-pattern: "the plan is a prediction; execution is where reality files amendments."** If a third distinct phase surfaces the same meta-pattern (e.g., a review-phase discovery changing PR scope), consider promoting the union to a durable skill: *execution-time-discovery.md* in `plugins/workflows/skills/_shared/`.
