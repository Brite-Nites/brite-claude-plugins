## task-1 — Source-of-truth fix extension: plugin-CLAUDE.md drift fix in same PR as command implementation

**Pattern type:** pattern-application (BC-6955 task-3 source-of-truth precedent — 3rd surface; BC-6965 task-1 canon-layer extension — 2nd surface within the joint promotion cluster)

**Confidence:** 9/10

**Context.** /workflows:review iteration 1 surfaced a P1 (conf 9, raised independently by both code-reviewer and cdr-compliance-reviewer): `commands/retro.md` describes `/flow:retro` as **per-domain** (output target = completed domain milestone, Q46 call signature `issue_id: <milestone_id>`), but `plugins/flow-architecture/CLAUDE.md` § Surface map § Reflect L27 and § Boundaries L139 describe it as **sub-flow-scoped**. The Q44 lock + the Q46 call signature pin per-domain; the plugin CLAUDE.md was the drift target. This is documentation drift between an operational artifact (the command spec) and a downstream reference doc (the plugin CLAUDE.md) — neither is the Q-lock canon, but both reference the same Q44 lock.

**Decision.** Update both stale lines in `plugin CLAUDE.md` in the same PR as the `commands/retro.md` implementation. Treat as faithful-echo source-of-truth-sync. Reasoning:
1. The plugin CLAUDE.md is the LLM-context guidance loaded when the plugin is active — drift there propagates to every future dispatcher that reads it before the command file.
2. Leaving the drift would re-surface as a P1 on the next `/flow:retro`-touching PR (BC-6996 plugin CLAUDE.md author pass is in the milestone) and on every parallel `/flow:retro` consumer (BC-6977 cloned `/flow:ship` references retro semantics).
3. BC-6955 task-3 + BC-6965 task-1 establish the source-of-truth-fix precedent for two layers (sibling-artifact + canon); this session extends it to a third layer (downstream-documentation), confirming the precedent is layer-agnostic — wherever the drift surfaces, fix the source-of-truth chain in the same PR.

**Rejected alternatives:**
- File a follow-up Linear issue for the CLAUDE.md drift: would defer for ~1-2 sprints and risk a second-pass reviewer re-finding the same P1 on the BC-6996 PR; cost of fix-in-same-PR is 4 lines, cost of defer is a second review cycle.
- Fix only `commands/retro.md`: the command file is correct as-shipped; the drift is upstream documentation.
- Amend the Q44 lock instead of the CLAUDE.md: Q44 is the authoritative source, not the drifted artifact — Q44 + the call signature were the basis on which both reviewers correctly identified the drift target.

**How to apply.** When `/workflows:review` surfaces a P1 documentation-drift finding that points to a downstream reference doc (plugin CLAUDE.md, plugin README, agent dispatch matrix) describing behavior that contradicts the operational artifact AND the Q-lock canon:
- (a) verify which layer is the source-of-truth (canonical Q-lock > operational artifact > downstream doc);
- (b) fix the drifted layer in the same PR, NOT downstream-only;
- (c) record the fix-target precedent in the compound-learnings trace so future sessions don't re-debate the layer to fix.

**Telemetry watch.** Joint promotion cluster (BC-6963 task-1 + BC-6965 task-1 + BC-6972 task-1) is now at **3 surfaces total** — promotion threshold reached for the broad source-of-truth-fix family. Promote to org-level handbook entry on next compound-learnings consolidation pass. Look for the pattern to recur in BC-6996 (plugin CLAUDE.md), BC-6977 (cloned /flow:ship — may surface mis-cited /flow:retro semantics), and BC-7057 (vertical-slice integration test — may catch drift the per-file reviewers miss).

## task-2 — Review-loop 3-iter convergence on simple-utility markdown spec

**Pattern type:** pattern-application (BC-6965 task-5 review-loop convergence — 2nd surface; different sub-pattern than BC-6965 — see contrast below)

**Confidence:** 8/10

**Context.** User directive on this session: "loop until clean." Three iterations:
- **Iter 1**: 4 review agents — 1 P1 (scope drift) + 3 P2 (cross-date claim self-contradiction, back-to-back disambiguation behavior unclear, L3-summary parallelism under-specified) + 6 P3. After confidence filtering (>= 7) + ultrathink validation, 9 confirmed + 1 dismissed (glob-collision overlooked the slug-regex + hyphen-delimiter constraint — see task-5 below).
- **Iter 2**: 2 P3 above threshold (back-to-back OR-logic UTC-midnight gap, prior-retro glob unbounded). Both applied. NO new defects introduced by iter-1 fold-in (contrast with BC-6965 where iter-2 fold-in self-introduced 1 new P3 caught by iter-3).
- **Iter 3**: 0 actionable findings across all 4 agents.

**Decision.** Document the 3-iter floor as the cap for simple-utility markdown specs (no orchestrator phase logic, no sibling clone surface, no breadcrumb schema). The simple-utility category converges cleaner than orchestrators because the surface area for cross-citation drift, schema mutations, and self-introduced defects is narrower.

**Rejected alternatives:**
- Single-iter would have missed the P1 scope drift entirely (only one cdr-compliance reviewer reads plugin CLAUDE.md alongside the diff target — code-reviewer caught it independently from the command-file side; cross-agent corroboration is needed).
- 5-iter cap (BC-5761 markdown-spec floor): too high for simple utility. The BC-5761 / BC-5762 5-iter pattern is for schema-mutation-prone work (state-object PRs with cross-phase drift), not for a single-purpose utility.
- 2-iter ceiling: iter-2 surfaced 2 legitimate P3s that improved the spec (the OR-logic was correct in spirit but ambiguous in form; the glob was unbounded over time). Stopping at 2 would have left both behind.

**How to apply.** When budgeting `/workflows:review` iterations for a markdown-spec PR:
- **simple-utility** (one file, no schema, no orchestration): 3-iter floor. Iter 1 catches P1 + material P2/P3; iter 2 catches cleanup nits; iter 3 confirms clean.
- **orchestrator / multi-phase clone** (BC-6965 surface): 3-iter floor BUT iter-2 fold-in commonly self-introduces 1-2 new P3 (citation drift, schema drift) caught at iter-3 fresh-context — same iter count, different defect-introduction profile.
- **schema-mutation-prone** (BC-5761/BC-5762 surface): 5-iter cap, may need more.

**Telemetry watch.** Track the iter-2 self-introduce-defect rate across the next 3 utility/orchestrator PRs:
- If utility PRs consistently show 0 self-introduced defects at iter-2 (BC-6972 surface = 0), confirm the simple-utility 3-iter floor is correct.
- If orchestrator PRs consistently show 1-2 (BC-6965 surface = 1 introduced), confirm the orchestrator 3-iter pattern needs the fresh-context iter-3 vs. utility 3-iter pattern that resolves cleanly.

Promotion candidate at 3rd surface from the joint cluster (BC-6965 + BC-6972 = 2/3 toward promotion).

## task-3 — Pre-push divergence: parallel-PR version-bump collision recipe

**Pattern type:** pattern-choice (NEW)

**Confidence:** 8/10

**Context.** BC-6972 worktree was created from origin/main at session start (commit `0fca25a`, plugin version 0.2.8). During the in-flight review loop, BC-6964 (`/flow:add-domain`) shipped in PR #287, bumping the same plugin to 0.2.9 and merging to origin/main. When BC-6972 reached push-ready, both branches had bumped `flow-architecture` plugin.json + marketplace.json to `0.2.9` — git's auto-merge on rebase silently took the matching version (no conflict marker, no diff), leaving BC-6972's logical bump as a no-op vs. the now-current main.

**Decision.** After rebase onto origin/main, **always re-check the plugin version vs. origin/main** before pushing. If the version on origin/main matches the version on the local branch (because a parallel PR bumped first), apply one additional bump (0.2.9 → 0.2.10) and amend the commit. Update the commit message to reflect the actual delta (`0.2.9 → 0.2.10` not `0.2.8 → 0.2.9`).

**Rejected alternatives:**
- Skip the bump and merge as-is: violates BC-6000 cache-propagation rule. The new `commands/retro.md` file would not propagate to clients still caching version 0.2.9 (BC-6964's version).
- Force-rebase BC-6972's bump onto origin/main: rebase auto-merge already handled this; the issue is that BOTH branches converged on the same target version. No mechanism can resolve same-target identical bumps without a manual bump.
- Land BC-6972 first, force BC-6964 to bump second: BC-6964 already shipped — the resolution must be BC-6972-side.

**How to apply.** Add a pre-push verify-version step to `/workflows:ship` Step 1 (Pre-Ship Checks):
1. After `git fetch origin main`, run `git show origin/main:plugins/<plugin>/.claude-plugin/plugin.json | grep version`.
2. Compare to local branch's `plugins/<plugin>/.claude-plugin/plugin.json` version.
3. If they match AND the local branch has any edits under `plugins/<plugin>/{hooks,skills,commands,agents}/**`, bump locally one further and amend.
4. Always include the bump arithmetic in the commit message (not the destination version alone) so reviewers can trace the propagation chain.

**Telemetry watch.** Surface count: 1 (NEW). Will track via plugin-velocity instrumentation — if `flow-architecture` continues at >1 PR/session pace through Brand Hub dogfood, expect 2-3 more collisions before BC-6998 ships. Each collision adds ~5 minutes of rebase-and-bump labor; if collisions exceed 4 occurrences, automate the pre-push version-collision detection in a SessionStart hook (Q30.8 hook-add reconsidered post-BCBC-6998).

## task-4 — Behavior-claim self-audit on locked-signature spec

**Pattern type:** pattern-choice (NEW)

**Confidence:** 7/10

**Context.** /workflows:review iter-1 P2 conf 8: my draft of `commands/retro.md` § Idempotency claimed "cross-date re-runs still update the same comment (the comment body always reflects the latest executive summary)" — but the Q44-locked signature line `'_Generated by /flow:retro for <DOMAIN> milestone on <ISO-8601>_'` includes a date-stamp. Q46 dedups via signature-line match; differing dates → differing signatures → new comments. My claim contradicted the locked signature shape I had quoted four sections earlier in the same file.

**Decision.** When drafting a spec that quotes a locked primitive (Q-lock signature, ADR-locked interface, CDR-locked schema), every behavior claim that references that primitive must be self-audited at draft time: does the claim hold under the locked shape, or does the claim require the primitive to behave differently than locked? If the latter, either amend the primitive (with audit trail) or correct the claim.

**Rejected alternatives:**
- Trust the reviewer to catch contradictions: works (this session did) but burns iter-1 budget on caught-at-draft defects. Cleaner to catch at author time.
- Amend Q44 to make the signature date-less for cross-date dedup: would require a Q44 amendment + audit trail + downstream propagation; the actual user-visible cross-date behavior (new comments accumulate as audit-trail) is more correct than same-comment-updates anyway.

**How to apply.** When a spec drafts § Idempotency, § Failure semantics, § Re-run behavior, or § Cross-call semantics for a feature whose primitives are locked elsewhere:
1. Quote the locked primitive in full (already standard).
2. After every behavior claim, write a one-line "implied by the locked shape: <yes/needs-amendment>" inline audit (drop the audit line before finalizing if claim holds; keep it as a §-level note if the claim required an amendment).
3. Re-grep the same section for any "still / always / never" universal claims and verify each against the primitive's locked shape.

**Telemetry watch.** Surface this pattern in BC-6977 (cloned /flow:ship — references multiple Q-locked primitives), BC-6996 (plugin CLAUDE.md — re-states multiple Q-locked behaviors), BC-7057 (vertical-slice integration test — exercises the locked primitives end-to-end). Promotion threshold: 3 surfaces.

## task-5 — P3-dismissal via ultrathink-validated structural constraint

**Pattern type:** pattern-application (sequential-thinking applied to /workflows:review finding triage — NEW sub-pattern, no direct prior)

**Confidence:** 7/10

**Context.** Iter-1 code-reviewer surfaced P3 conf 7: "L97 trends-vs-prior glob `docs/retros/<domain>-*.md` could collide with underscore-containing slugs (regex admits `EVENTS_BETA`)." The reviewer's claim was that glob `EVENTS-*` could over-match if a sibling slug exists with a shared prefix. Per user's "ultrathink" directive, I sequential-thinked the case: the glob pattern is `<domain>-*` where `-` is a literal delimiter; an alleged sibling slug `EVENTS_BETA` starts with `EVENTS_`, not `EVENTS-` — therefore glob `EVENTS-*` does NOT match `EVENTS_BETA-2026-05-11.md`. The reviewer overlooked the hyphen-as-delimiter constraint. Dismissed the P3.

**Decision.** Before applying every /workflows:review finding (especially P3), sequential-think through the case the reviewer claims and verify it against the structural constraints of the spec (slug regex, path delimiters, type registry). Dismissal is correct when a structural constraint already prevents the alleged case.

**Rejected alternatives:**
- Auto-apply every conf >= 7 finding: would over-correct, adding redundant defensive prose for cases the existing constraints already block.
- Dispatch a validation subagent for every dismissal: cost > benefit for P3 where one ultrathink pass is sufficient.

**How to apply.** When a /workflows:review finding claims a structural problem (collision, traversal, ambiguity):
1. State the alleged failure case in concrete inputs.
2. Trace the inputs through the spec's structural constraints (regex anchors, delimiters, type-registry membership, AC-grep anchors).
3. If a constraint prevents the alleged case, dismiss with a one-line reason recorded in the compound-learnings trace (NOT in the spec — adding "this case can't happen because X" prose adds noise).
4. If the constraint partially prevents the case (e.g., works for slug-regex `[A-Z][A-Z0-9_]*` but not for the iter-2 reviewer's broader concern), tighten the constraint (this session's iter-2 fix added regex-anchoring `^<domain>-\d{4}-\d{2}-\d{2}\.md$` post-glob — addressed both the dismissed iter-1 case AND the conf-7 iter-2 case).

**Telemetry watch.** Surface count: 1 (NEW). Track in subsequent review loops where reviewers raise structural-collision concerns. Promotion threshold: 3 surfaces.
