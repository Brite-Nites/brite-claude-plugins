# BC-5825: Split skeleton from skin when a large content fan-out dominates the task graph

**Date:** 2026-04-20
**Category:** scope-change
**Confidence:** 8/10

## Decision

When a single issue's task graph contains both *skeleton* work (high-design, low-repetition — schema, architectural decisions, one-off infrastructure) and *skin* work (pattern repetition — N similar content files, N test fixtures, N configuration variants), split them into separate issues during the brainstorm phase. Ship the skeleton first with ≥1 seed of each skin type as pattern-proof, then fan out the remaining skin work as blockedBy follow-ups. Rule of thumb: if the skin work alone exceeds the plan's per-issue task budget (~10-12 tasks for this codebase), or if the skeleton unblocks downstream consumers that don't depend on skin coverage, split.

## Context

BC-5825 email-copywriting was originally scoped as one issue with 9 tasks: skill skeleton + lazy-load infrastructure + 46 per-vertical preset files (`{preset}-{vertical}.md` × 2 presets × 23 handbook verticals). During the session brainstorm, the AskUserQuestion flow surfaced the 46-file fan-out as a context-bloat concern. User response: "i would really rather it be per vertical, but is there a way to do that, that won't make the skill too big?"

The recognition was: 46 preset files at ~40-60 lines each is ~2,300 lines of content. Even with lazy-load (one file read per invocation), the *authoring* burden — each file is hand-crafted copy skeleton requiring vertical-specific research — is substantial and repetitive. That workload splits cleanly from the skill-design workload (schema, anti-slop rules, runbook flows, evals).

Two things forced the split decision:

1. **Task budget.** A single 18-20 task plan exceeds the 12-task limit the session-start workflow recommends for a PR.
2. **Downstream unblock.** BC-5826 `/marketing:launch-campaign` consumes the JSON artifact shape from BC-5825 — it does NOT consume the per-vertical presets. Coupling launch-campaign to the full 46-file fan-out would block tonight-critical progress for days of preset drafting.

Resolution: BC-5825 narrowed to skeleton + 2 seed Municipalities presets (proof-of-pattern for both preset types). Per-vertical fan-out split into 3 issues by handbook tier:

- **BC-5879** (Active-tier, High priority) — 10 files (5 verticals × 2 presets)
- **BC-5880** (Exploring-tier, Medium priority) — 16 files (8 verticals × 2)
- **BC-5881** (Future-tier, Low priority) — 18 files (9 verticals × 2)

All three are `blockedBy: BC-5825` and can ship in parallel after merge. BC-5826 can start immediately on BC-5825 merge without waiting for any of the three.

## Heuristic for when to split

Apply the split test at brainstorm time, before plan writing:

- **Task count probe.** If the plan would exceed ~12 tasks, the issue is too big. Split or re-scope.
- **Work-type probe.** If the tasks divide cleanly into "one-time design" + "N repetitions of pattern X," the repetitions are skin work — consider splitting even if task count is within budget.
- **Consumer dependency probe.** If a downstream issue depends on the skeleton but NOT on the skin fan-out, the skin is fan-out-deferrable — split.
- **Seed-validation probe.** Can you ship the skeleton with ≥1 seed of each skin type to prove the pattern works? If yes, the skeleton issue is independently shippable + verifiable.

If 3 or 4 probes say yes, split. If only 1 or 2, keep together and budget the larger scope.

## What the split looks like in practice

- **Primary issue (skeleton):** scope narrowed to infrastructure + pattern-proof seeds. Issue description gets a "Scope narrowed on YYYY-MM-DD" note at the top linking the follow-up issues, and a "Preset fan-out split" section with the tier breakdown. Per-vertical verification items move to the follow-ups.
- **Follow-up issues (skin):** one per tier or one per natural grouping, all `blockedBy: primary`. Each follow-up's issue description cites the primary issue and references the pattern file shape established in the primary. Verification asserts file existence + format-rule compliance + pattern-match to the seeds.
- **Linear relationships:** `blocks` on primary, `blockedBy` on follow-ups. Priority on follow-ups reflects downstream-consumer urgency (Active was High because HOAs is the next-most-shipped Brite vertical; Future was Low because those are hypothesis-stage verticals).

## Precedent referenced

- **BC-5789** (per-item audit at filter time can rescue items the locked plan would have lost) — complementary: that precedent handles post-plan scope changes; BC-5825 handles pre-plan scope splits. Both enable shipping incrementally without committing to the full surface up front.
- **BC-5823** (handbook canon wins over issue-body scope for vertical/ICP/persona decisions) — the 23-vertical canon was the driver of the 46-file fan-out count. Without handbook canon, the split count would have been arbitrary.

## Confidence

8/10. The decision is unambiguous in this case (task budget + downstream unblock both said split), and the shape of the split maps naturally to a recurring pattern (skeleton + N pattern-matched follow-ups). The heuristic will apply well to any future issue that involves: a new skill + per-vertical content, a new data model + per-entity seed data, a new command + per-platform implementations. The one degree of uncertainty: whether the fan-out issues actually ship cleanly is still unproven — BC-5879/5880/5881 are Todo. If a fan-out issue surfaces friction (e.g., per-vertical research turns out to require upstream schema changes that should have lived in the skeleton), the heuristic may need refinement. Revisit after BC-5879 ships.
