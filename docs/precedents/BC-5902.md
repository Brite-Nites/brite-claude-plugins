# BC-5902: Hybrid subagent dispatch for heavy reads feeding interactive per-item loops

**Date:** 2026-04-21
**Category:** architecture
**Confidence:** 8/10

## Decision

When a multi-phase plugin runs an **interactive per-item loop over N items in main thread** — constrained there by `AskUserQuestion` which cannot fire from dispatched subagents — offload every heavy read (Linear fetches, ranking, quality-gate checks) to dispatched subagents that return compact JSON (<2KB per item). Main thread consumes the pre-dispatched outputs as data, never reads raw results directly after the initial batch. Fail-loud on any dispatch error (Retry / Pause / explicit-user-override-to-proceed via `AskUserQuestion`) — never silent degradation, even under extreme context pressure. Cap per-item agent fan-out at 10 concurrent (Linear MCP throughput ceiling per Phase 1 `project-audit` precedent).

## Context

BC-5763 W17 dogfood attempt 2 (2026-04-20) surfaced 4 P1 frictions sharing a common root cause: **Phase 2 context-budget pressure** induced the `sprint-scoping` skill to silently drop spec-required steps as the session progressed across 25 projects. Symptoms:

- BC-5896 — `list_issues` skipped for 3 projects (Brite GTM, Brite Base, Brite Handbook); SQ2 degraded to free-text "inferring from domain."
- BC-5897 — CQ1–CQ5 block ran only for the top carry-over issue on Brite Base (5 carry-overs); other 4 never interviewed.
- BC-5898 — `linear-housekeeping` emitted "All are pre-flight-unchecked (context pressure)" across 19 Phase 3 mutations; quality-gate preflight silently skipped.
- BC-5899 — § 7 cross-project bottleneck summary absent between Phase 2 exit and Phase 3 entry despite Holden carrying 6–7 primary assignments (well over the N=4 threshold).

Additionally BC-5867 had previously flagged the `workflows:brainstorming` inline Skill call in Phase 2 § 4 as a spec-misfit (too heavyweight for per-project ranking), but had been treated as an independent issue until BC-5902 analysis revealed it shared the same root cause: main-thread main-thread heavyweight operations per project across 25 projects.

Three architectural options were evaluated:
- **A** — Hybrid subagent dispatch. Phase 2 dispatches `project-enricher` per project (Sonnet, cap-10 parallel, mirrors Phase 1 `project-audit` fan-out); Phase 3 dispatches `housekeeping-preflight` once over the cycle-path mutation slice.
- **B** — Per-project context compact between projects. Rejected as lossy for § 7 cross-project tally (BC-5899) and carry-over tracking.
- **C** — External resume protocol (write state, prompt user to `/cadence:weekly --resume-project N+1` in fresh session). Rejected — breaks "one command, one session" intent and is terrible UX for weekly cadence.

**Chosen: Option A with full-bundle enricher** — the enricher absorbs backlog `list_issues` + carry-over `get_issue` enrichment + brainstorming ranking in one dispatch, closing BC-5867 as a by-product. Single PR closes 6 issues: BC-5902 parent + BC-5896/5897/5898/5899 children + BC-5867 absorbed.

Key design anchor: the Phase 1 `project-audit` agent (BC-5759) was already a working precedent for per-project fan-out. Option A just extends that pattern to the two subsequent phases.

## Alternatives Considered

1. **Bulk-once enricher** (one dispatch covers all 25 projects, returns a flat manifest `{project_id → enriched_card}`). Rejected. Maximum context compression but loses parallel dispatch (Phase 1 runs cap-10 concurrent, which is the Linear MCP throughput ceiling). Creates a new pattern not used elsewhere in Cadence, while per-project fan-out is a drop-in extension of the existing Phase 1 shape.

2. **Reuse project-enricher for Phase 3** (optional phase-3 mode accepting pre-derived mutation rows). Rejected. Phase 3 input is `mutation_rows[]`, not `{project_id, audit_card}` — the asymmetric interface would couple two unrelated concerns. Second agent (`housekeeping-preflight`) is cheap — a single file matching the same stylistic template.

3. **Post-Phase-2 state compact + inline Phase 3 gate re-run** (main-thread explicit compact between phases; Phase 3 retains inline per-row Skill → `cadence:issue-quality-gate` calls). Rejected. Relies on compact being lossless for Phase 3's per-mutation gate re-run, but attempt-2 evidence shows context pressure already blows at Phase 3 under the current shape with LESS state. One more subagent is cheap insurance.

4. **Ship the fix as four separate PRs** (one per child P1). Rejected. All four share the same root cause; fixing them in isolation would leave the architectural problem in place and the same class of context-pressure bug would resurface in the next phase/plugin (e.g. retrospective plugin, quarterly cadence). One parent architectural fix is the cleanest close path and generates a reusable precedent (this trace).

5. **Ship Haiku-tier agents** (Option A variant). Rejected mid-brainstorm at user's direction. Sonnet-tier matches the main thread's current brainstorming skill model for rank-quality parity; weekly cadence means ~26 Sonnet calls/week, a trivial cost footprint.

**Reusable beyond this case.** Any Cadence-style plugin that orchestrates an **interactive per-item loop over N items with main-thread `AskUserQuestion` constraint** should adopt the hybrid-dispatch pattern:

1. One per-item enricher agent (fan-out, cap-10 parallel) absorbs every heavy read.
2. If a batch phase follows the loop, one batch-once preflight agent absorbs per-row checks over the accumulated work.
3. Main thread keeps only Q&A + cross-item tally work (<10% of phase-total context).
4. Fail-loud everywhere — every dispatch error halts with `AskUserQuestion`, every spec-departure is user-opt-in.

Candidate future consumers: retrospective plugin (per-project retro interview over last cycle), quarterly cadence plugin (per-milestone interview over last quarter), annual OKR planning plugin (per-team OKR interview over last fiscal year). The pattern scales with item count, not with per-item complexity.

**Secondary learning — full-bundle enricher closes adjacent spec-misfits as by-products.** BC-5867 (brainstorming ranker invocation spec-misfit, a separate Phase 2 issue) was absorbed into the `project-enricher` agent's ranking step at no extra implementation cost. When a full-bundle agent naturally subsumes an orthogonal inline call, treat it as the correct close-path for both issues rather than preserving the old interface. Watch for this during brainstorm: "what else in this phase is also heavy and inline?" is the right probe.

**Tertiary learning — `Agent` in `allowed-tools` is required when a skill dispatches subagents.** Both SKILLs (`sprint-scoping` + `linear-housekeeping`) initially omitted `Agent` from `allowed-tools` frontmatter because the sister-skill convention did not declare it. Main-thread post-subagent review caught the omission before PR open. Runtime tooling enforces `allowed-tools` as an allowlist; a skill dispatching via `Agent` without declaring it fails silently at runtime (same class as BC-5810's MCP-tool-not-listed gotcha in agent files). Future skill refactors that add subagent dispatch must also add `Agent` to `allowed-tools`.

**Quaternary learning — subagents flag spec ambiguities instead of silently resolving.** Task 4's subagent flagged two spec issues: (a) grep-AC for `workflows:brainstorming` → 0 conflicted with verbatim edit text containing a documentary negation clause; (b) section-ref `§ 1.4` in the task prompt was actually `§ 1.2 Dispatch` in the command file. Both were flagged in the Completion Report rather than silently "corrected" or silently ignored. Main-thread resolution then applied a single-line fix. This is the intended subagent-per-task behavior: ambiguity surfaces to the orchestrator, not buried in the work product. Write task prompts that explicitly permit flag-and-proceed (Task 4 did: "Skip trivial choices").
