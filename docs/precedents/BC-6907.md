## task-2 — Integration-doc contract drift in deletion-style refactors: the docs describe the *deleted* artifact's I/O, not the replacement's I/O

**Decision:** When a refactor replaces component A with component B (even when B was already wired in), the integration docs may still describe A's input/output shape — and that drift can survive an entire `/workflows:review` triage as "trivial" because the diff is small and the *runtime* contract is correct. In BC-6907, three integration docs (`millionverifier.md`, `segment-routing.md`, `roofing-contractors-tx.md`) carried claims that were literally true of the deleted `tier_and_segment.py` but **structurally false** of `icp-scoring abc`: the script read nested `smtp.keep` + `smtp.catch_all` from JSONL; the skill reads top-level `catch_all` from a flat CSV. The script's output included 9 contact-level columns it hardcoded into `fields = [...]`; the skill writes input-shape + tier (so when fed `verified-flat.csv`'s 6 firmographic cols, it outputs 7, not 9). The worked example shell-invoked the script with `--in verified.jsonl`; the skill needs a `verified-flat.csv` reshape step the example never performed. The runtime is correct — `tam-mapping/SKILL.md` Phase 7 already owns the reshape — but operator-facing docs lied. Lesson: for deletion-style refactors, the review pass MUST include "verify each integration doc still describes the *replacement* contract, not the *deleted* contract" as an explicit check — diff-triage Haiku and the simplify/code/python/security/performance/cdr passes will all rate the diff "trivial" because the *executable* contract is preserved.
