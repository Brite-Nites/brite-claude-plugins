# BC-7051 — Fix async/sync context-manager TypeError in tam-map enrichers

## Issue
[BC-7051](https://linear.app/brite-nites/issue/BC-7051) — `enrich_waterfall.py:99` and `verify_smtp.py:68` both used the upstream shape `async with aiohttp.ClientSession() as session, open(outfile, "w") as f:`. Crashed with `TypeError: '_io.TextIOWrapper' object does not support the asynchronous context manager protocol` on every Python version since async/await. Fix: split into outer sync `with open(...)` + inner `async with ClientSession()`. Closes the BC-6906 inferred-not-tested gap on BlitzAPI, Prospeo, MillionVerifier vendor auth. PR: [#262](https://github.com/Brite-Nites/brite-claude-plugins/pull/262).

<a id="BC-7051-task-1"></a>
## Task 1 — Python `async with X, Y:` requires BOTH items to implement `__aexit__`; mixing a sync `open()` is a TypeError-on-execute bug class

| Field | Value |
|---|---|
| **Decision** | When a verbatim-ported upstream script combines `async with` and `open()` in the same statement, the minimal fix is split-CMs (outer sync `with open(...)`, inner `async with ClientSession()`); `aiofiles` is rejected when the issue spec calls out the "no new dependency" constraint |
| **Category** | bug-resolution |
| **Confidence** | 9/10 |
| **Precedent Referenced** | None (new class for the codebase precedent record) |

**Inputs**
- BC-7051 issue body §Context + §Scope (prescribes split-CM shape, rejects `aiofiles`)
- PEP 492 `async with X, Y:` desugaring rules (both items must be async CMs)
- Live repro on Python 3.13.11 + 3.14.3 (confirms not a Python regression)
- BC-6906 session evidence: this bug crashed 4 of 7 vendor round-trip smokes

**Alternatives Considered**
1. **Chosen** — Outer `with open(...)` + inner `async with ClientSession()`. Minimal diff (~2 lines per file plus re-indent), zero dependency change, identical resource ordering (file outlives session, session writes-while-file-open, file closes after session teardown).
2. Rejected — `aiofiles` migration. True async file I/O, but adds a dependency. Issue spec foreclosed this. Also: file write rate here (5 req/s serialized for BlitzAPI, 160 req/s for MillionVerifier) is dwarfed by network I/O; no measurable benefit.
3. Rejected — Single-line `async with contextlib.AsyncExitStack() as stack:` + `stack.enter_context(open(...))`. Cleaner in theory but diverges further from upstream than the split. Violates verbatim-port discipline.

**Outcome**
- Files changed: 2 (enrich_waterfall.py, verify_smtp.py) — 1 statement split + body re-indent each. Identical shape between both files (consistent application of the fix pattern).
- Tests: live smoke validation on Python 3.13.11 + 3.14.3 — both pass. MillionVerifier returned `result_code: 2` (catch_all) — vendor-specific data, definitive proof of real HTTP round-trip (cannot be silent-exception).
- Cost spent: ~$0.0504 total (Prospeo $0.05 + MillionVerifier $0.0004).
- Approved by: developer at Step 5 cost gate (T4 + T5 confirmation).

**Generalization**: Python's `async with A, B:` desugars to nested `async with`, requiring `__aexit__` on both items. Any verbatim port from a code source that pre-dates strict async semantics (or that was never executed) may carry this bug. Smell-check: any `async with` statement containing a comma needs auditing for sync items (`open()`, `contextlib.suppress`, plain `Lock`, etc.). The fix shape is always outer-sync + inner-async if the file outlives the session; reverse if the file should close before async teardown (rare).

## Task 3 — Vendor-specific return code as definitive vendor-auth proof; wall-time delta as inferential evidence

| Field | Value |
|---|---|
| **Decision** | When a smoke output can be interpreted as either real vendor response OR silent-exception, prefer fixtures that force the vendor to return vendor-specific data (e.g., a known-catch-all domain through MillionVerifier returns `result_code: 2`); when forcing isn't available, wall-time delta vs a control run is acceptable but second-class evidence |
| **Category** | pattern-choice |
| **Confidence** | 8/10 |
| **Precedent Referenced** | BC-6906 task-3 (single-adopter canon at plugin path with N=2 promotion) — adjacent methodology precedent |

**Inputs**
- BC-7051 acceptance criteria §3: "verify_smtp.py runs to completion on a 1-record input, exits 0, writes a valid JSONL line with a MillionVerifier `result_code` — vendor auth confirmed via real HTTP traffic"
- BlitzAPI smoke output (T3/T6): `enrichment_error: no email found` — ambiguous between HTTP 200 + no-email and silent exception in `enrich_waterfall.py`'s try/except
- Prospeo smoke output (T4): `enrichment_error: no email found` — same ambiguity, but wall-time 1.0s vs BlitzAPI-only 0.6s = ~0.4s delta consistent with a second HTTP round-trip
- MillionVerifier smoke output (T5): `result_code: 2` (catch_all) — vendor-specific code, cannot be produced by a silent exception path (the code lives in the vendor's response, the silent-exception path returns `result: "error"`)

**Alternatives Considered**
1. **Chosen** — Treat MillionVerifier's `result_code: 2` as definitive proof, treat BlitzAPI/Prospeo's `enrichment_error: no email found` + wall-time delta as inferential proof. Captured both classes in the PR description so future reviewers see the evidence tier.
2. Rejected — Insist on definitive proof for all 3 vendors. Would require either logging instrumentation in `enrich_waterfall.py` (violates verbatim-port discipline) or forcing a domain known to return an email (cost + brittleness — domain ownership of emails can change).
3. Rejected — Treat all 3 smokes as equivalent. Loses the evidence-tier distinction; future maintainer assumes BlitzAPI/Prospeo HTTP auth is as strongly evidenced as MillionVerifier's. Misleading.

**Outcome**
- Files changed (this PR): UPSTREAM.md "Local deviations" section calls out the MillionVerifier `result_code: 2` evidence specifically
- Tests: T3-T6 smoke matrix in PR description with explicit "Wall time / Exit / Vendor evidence" columns distinguishing the evidence classes
- Cost spent: $0.0504 total — strong-evidence MillionVerifier cost $0.0004 (cheapest); weaker-evidence Prospeo cost $0.05

**Generalization**: Smoke-test fixtures should be designed to force vendor-specific outputs when feasible. The evidence-tier hierarchy is: (1) vendor-specific data in output (definitive — cannot be silent-exception), (2) wall-time delta vs control (inferential — requires symmetric setup), (3) exit-code-only (weakest — same as no-execution-at-all if a silent except path exists). When choosing which vendor to spend cost on, prefer the lowest-cost vendor that gives Tier 1 evidence — here MillionVerifier at $0.0004 was the right spend over Prospeo at $0.05 if budget was tight. (Both were run here because issue spec required all 3.)
