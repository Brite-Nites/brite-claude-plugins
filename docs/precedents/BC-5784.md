## Task 1 — Issue-author `grep` verify matrices must anchor on plain-text phrase occurrence, not rendered phrase

**Category:** pattern-choice
**Confidence:** 6/10
**Tags:** pattern-choice, verify-matrix, grep-testing, inline-styling, issue-authoring
**Precedent Referenced:** None — novel pattern this session. Adjacent to BC-5761 / BC-5762 (verify-matrix iteration budgets) and BC-5797 (factual-anchor recipe gained verify-matrix-regex checks). No direct predecessor for the styling-vs-grep coupling.

### Decision

When an issue's objective-verify matrix specifies `grep -i "<phrase>"` against a prose target, the author and the executor share responsibility for ensuring the target document renders `<phrase>` as plain text — at least once — with no inline formatting breaking word-token adjacency. Inline code styling (backticks) emits a literal backtick between the styled token and the adjacent word in the source, so `grep -i "directory parameter"` returns **0 matches** against a bullet titled `` `directory` parameter trap`` even though the bullet semantically opens with that phrase. Concrete session evidence: BC-5784 T4 (`grep -ci "directory parameter"` against `salesforce.md`) returned `0` on first execute; returned `1` after retitle `` `directory` parameter trap`` → `Directory parameter trap` (backtick removed from the word-adjacent position; `` `directory` `` still appears later in the bullet body for semantic identification).

### Alternatives considered

1. **Amend the verify matrix to use a formatting-agnostic regex.** Swap `grep -i "directory parameter"` for `grep -iE "directory[\`<space>]*parameter"` — allow backtick-or-space between the two words. **Rejected** for this session because the fix would land on the author side (rewriting all future issues with grep matrices) and ripple through every existing issue with similar tests. Author-side is correct long-term but out of scope for a single-PR fix.

2. **Add a redundant plain-text occurrence of the phrase as a separate sentence.** E.g., keep `` `directory` parameter trap`` as the title and append "The directory parameter is required for every data/metadata tool." elsewhere in the bullet. **Rejected** this session as unnecessary duplication; the retitle is cleaner. But this is the correct mitigation when the styled form is semantically load-bearing (e.g., the identifier's backticks signal "this is a literal field name" and cannot be dropped).

3. **Treat the 0-match result as spec-follows-implementation: strip the grep test.** **Rejected.** The grep matrix is the contract the issue author wrote; executor should match the contract, not rewrite it. Stripping tests to clear verification is the same class of failure as self-downgrade (BC-5866 family).

### Rule derived

**Grep-phrase tests couple styling to verification.** When an issue spec includes `grep -i "<N-word phrase>"` against a prose target:

- **Executor responsibility:** before or after writing the target prose, run the grep locally. If the result is 0 matches, fix the prose — usually by ensuring the phrase appears unstyled once, at the bullet/paragraph title or an early sentence.
- **Author responsibility:** when writing the verify matrix, either (a) ensure the prose contract includes a specific unstyled occurrence, or (b) widen the regex to cross styling boundaries. Prefer (a) for readability; (b) is a footgun when the prose later shifts styling.
- **Review responsibility:** the test table pasted into the PR body must show the actual grep output, not a rewritten "✓". A 0-match line should trigger either a prose fix or an explicit matrix amendment in the PR.

### Out-of-scope signal

**Bonus doc paragraphs in `--scope prescriptive` issues need an explicit flag.** BC-5784's Plan section named exactly one subsection to add (`--tools` cherry-pick). This session added a second paragraph (`--no-telemetry` rationale) alongside, consistent with the §Registration paragraph pattern ("Toolsets", "`--allow-non-ga-tools`") already in the file. Added to PR body as a named deviation with "flag for revert if undesired" — reviewer can strip cleanly if policy is strict-scope-only. Not a durable rule, but worth naming so future sessions don't silently widen prescriptive issues without surfacing the choice. If repeated and accepted, the pattern crosses into durable territory (confidence currently ~5/10 — too bidirectional to file).
