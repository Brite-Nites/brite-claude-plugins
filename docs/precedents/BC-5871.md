## Task 1 — Linear MCP cursor pagination: single canonical stop signal, no defensive OR disjunct

**Category:** bug-resolution
**Confidence:** 7/10
**Tags:** bug-resolution, pagination-contract, linear-mcp, relay-cursor, simplify-introduced-bug
**Precedent Referenced:** none (new pattern)

### Decision

When specifying cursor-based pagination against Linear MCP (or any Relay-style API), the **sole authoritative termination signal** is `pageInfo.hasNextPage == false`. Do not add a defensive `OR nodeCount < limit` disjunct — a non-final page is allowed to return fewer than `limit` nodes while `hasNextPage` is still `true`, so the disjunct silently truncates the accumulator. The canonical pattern in `plugins/cadence/skills/linear-housekeeping/SKILL.md` already uses single-signal stop; spec consistency across the plugin matters.

### Surface in this session

During the simplify pass of BC-5871, the **efficiency agent** (conf 8) suggested tightening the fetch's pagination contract: *"loop while `pageInfo.hasNextPage == true`... stop when `hasNextPage == false` or the response's node count is less than `limit`."* I applied the suggestion verbatim.

The `/workflows:review` pass caught it as a **CONFIRMED P2**. Both code-reviewer and performance-reviewer independently flagged the disjunct as a silent-truncation vector; the Sonnet validator confirmed by cross-referencing the canonical linear-housekeeping pattern.

### Pattern

**Simplify-pass suggestions are not immune from correctness bugs.** The efficiency agent's instinct (specify stop-conditions concretely) was right; the specific wording was wrong in a subtle way. When applying any simplify-agent recommendation against a shared-plugin API surface, **validate against the canonical pattern in a sibling skill/command** before committing — a conservative cross-reference would have caught the disjunct.

### Applies when

- Writing any new `list_issues` / `list_projects` / `list_cycles` pagination loop in a Cadence command/skill
- Any Linear MCP recipe that paginates
- By extension: any Relay-style cursor API recipe in this plugin bundle

### Follow-ups

None — the fix landed in the same PR (`§ 1.4` pagination paragraph rewritten to use `hasNextPage == false` as sole signal). CLAUDE.md does not need a new gotcha for this — the existing BC-5871 gotcha already cites the canonical pattern. If a third Relay-style recipe ships the same disjunct in a future simplify pass, promote to architecture-8 and add a CLAUDE.md invariant.

## Task 2 — Seeded verification as a discovery surface (2nd instance): laterally extends BC-5870 task-2 to schema-departure scope widening

**Category:** scope-change
**Confidence:** 7/10 (up from BC-5870 task-2's 6/10 at first instance)
**Tags:** scope-change, verification-as-discovery, sibling-issue-widening, bc-5870-extension, second-instance, atomic-pr-discipline
**Precedent Referenced:** BC-5870 task-2 (verification-as-discovery-surface; adjacent bugs file as siblings with verification-origin framing, not absorbed into current PR)

### Decision

When seeded verification of PR-N's implementation reveals that an **existing sibling follow-up** (PR-M, filed during a prior session) has a **wider blast radius** than its issue body originally scoped, do NOT absorb the scope-expansion into PR-N. Update the existing sibling issue body (via Linear comment documenting the new evidence), keep PR-N atomic, and let PR-M's own execution handle the expanded AC.

### Surface in this session

BC-5871 spec-implements `unattributed_issues = linear_raw_completed_ids − union(audit_cards[].shipped.issues[].id)`. To verify end-to-end, I loaded real W17 `audit.json` and computed. Every card's `shipped.issues[]` was **empty** — same class of schema departure BC-6052 was filed against (which originally scoped only to `quality_gate_flags[]`).

Tallying all per-issue list fields across 25 W17 cards:
- `shipped.issues[]`: 0/25 populated (185 shipped total)
- `dropped.issues[]`: 0/25 populated (24 dropped)
- `carry_over.issues[]`: 1/25 populated (5 carry-over)
- `quality_gate_flags[]`: 0/25 populated (10 `_count > 0`)

BC-6052's scope widened from one field to four. Per the BC-5870 task-2 precedent (atomic-PR discipline), the right action was to **file a comment on BC-6052 updating its AC** rather than absorbing the schema-fix into BC-5871.

### Pattern

**Seeded verification is a discovery surface applied to existing follow-ups, not just new issues.** When BC-5870 task-2 was written, the framing was "adjacent bugs file as siblings." This session extends the framing: existing siblings whose scope turns out to be wider also get scope-updated-via-comment, without absorbing into the current PR.

### Applies when

- Seeded verification of a PR's output lands against real production data (rather than synthetic cases)
- The real data reveals that an existing sibling follow-up's AC is too narrow
- The scope-widening evidence is material (25/25 cards, not 1/25) — enough to warrant updating AC rather than being a one-off anomaly
- The current PR can ship on synthetic + partial-real verification without the sibling fix

### Follow-ups

- BC-5870 task-2 confidence can hold at 6/10 for now; this is a 2nd instance at 7/10. If a 3rd instance surfaces (e.g., a future PR's seeded verification widens another sibling's scope), promote BC-5870 task-2 to architecture 8/10 with a combined-precedent `skills/_shared/` rule.
- BC-6052's scope-update comment filed; AC #1 should widen from `quality_gate_flags` alone to all four list fields at its next touch.

## Task 3 — Item-number ordinals in prose specs are brittle; reference by slug/section-name

**Category:** pattern-choice
**Confidence:** 6/10
**Tags:** pattern-choice, spec-prose, ordinal-reference, slug-reference, renumber-brittleness
**Precedent Referenced:** none (new pattern, observed across BC-5870 → BC-5871 edit chain)

### Decision

In prose specs — especially CLAUDE.md gotchas and inter-section cross-references — refer to numbered-list items **by slug** (e.g., `§ 1.6 Quality flags subsection`, `§ 1.6 Cycle reconciliation line`), **not by ordinal** (`§ 1.6 item 5` / `item 6`). Ordinals shift every time the list inserts or reorders; slugs are stable against structural churn.

### Surface in this session

BC-5870 shipped a gotcha referencing `§ 1.6 item 5`. This PR inserted a new item 4 (Cycle reconciliation), pushing Quality flags from item 5 → item 6. The BC-5870 gotcha had to be updated as part of this PR's diff. I initially added a "bumped from 5 → 6" trailer to document the renumber; the review caught the trailer itself as noise and flagged the ordinal-reference pattern.

Fix applied: `§ 1.6 item 6` → `§ 1.6 Quality flags subsection`; `§ 1.6 item 4 renders` → `§ 1.6 Cycle reconciliation line renders`. Dropped the "bumped 5→6" trailer.

### Pattern

**Ordinal references couple prose specs to list positions.** Each insertion/reorder in a numbered section forces every downstream reference to update in the same PR (or drift silently). Slug references survive structural churn.

### Applies when

- Writing a CLAUDE.md gotcha that references a specific bullet/item in a `commands/*.md` spec
- Cross-referencing inside the same spec file between sections/items
- Documenting a known behavior in prose that depends on a specific numbered position

### Follow-ups

If a 3rd instance of renumber-induced gotcha-edit surfaces (e.g., a future § 1.6 item 5 insertion forces another round of CLAUDE.md edits), promote to architecture 7/10 and add an invariant to `plugins/cadence/CLAUDE.md § Gotchas`: "**Prefer slug references over ordinal references in cross-section prose.**" For now, one instance (this session) is below promotion threshold — file and watch.
