## BC-6000 — 2026-04-23 — Any change under `plugins/<plugin>/hooks/**`, `skills/**`, `commands/**`, or `agents/**` must increment `plugin.json` version + matching `marketplace.json` entry in the SAME commit — deferring the version bump silently stalls the fix in every client's cache

**Category:** architecture
**Confidence:** 8/10

**Inputs:**
- `MEMORY.md` § Conventions (pre-existing): *"Plugin cache keyed by version — bump both plugin.json and marketplace.json for propagation."*
- PR #127 + PR #128 (2026-04-22): added the `git push` carve-out to `plugins/workflows/hooks/hooks.json` but neither bump bumped `plugin.json` or `marketplace.json`. Last workflows version bump was commit `305d340` / PR #119 — three PRs before the hook fixes.
- BC-6000 ship-time telemetry (this trace): the `/workflows:ship` push step in this very session hit the cached `3.29.1` hook even though the working-tree `hooks.json` has the correct carve-out. Haiku evaluator additionally hallucinated a "modifies remote state" rationale not present in either the cached or working-tree prompt, confirming a secondary LLM-layer failure independent of the cache.
- Observed blast radius: 4+ consecutive `/workflows:ship` sessions (BC-5937, BC-5936, BC-5933, BC-5935, ...) hit the stale-cache block before anyone diagnosed it as a version-propagation failure rather than a hook regression.

**Alternatives Considered:**
1. **CHOSEN.** Codify: any edit to files under `plugins/<plugin>/{hooks,skills,commands,agents}/**` MUST be accompanied by a `plugins/<plugin>/.claude-plugin/plugin.json` version bump AND the matching `.claude-plugin/marketplace.json` entry bump, in the same commit. Enforce this as a pre-commit or CI guard if it recurs (candidate: `scripts/_lib/lint_plugin_version.py` that diffs `HEAD..HEAD~1` under the plugin path and fails if version strings are unchanged). Reason: the plugin-cache keying is immutable Claude Code infra; clients will ALWAYS serve the prior cached version until the version changes. Deferring the bump to "later" is not deferrable — it is equivalent to not shipping. Four sessions of silent ship-friction is the cost of treating the convention as advisory rather than mandatory.
2. Bump version on a separate "release" commit after a batch of content changes. Rejected — the window between content-change commits and release-bump commits is exactly the broken-cache window. If the release commit is delayed, content changes silently fail at every client. PR #128 → PR #195 spanned ~24 hours of sessions where the hook fix was in the working tree but not in any client's cache.
3. Accept the friction: let sessions workaround via `!`-prefix push. Rejected — workaround cost is per-session and the agent-automation contract that `/workflows:ship` handles the push end-to-end is load-bearing for session flow.
4. Rely on the MEMORY.md convention alone (pre-existing). Rejected — BC-6000 proves the convention is insufficient. It was documented but not operationalized; the fix-author saw the hook bug, fixed the prompt, and shipped without the bump because "version bumps are a release concern, not a content-change concern." Convention needs to surface at the point of decision, which means either a CLAUDE.md gotcha bullet (this session's immediate fix) or a CI guard (follow-up).

**Outcome:**
- Files changed: `plugins/workflows/.claude-plugin/plugin.json` (version `3.29.1` → `3.29.2`), `.claude-plugin/marketplace.json` (workflows entry same bump), `scripts/test-hooks.sh` (+2 regex regression cases for `git push -u origin <branch>` and `git push origin --delete`).
- Tests: 2 added (`scripts/test-hooks.sh` 37 → 39), 39 passed, 0 failed. `./scripts/validate.sh` 0 errors / 16 warnings baseline preserved. `./scripts/check-guardrails.sh` 0 violations.
- Approved by: self-verified + diff-triage TRIVIAL verdict (12th consecutive). Ship-time push hit the very bug this PR fixes — needed `!`-prefix workaround to push the fix itself. CLAUDE.md `## Gotchas` section updated with an explicit bullet so future plugin-content authors see the rule at point of edit.

**Precedent Referenced:** `MEMORY.md` § Conventions (pre-existing) — "Plugin cache keyed by version — bump both plugin.json and marketplace.json for propagation." This trace operationalizes the convention: elevates it from a passive note to an architecture-level rule binding every edit under `plugins/<plugin>/{hooks,skills,commands,agents}/**`. Future rule refinements should consider adding a CI guard that fails any PR touching those paths without a version bump in the same diff.

## BC-6000 — 2026-04-23 — LLM-layer hook evaluator (Haiku) can hallucinate block rationale outside its prompt — prompt-layer carve-outs are necessary but not sufficient

**Category:** bug-resolution
**Confidence:** 6/10

**Inputs:**
- Working-tree `plugins/workflows/hooks/hooks.json` § PreToolUse prompt (post-PR #128) explicitly carves out: *"plain `git push`, including `git push -u origin <branch>` to a new branch and `git push origin --delete <branch>`, is NOT destructive."*
- BC-6000 ship-time observation (this session): the cached `3.29.1` prompt BLOCKED with a rationale — *"The command contains 'git push', which is a potentially destructive network operation that modifies remote repository state."* — that is NOT in the cached prompt either. The cached prompt's list is: *"Destructive commands: rm -rf, git push --force, DROP TABLE, kill -9, chmod 777, mkfs, dd, format"* — no "modifies remote state" phrasing anywhere. The Haiku evaluator generated the rationale from training-data priors about the destructiveness of `git push`, not from the prompt it was handed.

**Alternatives Considered:**
1. **CHOSEN (deferred).** File as a follow-up child issue after the BC-6000 version bump ships and clients pick up `3.29.2`. The primary BC-6000 fix (version bump) is independent of this — even if the evaluator still hallucinates on the updated prompt, the primary cache-staleness pipeline is unblocked. Treat the hallucination as a separate, post-verification investigation. Reason: scope containment — BC-6000's load-bearing fix is the cache bust; coupling the evaluator-layer fix here would delay the unblock. Deferred fix options include: (a) tighten the carve-out wording to be unignorably explicit (currently one clause in a multi-clause bullet; would make it its own bullet), (b) add a deterministic regex pre-check BEFORE the LLM layer that returns `{"ok": true}` for known-safe `git push` variants, bypassing the LLM entirely, or (c) switch the LLM layer from Haiku to Opus or Sonnet for the handful of high-friction commands where hallucination-class errors have been observed.
2. Fix the evaluator layer in BC-6000 inline. Rejected — would require empirical testing of the updated prompt against the live evaluator, which is not deterministic in bash CI. Would bloat BC-6000's scope beyond the 4-line surgical fix, delaying ship. The issue body itself proposes the deferred-child-issue disposition.
3. Switch from LLM evaluator to pure-regex evaluator for the Bash PreToolUse hook. Rejected (for now) — the LLM layer catches nuanced patterns (credential leakage, piped downloads, contextual secret usage) that a pure-regex layer cannot. Losing the LLM layer would regress on categories that have no false-positive history. The bug is: LLM layer needs a deterministic escape-hatch for high-confidence-safe commands, not that the LLM layer should be removed.

**Outcome:**
- Files changed (this session, BC-6000 scope): none — trace only.
- Tests: observational confirmation, no code path.
- Approved by: session-level observation, deferred to follow-up child issue per BC-6000 issue-body proposed-fix section.

**Resolution (2026-04-23 fresh-session verification):** Post-merge fresh-session test (clean Claude Code boot, stale `3.29.1` cache purged, `3.29.2` active) confirms the Haiku evaluator does NOT hallucinate on the updated prompt. Both `git push -u origin HEAD` (new branch) and `git push origin --delete <branch>` passed through the PreToolUse hook with zero intervention — no security prompt triggered for either command. Prompt-layer tightening (the PR #128 carve-out with explicit enumeration of `git push -u origin <branch>` and `git push origin --delete <branch>`) was **sufficient in isolation** to eliminate the hallucination class observed in the stale cache. **No follow-up child issue filed — the deferred concern did not materialize.** The three prospective fixes (tighter wording / deterministic regex pre-check / evaluator-model upgrade) remain available as defense-in-depth should the hallucination recur; they are now unscoped contingencies rather than planned work. Ship-time confusion in the BC-6000 session itself — where a resumed `claude --resume` session served the cached `3.29.1` prompt even after the marketplace clone was updated — is a separate Claude-Code-layer caveat worth documenting: a fully fresh session launch (not `--resume`) is required to re-bind hooks to a newer plugin version. Added to the BC-6000 Linear verification comment.

**Precedent Referenced:** none direct. Adjacent: `memory/gotcha_security_hook_blocks_infra.md` (same hook layer, different command class — infra commands like Bitwarden CLI also produce evaluator false-positives; workaround is also `!`-prefix or `computer-use write_clipboard`). The shared insight across both: the Haiku evaluator is a best-effort safety layer, not a correctness layer; any command that the evaluator consistently misfires on should route to a deterministic pre-check OR a workaround published in memory for authors to invoke at will. **Post-verification refinement**: tightening the prompt-layer carve-out with explicit command-variant enumeration is a viable first-line remedy that should be attempted before reaching for deterministic pre-checks or evaluator upgrades; BC-6000 proves prompt discipline can be load-bearing.
