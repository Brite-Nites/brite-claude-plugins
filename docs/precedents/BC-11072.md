## Task 1 — Live-verify proposed RECOVERY prescriptions, not just behavior claims

**Date:** 2026-05-22
**Category:** pattern-choice
**Confidence:** 7/10
**Tags:** verification, recovery-prescription, live-spike, plan-gate, eb-api

### Decision

When correcting a wrong API-behavior claim in docs, **live-verify both the new behavior claim AND any proposed recovery path before writing it into the docs.** The recovery prescription is itself a behavior claim — about what API capability is available to work around the failure — and inherits the same verification requirement as the original wrong claim it's replacing.

Concretely, at plan-write time: if the proposed AFTER-text contains a "to recover, do X" line, X must be verifiable against the actual API surface, not the docs' description of the API surface. The MCP schema or `search_api_spec` output is the source of truth; downstream docs (`email-bison.md`'s usage examples) may have inherited the same wrong assumption that the corrected claim was originally based on.

### Inputs

- BC-11072 originally proposed an AFTER-text that included a recovery prescription: *"To merge against existing leads, fetch existing IDs first (`list_leads` filtered by `email`) and only chunk genuinely new emails."*
- Operator asked at plan-gate: "Are we sure? Did we cover all bases?"
- That question triggered a structured gap-analysis (high-confidence claims vs. interpolated claims vs. unverified claims).
- Gap-analysis revealed the recovery path was unverified — I had assumed `list_leads` supported an `email=` filter without checking.
- Live spike (MCP schema dump + API-spec dump via `search_api_spec`) revealed `list_leads` has **no** `email` / `ids[]` / exact-match filter. Only `search` (general substring) and structural filters (tag, status, dates).
- Spike also discovered EB's `search` degrades to "no filter, return all leads" when the search term contains `@` and matches nothing — independently confirming the recovery path was unworkable even with `search`.
- Plan-write proceeded with the recovery prescription **removed**: docs now state the behavior (atomic-422), state what doesn't exist (no upsert variant), and leave recovery to the caller.

### Alternatives Considered

1. **Live-verify both behavior + recovery before plan-write** *(chosen)* — Cost: ~5 minutes of spike work (anchor lead create + mixed-batch POST + cleanup + schema/spec dumps). Benefit: caught a wrong recovery prescription before it landed in 12 production doc sites. The recovery path was about to be silently wrong in the same family as the wrong claim we were correcting.
2. **Verify only the behavior claim, trust the recovery sketch** — Faster. Would have shipped 12 sites of "filter `list_leads` on email first" as a workaround, then shipped a *different-but-still-wrong* claim. Future agents reading the corrected docs would either fail looking for the missing `email` param or fall into the `@`-degradation no-filter trap. Rejected because the spike cost was small and the failure mode was concrete (replace one wrong claim with another).
3. **Skip recovery prescription entirely without verifying** — Operationally similar to the chosen path (no recovery in the final docs), but doesn't surface the gap as a class for future PRs. Rejected because surfacing the verification gap is the durable lesson.

### Why durable

This extends [BC-6515 task-1](BC-6515.md#BC-6515-task-1) ("live-verify before enshrining doc claims") with a genuinely new sub-shape:

- **BC-6515 task-1 covered:** narrative claims (the transcript said X happened; do we believe the transcript?) — verify behavior before doc-writing.
- **BC-11072 task-1 covers:** proposed recovery paths — verify the recovery mechanism exists before doc-writing.

The discriminator: BC-6515 was about historical claims; BC-11072 is about prescriptive forward claims. Both are claims the docs make about the API surface, and both need direct verification before they get enshrined.

The recovery-prescription class is particularly prone to the "replace one wrong claim with another" anti-pattern when fixing a documented behavior, because the operator's natural instinct is to provide a workaround alongside the corrected behavior. That instinct is good, but the workaround inherits the same verification cost as the corrected claim it's paired with.

**Trigger heuristic:** at plan-write time, if the AFTER-text contains "to recover, do X" or "the workaround is Y" or similar prescriptive forward-looking advice about API capability, treat X / Y as a separate verification line-item. Hit the actual MCP schema or `search_api_spec` for the referenced tool/endpoint. Do NOT trust the docs' description of capabilities you're about to inherit from.
