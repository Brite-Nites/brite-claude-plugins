## Task 1 — Coupled-drift discovery during plan; producer-only fix would leave consumer blind

**Category:** pattern-choice
**Confidence:** 7/10 (1st instance of "grep consumer when touching producer" applied at planning, not review; mechanism familiar from state-schema lockstep but new surface)
**Tags:** pattern-choice, coupled-drift, producer-consumer, plan-time-grep, same-pr-coupling, schema-canonicalization

### Decision

When a plan modifies one side of a producer-consumer contract (here: the agent's output schema for `quality_gate_flags`), grep the consumer side for the canonical field name BEFORE finalizing scope. If the consumer references a drifted shape (here: `commands/weekly.md § 1.6` was reading `audit_cards[].flags[]` and `flag.check`), couple the consumer fix into the same PR — fixing the producer alone leaves the consumer blind to the post-fix shape.

The coupling decision is **causal**, not merely thematic: pre-fix, the renderer would have produced `0 flags` even against a fully-populated correct shape — the agent obeying its tightened spec is silently blocked by the renderer's stale field name. A producer-only PR would have shipped a self-defeating fix.

### Surface in this session

BC-6052 was filed agent-side ("project-audit subagent drops per-flag list"). During planning, reading `commands/weekly.md § 1.6` to confirm the expected render path surfaced two stale references on line 298: `audit_cards[].flags[]` (canonical name is `quality_gate_flags`) and `flag.check`. The plan's "Discovered during read" section captured this and added Task 2 (renderer fix) to scope. The synthetic 12-flag trace in the plan's Verify section — built post-fix — confirmed the renderer rules resolve cleanly only against the post-fix field names; pre-fix, both ranking branches evaluate to `undefined`.

### Pattern

**Plan-time grep of the consumer side closes a self-defeating-fix loophole.** State-schema-drift gotchas (cadence/CLAUDE.md BC-5760/BC-5761 precedent) cover cross-phase drift — Phase N producer vs Phase N+1 consumer. This is the same shape applied to producer-vs-renderer at the schema-field level, surfaced at planning rather than at fix-review. The plan-time grep cost was a few seconds; the avoided cost is shipping a producer-fix that doesn't render correctly until a later PR catches the consumer drift.

### Applies when

- Any spec/schema fix that tightens a producer's output shape — grep every consumer for the field name and the drifted shorthand variants before finalizing scope
- Any rename or canonicalization at a schema boundary — the rename PR must touch every consumer site, not just the producer
- By extension: when the existing CLAUDE.md gotcha for the area names the contract but not the field, the gotcha is a candidate for extension in the same PR (see BC-6052 task-2 below)

### Follow-ups

- Watch for 2nd instance of "consumer-grep at plan time catches drift before fix" — promote to a load-bearing rule in CLAUDE.md if it recurs
- If repeat instances surface, consider an automated lint rule that greps `commands/*.md` for known schema field names against `agents/*.md` Output schemas

## Task 2 — Gotcha-site canonical-name pin: extend the existing gotcha, don't add a new one

**Category:** pattern-application
**Confidence:** 7/10 (1st instance; confirms the natural durable-knowledge-site for canonicalization is the existing thematic gotcha, not a new one)
**Tags:** pattern-application, claude-md-gotcha, canonical-field-pin, drift-prevention, durable-knowledge-site, gotcha-extension

### Decision

When a regression fixes a contract that an existing CLAUDE.md gotcha names but does not pin, extend the existing gotcha to pin the canonical field name and prohibit both surfaces of drift — rather than adding a sibling gotcha citing the new issue. The gotcha is the durable-knowledge site for the area; the next person editing § 1.6 or the agent schema reads the gotcha and sees the contract before touching either side.

For BC-6052: `plugins/cadence/CLAUDE.md` line 55 already named the BC-5870 quality-flags 10-flag threshold contract but did not pin the canonical field name. The CDR-compliance review agent flagged this (P3, conf 7) and the fix appended one sentence to the existing gotcha:

> **Canonical field name is `quality_gate_flags`** per `agents/project-audit.md` § Output: renderer reads `audit_cards[].quality_gate_flags[]` and `quality_gate_flag.check`; readers MUST NOT fall back to a `flags[]` or `quality_gate_flags_count` shape, and the agent MUST NOT emit count-only / aggregate / summary forms. … BC-6052 pinned the canonical field name after the renderer drifted to bare `flags[]` and the agent runtime improvised `quality_gate_flags_count` against W17's audit.json.

### Surface in this session

The CDR-compliance review (Step 4 thorough-mode review pipeline) flagged the gotcha as compliant-but-incomplete: it covered the threshold contract but didn't pin the field name, leaving the re-drift surface that BC-6052 had just exposed. Validator confirmed (CONFIRMED). Review-fix commit appended one sentence; net diff was 2 lines (the field-name-pin edit + the citation-precision fix on `agents/project-audit.md:28`). One commit, two cosmetic-but-load-bearing additions.

### Pattern

**Extend over add when the existing gotcha already names the area.** A new sibling gotcha citing BC-6052 directly would have been correct but would split the durable knowledge across two adjacent bullets in CLAUDE.md, raising the "where do I look" cost for the next reader. Extending the BC-5870 gotcha keeps the threshold contract + the canonical field name in one bullet — both rules are about the same Phase 1 quality-flags subsection, so they belong together. Origins line at the end of the bullet now cites both `Origin: BC-5870 (W17 dogfood…); BC-6052 pinned the canonical field name…`.

Distinct from BC-5901 task-1's "split the precedent into named sub-patterns" pattern — that was about precedent files in `docs/precedents/`. This is about CLAUDE.md gotchas, where bulletwise tidiness matters because every bullet competes for the next reader's first-glance attention budget.

### Applies when

- A regression fix surfaces a contract that an existing thematic gotcha names but does not fully pin — extend in place
- The fix's canonical-name addition is one sentence or less — extension is cleaner than addition
- The Origins line on the existing gotcha can credibly carry two issue citations without becoming a forensic chain — three or more citations probably justifies a new bullet

### Follow-ups

- Watch for "extension vs new sibling gotcha" judgment calls in future regression PRs — if a 2nd instance hits, the rule is solid for cadence/CLAUDE.md and likely transfers to other plugins' CLAUDE.md files
- If extension grows the bullet over ~150 words, file a follow-up to refactor — long bullets defeat the at-a-glance gotcha pattern

## Task 3 — Multi-agent simplify convergence on load-bearing redundancy: keep, don't auto-apply

**Category:** pattern-choice
**Confidence:** 6/10 (calibration of "when convergent simplify findings should be rejected"; the rule's no-suppression intent preserved by classifying as suggestion + rationale, not silent reject)
**Tags:** pattern-choice, simplify-pass, redundancy-judgment, anti-drift, regression-prose-budget, multi-agent-convergence

### Decision

When all 3 simplify agents (code-reuse, code-quality, efficiency) converge on the same finding — here: "the prohibition against `quality_gate_flags_count` is stated 3× in `agents/project-audit.md`" — and the originating change is a regression fix whose redundancy is the load-bearing protection against the regression, the right move is **report as suggestion + cite the regression rationale**, not auto-apply.

The performance agent's analysis was the deciding signal: ~4400 tokens × 26 fan-out calls per `/cadence:weekly` run is well under the 1K × 26 = 26K threshold (~5× under). The redundancy is the doubled enforcement that BC-6052 is buying — Haiku ignored a single mention against W17's real data, and the spec-side fix's only lever for runtime obedience is enforcement-via-repetition until BC-5874's third dogfood proves otherwise.

### Surface in this session

3 parallel simplify agents flagged the same triple-redundancy at confidence 5–8/10. The repo has no test runner (validate.sh is a structural linter), so per the spec, simplify findings stay as suggestions — auto-fix was disabled. The findings remained in the final report as P3 advisory; the developer judged each one against the regression-rationale and rejected all 3 simplifications.

### Pattern

**Convergent simplify findings on regression-fix prose are correct-but-rejectable when the redundancy is the regression's protection.** The simplify pass did its job (surfacing the redundancy); the orchestrator did its job (presenting the trade-off + the regression rationale to the developer); the developer made the judgment call. The pass-rejection is itself a useful signal: when 3 agents converge on a finding and the developer rejects it, the rejection rationale belongs in the precedent file so the next regression-fix author can cite it ("per BC-6052 task-3, anti-drift redundancy in regression fixes is load-bearing if it survives multi-agent simplify").

Distinct from "validation step IS the authoritative severity pass" (BC-5831 task-1) — that was about review-pipeline P1/P2/P3 misclassification. This is about simplify-pass redundancy detection vs regression-protection rationale; the convergence is correct in detection but wrong in prescription, and the prescription failure mode is recurrent enough across regression-fix PRs to log.

### Applies when

- Regression fix touches prose loaded into a Haiku/Opus subagent context (the fan-out cost is real but bounded)
- Simplify agents flag the new prose as redundant with itself (within-file convergence) or with sibling sites (cross-file convergence)
- The regression's primary lever for runtime obedience is enforcement-via-repetition (no test surface, spec-side only)
- Token-cost-vs-failure-cost trade falls under the typical "P3 unless >1K × 26" threshold

### Follow-ups

- Watch for 2nd instance of "convergent simplify finding rejected for regression protection" — promote to load-bearing if confidence holds
- If a 3rd instance pushes total fan-out delta over ~10K tokens, the calculus may flip; file a follow-up to refactor toward extracted lint rules rather than prose enforcement
