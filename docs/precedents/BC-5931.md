## Task 1 — Claim-grounding pattern reaches 3rd instance; architecture-9 promotion candidate

**Category:** architecture
**Confidence:** 9/10
**Tags:** architecture, claim-grounding, factual-correctness, mechanical-port, simplify-pass, cdr-compliance, fact-verification, line-citation, source-attribution

### Decision

The "claim-grounding" pattern — surface factual drift via a ground-truth-verifying review agent rather than relying on brainstorm/plan gates — has now surfaced for the **third time** in three sessions:

- **BC-5946 task-3** (2026-04-24, conf 8/10): Integration-guide claims must grep against wrapper source, not author memory. Surfaced via review pass on tam-map MCP guides.
- **BC-5928 task-1** (2026-04-26, conf 7/10): Mechanical ports have a factual-correctness surface that simplify catches but brainstorm/plan cannot; trust ≥6/10 simplify findings on factual claims. Surfaced via simplify pass on sf-lwc rule #7 (`@AuraEnabled` security semantics).
- **BC-5931 task-1** (this session, conf 9/10): cdr-compliance review agent flagged sf-data Rules 2/3 + header attribution comment citing `§Apex & Automation` for lines 143-144 in `brite-salesforce/CLAUDE.md`, but those lines actually live in `§Metadata Authoring` (header at line 120; `§Apex & Automation` starts at line 178). Verified by grep against source. Pattern: line-number citations require verifying the **enclosing section header**, not just the line content.

**Promotion to architecture-9.** Three independent surface instances across three sessions confirm the pattern's durability. The unified rule is:

> **"Claims-as-evidence" patterns require ground-truth verification at a discovery surface distinct from brainstorm/plan.** Brainstorm and plan gates evaluate scope and shape, not correctness. The discovery surface for factual drift is whichever review agent has direct grep access to the source-of-truth file:
>
> - Integration-guide → wrapper source (BC-5946)
> - Mechanical port rule body → cross-repo CLAUDE.md (BC-5928)
> - Line-number source citation → cross-repo CLAUDE.md *with section-header verification* (BC-5931)
>
> **Trust ≥6/10 findings on factual claims, not just ≥7/10.** Below-7 confidence is acceptable for grep-verifiable factual claims because the agent did the legwork — confidence reflects the agent's certainty about its grep result, not the importance of the finding.

### Alternatives considered

1. **Treat as another single-instance pattern, defer architecture promotion** — Conservative. **Rejected.** Three instances across three sessions in 6 days, each with a different surface (integration guide / mechanical port body / line-number citation), satisfies the 3-instance bar. The shared mechanism (grep against external source-of-truth at review time) is durable.

2. **Promote without unifying — keep BC-5946, BC-5928, BC-5931 as three separate architecture-7 patterns** — Preserve specificity. **Rejected.** The unified "claim-grounding" framing captures the essential insight (factual claims need a grep-verifying agent) without losing the per-surface specifics, which remain in the individual session traces.

3. **Promote to architecture-9 but leave the "≥6/10 trust threshold" as a separate sub-rule** — Hierarchy. **Considered, partially adopted.** The trust threshold is incorporated into the unified rule because it's the operational handle — without it, the pattern is descriptive but not actionable.

### Rule derived

**Architecture-9 (durable):** *Claim-grounding requires a discovery surface distinct from brainstorm/plan.* When an artifact under review makes a factual claim about an external source — line numbers, section headers, function signatures, integration tool semantics, library semantics — the verifying surface is whichever review agent has direct grep access to the source-of-truth. Trust ≥6/10 findings on factual claims; the confidence score reflects the agent's certainty about its grep result, not the finding's stakes.

Procedure:

1. **At review time**, the cdr-compliance / code-quality / domain-specialist agents are the claim-grounding surface for any cross-source factual claim.
2. **Don't auto-fix below 7/10 in general**, but **do** auto-fix 6+/10 if the finding is a factual claim with grep-verifiable evidence.
3. **Verify before fixing** — re-run the grep yourself; agents can hallucinate ground-truth too. (Memory pattern: "Agents incorrectly claim X" lives in this same neighborhood.)
4. **Commit message names the factual fix explicitly** so the PR reviewer sees content correction vs. polish.

### Promotion note

**Promoted to architecture-9 (durable).** Add to `memory/MEMORY.md` Conventions or Reference section under "Claim-grounding pattern (architecture-9)". Future surface instances may add new claim classes (e.g., schema-shape claims, API-version claims) but the rule itself is now stable.

The promotion is somewhat unusual — most architecture promotions wait for a 4th or 5th instance — but the 3-instance set has very high quality (each instance was verified by independent grep against external source-of-truth, all three resulted in PR fixes that landed cleanly, and the unifying mechanism is technically clear). The 9/10 confidence on this session's specific instance also supports earlier promotion.

## Task 2 — Split when upstream concern is orthogonal to Brite addition (sf-docs verbatim + new sibling skill)

**Category:** pattern-choice
**Confidence:** 7/10
**Tags:** pattern-choice, lineage-class, sibling-split, verbatim-adoption, upstream-purity, concern-separation, brite-original-skill

### Decision

When a Phase 3 customization issue prescribes Brite additions to an upstream skill, **first check whether the additions match the upstream's existing concern**. If they don't — if the addition is a different concern that happens to share a name-space — the right resolution is **adopt verbatim** (attribution comment only, no Brite Context, no Discipline rules) and **author the Brite concern in a new sibling skill**.

**Specific instance this session.** BC-5931 spec called for adding "brite-salesforce/docs/artifacts inventory + ADR convention + cross-repo references" to sf-docs. Brainstorm surfaced the mismatch: upstream sf-docs is a **web-retrieval playbook** for `developer.salesforce.com` / `help.salesforce.com` with explicit non-goals "no local corpus, no repo-specific scripts, no PDF fallback" (lines 197-203 of upstream SKILL.md). The Brite additions point at *internal* docs — a different concern.

Resolution applied:
- sf-docs adopted **verbatim** (only edit: a 1-line attribution HTML comment naming the verbatim decision and pointing at the sibling skill)
- New skill `sf-internal-docs` filed as BC-6081 to own the Brite-internal concern
- `plugins/revops/UPSTREAM.md` gained a `## Lineage classes` section documenting three classes: (1) Adapted from upstream, (2) Adopted verbatim from upstream, (3) Added by Brite

**This is the first instance of class 2 in revops** (sf-diagram-mermaid predates the taxonomy and ships fully verbatim with no attribution comment — leaving as-is). It's the precedent-setter for the class.

### Alternatives considered

1. **Append-only: keep sf-docs upstream behavior + add a `## Brite Internal Reference Map` section** — Simpler diff. **Rejected.** Description-field activation routing wouldn't fire on "where's our ERD?" anyway because the upstream description is "official Salesforce documentation retrieval guidance." The append would be partially broken at the activation layer, AND it would weaken the upstream's explicit non-goal "no local corpus, no repo-specific scripts" — coupling a stable upstream contract to a Brite-volatile artifact inventory.

2. **Reframe sf-docs entirely** (replace web-retrieval body with internal-docs content) — Honest about new role. **Rejected.** Would break the cross-skill contract — other sf-* skills delegate to sf-docs *for web retrieval*, and that pathway would degrade. Plus catastrophic upstream-merge surface for any Jaganpro sf-docs improvement.

3. **Bundle sf-internal-docs author into BC-5931 (this PR)** — Single PR closes BC-5804. **Considered, rejected at brainstorm Q4.** New-skill author is materially more work than per-skill customization, and Brite-original is a lineage precedent-setter that deserves its own audit. User chose split-to-follow-up at the brainstorm gate.

### Rule derived

**Before applying a Phase 3 customization, verify the addition matches the upstream's concern.** Specifically:
- Read the upstream's **Non-Goals** section (most upstream skills have one or imply one).
- Read the upstream's **description** field — does it match the issue's prescribed activation surface?
- If the addition is a different concern (verifiable by description-field mismatch + non-goal violation), **split**: adopt verbatim + author the Brite concern in a new sibling skill.

Splitting carries costs:
- New lineage class to document (UPSTREAM.md)
- New skill author scope (file follow-up issue)
- Plugin scope drift (skill count grows)

Accept these costs when the alternative is partial-activation-broken append or upstream-contract-breaking reframe.

### Promotion note

First instance of "concern-separation split" in revops. The pattern is general (could apply to any future plugin where upstream concern ≠ issue-spec addition), but it's session-1 here. Watch for a second instance — could be in marketing skills (where coreyhaines31 upstream skills sometimes have orthogonal Brite concerns) — to promote to architecture-7. The dual ingredient (verbatim adoption + lineage-class taxonomy) is the precedent-setting contribution; future instances would inherit the UPSTREAM.md taxonomy.

## Task 3 — "Fix all" mode: ultrathink + sequential-thinking + 12-task fix pass

**Category:** pattern-choice
**Confidence:** 7/10
**Tags:** pattern-choice, ultrathink, review-fix-pass, finding-classification, scope-discipline, fix-prioritization, agent-claim-validation

### Decision

When the user invokes `ultrathink` after `/workflows:review` and asks to fix ALL P1/P2/P3, the orchestrator's job is **not** to mechanically apply every finding — it's to **classify each finding** and apply only the actionable ones, with explicit rationale for the skipped ones documented in the commit message + plan-doc.

**Specific instance this session.** Review pass surfaced 0 P1, 3 P2, 11 P3 across 5 agents (after dedup + confidence filter ≥7). User invoked ultrathink + "fix all". I classified 13 findings (including filtered-conf <7) into:

- **Actionable (10):** factual errors, dead references, missing taxonomy, plan-doc resync — all fixed in fix pass
- **Already addressed (1):** sf-docs comment 470-char (was simplify-pass tightened)
- **Wrong agent claim (1):** cross-ref "asymmetry" on Email Bison/OutboundSync — handshake vs data shape are genuinely distinct concerns, agent's claim was incorrect
- **Speculative (2):** "move citations to footnote" (perf 7/10) — agent explicitly said speculative, not measured; inline citations are better UX
- **Either-defensible (1):** patch vs minor version bump — no user-facing change either way
- **Load-bearing (2):** plan parenthetical "lineage precedent-setter, deserves its own audit" — load-bearing rationale; three verify tables in plan — skim-friendly per-task

The 7 actionable categories were applied via 12-task list (sequential-thinking-organized) in a single fix-pass commit (`b8c1cac`). Skipped findings documented with rationale in the plan-doc's new `## Post-review amendments` section.

### Alternatives considered

1. **Mechanically apply all 13 findings without classification** — Literal reading of "fix all". **Rejected.** Mechanical application of agent-claim-debatable findings (cross-ref "asymmetry") would degrade the artifact. Mechanical application of speculative findings ("move citations to footnote") would speculatively restructure without measured benefit. The orchestrator's classification IS the value-add over what the agent recommendations provide.

2. **Skip findings <7 confidence** — Per the standard review filter. **Rejected.** User explicitly asked for ALL — including filtered. Some <7 findings ARE actionable (sf-data:60 dual citation at 7/10 *and* "stance:" preambles at 8/10 came in below the dedup-filter threshold but were obviously legitimate).

3. **Apply selectively but don't document skipped findings** — Less plan-doc bloat. **Rejected.** Documenting the skipped findings with rationale is itself a precedent-setting artifact — future review-pass cycles inherit the classification template. The plan-doc gains a `## Post-review amendments` section worth ~20 lines but earns its place by capturing the decision audit trail.

### Rule derived

**"Fix all" mode requires finding classification, not mechanical application.** Procedure:

1. **Aggregate** all findings (including filtered-conf <7) into a single list.
2. **Classify** each as: actionable / already-addressed / wrong-agent-claim / speculative / either-defensible / load-bearing.
3. **Apply** only actionable findings — but apply ALL of them (don't sub-filter on confidence within the actionable bucket).
4. **Document** skipped findings with rationale in the plan-doc + commit message. The audit trail IS the deliverable.
5. **Use sequential-thinking + a task list** for 5+ findings to keep classification disciplined and visible.

This rule supersedes the `/workflows:review` standard "≥7 confidence filter" specifically for "fix all" mode. The standard filter is a default for review presentation; "fix all" is an override that demands per-finding judgment.

### Promotion note

First explicit instance of "fix all" mode behavior. The pattern is straightforward enough that it might not promote to architecture — orchestrators have always done classification, just not always documented it. The new ingredient here is the **plan-doc Post-review amendments section** as a durable artifact. Watch for a second instance to confirm the section becomes a template; until then, file as pattern-choice not architecture.

## Task 4 — File forward-referenced follow-up issue early, not at ship phase

**Category:** pattern-choice
**Confidence:** 6/10
**Tags:** pattern-choice, follow-up-issue, forward-reference, dead-reference, ship-phase-vs-review-phase, attribution-comment-honesty

### Decision

When a current-PR artifact (skill body, attribution comment, plan-doc) **forward-references** a follow-up issue, file the follow-up issue **during the review phase**, not the ship phase. This converts the forward reference from a promise into a concrete BC-#### that future readers can navigate.

**Specific instance this session.** Plan §Task 4 originally said "file follow-up issue at ship phase." But the sf-docs attribution comment said "filed as a follow-up to BC-5931" — that reads as a promise, not a fact. Both code-reviewer (P3 8/10) and architecture-reviewer (P3 7/10) flagged this as a forward-reference smell. Resolution: filed BC-6081 during review fix-pass; sf-docs attribution updated to "see BC-6081" with the real issue number.

The plan-doc was updated to mark Task 4 DONE and explain the bring-forward.

### Alternatives considered

1. **Defer to ship phase per original plan** — Keep ship-phase scope. **Rejected.** Ship-phase issue creation works fine for issues that aren't load-bearing on the current PR's text. But for forward-references in the artifact, the dead reference ships in the merge — even after the issue is later filed, the comment in `git log` will still read as "filed as a follow-up" forever, which is worse than a concrete BC-####.

2. **Reword the forward reference to avoid the promise** — Soft alternative. **Considered.** Plan §172 originally suggested "see follow-up issue (filed at PR ship)" — the actual file deviated from the plan by adding the unfilled "BC-5931 follow-up issue" promise. The simplify pass softened to "filed as a follow-up to BC-5931" but didn't remove the promise. Filing the issue was cleaner than refining the wording further.

3. **Ship without the follow-up reference at all** — Punt to a later PR. **Rejected.** The sibling-pointer is the architectural rationale for the verbatim adoption — readers need to know where the Brite concern landed.

### Rule derived

**For PRs that forward-reference a follow-up issue in artifact text, file the follow-up during review phase rather than ship phase.** The marginal cost of issue-filing (~2 minutes) is well below the cost of a dead reference shipping in the merge.

Procedure update for BC-5931 plan template:

> §Task N (file follow-up issue): "File during review phase if the current PR's artifact text references the follow-up issue. File during ship phase if the follow-up is a pure scope reminder with no in-artifact reference."

### Promotion note

Adjacent to BC-5870 task-2 (verification-as-discovery-surface) and BC-5928 task-1 (simplify catches factual drift) — all three are "review pass surfaces a class of issue that the original plan didn't anticipate." Specifically here, the plan said "file at ship phase" but the review pass found that the in-artifact reference made early filing the better call. Pattern: plan gates predict, review/ship gates correct.

Watch for a second instance to promote to architecture-7. Likely surface: any future PR with a forward-referenced TBD link.
