## Task 1 — Instrumentation-first investigation when hook behavior is unclear: tee-wrap pattern as gold-standard diagnostic

**Category:** pattern-choice
**Confidence:** 8/10
**Tags:** pattern-choice, instrumentation-first, tee-wrap, hook-debugging, diagnostic-tooling

### Decision

When BC-6434 surfaced as "SessionStart hooks fail to fire," the original issue body listed three hypotheses (timeout, registration, output routing) without a way to distinguish between them. The temptation was to bump timeouts (cheap probe) or skip straight to filing upstream (defensive). Both would have been wrong moves: timeout-bump-first is a coin flip with no diagnostic value if it fails; upstream-first commits to a fix path before classifying.

I chose **instrumentation-first**: tee-wrap each hook's command with a timestamp+cwd preamble + `tee -a /tmp/<plugin>-banner.log` of stdout. The preamble line is independent of any Claude Code routing layer (it's a shell `>>` redirect to a regular file), so its presence vs. absence binarily classifies "hook ran" vs. "hook didn't run." The teed stdout further classifies "hook ran AND produced expected output" vs. "hook ran but stdout was empty/corrupted."

The pattern was applied at brainstorm-Q1 with user approval. Result: one repro round disambiguated the bug. Logs populated → hook fires correctly → not a timeout, not a registration issue → must be a downstream routing issue. A second probe (asking the model in a fresh session whether it received the system-reminder) further showed the routing reaches the *model* but not the *user-visible terminal block* — narrowing diagnosis from "routing broken" to "UI rendering broken in a specific direction."

### Alternatives considered

1. **Timeout-bump first** — Bump revops 3s → 10s, retest. Rejected: cheap but uninformative if it fails (we'd still need instrumentation as Round 2). Workflows hook's 5s timeout already showed banner in plugin-home cwd, so timeout was already a weak hypothesis.

2. **File upstream Claude Code issue without local diagnosis** — Rejected: would have committed to "platform bug" framing without evidence. If it turned out to be our config, we'd have a noisy upstream report to retract.

3. **In-script logging (modify `sfdx-banner.sh` itself)** — Considered but rejected: if the bug is hook *registration* (script never runs), in-script logging tells us nothing the outer-wrapper approach wouldn't.

4. **Comparison test against another working plugin** — Useful but supplementary. Workflows banner (different timeout, different content) failed identically, which DID provide cross-plugin signal but not direct evidence of the failure mode.

### Rule derived

**When debugging a hook whose stdout is supposed to surface in a system-reminder (or any opaque routing layer), tee-wrap the hook command with a timestamp+cwd preamble line that writes via shell `>>` redirect, plus `tee -a` of the original stdout.** The preamble is your binary "did the hook run at all" signal; the teed stdout is your "what did it produce" signal. Cost: 2 commits per plugin (instrument + revert) and 2 patch versions per plugin (BC-6000 same-commit cache rule). Benefit: one repro round produces definitive classification across timeout/registration/routing hypothesis space.

Procedure:
1. Wrap hook command: `{ printf '[%s] %s hook fired in cwd=%s\n' "$(date '+%Y-%m-%dT%H:%M:%S%z')" "<plugin>" "$PWD" >> /tmp/<plugin>.log; <original command> | tee -a /tmp/<plugin>.log; }`
2. Bump plugin version + marketplace.json mirror per BC-6000 same-commit rule
3. User opens fresh session in target cwd, types any prompt, exits, pastes log contents
4. Classify: log empty → didn't run; log has preamble only → script silent (correct for some cases like non-SFDX cwd); log populated → hook works, downstream routing is the bug
5. Revert tee-wrap in fix commit; bump again

### Promotion note

This is the **1st surface** for the tee-wrap-instrumentation-first pattern. May extend BC-5806 task-1 (perf-budget-as-floor) from passive observation to active diagnostic discipline. At 2nd surface (any other "hook output is opaque, want to classify before fixing"), promote pattern-choice 7/10 → 8/10. At 3rd surface, codify in `docs/guides/hook-debugging.md` or similar.

## Task 2 — Goal redefinition when execution-time evidence proves the goal unreachable: add an Outcome paragraph rather than rewrite history

**Category:** pattern-application
**Confidence:** 7/10
**Tags:** pattern-application, plan-doc-coherence, goal-redefinition, outcome-paragraph, post-diagnosis-reframe

### Decision

BC-6434's plan was authored with Goal: "fresh session opened in `~/Projects/work/brite-nites/brite-salesforce/` shows both the workflows `Brite Session Context` banner and the revops `RevOps Active` banner." After the instrumentation→repro→classify loop, this goal turned out to be unreachable from `hooks.json` alone — the upstream regression #24425 means SessionStart hook stdout is no longer rendered as a visible terminal block in v2.1.x.

Three options for the plan doc:
1. Rewrite the Goal section in place (loses the original framing)
2. Mark the plan as failed and abandon it (loses the diagnostic work)
3. Append an **Outcome paragraph** that explicitly redefines the achievable goal

I chose option 3. The original Goal stays verbatim (preserves the "what we set out to do" framing for future readers), and an immediately-following "Outcome (post-diagnosis):" paragraph names the achievable goal: "classification + upstream issue cite + CLAUDE.md gotcha + Linear update." This pattern keeps the plan coherent without pretending the original premise was correct.

### Alternatives considered

1. **Rewrite Goal section in place** — Rejected. Loses the historical signal. A future reader auditing how Brite handles "platform bugs that can't be fixed locally" needs to see both the original framing and the redefined outcome.

2. **Mark plan failed, file new plan for Path A revert** — Rejected. The diagnostic work IS the plan output; treating it as "failed" misframes the value. Path A was selected at the brainstorm-fix-gate, which is part of the original plan's flow.

3. **Strikethrough the original Goal text** — Considered. Markdown strikethrough renders as `~~text~~`. Cosmetically adequate but visually noisy and less informative than an explicit Outcome paragraph that names *what was achievable*.

### Rule derived

**When a plan's Goal proves unreachable mid-execution due to evidence outside the plan's control (platform regression, deprecated API, vendor pivot), add an explicit Outcome paragraph immediately following the Goal.** The Outcome paragraph names the achievable target without rewriting history.

Triggers:
- Diagnosis section reveals the original goal premise was wrong
- A platform/vendor decision invalidates the original approach
- Research turns up the original goal was based on a stale assumption

The Outcome paragraph should:
- Cite the upstream evidence (issue #, ADR, vendor doc)
- State the redefined achievable goal in one sentence
- Not delete the original Goal text

### Promotion note

1st surface. The pattern is structurally similar to BC-5806 task-3 / BC-2717 task-2 reconciliation tables (both codify spec-vs-reality drift), but at a different level — reconciliation tables capture issue-body-vs-ground-truth at *plan-time*; the Outcome paragraph captures Goal-vs-evidence at *execute-time*. If a 2nd instance of "execute-time Goal redefinition" appears, promote pattern-application 7/10 → 8/10. The two patterns may converge into a single "issue/plan/goal coherence under contradictory evidence" architecture-9 cluster at the 4th-5th surface.

## Task 3 — Reconciliation-table 5th surface reaffirms architecture-9; novel hypothesis-vs-evidence variant opens sub-pattern slot

**Category:** pattern-application
**Confidence:** 7/10
**Tags:** pattern-application, reconciliation-table, durability-evidence, architecture-9, hypothesis-vs-evidence-variant

### Decision

BC-6434's plan opens with a 2-row reconciliation table at the top, capturing two issue-vs-ground-truth drifts:
- "cadence's Brite Session Context banner" → cadence has no hooks; the banner is from `workflows`
- "3-second timeout hypothesis" → workflows hook (timeout 5s) also failed, weakening this hypothesis before any work began

This is the **5th surface** for the issue-vs-ground-truth amendments-table pattern (chain: BC-5947 → BC-5806 → BC-5832 → BC-2717 → BC-5906 → BC-6434), which reached architecture-9 at BC-2717. Per memory `session_bc_2717.md`, the pattern is durable at arch-9. BC-6434 is durability evidence, not promotion fuel.

Novel application: BC-6434's reconciliation rows are **hypothesis-vs-evidence**, not just spec-vs-ground-truth. Row 2 weakens an issue-body hypothesis using cross-plugin counter-evidence. This is structurally distinct from "issue says X, file says Y" amendments. It opens a sub-pattern slot: at a 2nd instance of "diagnosis-table-shape captures hypothesis disposition," promote a sub-pattern note for diagnosis-table specialization.

### Alternatives considered

1. **Drop the reconciliation table entirely** — Rejected. The cadence-misattribution is genuinely load-bearing for scope ("are we touching 3 plugins or 2?"). The timeout-hypothesis row primes the reader for why instrumentation-first is the right move.

2. **Inline the corrections into prose paragraphs** — Rejected per BC-5806 task-3. A reconciliation table at the top of the plan ensures reviewers see departures in the first 30 seconds; inline corrections require scrolling and risk being missed.

3. **Frame as 3rd-surface promotion (original plan claim)** — Rejected after architecture-reviewer flagged that the pattern is already at arch-9 in adjacent specializations (verified by reading BC-5906, BC-2717, BC-5832 precedents). Reframed mid-review-pass via simplify+fix-pass.

### Rule derived

**At post-arch-9 surfaces of an established pattern, claim durability evidence rather than promotion.** The promotion ladder caps at architecture-9; further surfaces serve to confirm calibration, not advance it.

When applying a known arch-9 pattern with a novel structural variant (e.g., hypothesis-vs-evidence vs. spec-vs-ground-truth), open a *sub-pattern slot* in the precedent file: name the variant explicitly, note that promotion of the sub-pattern follows its own ladder. This avoids inflating the parent pattern's claimed surface count (which calibrates wrongly) while still recording the novel application.
