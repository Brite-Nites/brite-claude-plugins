## task-1 — NEW pattern-choice: pre-flight audit verdict-shape with observable-axis split (READY / DEFERRED / NEEDS-FIX)

**Decision:** When auditing readiness against an acceptance gate whose criteria are partially pre-flight-observable and partially execution-only-observable, the verdict taxonomy is **three-valued, NOT binary**: `READY` (criterion's pre-flight preconditions hold), `NEEDS-FIX` (criterion's pre-flight preconditions fail and can be remediated), `DEFERRED` (criterion is observable only during gate execution itself; pre-flight cannot rule it in or out). Each pre-flight-observable criterion receives READY or NEEDS-FIX; each execution-only criterion receives DEFERRED with rationale.

For BC-7058's audit of Brand Hub against Q8's 7 sub-criteria for BC-6998 dogfood success: 3 READY (output-schema preconditions, build/lint/test, Linear-chain preconditions), 4 DEFERRED (9 phases complete, 5 gates fire, `/flow:audit` exit 0, dogfood findings authored), 0 NEEDS-FIX. The DEFERRED bucket is not a cop-out — it's an honest classification of what pre-flight CAN and CANNOT verify. A two-valued "READY/NEEDS-FIX" taxonomy would have forced false-READY on the 4 execution-only criteria or false-NEEDS-FIX (which would have wrongly blocked BC-6998).

**Why three values matter:** the audit's downstream consumer (BC-6998 dogfood) needs to know which criteria still bear execution risk vs. which are already validated. Binary verdicts hide that distinction; three-valued verdicts surface it.

**Category:** pattern-choice

**Confidence:** 7/10 — NEW pattern; load-bearing-pending until 2nd-surface confirms applicability outside Q8 acceptance-gate context.

**Inputs:**
- BC-7058 issue spec: "For each of Q8's 7 sub-criteria, findings doc has explicit pre-flight verdict: `READY` / `NEEDS-FIX` / `DEFERRED` (7 separate greps)"
- Q8 7 sub-criteria (`fda-plugin-drafter-e-revision-2.md:1117-1133`) — 4 of 7 are observable only during retrofit phase execution
- Audit outcome: 3+4+0 split rendered the verdict honestly; no false-positives toward either direction
- Brand Hub repo state at audit time: `npm run build && lint && test` all exit 0 (sub-criterion 5 pre-flight verifiable); intent.md absent (sub-criterion 3 pre-flight verifiable as "no collision risk")

**Alternatives Considered:**
1. (Chosen) Three-valued verdict with explicit observable-axis split (READY / NEEDS-FIX / DEFERRED). Reason: matches the underlying structure of acceptance criteria (some pre-flight-observable, some execution-only); honest about audit's epistemic reach.
2. Binary verdict (READY / NEEDS-FIX) with execution-only criteria collapsed into one of the two. Rejected: forces dishonesty — either false-READY (pre-flight passes a criterion it didn't actually verify) or false-NEEDS-FIX (pre-flight blocks gate execution it shouldn't have a vote on).
3. Two-axis matrix (observable-pre-flight × verdict) shown as 2×3 grid. Rejected: more accurate but more cognitive overhead per row; three-valued column suffices because observable-axis is implicit in the verdict (DEFERRED → execution-only).
4. Skip audit entirely for execution-only criteria. Rejected: BC-6998 dogfood consumer needs to see ALL 7 sub-criteria represented even when pre-flight can't render verdict, so context is preserved.

**Precedent Referenced:**
- None — NEW pattern. Re-surface in BC-6998 dogfood-findings doc and future acceptance-gate audits will validate or refine.

**Tags:** new-pattern, pattern-choice, audit-verdict-taxonomy, three-valued, observable-axis-split, acceptance-gate

**Outcome:**
- PR #284 opened with audit doc using three-valued verdicts; downstream BC-6998 consumer gets honest signal about pre-flight epistemic reach.
- All 5 issue-spec ACs pass; including the 7-verdict grep check (3 READY + 4 DEFERRED rendered correctly in table form).
- Pattern's 2nd surface: BC-6998 dogfood-findings doc will use a different verdict shape (success/failure per Q8 sub-criterion at execution time) — but the 3-valued pre-flight pattern remains reusable for future acceptance-gate audits (BC-7057 vertical-slice readiness, future v1.1 acceptance gates, etc.).

## task-2 — pattern-application: Linear MCP read-path-fragility cluster, 3rd surface

**Decision:** Two more Linear MCP read-path filter gotchas surfaced at the same audit session, joining the existing `list_issues milestone:` failure into a cluster of 3 distinct symptoms with one root-cause shape:

1. `list_issues milestone:` returns issues from multiple milestones (1st surface, BC-2717 era) — `gotcha_linear_list_issues_milestone_filter.md`
2. **NEW: `list_issues project:` returns 0 issues** when project has many (BC-7058) — `gotcha_linear_list_issues_project_filter.md`
3. **NEW: `get_project` rejects bare UUID** while accepting slug (BC-7058) — `gotcha_linear_get_project_needs_slug.md`

The unifying root-cause shape: **Linear MCP read-path scoping parameters are fragile**; some are silently broken (project filter returns 0, milestone filter returns unfiltered cross-scope), some are silently rejected (UUID for get_project). The write path (`save_issue`, `save_comment`, `save_milestone`) is consistently trustworthy — its response body shows the resulting state cleanly, which is the right verification pattern.

**Operational rule:** Do not trust Linear MCP read-path scope-filter parameters. Always verify by reading the response and filtering client-side, OR use the write path's response inspection pattern. Specific recipes:
- `list_issues project:` → use `team: "<team>" query: "<project name>"` then filter `response[].projectId == "<UUID>"`.
- `list_issues milestone:` → use `get_issue` per-ID and read `projectMilestone.name`.
- `get_project` → use slug, not UUID. If only UUID is known, fall back to `list_projects query: "<name>"` and read the resolved entry's URL for the slug.

**Category:** pattern-application

**Confidence:** 8/10 — 3 distinct symptoms, 1 root-cause shape (read-path scope-filter fragility), 1 consistent workaround pattern (verify by response inspection, not query trust). The pattern survives across releases (1st surface was BC-2717 era, BC-7058 is months later) — points to a structural MCP-server limit, not a transient bug.

**Inputs:**
- Existing gotcha `gotcha_linear_list_issues_milestone_filter.md` (1st surface)
- NEW gotcha `gotcha_linear_list_issues_project_filter.md` (2nd surface — same session, this PR's compound-learnings)
- NEW gotcha `gotcha_linear_get_project_needs_slug.md` (3rd surface — same session, this PR's compound-learnings)
- Counter-example: `save_issue` + `save_comment` + `save_milestone` responses are trustworthy (BC-6436 state-param gotcha + this session's BC-7058 `state:` field change verified via response inspection)
- BC-7058 audit workflow: 2 of the 3 gotchas were caught at the same Linear-access verification gate, before any downstream work depended on them

**Alternatives Considered:**
1. (Chosen) Document each new gotcha as a separate memory file with cross-links + record the cluster pattern as one precedent trace. Reason: each gotcha needs its own searchable memory entry (so future code looking for "list_issues project filter doesn't work" finds it directly); the precedent trace captures the unifying root-cause shape so future Linear MCP issues are diagnosed faster.
2. Collapse all 3 gotchas into one mega-gotcha file. Rejected: future readers searching for specific symptoms (the most likely access pattern) would miss the mega-file. Per-symptom files index better.
3. Skip the precedent trace and rely only on the memory entries. Rejected: the cluster's existence is itself a durable insight (Linear MCP read-path is structurally fragile; trust the write path). Without the precedent, the next surface would be re-diagnosed from scratch instead of recognized as cluster-member.
4. File a Linear-MCP-server upstream issue. Out of scope for BC-7058; could be a follow-up if cluster grows to N>4 surfaces.

**Precedent Referenced:**

- BC-6436's `gotcha_linear_save_issue_state_param.md` is the write-path counter-example — write-path response trustworthiness is the inverse pattern.
