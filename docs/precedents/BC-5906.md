## <a id="BC-5906-task-1"></a>Task 1 — Convergent-dogfood chain pattern: each iteration files its successor blocked-by its own follow-ups

**Decision:** Multi-phase command-spec validation against external APIs follows a **self-perpetuating dogfood chain**: round-N produces follow-ups, then files round-(N+1) `blockedBy` those follow-ups. The chain terminates when a walk surfaces zero blocking findings; otherwise it recurses. Pattern operationalized via Linear `blockedBy` relations + an explicit loop-closing step in each round-N issue's verification checklist.

**Confidence:** 7/10 (1st surface; promotion path: verify on BC-6308 round-3 → 8/10; arch-9 at 3rd instance with a 2nd command exercising it, e.g., `/marketing:tam-map` BC-6002 lifecycle)
**Category:** architecture
**Tags:** architecture, dogfood-chain, convergent-iteration, blocked-by-recursion, spec-reality-validation

**Why:**

- Single-shot dogfood walks chronically under-cover spec/reality gaps. Round-1 BC-5826 paper-walked Phases 3-11 after F13 surfaced and produced 12 frictions. Round-2 BC-5906 live-walked the same phases and produced 16 cross-cutting Sx findings + 17 of 18 F-row resolutions — a **~3x signal increase** (related precedent — see Task 2). The implication: a single round is structurally insufficient.
- The pattern that emerges naturally is iterative refinement: round-N → fixes → round-(N+1) → fixes → ... → convergence. Without explicit infrastructure (Linear `blockedBy` + loop-closing step), the chain breaks because nobody schedules round-(N+1) once the round-N follow-ups are filed.
- BC-6308 was filed as round-3 with all 9 round-2 follow-ups as `blockedBy` + an explicit verification-checklist item: "If round-3 surfaces blocking findings, file round-4 with same structure; if zero, mark Done as 'convergence achieved'." This makes the chain self-perpetuating — each round's verification step gates the next.
- The structural property: **dogfood iterations have a natural termination condition** (zero blocking findings) that bounds recursion. Unbounded loops aren't a risk; spec convergence terminates the chain.

**How to apply:**

- For any multi-phase command-spec validation against an external API (e.g., `/marketing:launch-campaign` against EB, future `/marketing:tam-map` against the TAM-construction MCPs):
  1. **Each round-N dogfood issue MUST include** a verification-checklist item titled "Loop-closing step (REQUIRED)" with the recursion rule: "If round-N produces blocking findings, file round-(N+1) with this issue's structure as template, `blockedBy` all newly-filed round-N follow-ups. If zero blocking findings, mark Done as 'convergence achieved'."
  2. **Round-(N+1) issue, when filed**, MUST list every round-N follow-up under `blockedBy`. This makes the dependency graph load-bearing: round-(N+1) cannot start until the round-N corrections actually land.
  3. **Hypothesis ID prefixing**: round-1 used F-prefix (F1-F32), round-2 used F-prefix continuation + Sx-prefix for cross-cutting findings (Sx-1 through Sx-16), round-3 should use R-prefix to distinguish without collision. Each round can reference its predecessors' IDs verbatim in the fix-validation rows.
  4. **Reuse inputs verbatim** from the previous round when possible (round-2 reused round-1's `test-leads.csv` + `test-copy.json`). This isolates the variable being tested (the spec, not the inputs) and reduces setup load for each iteration.
  5. **Augment inputs only when a follow-up adds a new dimension** (e.g., BC-6307 email-type segmentation requires augmenting the CSV with role-based addresses for round-3 to exercise that bucket).

**When NOT to apply:**

- Single-phase commands with no external API to validate against — paper-review is sufficient.
- Spec validation against synchronous, well-documented APIs (e.g., internal services with frozen contracts) — the surface area is too small for chain dynamics.
- Decision-only artifacts (ADRs, design docs) — the convergence concept doesn't apply; these get reviewed once.

**Promotion path forward:**

- 2nd surface → 8/10. Likely candidate: BC-6308 round-3 itself, when it walks. If round-3 produces non-zero findings, the loop-closing step fires and the pattern is confirmed at 2nd instance.
- 3rd surface → architecture-9 with structural lift to a `docs/precedents/README.md` or `docs/designs/` artifact codifying the pattern. Likely candidate: when `/marketing:tam-map` BC-6002 lifecycle dogfood runs (the only current 5-MVP issue with multi-phase external-API validation surface).
- Beyond architecture-9: candidate for a generalized `/cadence:dogfood-chain` workflow command that scaffolds round-(N+1) issues automatically from round-N's filed follow-ups + transcript.

**Evidence the prescription is load-bearing on this surface:**

- BC-5906 produced 16 Sx findings — significantly higher than round-1 BC-5826's 12 frictions. Without a round-3, those 16 corrections would land in production and ship without re-validation. BC-6308 closes that gap explicitly.
- The `blockedBy` relation (9 issues) makes dependency visible in Linear's project view. A reviewer of BC-6308 sees the 9-issue chain at a glance — the structural integrity isn't prose-only.
- BC-6306 (Urgent — production blocker) demonstrates that round-2 caught at least one finding that would have shipped silently to real customers. The chain concept ensures this class of finding gets caught BEFORE the launch event, not after.

## <a id="BC-5906-task-2"></a>Task 2 — Live-walk dogfoods produce ~3x the signal of paper-walks for external-API validation

**Decision:** When a command spec must be validated against an external API (Email Bison, Salesforce, etc.), prefer **live-walk** (actually executing mutations against a non-prod workspace) over **paper-walk** (reading the spec + API docs without execution). Live-walk surfaces field-name mismatches, default-value behaviors, render-time auto-prepends, architecture mismatches, and quirks that paper-walk structurally cannot detect.

**Confidence:** 7/10 (1st surface; promotion path: verify on BC-6308 round-3 — if round-3 again produces ~3x more findings than its paper-walk would have predicted, promote to 8/10)
**Category:** pattern-choice
**Tags:** pattern-choice, dogfood-methodology, live-walk, paper-walk, signal-ratio, external-api-validation

**Why:**

- BC-5826 round-1 paper-walked Phases 3-11 (after the F13 endpoint gap surfaced at Phase 10). 12 frictions caught in the paper-walk (F1, F2, F4, F5, F6, F7, F8, F9, F10, F11, F12, F13).
- BC-5906 round-2 live-walked the same phases. 16 cross-cutting Sx findings + 17 of 18 F-row resolutions = 33 distinct outcomes.
- Pure ratio comparison is imprecise (different denominators), but the structural classes round-2 caught that round-1 could not are the load-bearing point:
  - **Field-name mismatches** (Sx-6: `job_title` vs `title`, `company_name` vs `company`, no `company_domain`) — only surface when the API silently ignores them. Paper-walk treats spec field names as canon.
  - **Default-value behaviors** (Sx-15: `plain_text` defaults to `false`) — only surface when you actually create state and inspect it. Paper-walk lacks the inspection step.
  - **Render-time behaviors** (Sx-14: EB auto-prepends "Re:") — only surface in actual API responses to actual requests.
  - **Architecture mismatches** (Sx-9: extended-tier MCP "tools" not callable in-session) — only surface when you try to invoke them.
  - **API-spec-vs-API-behavior contradictions** (Sx-5: `last_name` marked required, accepted as null) — only surface when you intentionally violate the spec's stated constraint and observe behavior.
- Paper-walk caught structural issues (F13: no preview endpoint exists). Live-walk caught those PLUS the five classes above. The marginal value of live-walk is high.

**How to apply:**

- For any multi-phase command-spec validation:
  - **Always do paper-walk first** (cheap, scopes the live-walk, catches structural-blocker issues like F13 that would invalidate live execution).
  - **Schedule a live-walk follow-up** on a non-prod workspace BEFORE any production launch. Round-2 BC-5906-style is the canonical shape: explicit hypothesis list, per-phase verbatim evidence, batched follow-ups.
  - **Budget ~5 hours** for a 7-phase live-walk + transcript + cleanup + Linear follow-ups (BC-5906 took roughly that across 13 commits).
  - **Reuse round-1 inputs verbatim** when known-good. Round-2 BC-5906 reused round-1's 6-lead CSV + copy artifact, focused agent attention on hypothesis validation rather than input authoring.
  - **Batch follow-ups** into 5-7 focused issues, not 1-per-finding (~16 issues). User preference confirmed during BC-5906; reviewers get coherent units of work. (See Task 3 below for the calibration data point.)

**When NOT to apply:**

- Spec validation against fully-documented internal services with frozen contracts — paper-walk is sufficient; live-walk doesn't surface enough new signal to justify the workspace-state cost.
- Single-phase commands — the multi-phase interaction surface is what makes live-walk valuable.
- Spec changes that ONLY touch internal logic (no external API call shape changes) — paper-walk against the diff is sufficient.

**Calibration data:**

- Round-1 BC-5826 paper-walk: 12 frictions on a 7-phase command + 4 phases paper-walked.
- Round-2 BC-5906 live-walk: 16 Sx + 17 F-row resolutions = 33 outcomes on the same 7-phase command (Phases 3-9).
- Signal ratio: ~2.8x to 3x (depending on how you count partial-confirmations vs full-resolutions).
- Time cost: Round-1 was likely faster (paper-walk doesn't require API state setup/cleanup). Round-2 was ~5 hours including all 13 commits + transcript + cleanup + follow-ups. The marginal cost per additional finding is comparable to or better than other validation approaches.

**Promotion path forward:**

- 2nd surface → 8/10. Likely candidate: BC-6308 round-3 itself. The fix-validation hypotheses (R-1 through R-9) will produce a directly-comparable signal-ratio data point against the no-fix-validation paper-walk that the spec corrections went through.
- 3rd surface → architecture-9 with structural lift to `docs/designs/dogfood-methodology.md` or similar.

## <a id="BC-5906-task-3"></a>Task 3 — 4th-surface confirmation of plan-doc reconciliation-table at architecture-9

**Decision:** Plan documents for issues with stale body claims open with an issue↔ground-truth reconciliation table BEFORE the Tasks section. 4th-surface confirms the pattern is durable; no further promotion needed (already at architecture-9 per BC-2717 task-2).

**Confidence:** 9/10 (4th surface; pattern stays at architecture-9; this is durability evidence, not promotion)
**Category:** pattern-application
**Tags:** pattern-application, plan-doc-shape, amendments-table, fourth-surface, durability-evidence, bc-2717-extension

**Why:**

- Surface progression for "issue↔ground-truth amendments table at plan-doc top":
  - 1st surface: BC-5947 (2026-04-26) — registered at pattern-application 6/10
  - 2nd surface: BC-5832 (2026-04-26) — promoted to 7/10 with 5-column front-matter table format
  - 3rd surface: BC-2717 (2026-04-27) — promoted to architecture-9 with confirmation that the pattern is structural, not coincidental
  - 4th surface: BC-5906 (2026-04-27) — durability evidence
- BC-5906 plan opens with a 3-row reconciliation table:
  1. Issue body said "blocked by BC-5826/5904/5905"; ground truth: all three Done as of 2026-04-21.
  2. Issue body said "dogfood inputs at `.claude/worktrees/<branch>/dogfood/`"; ground truth: round-1 worktree was gitignored at commit time, inputs preserved post-merge to `docs/dogfood/bc-5826/` via PR #185.
  3. Issue body listed F22 as a hypothesis to validate; brainstorm decision deferred F22.
- Without the reconciliation table, the plan would have inherited 3 false premises and the dogfood walk would have either failed (trying to start blocked work) or wasted time (looking for inputs at a path that didn't exist).
- The 4 surfaces each had different drift classes: BC-5947 (policy/dependency landed after issue), BC-5832 (ADR resolution constraints), BC-2717 (amendment to the issue body's tasks), BC-5906 (blockers shipped + inputs relocated + brainstorm deferral). Pattern generalizes across drift classes.

**How to apply:**

- See BC-2717 task-2 + BC-5832 task-3 for the canonical operationalization. BC-5906 didn't refine the pattern; it confirmed durability at the 4th surface.
- Practical reminder: when plan-writing for any issue created >2 weeks ago OR with explicit blockers OR referencing path/file conventions that may have shifted, **start with the reconciliation table**. The cost is low (~3-row table); the benefit is preventing 3+ false premises from contaminating the plan.

**Why no further promotion:**

- Architecture-9 is already saturated for this pattern — the only path beyond is structural lift (e.g., a `writing-plans` skill rule that mandates the table when issue age exceeds a threshold). 4 surfaces is sufficient evidence that such a structural lift would be load-bearing; not yet shipped.
