## Task 1 — Foundation-vs-specific scope reframe + variable-agnostic spec teaching

**Date:** 2026-05-05
**Category:** scope-change
**Confidence:** 8/10
**Tags:** scope-reframe, foundation-vs-specific, variable-agnostic-spec, plan-gate, durable-vs-transitional

### Decision

When an issue body lists specific files/items to update but the operator reframes scope to "foundation, not specific content" — typically signaled by phrases like "X is hard-coded right now but won't be moving forward" — pivot the plan to durable inheritance points (skill skeletons, gates, anti-slop rules, vendor-fact references) rather than the listed files. Write spec rules variable-agnostically: teach the pattern, don't enumerate today's specific tokens. The reframe is project-level (per BC-6300 task-1 user-delegation scope) and only the operator can make it; surface it proactively when transitional architecture is mentioned.

For BC-6613: the issue body listed scope-item-1 ("high-risk variable types: recency anchors, proof points, friction signals, sender names, free asset nouns, vertical descriptors") and scope-item-2 ("minimum 3 production presets" with paths). Initial plan honored both literally. Operator pushback at brainstorm-end ("i dont want to overcomplicate or over rely on what variables are present right now. these could change. the goal is to put the foundation in place so that it functions across all campaigns we can run for the different verticals") triggered the reframe. Final plan: 5-layer foundation (skill teaches pattern, skill skeletons inherit, anti-slop allows Liquid output, gate accepts pattern, sanity checklist allows Liquid output, vendor-fact reference); preset bodies untouched (Holden's hand-coded scaffolds are transitional; future handbook-sync feature will replace them); one-line discoverability pointer per preset.

### Inputs

- Issue body scope item 1 enumerated 6 specific variable categories ("recency anchors, proof points, friction signals, sender names, free asset nouns, vertical descriptors")
- Issue body scope item 2 named 3 specific preset paths
- Operator pushback transcript (verbatim): "the vertical pages are hard coded right now but that wont be the way it is moving forward. i am curious why we are doing the liquid pattern for these? is this just for testing or is this like us getting them campaign ready?"

### Alternatives Considered

Anti-slop and sanity-checklist regexes tightened to allow Liquid output. Gate accepts Liquid as a 5th resolution path. Vendor-fact reference reproduces canonical patterns verbatim. Preset bodies untouched; one-line discoverability HTML comment per preset for future authors. Closes the BC-6308 R-2b failure class at every layer that touches campaigns.

## Task 2 — Review-time scope-expansion when tightening a file-wide rule

**Date:** 2026-05-05
**Category:** pattern-application
**Confidence:** 7/10
**Tags:** anti-slop, rule-tightening, review-time-scope-expansion, drift-class, grep-discoverable

### Decision

When tightening a load-bearing rule (regex, gate, validation predicate) that is REFERENCED OR RESTATED at multiple sites across the file beyond the primary anti-slop / spec section, plan-time grep should enumerate every site BEFORE execute. If the plan misses sites, REVIEW-time grep (parallel to BC-6298 task-1 / BC-6544 task-1 / BC-6548 task-2 plan-time scope-expansion) is the safety net. Without it, stale broad-rule mentions contradict the new tightened rule, and a faithful agent reading the rules would flag the new tightened-rule's ALLOWED cases as violations — undoing the entire fix.

For BC-6613: plan tasks 3 and 5 tightened the `{{` typo rule from "no `{{` anywhere" → `\{\{[A-Z_]+\}\}` (later `\{\{\s*[A-Z_]+\s*\}\}`) at the primary anti-slop bullet (SKILL.md:588) + sanity checklist (launch-campaign.md:223). Code-reviewer P1 (9/10) caught 5 ADDITIONAL sites in SKILL.md still enforcing the old broad rule: line 47 (gotcha bullet), line 448 (Flow 1 step 6), line 568 (Health rubric score 10), line 571 (Health rubric scores 1-3), line 608 (behavioral test). Without this catch, Skeleton A's `{{ recency }}` Liquid output would have self-flagged as a format violation.

### Inputs

- Plan task 3 implementation: tightened SKILL.md § Anti-Slop bullet (1 site)
- Plan task 5 implementation: tightened launch-campaign.md Phase 1 step 6 (1 site)
- Plan did NOT enumerate other file-wide sites referencing the old rule
- Code-reviewer review pass (9/10 confidence): grep for `{{` in SKILL.md surfaced 5 stale broad-rule mentions
- Each stale mention used different framing: "Never `{{firstname}}` either" (gotcha), "check for `{{`" (Flow), "no `{{`" (rubric), "`{{` double-brace present" (rubric), "zero `{{` tokens" (behavioral test) — required individual treatment, not blind regex replace

### Alternatives Considered

1. **Defer all 5 stale rules to follow-up issue** — REJECTED. Canonical Skeleton A's `{{ recency }}` would self-flag as a violation; agent self-correction would undo the BC-6613 fix at first invocation. Ship-blocking.
2. **Fix only the 2 highest-risk sites (gotcha + behavioral test)** — REJECTED. Rubric and Flow 1 sites would still teach the wrong rule to anyone reading them downstream — drift accumulates.
3. **Fix all 5 sites in same review-fix commit** *(chosen)* — Each site got tightened wording with the new regex AND an explicit "Liquid output `{{ var }}` is allowed and not a violation" carve-out callout. Plus an updated authoring guidance subsection in the new § Liquid + spintax for graceful per-lead fallback explaining lowercase Liquid local naming as the convention that keeps the regex unambiguous.

### Outcome

- **Files changed:** `email-copywriting/SKILL.md` (5 stale-rule sites + 1 anti-slop bullet rationale)
- **Validate.sh + check-guardrails.sh:** 0 errors / 0 violations throughout the fix-pass
- **Grep verification:** post-fix grep for orphan stale `{{` rules returns clean

## Task 3 — Spec rules need regex shape, not prose placeholders

**Date:** 2026-05-05
**Category:** pattern-choice
**Confidence:** 7/10
**Tags:** spec-authoring, regex-enforcement, prose-placeholder, gate-bypass, security

### Decision

Spec rules that gate runtime behavior on a constraint (e.g., "must be non-empty", "must be uppercase identifier", "must contain X but not Y") need a REGEX SHAPE the implementer can apply mechanically, not just a prose placeholder describing the intent. Without regex enforcement, the rule decays at implementation time to "the keyword is present" rather than "the constraint is met." Empty placeholders like `<non-empty-string>` communicate intent to readers but don't enforce against a careless author writing the empty case literally.

For BC-6613: initial gate path (a) at launch-campaign.md:218 was authored as: *"Wrapped in an `{% assign %}` block whose filter chain includes `default: '<non-empty-string>'`. Canonical: `{%- assign name = '{TOKEN}' | strip | default: 'fallback' -%}`."* Security-reviewer P2 (8/10) caught: an author writing `default: ''` (empty literal) would textually satisfy the gate (the `default:` keyword is present), but render empty for missing values — recreates the BC-6308 R-2b empty-render bug Liquid was meant to fix. Fix: tighten gate prose to mandate detection regex `default:\s*['"][^'"]+['"]` (the literal must contain at least one non-quote character).

### Inputs

- Initial path (a) prose used `<non-empty-string>` placeholder — communicates intent, doesn't enforce
- Security-reviewer empirical test: `default: ''` would textually satisfy the rule; renders empty
- Verified: prose placeholder is read by humans as "non-empty"; regex `default:\s*['"][^'"]+['"]` is read by mechanical implementers as "literal must contain ≥1 non-quote char"
- Same diagnostic surfaced for the typo regex (P2 #2): the prose claimed regex catches uppercase-with-or-without-spaces, but the actual regex `\{\{[A-Z_]+\}\}` only caught the unspaced form — prose-claim-vs-regex-shape mismatch in both directions

### Alternatives Considered

1. **Keep prose placeholder, add a sentence "must be non-empty"** — REJECTED. Same prose-not-regex problem; sentence is unambiguous to humans but doesn't add an enforceable check shape.
2. **Add a CSV / JSON validator at Phase 4 UPLOAD time** — DEFERRED. Closing the bypass is single-PR scope; designing a parser-aware validator is BC-6554-round-4-informed follow-up work.
3. **Tighten gate prose with explicit detection regex** *(chosen)* — Path (a) bullet now reads: *"Wrapped in an `{% assign %}` block whose filter chain includes a `default:` filter with a non-empty string literal. Gate detection regex: `default:\s*['"][^'"]+['"]` (the literal must contain at least one non-quote character; `default: ''` and `default: ""` do NOT satisfy this path)."* Same treatment applied to the typo regex tightening (`\{\{\s*[A-Z_]+\s*\}\}`) — closes the spaced-uppercase coverage gap.

### Outcome

- **Files changed:** `commands/launch-campaign.md` (path a regex tightening, 1 line); `commands/launch-campaign.md` + `email-copywriting/SKILL.md` + `tools/integrations/email-bison.md` (typo regex tightening at 9 sites total via replace_all)
- **Closes:** empty-default-bypass class + spaced-uppercase coverage gap
- **PR commit:** `0deb086` (P2 fixes)

Some prose placeholders (e.g., human-readable doc snippets, example captions) are intentionally non-mechanical. The promotion criterion specifically targets RUNTIME-GATING rules, not all prose.
