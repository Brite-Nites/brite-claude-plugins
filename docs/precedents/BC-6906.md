# BC-6906 — Production migration: tam-map secrets to `bw-run.sh` wrapper

## Issue
[BC-6906](https://linear.app/brite-nites/issue/BC-6906) — migrated 7 tam-map API keys from `~/.zshrc` exports to Bitwarden Engineering collection, fetched at every MCP/CLI process spawn by the production `plugins/marketing/scripts/bw-run.sh` (98 lines) + 11-case test suite (39 sub-assertions). Promotes BC-6905's spike POC. Establishes `bw-run.sh` as the canonical Brite plugin secret-config pattern in CONTRIBUTING.md (ADR-010 follow-up filed as BC-6958). PR: [#259](https://github.com/Brite-Nites/brite-claude-plugins/pull/259).

## Task 1 — Lifecycle-side rotation gap: `/reload-plugins` reloads plugin metadata only, does NOT re-spawn MCP server processes

| Field | Value |
|---|---|
| **Decision** | Document `/reload-plugins` as insufficient for credential rotation; the wrapper fetches per-spawn but stdio MCP server processes are session-persistent — rotation propagates only on full Claude Code re-launch (or per-server `claude mcp restart` if available) |
| **Category** | architecture |
| **Confidence** | 9/10 |
| **Precedent Referenced** | BC-6905 spike adapt-list item 3 ("Lifecycle-side rotation gap MUST be measured") + BC-6905 Q6 (wrapper-side rotation verified by SHA-pattern X→Y→X) |

**Inputs**
- docs/research/bw-run-spike.md § Q6 (wrapper-side PASS; lifecycle-side deferred)
- T14 manual smoke test execution (2026-05-10) — mutated `tam-map-spider-api-key` value (39→40 chars confirmed via `bw sync && bw get password ... | wc -c`); verified spider_get_credits tool call returned the original value with no auth error both before and after `/reload-plugins`

**Alternatives Considered**
1. **Chosen** — Document the gap honestly across CONTRIBUTING.md § Plugin secret-config canon, plugins/marketing/commands/setup-tam-map.md (frontmatter description + intro paragraph + closing message + Phase 3b troubleshooting branch), plugins/marketing/scripts/tam-map/README.md "Why the wrapper" section, and docs/designs/BC-6906-bw-run-prod-migration.md AC #11 row + Risks section. Frame remediation as "re-launch Claude Code from a shell where `BW_SESSION` is exported" — still cheaper than the pre-wrapper world (no `~/.zshrc` edits required).
2. Rejected — Reword AC #11 silently to "MCP re-spawn is sufficient WITH /reload-plugins" without measurement evidence. Loses honesty; future maintainer hits the gap and re-discovers it.
3. Rejected — Block ship until upstream Claude Code adds an MCP-re-spawn-on-credential-change hook. Out of scope; AC #10 (fresh-machine smoke) already passes; the rotation gap is documentable.
4. Rejected — Add `unset BW_SESSION; exec claude` self-relaunch logic to bw-run.sh on rotation detection. Violates the wrapper's documented non-goals (no caching, no token refresh, no retry).

**Outcome**
- Files changed: 4 (CONTRIBUTING.md, plugins/marketing/commands/setup-tam-map.md, plugins/marketing/scripts/tam-map/README.md, docs/designs/BC-6906-bw-run-prod-migration.md) — all rotation language softened to match measured reality.
- Tests: 0 added (T14 is a manual smoke; the wrapper-side guarantee is already covered by Test 6 BW_SESSION-unset path and Test 11 bad-arg-shape variants)
- Approved by: developer (T14 measurement run during /workflows:ship gate)

**Generalization**: any wrapper that resolves credentials at process spawn must distinguish two rotation-propagation classes — one-shot processes via Bash (spawn-per-call) vs long-lived MCP servers (spawn-once-per-session). For the latter class, the user-facing remediation is a session-relaunch, not a tool-call. Document in canon docs explicitly; don't let "vault is single source of truth" framing imply zero-touch propagation.

## Task 2 — Auto-detect longest common prefix for batch-fetch interface (4-constraint multi-anchor decision)

| Field | Value |
|---|---|
| **Decision** | Wrapper auto-detects the longest common prefix of item names; if ≥3 chars, runs ONE `bw list items --search <prefix>` round-trip + jq filter per item (BC-6905 Q3's 86% saving at N=7); if <3 chars (divergent naming), falls back to per-item `bw get password` |
| **Category** | pattern-choice |
| **Confidence** | 8/10 |
| **Precedent Referenced** | BC-6905 adapt-list item 1 ("Wrapper interface MUST batch via `bw list items --search`") |

**Inputs**
- BC-6906 issue body's prescribed call-site shape (`.mcp.json` examples use bare `KEY=item` form, no `--prefix` flag visible)
- BC-6906 acceptance criteria #1 (4 mandated test cases including "divergent naming" — must be a meaningful test, not a tautology)
- CONTRIBUTING.md canon framing (predictable, safe-by-default, fast)
- BC-6905 Q3 measurement (3.21s constant time for batch; 86% saving at N=7)

**Alternatives Considered**
1. **Chosen** — Auto-detect LCP, fallback to sequential when prefix < 3 chars. Wins on all 4 hard constraints simultaneously: (a) matches issue's prescribed `.mcp.json` call-site shape verbatim (no new flag); (b) makes the "divergent naming" mandated test meaningful (exercises real fallback path); (c) fits canon framing (predictable + safe-by-default + delivers 86% saving in prevailing case); (d) contains privacy spread (only items matching common prefix in wrapper memory, not entire vault).
2. Rejected — Explicit `--prefix <p>` flag. Caller-error class (forgetting the flag silently pays sequential cost in production). Edits the issue's prescribed `.mcp.json` shape across 3 MCPs + multiple skill call sites. Test 4 ("divergent naming") under one prefix is semantically incoherent.
3. Rejected — Always batch via `bw list items` (no `--search` filter). Constant time, simplest, but fetches the entire user-accessible vault per spawn. Privacy concern: wrapper memory holds names of every vault item the user has access to (not just plugin-domain). Test 4 passes for the wrong reason (tautology).

**Outcome**
- Files changed: plugins/marketing/scripts/bw-run.sh (LCP function ~10 lines + branch on threshold)
- Tests: 39/39 PASS, including Test 3 (multi-key batch verifies 1 list call) and Test 4 (divergent naming verifies sequential fallback)
- Approved by: developer (after sequential-thinking analysis presenting the 4-constraint table)

**Generalization**: when an issue's call-site shape is prescriptive AND a test case names a behavior that needs to be exercised, the design choice that makes BOTH true is preferred over alternatives that satisfy one at the other's expense. Multi-constraint convergence is a stronger signal than single-anchor reasoning.

## Task 3 — Single-adopter canon ownership at plugin path with explicit N=2 promotion path

| Field | Value |
|---|---|
| **Decision** | Keep `bw-run.sh` at `plugins/marketing/scripts/bw-run.sh` until a second plugin actually adopts; document in CONTRIBUTING.md "Authority and scope" paragraph that promotion to repo-level `scripts/bw-run.sh` happens at N=2; resist premature extraction |
| **Category** | architecture |
| **Confidence** | 8/10 |
| **Precedent Referenced** | architecture-reviewer P2 [conf 7] flagged cross-plugin canon under marketing namespace + V5 validator confirmed but DOWNGRADED A-F1 ("copy or symlink") to P3 as premature for single-adopter |

**Inputs**
- BC-6906 review § A-F2 (CONTRIBUTING.md § Plugin secret-config canon scope inconsistency: script under one plugin, framing repo-wide)
- BC-6906 review § A-F1 (copy/symlink adoption pattern creates duplicated SoT) — V5 validator marked premature for current single-adopter state
- BC-6906 review § A-F3 (ADR-010 warranted) — V5 validator confirmed BUT recommended filing as follow-up issue rather than authoring in this PR

**Alternatives Considered**
1. **Chosen** — Add "Authority and scope" paragraph to CONTRIBUTING.md canon section explicitly framing the marketing-plugin copy as canonical-until-N=2. On second adoption, promote to repo-level `scripts/bw-run.sh` and have each plugin reference via thin shim. File ADR-010 as follow-up (BC-6958) rather than blocking this PR. Resists premature canon extraction (validator's "premature for single-adopter" framing).
2. Rejected — Extract `bw-run.sh` to repo-level `scripts/` in this PR. Premature for single adopter; risks pre-committing to a structure (`${CLAUDE_PLUGIN_ROOT}/../../scripts/bw-run.sh`) before knowing whether revops/cadence even want the same wrapper shape. Also forces verification of `${CLAUDE_PLUGIN_ROOT}/../../...` resolution in installed-plugin (non-monorepo) layout, which is out of BC-6906 scope.
3. Rejected — Defer the canon framing entirely; ship as a marketing-only utility without claiming repo-wide applicability. Loses the documentation value (future plugins re-litigate the same pattern); the canon's actual reach is measurably broader than marketing.
4. Rejected — Author ADR-010 in this PR alongside the migration. V5 validator explicitly recommended NOT — would balloon review surface unnecessarily; ratifying ADR for a single-adopter canon is the right shape AFTER a second adopter exists, not before.

**Outcome**
- Files changed: CONTRIBUTING.md (added "Authority and scope" paragraph + N=2 promotion guidance to step 2 of "Adopt in a new plugin")
- Tests: N/A (architectural framing)
- Approved by: developer (V5 architecture-reviewer validator output, then applied as part of round 1 P2 fixes)
- Follow-up: BC-6958 (Author ADR-010 — Plugin secret-config canon)

**Generalization**: canon-establishment work for a single adopter should explicitly frame the canonical state as transitional, name the trigger for promotion (e.g., N=2 adopters), and resist premature repo-level extraction. The framing is durable; the location is not. Cross-cite the trigger condition in both the canon doc AND the script's home directory so the next contributor reaches the same decision the same way.

## Task 4 — Pure-bash test framework over bats-core: 5-anchor convergence under repo's anti-dependency rule

| Field | Value |
|---|---|
| **Decision** | Use pure-bash assertions with PATH-mocked `bw` stub for `bw-run.test.sh` (single self-contained file, no new test-runner dep); reject bats-core and self-test-flag alternatives |
| **Category** | pattern-choice |
| **Confidence** | 7/10 |
| **Precedent Referenced** | BC-6905 spike scripts (measure.sh, exercise-q4.sh, exercise-rotation.sh, verify-q7.sh — all pure-bash with inline assertions) + MEMORY.md "No PyYAML in test scripts" anti-dep rule |

**Inputs**
- BC-6906 issue spec naming `plugins/marketing/scripts/bw-run.test.sh` (singular file)
- MEMORY.md anti-dep rule: "Repo has no dependencies — embedded Python must use stdlib only"
- BC-6905 spike POC test driver script idiom (pure-bash with `assert_eq`-style inline checks)
- CONTRIBUTING.md canon adoption checklist requirement: future plugins copy `bw-run.test.sh` mirroring the marketing-plugin shape (canon must be self-contained)

**Alternatives Considered**
1. **Chosen** — Pure-bash with PATH-mocked stub via `mktemp -d`. Five anchors all align: (a) issue spec literalism (one file); (b) repo's anti-dep rule (no new test runner); (c) BC-6905 spike continuity (same idiom); (d) canon self-containment (other plugins copy without third-party install); (e) failure-mode pricing (bats' TAP value scales with test count, marginal at 5 cases). Mitigation for plain failure output: `assert_eq <actual> <expected> <name>` helper prints `FAIL [name]: expected X, got Y` plus fail-count summary at exit.
2. Rejected — bats-core test runner. Better TAP output, structured `@test` blocks, but requires `brew install bats-core` on dev machines + CI step. First test-runner dep in the repo. Canon copy-paste no longer self-contained for adopters.
3. Rejected — Self-test inside `bw-run.sh` (`--self-test` flag). Single file, no separate test file. Deviates from issue spec's named target (`bw-run.test.sh`) and conflates test code with production wrapper.

**Outcome**
- Files changed: plugins/marketing/scripts/bw-run.test.sh (NEW, 191 lines, 11 cases, 39 sub-assertions)
- Tests: 39/39 PASS at completion (started at 18/18 spec-mandated, doubled after review-driven additions)
- Approved by: developer (after sequential-thinking analysis presenting the 5-anchor table)

**Generalization**: when a repo has codified an anti-dependency rule for test scripts, extending that rule into adjacent test surfaces (here: bash test for a bash wrapper) preserves canon self-containment for adopters. The "industry-standard framework" argument loses to "canon must be copy-paste-able" when the script is positioned as cross-plugin canon.
