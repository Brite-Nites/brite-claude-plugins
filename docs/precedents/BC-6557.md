## Task 1 — Phantom-fork validation at engine level before deferring features to v2

**Date:** 2026-05-04
**Category:** scope-decision
**Confidence:** 7/10
**Tags:** plan-gate, scope-decision, sequential-thinking, engine-cost, phantom-fork, research-design

### Decision

When a design discussion offers a "ship simple first, expand later" framing, trace the actual engine code for both the simple and expanded options before accepting the narrowing. If the engine code is identical or near-identical (the difference is documentation, schema, or author UX rather than core logic), the fork is **phantom** — scope it all in v1 because deferring buys nothing. If the engine code genuinely differs, the fork is real and the narrowing decision becomes a real tradeoff to weigh.

For BC-6557: user asked "ship simple substitution first, add variable-referencing later, or scope it all now?" Engine-level trace showed simple substitution = `if raw is null: return formula.if_missing` and variable-referencing = `if raw is null: return render_string(formula.if_missing, lead, campaign)`. The diff is one function call to a render engine that already exists (it renders the template body). ~5 lines of code difference. Scoping it all in v1 added zero engine complexity and one rule (no-cascading) to keep the recursion problem out. The narrowing path would have shipped the same engine with a documentation choice.

### Inputs

- User question: "would it make sense to just do simple substitution for now and then add in the variable referencing later on or should we just scope it all out now?"
- User explicit ask for sequential-thinking pass to validate the proposal before commit
- Engine-level pseudocode trace for both options (in sequential-thinking thought 5):
  - Simple: `rendered = formula.if_missing` (literal string)
  - With var-ref: `rendered = render_engine.substitute(formula.if_missing, lead, campaign)`
- Recognition that `render_engine.substitute()` is the same function used to render the template body — already exists, no new dependency
- Cost analysis: ~5 lines of code, no new abstractions, no new failure modes (with the no-cascading rule)
- Discovery that the recursion concern (which would have argued for narrowing) is sidestepped by a constraint, not by limiting the verb set

### Alternatives Considered

1. **Ship simple first, defer variable-referencing to v2** *(rejected — phantom fork)* — would have shipped the same engine with a doc note saying "if_missing is a literal string." v2 would have changed the doc note to "if_missing is a literal string OR a template-token-bearing string" and added the render engine call. Same engine code, different docs. Pure documentation deferral with no code-cost reason.
2. **Recursive evaluation from day one** *(rejected for v1)* — would require cycle detection in the engine, which IS a real engine-level cost (~tens of lines + a test surface). The no-cascading rule sidesteps this without forfeiting variable-referencing. Real fork; deferred legitimately.
3. **Scope it all in v1** *(chosen)* — variable-referencing in v1, no-cascading rule prevents recursion concern, engine cost is the same as the narrow option. v2 can lift the no-cascading rule if real authoring patterns demand recursion.
