## task-1 — 2nd surface of BC-6959 task-1 (rebase + bump-to-main_version+1); cascade catches

<a id="BC-6977-task-1"></a>

**Decision:** Rebase + version-bump math fires **twice** in a single session under high parallel-PR velocity — once via in-flow review (caught BC-6975 #296 → 0.2.12), once via independent post-PR reviewer (caught BC-6975 #297 → 0.2.14). Both rebases bumped to `main_version + 1` per the BC-6959 task-1 recipe; final landed version is `0.2.15`.

**Category:** pattern-application

**Confidence:** 10/10

**Inputs:**
- Iter-1 code-reviewer flagged P1 version collision: main at 0.2.12 (BC-6975 #296 merged ~hours before this branch); branch at 0.2.12 → bumped to 0.2.13 + rebased onto `b2d94a5`.
- Independent post-PR reviewer (round 1) flagged P1 version collision: main at 0.2.14 (BC-6975 follow-up #297 landed during the in-flow review loop); branch at 0.2.13 → bumped to 0.2.15 + rebased onto `96f93a2`.
- Independent post-PR reviewer (round 2) returned `CLEAR TO MERGE 10/10` against `1889ae6` parent.
- `gh pr view 298 --json mergeStateStatus` returned `CLEAN` post-rebase.

**Alternatives Considered:**
1. **Apply BC-6959 task-1 recipe twice (chosen)** — both rebases used the locked recipe `git fetch origin main; git rebase origin/main; resolve version-line conflicts to main_version+1; force-push`. Reason: the recipe is correct at both surfaces; cascade is a property of parallel-PR velocity, not a recipe flaw.
2. Run a single rebase after the independent reviewer flagged the second collision — rejected because the in-flow review loop ran for ~30 min between the two PRs landing; the first rebase + bump was load-bearing for the in-flow loop's correctness (subsequent fold-ins assumed version 0.2.13).
3. Use a moving-target version (e.g., `0.2.99`) to avoid collision — rejected; non-monotonic version sequences break the BC-6000 plugin-cache contract.

**Outcome:**
- Files changed: `plugins/flow-architecture/.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json` (both bumped twice during session: 0.2.11 → 0.2.13 → 0.2.15 net change)
- Tests: validate.sh 0 errors at both rebase points
- Approved by: independent reviewer round-2 (CLEAR TO MERGE 10/10)
- **Promotes BC-6959 task-1 to load-bearing at 2nd surface** — the recipe held at both consecutive cascade points within one session.
- **Force-push friction (workaround documented):** `git push --force-with-lease` is blocked by the destructive-command security hook even though `--force-with-lease` is safer than `--force`. Workaround: user runs the push via `!` prefix in the terminal. Same pattern as BC-6000's `git push -u origin <branch>` workaround, but the destructive-flag check now extends to `--force-with-lease`. Cheap to fix at the hook level; track as a separate plugin-level issue rather than re-litigating per-session. **(Superseded by BC-11889, workflows v3.31.0 — `--force-with-lease` now passes the regex on all branches; the `!` escape hatch is no longer needed for this command.)**

## task-2 — 7th surface of BC-6965 task-5 (review-loop convergence); fast convergence at small LOC

<a id="BC-6977-task-2"></a>

**Decision:** `/workflows:review` "loop until clean" converged in **4 iterations** on a 301-line markdown-spec PR — same iteration count as BC-6959 task-2's 1500+ LOC observation, demonstrating the 4-iter floor is LOC-independent at the spec-heavy scale.

**Category:** pattern-application

**Confidence:** 9/10

**Inputs:**
- Iter 1: 2 P1, 8 P2, 9 P3 — primarily real bugs (parallel-PR drift, broken Step 8 `list_issues` filters per `gotcha_linear_list_issues_*_filter.md`).
- Iter 2: 0 P1, 3 P2 (`$base_branch` subprocess scoping, stale "below" → "above" pointer, error-recovery scope ambiguity), 10 P3 — fold-in self-introduced defects (BC-6959 task-2 pattern confirmed).
- Iter 3: 0 P1, 1 P2 (cache-pointer first-read), 2 P3 (regex wording, example date) from code-reviewer; **security/performance/CDR all CONVERGED 0/0/0** (3 of 4 reviewers converged at iter-3, not iter-4).
- Iter 4: **all 4 reviewers CONVERGED 0/0/0**.

**Alternatives Considered:**
1. **Run all 4 reviewers each iteration (chosen)** — even after 3 of 4 converged at iter-3, dispatched all 4 at iter-4 because iter-3 code-fixes touched lines 34, 45, 153 which are mid-file regions adjacent to security-validated content. Reason: BC-6959 task-2's "iter-N fold-in self-introduces" warning is structural — converged reviewers may flag new issues if adjacent text changes.
2. Skip iter-4 once 3 of 4 converge at iter-3 — rejected; would have missed the verification-of-convergence signal. Cheap insurance.
3. Treat user's "loop until nothing comes back" as 1-iter max — rejected per BC-6965 task-5 (iter-1 leaves 6+ P2 unresolved).

**Outcome:**
- 27 total findings across iter-1 (19) + iter-2 (13) + iter-3 (3) + iter-4 (0); folded 23, dismissed 4 (reviewer-marked no-action or contradicting Q53 lock).
- 4 iterations converged in measurable bounded-resource budget (~5-7 min agent dispatch per iter; ~25 min total).
- Tests: validate.sh 0 errors across all fix-fold amends.
- Approved by: iter-4 returned CONVERGED on all 4 reviewers (verbatim "CONVERGED — no findings").
- **Extends BC-6959 task-2 finding:** the 4-iter floor is not LOC-gated. Spec-heavy markdown PRs at any size (301 LOC here, 1500+ LOC at BC-6959) hit the same convergence trajectory.

## task-3 — 2nd surface of BC-6959 task-3 (independent reviewer post-PR); fires reliably under parallel-PR velocity

<a id="BC-6977-task-3"></a>

**Decision:** Dispatch one independent reviewer with **completely fresh context** post-PR-creation. Catches stale-branch / version-conflict / parallel-PR-drift that the in-flow `/workflows:review` loop is structurally blind to. This session is the **2nd surface of BC-6959 task-3** — fires reliably under parallel-PR velocity and is now load-bearing as the canonical post-PR gate.

**Category:** pattern-application

**Confidence:** 10/10

**Inputs:**
- In-flow `/workflows:review` (4 iters) ran against `git diff origin/main...HEAD` cached at iter-1 — saw BC-6975 #296 (0.2.12) but NOT #297 (0.2.14) because the iter-1 fetch happened before #297 landed.
- Independent reviewer round-1 ran `git fetch origin main` from scratch — caught: (a) version delta 0.2.13 (PR) vs 0.2.14 (main); (b) `b2d94a5` (in-flow base) → `96f93a2` (current main) drift.
- Independent reviewer round-2 (post-rebase) ran `gh pr view 298 --json baseRefOid,mergeable` — verified `MERGEABLE / CLEAN` against `96f93a28220cb38bbe8d033ea59c196eab845304`.
- Without the independent reviewer, merge would have created non-monotonic version sequence: main 0.2.14 → merged 0.2.13 (silent plugin-cache downgrade per BC-6000).

**Alternatives Considered:**
1. **Independent fresh-context reviewer mandatory post-PR (chosen)** — the in-flow loop cannot see post-iter-1 state drift. Reason: this session demonstrates the gate firing twice (the in-flow loop caught the first collision, the independent reviewer caught the second one that landed AFTER the in-flow loop's iter-1 fetch). Without both, merge would have downgraded the plugin.
2. Re-run `/workflows:review` with `git fetch` between iters — rejected per BC-6959 task-3 reasoning; re-fetching changes the diff under each iter's feet and breaks the iter-N fold-in convergence model.
3. Trust the in-flow loop and merge — proven wrong twice in 2 sessions; promotes to "never trust in-flow loop alone".

**Outcome:**
- Files changed: 0 from the reviewer-finding itself (the finding triggered the second rebase, not a code fix).
- HOLD verdict (round 1) → CLEAR TO MERGE verdict (round 2 post-rebase).
- Final merge state: `1889ae6` on main, plugin 0.2.15, BC-6977 auto-flipped to Done via Linear's GitHub integration.
- **Promotes BC-6959 task-3 to load-bearing at 2nd consecutive surface.** The independent reviewer gate is now a required post-PR step, not optional.

**Precedent Referenced:**
- [BC-6959 task-3](BC-6959.md#BC-6959-task-3) — Originating case (1st surface); this is the 2nd consecutive surface.
- BC-6965 PR-flow precedent — similar gate on a smaller diff; caught no parallel-PR drift but established the pattern.
