## Decision

Third-of-N Phase 2 RevOps orchestration command (`/revops:post-deploy-runbook`) inherits the BC-5790+5791 6-phase template and adapts it for a **zero-mutation walkthrough** of manual post-deploy steps. Five BC-5792-specific departures declared upfront in plan §Departures: (1) zero `sf` CLI mutations (command narrates user actions), (2) no `--target-org` pin (org-agnostic — user already deployed), (3) **dynamic phase enablement** via Phase 1 diff-based detection flags, (4) **3-way gate** (Completed / Skip / Need help) replacing sibling 2-way Yes/No, (5) Phase 6 Skip-follow-up synthesis. Two additional post-fix departures documented: **deny-`__c` Kanban detection** (any non-custom object, not an 8-object allowlist) and **batched grep** (N→1 subprocess reduction in Phase 1.3 + Phase 4.1).

Two review cycles ran. Pass 1 (pre-ship): 0 P1, 3 CONFIRMED P2s fixed, 1 P2 dismissed. Pass 2 (post-ship re-review per BC-5866): caught a factual SF error pass 1 missed — `Setup → Apex Jobs → Scheduled Jobs` is not a parent-child path, those are **sibling** Setup pages under `Environment → Jobs`. BC-5866's "reviewer's lens shifts post-verdict" class precedent is now three sessions deep.

## Key alternatives considered

1. **Brainstorm before planning** — Session-start complexity criteria flagged Phase 1 diff-based detection as a "new mechanic." Dismissed: issue body is fully specified (6 phases with exact UI paths + anonymous Apex template); BC-5790+5791 lock frontmatter + Rules contract; any genuine design choice collapses to mechanical regex-pattern selection. Proceeded direct to planning, accepting the two narrow design points (no-op clean fast-exit per T5; Skip surfaces as narrated follow-up, no Linear mutation — preserves `allowed-tools: Bash, AskUserQuestion` template) inline.
2. **Single 2-way gate per phase** (Completed / Skip) vs 3-way (add Need help) — Chose 3-way because post-deploy steps are manual and user-error-prone; extended guidance on Need help saves a "what do I click" round-trip. Trade-off: 3-way adds a repeat-loop mechanic the siblings don't have. Accepted; Rules block now owns the "Need help is a repeat, not an advance" invariant (rule 7).
3. **`commands/_shared/sfdx-cwd-preflight.md` extraction** (simplify-agent F1 conf 7, both passes) — Dismissed both times. Three copies across Phase 2 siblings is the tipping point per BC-5866 "rename/extract on second adopter" precedent, but: (a) `commands/_shared/` would be a new convention in this repo (prior `_shared/` precedent is `skills/_shared/` under cadence plugin, not `commands/_shared/`), (b) the 14-line block is readable inline, (c) markdown `_shared/*.md` indirection is LLM-interpretation overhead, not compile-time dedup. **Sub-rule:** the "rename/extract on second adopter" precedent applies only within a plugin's established convention space — cross-convention extractions (first `commands/_shared/` ever) deserve a dedicated issue, not a review-cycle auto-fix.
4. **Custom-range free-text shell injection (security-reviewer P2, pass 1 and pass 2)** — Dismissed both cycles by Sonnet validator with the same reasoning: the "interpolate verbatim" is LLM-runtime prose directive, not raw shell concatenation. The LLM is the quoting layer when it constructs the Bash call from the markdown instruction. Halt-on-nonzero exit in Phase 1.3 prevents any injected chain from reaching Phase 2+. No `eval "$INPUT"` sink exists. Consistent dismissal on a repeated finding is itself a durable outcome — the threat model is a false-analogy class that future reviewers will keep raising; document here so the dismissal isn't re-litigated cycle after cycle.
5. **Consolidate 3-way gate contract into Rules** (code-reuse F3 conf 7) — Deferred as suggestion. BC-5866's "per-section marker beats per-call marker" precedent pushes toward explicit per-site ownership of gate semantics; hoisting the entire 3-way contract to Rules would remove the per-gate anchoring that BC-5866 ratified. Kept inline; future `_shared/` extraction (if ever) can revisit.

## Rule derived

**For third-of-N template-inheriting commands, run the full review cycle twice — pre-ship and post-ship — even when pass 1 comes back green.** BC-5866 established this pattern for the cadence plugin; BC-5792 reinforces it for Phase 2 RevOps commands. Three cumulative datapoints now: BC-5866 pass 2 caught a fenced-reminder asymmetry bug; BC-5792 pass 2 caught a factual SF Setup UI breadcrumb error (wrong in 3 places). Pass 1's verdict changes what pass 2 agents look for — the lens genuinely shifts. Empirically ~3–6 real fixes per post-ship re-review on Phase 2 work.

**Sub-rules captured:**

1. **SF UI breadcrumb factual checks belong in the review-agent prompt** — the pass 1 cdr-compliance agent verified the `brite-salesforce/CLAUDE.md` §Apex & Automation citations were accurate, but did not verify the Lightning Setup navigation shape. Pass 2 code-reviewer prompt included "any remaining factual errors in SF-specific guidance (Setup UI paths, SOQL queries, `sf` CLI usage)?" — that one phrase unlocked the catch. Carry this into the BC-5806 SessionStart-hook and BC-5927/5928/5931 skill customizations since they all cite Setup UI paths.
2. **Validator-dismissed findings stay dismissed on repeat passes when the threat model is stable** — the custom-range "interpolate verbatim" P2 dismissal reasoning is identical pass-to-pass. Document once (here), cite in subsequent cycles rather than re-argue.
3. **Pass 2 simplify still earns tokens when pass 1 fixes introduce micro-regressions** — pass-1 edits can contradict surrounding prose in ways pass 1 can't see in its own diff (Phase 3.1 narration edit-artifact). Schedule pass 2 for third-of-N+ commands regardless of pass 1 outcome.
4. **`grep -c` acceptance thresholds use `≥ N` floor, not `= N`** — frontmatter + hoisted directives inflate line counts beyond the gate count. Specify floors in plans, not exact values.
5. **Cross-convention `_shared/` extractions deserve dedicated issues, not review-cycle auto-fixes** — the "rename/extract on second/third adopter" BC-5866 precedent applies within an established `skills/_shared/` or equivalent; introducing `commands/_shared/` for the first time is an architectural decision with its own issue lifecycle.

## How to apply

- **When:** any third-of-N+ template-inheriting command in the Phase 2 RevOps or cadence families. Also applies to Phase 3 skill siblings (BC-5927/5928/5931) where each shares template contract with the now-ratified BC-5798.
- **Review shape:** thorough mode twice — pre-ship (`/workflows:review`) and post-ship (`/workflows:review` again after first cycle's fixes land). 4 agents per pass (code + security + performance + cdr-compliance). Per-finding Opus for P1 + Sonnet for P2/P3. Pass 2 prompt must include an "already resolved — do NOT re-flag" list drawn from pass 1's fix log.
- **Zero-mutation command pattern:** when a command narrates user-performed actions rather than issuing CLI calls, declare mutating phases = 0 explicitly in Rules block (bullet 1), document org-agnosticism (bullet 5), and keep `allowed-tools: Bash, AskUserQuestion` — no Linear mutation tools even for Skip-follow-up tracking; the user creates Linear issues manually if needed. Preserves the BC-5790/5791 Phase 2 template contract.
- **Diff-based conditional phase enablement:** use Phase 1 to set N boolean flags from `git diff --name-only` classification; each later phase opens with `*(conditional on <flag>)*` in its title and returns early if the flag is false. Phase 6 reports any flag-false phase as `N/A — not detected` — that's the only site `N/A` narration appears.
- **3-way gate Need-help pattern:** hoist "If Need help: print guidance, re-ask" as a standalone directive **after** the options list, not inside the option label. Rules block owns "Need help is a repeat, not an advance" as a global invariant (rule 7). Per-gate guidance blocks stay inline because they're phase-specific.
