# BC-5924: Service-user permission audit methodology for a plugin-consumed MCP

**Date:** 2026-04-22
**Category:** pattern-choice
**Confidence:** 7/10

## Decision

For auditing a service user's blast radius against a plugin-consumed MCP (Salesforce here; same shape applies to any future service-credential-backed integration):

1. **Run read-only SOQL via the direct CLI (`sf data query --target-org <alias>`) from the cross-repo (`brite-salesforce`), not via the plugin MCP.** Four queries — User identity, PermissionSetAssignment, PermissionSet (high-risk flags), ObjectPermissions — cover the baseline.
2. **Land the audit output as a dedicated section in the plugin's integration doc** (`plugins/marketing/tools/integrations/salesforce.md` → `## Service User Permissions`), with five subsections: identity, current permset assignments, object-level effective-access matrix, destructive capabilities, minimum-required-per-consumer matrix.
3. **End the section with a re-runnable `### Audit methodology` footer** listing the four SOQL queries verbatim with `<placeholder>` tokens, so Part B and quarterly refreshes re-execute without re-discovering the queries.
4. **Sensitive identifiers stay as placeholders** (service-user email, service-user SF ID) per the existing §Auth Bitwarden convention. Permset names, object names, and profile names are OK in source — they match the exposure level the rest of the doc already uses.
5. **Update `## Last verified` with a new dated paragraph** naming the audit + linking the follow-up tightening issue; don't replace the prior paragraph — audit trail over tidy.

## Context

`@salesforce/mcp` has no server-side read-only mode, row limits, or destructive-tool gates. Blast radius is entirely a function of the service user's profile + permset assignments. The plugin's `--toolsets data` scoping is false comfort if the user has `Modify All Data` — any future cross-toolset tool enable would inherit unbounded powers. This is true for every service-credential-backed MCP, not just Salesforce.

The audit can technically run via the plugin MCP's `run_soql_query`, but in practice three frictions push toward direct CLI:

- The MCP's `usernameOrAlias` parameter rejects aliases and the `DEFAULT_TARGET_ORG` sentinel (see §Outcome gotcha — only the literal username works).
- MCP startup-time org resolution can lag behind `sf config set target-org` changes until `/reload-plugins`.
- Permset / ObjectPermissions queries are admin-read operations — running them from the repo (`brite-salesforce`) that owns the admin alias keeps auth context aligned with the thing being audited.

## Alternatives Considered

1. **Audit via the plugin MCP only.** Rejected — hit the `usernameOrAlias` trap mid-session, plus the MCP's cache sometimes diverges from `sf config`. Direct CLI is simpler and portable to Part B's destructive deploy path anyway.
2. **Audit output as a standalone `docs/audits/BC-5924-permission-baseline.md`.** Rejected — integration-specific audits belong next to the integration contract (§Auth, §Registration, §Tool inventory). Pulls up every time a skill author reads the doc; external audit file would be out-of-mind.
3. **Compact 40-line section (no re-runnable methodology footer).** Rejected — the issue's 40-line estimate missed Part B's needs. A 90-line section with methodology at the end lets Part B re-execute mechanically and saves a future session from re-deriving the SOQL. Worth the 50 extra lines.
4. **Commit the service-user email + SF ID inline for clarity.** Rejected — breaks §Auth's placeholder convention, telegraphs tenant identity on a repo leak. Bitwarden reference preserves the convention and the identifiers are one lookup away.
5. **Do the audit + the tightening in one issue (original BC-5785 shape).** Pre-decided by the 2026-04-21 rescope (`docs/plans/revops-milestone-rescope-plan.md`). The audit-only half (this issue) is single-repo read-only; the tightening half (BC-5925) is cross-repo destructive — different blast radius, different ship cadence.

## Outcome

Delivered `plugins/marketing/tools/integrations/salesforce.md` § Service User Permissions (+92 lines in two commits), `docs/plans/BC-5924-plan.md` (audit plan file). `validate.sh` 0 errors / 16 warnings (baseline preserved); `check-guardrails` 0 violations. `/workflows:review` diff-triage: TRIVIAL (pure markdown docs, 0 runtime code) — Steps 3–7 skipped correctly. Orchestrator spot-checks (sensitive-data leak, markdown link/anchor resolution, Linear issue existence) caught no issues. Shipped as [PR #178](https://github.com/Brite-Nites/brite-claude-plugins/pull/178).

**Finding, documented in source:** service user `marketingadmin@britenites.com` is on `System Administrator` profile with 6 permsets including `Automation_Validation_Bypass`. Minimum required per planned skills: `Api Enabled` + Read on 11 objects. Tightening tracked in [BC-5925](https://linear.app/brite-nites/issue/BC-5925/) — Part B now has concrete findings to act on.

**Session-discovered gotcha** (captured as `## Known gotchas` bullet in-PR, also memory entry): the plugin MCP `run_soql_query` `usernameOrAlias` parameter requires the literal username, not the alias (`marketing-claude-prod`) or `DEFAULT_TARGET_ORG` sentinel, despite `--orgs DEFAULT_TARGET_ORG` working at server startup. Cost me 2–3 failed MCP calls mid-session before I pivoted to passing the literal username; the gotcha bullet should save future skill authors the same detour.

**Reusable beyond this case.** The audit-methodology shape applies to any future service-credential-backed MCP integration Brite adds — most near-term, any new Salesforce service user (e.g., a hypothetical read-only analytics service user), and any Email Bison workspace audit if EB gains a comparable "what can this token do?" introspection surface. The five-subsection template (identity, permset assignments, effective access, destructive capabilities, minimum-required-per-consumer) transfers; the re-runnable methodology footer transfers; the sensitive-identifier placeholder convention transfers.

**Secondary observation.** The original issue body estimated "~40 lines" for the section. Actual shipped: ~90. The overrun came from adding the re-runnable methodology footer (~15 lines) + the minimum-required-per-skill matrix's 5 rows with SOQL citations (~10 lines more than estimated). Both additions earn their length — one directly enables Part B, the other surfaces the gap width. Estimate was a useful anchor, not a budget to respect.

**Tertiary observation.** The `sf org display --verbose` command exposes a live access token in stdout. Benign in a short-lived dev session but worth knowing — if adopted in any scripted flow, redirect stderr/stdout to a file with mode 600 (or use `--json` + jq for the two fields actually needed). Not memory-worthy as a standalone gotcha, but mentioned here so future service-credential audits that run the same command don't accidentally log the token into CI output.

**Precedent Referenced:** none directly. Complements but does not reference BC-5793 (first-of-N template lock) — this is a first-of-kind audit pattern, not a template application. If a second service-credential audit ships against this template (likely candidate: a read-only SF analytics user, or an EB-workspace audit if EB adds introspection), that sibling should cite this file as the precedent it's validating.
