## Task 1 — Dogfood-artifact handling: template files reflect current truth; evidence files reflect historical truth

**Date:** 2026-04-29
**Category:** pattern-choice
**Confidence:** 8/10
**Tags:** pattern-choice, dogfood-artifacts, evidence-preservation, template-vs-evidence, asymmetric-update

### Decision

When a spec-drift fix invalidates the input shape used in a prior dogfood walk, dogfood `test-copy.json` artifacts split into two classes that get **opposite** treatments:

1. **Production-template artifacts** (e.g., `docs/dogfood/bc-5826/test-copy.json` — the X17 first-walk template, generic and reusable) → **fix in lockstep with the spec.** These are forward-facing recipes the next walk grabs from. Leaving the broken pattern propagates the bug.
2. **Round-evidence artifacts** (e.g., `docs/dogfood/bc-5906/test-copy.json` — the round-2 input that surfaced Sx-14) → **keep verbatim.** These are backward-facing receipts cited by the round's transcript (`docs/dogfood/bc-5906/round-2-transcript.md` § Spec-vs-reality findings). Editing them retroactively erases the evidence chain and prevents reproducing what was tested.

The principle: production-template files reflect *current* truth; evidence files reflect *historical* truth. Same asymmetry as not amending git commits after they're in the public record.

### Inputs

- BC-6301 plan-gate Q2 surfaced 3 options: fix both, fix one, fix neither
- `docs/dogfood/bc-5906/round-2-transcript.md` cites the bc-5906/test-copy.json content as "the malformed input we sent" — round-3 (BC-6308) re-walk will reference it
- `docs/dogfood/bc-5826/test-copy.json` predates BC-5906 and has been used as a generic template across the round-2 chain
- User restated the principle in own words during plan-gate: bc-5826 is "the outline we use for future dogfooding" while bc-5906 is "the results from the dogfooting and how we determined what was going wrong"

### Alternatives Considered

1. **Fix bc-5826, keep bc-5906 verbatim** *(chosen)* — preserves both directions of truth: the template is correct for the next walk; the evidence chain is intact for retro audit. Asymmetry matches the file's role.
2. **Fix both** — rejected. Erases the round-2 evidence chain. Anyone reading round-2-transcript.md afterward sees a citation to a file whose contents no longer match what was actually tested.
3. **Fix neither** — rejected. bc-5826 would drift from the corrected spec immediately. Anyone copying the production-template file inherits the bug we just fixed.

### Outcome

- **Files changed:** `docs/dogfood/bc-5826/test-copy.json` step_2.subject de-prefixed; `docs/dogfood/bc-5906/test-copy.json` untouched
- **Tests:** JSON validity confirmed via `python3 -c "import json; json.load(...)"` post-edit
- **Approved by:** user (explicit confirmation after walkthrough of the asymmetry)

### Precedent Referenced

None in `docs/precedents/INDEX.md` for the dogfood-artifact asymmetry rule itself — first-time precedent. Conceptually adjacent: BC-5870 task-2 (verification-side-effects — don't absorb fixes into verifier's PR) shares the "preserve evidence trails" principle but applies to PR-scope hygiene rather than artifact-class semantics.

### Promotion candidate

1st instance for the *file-class asymmetry* framing. 2nd-instance candidate triggers when any future spec-fix invalidates a prior dogfood input AND the surrounding dogfood directory contains both template and evidence files. Likely surfaces during BC-6308 round-3 dogfood (if round-3 evidence files exist when a future spec-drift correction happens) or any cross-vertical preset migration that touches multiple dogfood directories. At 2nd instance, consider promotion to a `docs/conventions.md` entry or handbook section on dogfood-driven workflows.

## Task 2 — 5x pattern-match → skip brainstorm via objective complexity criteria

**Date:** 2026-04-29
**Category:** scope-change
**Confidence:** 7/10
**Tags:** scope-change, brainstorm-skip, pattern-match, objective-complexity, inner-loop-discipline

### Decision

When the inner-loop complexity check (session-start Step 5) hits a 5th application of the same proven pattern, log the skip-brainstorm decision explicitly with the pattern-match count as the criterion — don't re-explore alternatives that have been ruled out 4 times. For BC-6301, brainstorming was skipped with reasoning: *"5th application of 'spec drift → reverse rule + sweep refs + update canonical reference' (BC-6298/6299/6300/6306). EB API behavior is determinative — no design alternatives."*

The pattern-match-skip rule supplements the standard 4-criterion complexity check (multi-module, 4+ tasks, 2+ approaches, new pattern) — it's a 5th informal criterion: *"Nth application of an established pattern (N >= 3) where the API/spec contract is determinative."*

### Inputs

- EB API contract (boolean variant, auto-Re: prepend) determines the fix shape — no design alternatives
- Standard complexity criteria all signal "skip brainstorm": single-approach, 6 tasks (within plan-only-without-brainstorm threshold), no new patterns/integrations
- Inner-loop spec (`commands/session-start.md` Step 5) does NOT codify pattern-match as an explicit criterion; the decision is judgment-call territory

### Alternatives Considered

1. **Skip brainstorm + log pattern-match reasoning explicitly** *(chosen)* — fastest path to plan, honors the proven pattern's track record, and the explicit log preserves auditability. Future operators reading the trace can see *why* brainstorming was skipped, not just that it was.
2. **Brainstorm anyway because the criterion isn't codified** — rejected as performative. The 4 prior ships ruled out the same alternatives the brainstorm would re-explore (test-now vs defer, scope expansion to adjacent EB gotchas, etc.). Repeating the exercise at the 5th instance is sunk-cost theater.
3. **Add the pattern-match criterion to session-start.md as a 5th codified rule** — considered but deferred. Session-start.md is project-level config (per `feedback_user_delegation_scope`, not in the user's delegation scope to amend mid-execution). The `/workflows:promote-precedent` path or a Holden-led inner-loop spec review is the right venue for that codification — not this session.
