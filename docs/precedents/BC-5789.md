# BC-5789: Per-item audit at filter time can rescue items the locked plan would have lost

**Date:** 2026-04-20
**Category:** pattern-choice
**Confidence:** 9/10

## Decision

When a plugin's master plan locks a "delete this batch of N items" filter, the implementing session should still walk each candidate individually at filter time rather than executing the batch deletion. The audit can preserve the locked decisions almost entirely while surfacing items worth a follow-up evaluation that the batch framing hides. Surface a follow-up Linear issue for any rescued items so they get a fair second look without expanding the current PR's scope.

## Context

BC-5789 imported Jaganpro/sf-skills (36 skills + 7 agents) via `git subtree`. The locked master plan §3.5 + ADR-007 §3.5 said: keep 13 customizable + 1 deferred + delete 22 skills + delete all 7 agents. The delete list was treated as one bulk decision — `rm -rf` of 6 globs + the entire `agents/` dir.

When the user requested an item-by-item audit at filter time, walking 29 individual decisions confirmed all 22 skill deletions on the same rationale the plan already named. But for the 7 agents, the per-item walk surfaced 3 candidates whose skill dependencies were ENTIRELY OR MOSTLY KEEP skills — `fde-release-engineer` (sf-deploy + sf-connected-apps), `ps-solution-architect` (sf-metadata + sf-flow + sf-permissions + sf-testing + sf-diagram-mermaid), `ps-technical-architect` (8 KEEP skills). The "delete all 7 agents" framing hid these because it was based on "they're consulting personas" — not on whether each agent's underlying toolkit survived the filter.

Without per-item audit, BC-5789 would have deleted 3 viable agents that have no obvious replacement in Brite's stack. Cherry-picking from the pinned subtree commit (`ff1ab74`) is possible but adds friction.

## Alternatives Considered

1. **Honor the batch deletion as written, ship faster.** Rejected: the "delete all 7 agents" framing was sound when filed but lost specificity. Three deletions would have been wrong-by-default and required cherry-pick recovery later.
2. **Re-open the plan and revise §3.5 / §7 Issue 1.2 before executing.** Rejected: the plan is correct in scope (filter rationale per skill family is right). The opportunity is in the implementation moment, not the plan.
3. **Walk each candidate individually at filter time, file a follow-up issue for rescued items (chosen).** Preserves the plan's locked deletions, surfaces edge cases without re-opening planning, and routes salvageable work to its own scoped issue (BC-5820) where the porting question can get the design attention it needs without bloating the scaffold PR.

## Outcome

29 individual delete decisions made. 22 skill deletions confirmed (all on the rationale the plan already named). 4 agents deleted as planned. 3 agents deleted with cherry-pick path documented + follow-up issue BC-5820 filed under RevOps milestone (Low priority, Backlog) for porting evaluation against Brite's existing agent infrastructure. Net: BC-5789 ships exactly as scoped; the 3 rescued agents get their own honest evaluation in BC-5820.

**Reusable beyond this case.** Any future plugin import via subtree (or any "filter a batch of N items" decision) should default to per-item audit at execution time when the items have heterogeneous downstream dependencies. The audit is cheap (~5–10 min for 29 items with prior context) and the cost of missing a salvageable item is high (cherry-pick friction + design context loss).

**Strengthens** `feedback_thorough_audits` by adding the specific finding that per-item audits can rescue items the batch framing hides — not just produce more thorough categorization.

**Precedent Referenced:** none (new pattern)
