## BC-6784 task-1 — Live-vs-archaeological spec-value check before executing follow-ups

**Confidence:** 8/10

**Category:** pattern-choice (review-validation discipline)

**Tags:** follow-up-discipline, archaeology-check, spec-value, busywork-prevention, BC-6780-extension

**Decision:** Before executing a Linear follow-up's spec, run a 30-second "live-vs-archaeological" check on the target. If the primary action is editing a closed Linear issue body, a completed transcript, or any historical doc, the future-protective value is usually near zero and the right move is closing with a comment rather than executing the edit. If the target is a live spec, runtime config, or production artifact future agents/operators read, execute. For ambiguous targets, surface the question once and let the user decide.

**Why:** This session, BC-6783's spec said "edit BC-6554's S-9 row to match BC-6306 implementation scope." I executed without checking whether the edit would actually protect anything. The closed issue body got slightly more accurate; future agents and operators were unaffected because the operational truth (only `plain_text` is PATCHed) was already correct in the live spec, the canonical reference doc, the BC-6306 precedent, and the round-4 transcript. The edit was archaeology — fixing a typo in a closed history book that nobody re-reads.

User pushed back ("what did editing an old linear issue do to help with the future?") and the honest answer was: nothing. Same root cause as BC-6780 task-1 vocabulary-capture pattern (rubber-stamping agent findings without independent validation), just at a different surface — rubber-stamping issue specs without spec-value validation. Both have the same fix shape: pause + check + ask.

BC-6784 itself passed the check cleanly — target is live `launch-campaign.md` and `email-bison.md`, future agents and operators read both. Execution was correct.

**How to apply:** When picking up a follow-up, before opening a worktree or making edits, ask: "what live artifact does this protect?" Live spec / runtime config / reference doc → execute. Closed Linear issue body / completed transcript / archived precedent → likely archaeology; surface to user with one targeted sentence: "this would edit a closed history record; close with a comment instead?" Trigger threshold: any follow-up whose primary action is body-editing a closed/done Linear issue, or modifying `docs/dogfood/`, `docs/precedents/`, or `round-N-transcript` files.

This complements feedback_question_spec_value.md (memory rule, soft mechanism). Promotion to a workflow-command pre-check or CLAUDE.md gotcha would be the harder mechanism but requires a separate project-level decision.

**Precedent referenced:** BC-6780 task-1 (orchestrator must independently re-trace runtime when review agents echo own design vocabulary back), BC-5830 task-2 / BC-5953 task-2 (false-analogy class). Same root failure (failing to validate before executing); different surface (spec value vs finding accuracy). 2nd-instance pattern; promotion-eligible if 3rd surface emerges.
