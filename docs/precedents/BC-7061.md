## task-2 — Preflight as hard gate vs case-counter pollution (novel-pattern; 1st surface)

<a id="BC-7061-task-2"></a>

**Decision:** When a single set of counter helpers (`pass`/`fail`/`skip`) is called from two semantically distinct levels — preflight (was the fixture authored correctly?) AND case-sweep (does the SUT classify correctly?) — the summary stats conflate the two and the developer-facing total lies. Resolution: promote preflight from advisory (counter-incrementing) to hard gate (`[OK]`/`[FAIL]` plain-print + `exit 1` on FAIL). The case-counter then reflects only the SUT-correctness signal, which is the primary contract.

**Category:** bug-resolution

**Confidence:** 9/10

**Inputs:**
- BC-7061 initial implementation (commit `bf36eee`) called `pass()` / `fail()` from both (a) 2 preflight checks (`>= 14 cases`, schema-field presence) and (b) 15 per-case classifier checks. The shared `$PASS` counter produced `PASS: 17` in the auto-generated report for a 15-case fixture. The per-mode TP matrix correctly summed 15, but the report Summary line was misleading.
- Bug surfaced by the /workflows:review simplify-pass code-quality agent (conf 9). The fix landed in commit `3621f94`.
- Worse: preflight `fail()` only incremented `$FAIL` and let the case sweep continue against a malformed fixture, producing confused downstream output. A fixture with 12 cases or missing required fields would still attempt classification, then produce a mix of PASS/FAIL/DRIFT that obscured the root cause.

**Alternatives Considered:**
1. **Promote preflight to hard gate; drop counter helpers there (chosen)** — `printf '  [OK] ...'` for pass, `printf '  [FAIL] ...' >&2; exit 1` for fail. Counter helpers (`pass`/`fail`/`skip`/`drift`) become case-sweep-only. Summary line semantics: PASS = case-correctness-pass.
2. **Add separate `preflight_pass()` / `preflight_fail()` helpers that print but don't increment** — rejected. Preserves dual-signal cleanly but leaves preflight as advisory; a malformed fixture would still progress to a confused case sweep.
3. **Track preflight + case counters separately and display both in the summary** — rejected. More info-dense report but doesn't fix the root issue (advisory preflight against malformed fixtures is bad UX).
4. **Reset `PASS=0; FAIL=0` after preflight before case sweep** — rejected. Mutation-at-a-distance pattern; future maintainers wouldn't see the reset and would misattribute counter values.

**Outcome:**
- File changed: `plugins/flow-architecture/tests/run-mode-classifier-eval.sh` (preflight section refactored).
- Summary line now accurately reflects case-sweep results: `15 pass / 0 fail / 0 drift / 4 skip` (later `20 pass` after case fan-out).
- **Reusable pattern:** in any harness where preflight checks have a fundamentally different semantic than case-level checks (fixture-author validation vs SUT correctness), preflight should hard-exit on fail rather than share a counter namespace with the case sweep.
- Specifically applicable to: `run-audit-smoke.sh` (BC-7059 — its preflight at Section 1 currently uses the same `pass()`/`fail()`; same potential conflation, just hasn't surfaced because all hard-gate checks happen to be clean today).
- Documented in inline comments at the harness preflight section so future contributors see the rationale without needing the precedent trace.

**Precedent Referenced:**
- None — first surface of this specific pattern. Related but distinct: BC-7059 task-2 (literal-string-in-source AC anchor) is a different drift-detection pattern operating on emitted result IDs rather than counter semantics.

## task-3 — Schema preflight as TSV-stream contract enforcer (pattern-application; 1st surface, generalizes BC-7059 task-2 framing)

<a id="BC-7061-task-3"></a>

**Decision:** When a harness packs structured data through a delimited stream (TSV / NSV / single-character) consumed by a parser that assumes the delimiter never appears in payload, validate that contract at fixture-authoring time in the preflight schema check. Reject any case whose payload columns contain the forbidden delimiter character(s) with a per-case diagnostic. Replaces "happens to be clean today" with an enforced invariant; future fixture additions surface contract violations as loud preflight failures instead of silent mid-field corruption.

**Category:** pattern-application

**Confidence:** 8/10

**Inputs:**
- BC-7061 harness emits per-case TSV from a python3 generator (4 columns: `id`, `expected_mode`, `description`, `compact-json`) consumed by bash `while IFS=$'\t' read -r case_id expected description case_json`. The 2nd-pass code-reviewer (conf 7) flagged: "if a future fixture author adds a literal `\t` or `\n` inside a description, bash `read -r` silently splits mid-field and corrupts the trailing `case_json` column."
- All 20 current descriptions verified clean — the failure mode is hypothetical for now. The reviewer's recommendation: "either escape description via json.dumps OR drop description from TSV and look up by id in the report-gen." Both options are heavier than enforcing the contract at preflight.
- Generalizes BC-7059 task-2's framing: BC-7059 used a literal-string-in-source AC anchor + runtime bucket to catch drift in *emitted-result-ID space*. BC-7061 task-3 uses preflight schema validation to catch drift in *fixture-author payload space* before the case sweep runs.

**Alternatives Considered:**
1. **Reject `\t`/`\n` in id/description via preflight schema check (chosen)** — minimal touch (15 LOC in the existing preflight python3 heredoc); per-case diagnostic format `{id}:tsv-unsafe-{field}`; converts the implicit contract into an explicit one. Future maintainers see the rule + reason inline.
2. **Escape description via `json.dumps(description)` in the generator + `json.loads()` in the consumer side** — rejected. Adds parse cost per case (15 `json.loads` for the description column); makes the bash-side string handling less direct (`description` would need stripping of JSON quotes before use in `fail()` messages).
3. **Drop description from the TSV; look up by `id` via `desc_by_id` in report-gen only** — rejected. Loses the developer-facing FAIL diagnostic message (`fail "MC-08: expected='incremental-add' actual='retrofit' — full FDA + breadcrumb status=completed → ..."`). Without the description in the bash FAIL line, the developer has to cross-reference the fixture to interpret a failure.
4. **Use a Record-Separator delimiter `\x1e` instead of `\t`** — rejected. Bash `IFS=$'\x1e'` works but the harness output becomes less readable in console debug runs (control chars echo as raw bytes).

**Outcome:**
- File changed: `plugins/flow-architecture/tests/run-mode-classifier-eval.sh` (preflight schema check augmented).
- New diagnostic surface: `[FAIL] schema violations: {id}:tsv-unsafe-{field}` exits 1 before any classification runs.
- Reviewer-cluster verdict on the fix: code-reviewer 3rd-pass returned 0/0/0 "Clean — ship"; test-quality 3rd-pass: "meta-test: the fixture validates itself"; security 3rd-pass: "strictly narrowing validator, no new attack surface, defensive belt only — confidence 9/10."
- **Reusable pattern:** any harness that packs structured data through a delimited stream (TSV, NSV, semicolon-delimited, etc.) can replicate the preflight-validates-contract approach. Specifically applicable to: future eval-harness siblings that emit multi-column streams; any context-skill that builds CSV/TSV output and consumes it later in the same pipeline.

**Precedent Referenced:**
- [BC-7059 task-2](BC-7059.md#BC-7059-task-2) — literal-string-in-source AC anchor as drift-detection bucket. BC-7061 task-3 generalizes the framing: BC-7059 catches drift in *emitted-output-ID space* (runtime bucket); BC-7061 catches drift in *fixture-author-payload space* (preflight schema). Same "schema-as-contract" discipline, different surface.

**Tags:** pattern-application, schema-enforcement, tsv-stream-contract, preflight-validation, contract-enforcer, BC-7059-task-2-generalized
