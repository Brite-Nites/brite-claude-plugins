# BC-12347 — `.forceignore` pre-flight: bash case quoting silences glob patterns

<a id="BC-12347-task-1"></a>

## Task 1 — Bash `case` pattern quoting: `*"$pat"*` vs `*$pat*`

**Date:** 2026-06-25
**Category:** bug-resolution
**Confidence:** 9/10
**Precedent Referenced:** independent review receipt (docs/guides/independent-review-receipt.md)
**Tags:** bash, case-pattern, glob-quoting, forceignore, review-receipt

### Decision

When matching file paths against patterns read from a config file (`.forceignore`,
`.gitignore`, fnmatch-style inputs), **use unquoted `$pat` in bash `case`
patterns**: `case "$fpath" in *$pat*)`, not `case "$fpath" in *"$pat"*)`.

Double-quoting `$pat` in a `case` pattern suppresses glob expansion: `*`, `?`,
and `[...]` inside the quoted expansion are treated as literal characters, not
wildcards. This is correct for substring matching of known-safe strings, but
wrong when the variable comes from a file that uses glob syntax — as `.forceignore`
files do. Patterns like `prompts/*`, `**/namedCredentials/**`, and
`*.namedCredential-meta.xml` all contain `*`; double-quoted, they never match.

### Inputs

- BC-12347 added a `.forceignore` pre-flight to `/revops:deploy-prod` and
  `/revops:deploy-sandbox`. The pre-flight reads `.forceignore` line by line and
  checks whether each diff path matches any pattern.
- The matching loop used `case "$fpath" in *"$pat"*) hit=1 ;; esac`.
- The bug: `prompts/*` in `.forceignore` — explicitly named in BC-12347's issue
  body as a known brite-salesforce pattern — was treated as the literal string
  `prompts/*` (asterisk = literal). A file like
  `force-app/main/default/prompts/MyPrompt.prompt-meta.xml` never matched.
- The pre-flight would silently exit `FORCEIGNORE_BLOCKED=0`, proceed to deploy,
  and let `sf project deploy start` silently drop the prompts file — the exact
  failure mode the guard was introduced to prevent.
- Neither the author nor `validate.sh` caught this. It was caught by a cold
  independent reviewer using the review-receipt pattern (PR #494).

### Fix

Remove the double quotes around `$pat` in both case statements:

```bash
# Before (broken — glob chars literal)
case "$fpath" in *"$pat"*) hit=1 ;; esac

# After (correct — glob chars expand)
case "$fpath" in *$pat*) hit=1 ;; esac
```

In bash `case` patterns, `**` collapses to `*` (bash doesn't support double-star
depth matching in case), which is correct for Salesforce `.forceignore` semantics:
`**/namedCredentials/**` becomes effectively `*namedCredentials/*` and still
matches the full path.

### Alternatives Considered

1. **Unquote `$pat`, outer `*` wraps** *(chosen)* — `*$pat*` — glob chars in
   the pattern expand; leading/trailing `*` ensure prefix/suffix paths also
   match. Simple, no extra code.
2. **Use Python/awk fnmatch** — Accurate glob semantics (including `**` depth),
   but adds a subprocess per path per pattern. Overkill for a pre-flight that
   runs at most a few dozen comparisons.
3. **Maintain a separate literal-path list** — Only check against known-literal
   patterns from `.forceignore`. Fragile: breaks whenever brite-salesforce adds
   a new glob-style entry.

### Why durable

The quoting distinction (`*"$pat"*` = literal vs `*$pat*` = glob) is
counter-intuitive because double-quoting is the safe default in bash for
everything *except* case patterns used as wildcards. Any time a bash pre-flight
reads patterns from an external file and uses them in `case` matching, this
gotcha applies. It is invisible to `set -x` traces (both forms look the same in
output) and won't be caught by standard shell linters.

The independent review receipt pattern — a structured cold-reader handoff with
named dimensions and a machine-readable verdict — is what surfaced this. The
author had been heads-down on the logic and seeded the hard question in the
handoff prompt; the independent reader confirmed it in one pass.
