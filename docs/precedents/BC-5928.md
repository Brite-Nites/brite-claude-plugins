## Task 1 — Mechanical ports have a factual-correctness surface that simplify catches but brainstorm/plan cannot; trust ≥6/10 simplify findings on factual claims

**Category:** pattern-choice
**Confidence:** 7/10
**Tags:** pattern-choice, mechanical-port, factual-drift, simplify-pass, fact-verification, claim-grounding

### Decision

When porting cross-repo rules into a new skill body, the **rule statement** lives wherever the source CLAUDE.md says it does — but the underlying **factual claim** may be a paraphrase that introduces drift. The brainstorm and plan gates cannot catch this because they evaluate scope and shape, not correctness. The simplify pass — specifically the **code-quality** simplify agent — is the right discovery surface for factual drift in mechanical ports. **Trust ≥6/10 confidence findings on factual claims, not just ≥7/10.**

**Specific instance this session.** Plan rule #7 for sf-lwc said: *"Apex methods exposed with `@AuraEnabled(cacheable=true)` enforce CRUD/FLS through the calling user's profile + permission sets."* This is **wrong**. The annotation runs Apex in the calling user's session — so user-level access checks apply — but the annotation itself does NOT enforce CRUD/FLS on DML or SOQL. Enforcement comes from `with sharing` on the class, `WITH SECURITY_ENFORCED` on SOQL, or `Security.stripInaccessible` / `Schema.DescribeFieldResult` on DML. The plan paraphrased `brite-salesforce/CLAUDE.md` line 201 (`with sharing` does NOT restrict User queries) and conflated it with @AuraEnabled semantics from general Apex security knowledge.

The simplify code-quality agent flagged this at **6/10 confidence** with the rephrase as a suggestion. Below the conf-7 simplify-fix threshold I would have applied automatically. But because the finding was a **factual error** (not a wording preference), I treated it as actionable, hand-validated against Salesforce's actual `@AuraEnabled` semantics, and applied the fix during the simplify auto-fix pass before launching the review agents.

The downstream review agents (security-reviewer in particular) confirmed the corrected wording was sound, and validated that the SOQL-vs-DML guidance was correctly separated.

### Alternatives considered

1. **Apply only ≥7/10 simplify findings; defer 6/10 to review-agent fix loop** — Standard threshold. **Rejected for this case.** The 6/10 finding was a factual claim, not a wording preference; deferring would have shipped the wrong fact in the first commit and required a follow-up review-fix commit. Cleaner to fix during simplify when the fact is fresh.

2. **File the factual-error finding as a P2/P3 in Step 5 review classification, not Step 3 simplify auto-fix** — Treat as substantive review finding. **Rejected.** The simplify pass spec says "behavior-preserving improvements only," and a factual correction does change behavior (Claude would now suggest different security primitives). But the spirit of "behavior-preserving" is "doesn't break tests, doesn't change runtime semantics" — for SKILL.md content, "behavior" is "what guidance Claude delivers," and correcting a wrong fact is a behavior **fix**, not a behavior **change**. Simplify pass was the right gate.

3. **Trust the plan as written and ship the wrong fact, fix in a follow-up PR** — Iterative refinement. **Rejected.** Wrong facts in skill bodies have outsized blast radius — every SF-adjacent session that triggers sf-lwc would receive misleading security guidance. The cost of a follow-up PR vs an in-line fix is asymmetric here.

### Rule derived

**Mechanical ports of cross-repo rules have a factual-correctness surface distinct from scope and shape. The brainstorm and plan gates cannot catch factual drift because they evaluate scope and shape, not claims. The simplify code-quality pass IS the right gate, and 6/10 findings on factual claims should be treated as actionable, not deferred.**

Procedure:

1. **In simplify pass**, distinguish "wording preference" (defer if conf <7) from "factual claim" (apply if conf ≥6 and ground-truth-verifiable).
2. **Ground-truth-verify** the factual claim before applying — don't just trust the agent. For Salesforce Apex semantics: check Salesforce platform docs or grep canonical examples in the source repo (e.g., `brite-salesforce/force-app/main/default/classes/`).
3. **Apply the fix during simplify**, before review agents launch — review agents see the corrected version, not the wrong one.
4. **Commit message** should call out the factual correction explicitly so the PR reviewer understands it's a content fix, not just polish.

### Promotion note

First instance of "simplify catches factual drift in mechanical port" as a named pattern. If a second mechanical port surfaces the same dynamic (simplify code-quality agent flags a paraphrased fact at conf 6-7), promote to architecture-8. The factual-correctness surface is conceptually adjacent to BC-5946 task-3 ("integration-guide claims must grep against wrapper source, not author memory") — both are claim-grounding patterns. Watch for the third instance to promote a unified "claim-grounding" architecture-9 rule.

## Task 2 — BC-6000 rule operationalized cleanly on second post-rule PR; no execute-time re-discovery needed

**Category:** pattern-choice
**Confidence:** 6/10
**Tags:** pattern-choice, bc-6000-operationalization, rule-maturation, plan-completeness, mechanical-port

### Decision

The BC-6000 same-commit version-bump rule landed on 2026-04-23. The first post-rule PR (BC-5927, 2026-04-24) **discovered the rule's relevance at execute-time** — I had to amend the plan mid-session when the worktree CLAUDE.md surfaced the gotcha during a `Read` call. BC-5927 task-2 captured this as "execute-time CLAUDE.md re-read is a discovery surface distinct from brainstorm."

This session (BC-5928, 2026-04-26) is the **second** post-rule PR touching `plugins/<plugin>/skills/**`. The plan written in Step 6 included the version bump from the start (revops `0.2.0 → 0.2.1`, called out in Design Decision #7), with no execute-time discovery needed. The rule was applied as if it had always been there.

**This confirms BC-6000 has reached operational maturity** — the rule no longer needs execute-time re-discovery; it's now part of the standing checklist for any PR touching plugin source.

### Alternatives considered

1. **File no precedent for this; the rule is just being followed** — Skip filing. **Considered but rejected.** The transition from "rule needs execute-time discovery" (BC-5927) to "rule is operationalized in plan" (BC-5928) is itself a useful precedent for future rule-maturation cycles — it gives a concrete data point on how many PRs a new rule takes to bed in.

2. **Promote to architecture-7 immediately** — Treat as a generalizable rule-maturation pattern. **Rejected.** One data point (BC-6000 took 1 post-rule PR to operationalize) doesn't generalize. Wait for a second rule-maturation cycle on a different rule before promoting.

### Rule derived

**A rule's operational maturity can be measured by counting post-rule PRs until the rule no longer surfaces as execute-time discovery.** BC-6000 took 1 post-rule PR (BC-5927) before becoming a planning-time checklist item (BC-5928). This is a fast bedding-in cycle and suggests the rule was well-scoped.

Loose corollary for future rule landings: if a rule is still surfacing as execute-time discovery 3+ post-rule PRs after landing, the rule may need clearer wording, a hook, or a checklist promotion.

### Promotion note

Thin observation. Confidence 6/10 because the data point is real but the rule derived isn't strongly generalizable yet. File as pattern-choice, not architecture. If a second rule-landing+maturation cycle generates the same N=1 → N=2 pattern, promote to architecture-7 with a "rule operational maturity counter" rule.
