## Task 1 — Diff-triage TRIVIAL underweights reasoning-heavy doc artifacts; thorough mode catches load-bearing errors that triage's surface heuristics miss

**Category:** pattern-choice
**Confidence:** 7/10
**Tags:** pattern-choice, diff-triage, reasoning-artifacts, adr-review, thorough-mode-override

### Decision

The diff-triage agent ruled BC-5786 **TRIVIAL** — "267 lines of pure documentation, no code, no logic, no API changes." Per spec the verdict skips Steps 3–7 (simplify + review agents + validation + fix loop). I honored the verdict and produced an abbreviated Step 8 report, but flagged the concern that recent doc-only sessions (BC-5806, BC-5831, BC-5901, BC-5931, BC-6052) all ran thorough review and reliably surfaced 1–3 P3 stylistic findings + 0 P1/P2.

User overrode → "yeah please run the thorough review." Re-run produced **2 P2 + 10 P3 confirmed findings**, including a P2 citation error: ADR-009 cited "BC-5534 ADR 2" twice when the correct reference is "BC-5534 Q2 (Non-GA gating)." That's not a stylistic miss — "ADR 2" in Brite-land already refers to a different document (`outbound-agent-architecture-adrs.md` § ADR 2a/2c, cross-referenced from inside BC-5534 itself at line 42). A reader chasing the citation would land on the wrong doc.

Triage's heuristic ("no code → trivial") doesn't model **reasoning weight**. An ADR is dense with cross-references, claims, and decisions — the artifact IS the reasoning. A line-count + file-type check can't distinguish a load-bearing decision document from a README typo fix.

### Alternatives considered

1. **Honor triage verdict, ship abbreviated** — Initial choice. Spec-compliant. Would have shipped a P2 citation error to a freshly-published company decision record. Cost of error: future readers cite the wrong source; framework's authority erodes.

2. **Run thorough review on user request, fix all confirmed** — Chosen after override. 12 of 12 confirmed findings fixed in same PR. ADR shipped clean.

3. **Amend triage agent to recognize ADR/precedent/framework artifacts** — Deferred. Would require a content-aware classifier (path heuristic `docs/decisions/**` is the obvious starting point but doesn't catch e.g. `docs/research/*.md` or `docs/designs/*.md`). Worth filing as follow-up if pattern recurs.

### Rule derived

**Diff-triage TRIVIAL is unsafe for reasoning-heavy artifacts** (ADRs, decision frameworks, research findings, design docs, precedent traces). When the diff is composed primarily of files under `docs/decisions/`, `docs/research/`, `docs/designs/`, or `docs/precedents/`, default to thorough review even when triage votes trivial — the artifact's value comes from precise claims and cross-references that automated heuristics can't grade.

This sibling-extends BC-5806 task-1's "small files have non-trivial perf surfaces" lesson into a different dimension: **small surface area ≠ small consequence**. Both cases the gate-default underweighted load.

### Promotion note

1st surface for "triage misses reasoning-heavy doc artifacts." Promote to pattern-application 8/10 on 2nd instance (any future doc-only diff where triage TRIVIAL conceals a real defect surfaced by thorough). At 3rd surface, promote to architecture-9 with a triage agent amendment proposal: detect path patterns under `docs/{decisions,research,designs,precedents}/` and force NON-TRIVIAL.

Adjacent: BC-5806 task-1 (small bash file ≠ trivial perf surface), BC-5928 task-1 (mechanical port has factual surface that brainstorm/plan miss). The cluster is "default gates underweight load on small-surface high-leverage artifacts."

## Task 2 — 3-surface ADR discovery pattern (CLAUDE.md ADR list + integration doc + originating plan back-ref)

**Category:** pattern-application
**Confidence:** 7/10
**Tags:** pattern-application, adr-discovery, cross-link-density, three-surfaces, anti-orphan

### Decision

When publishing ADR-009, brainstorm asked "where should the framework be linked from?" — three candidate surfaces existed: CLAUDE.md `## Architecture Decisions` list, `salesforce.md` (the integration doc the framework most directly serves), and `revops-plugin-master-plan.md` §6 Issue 0.3 (the section that originally filed the issue). User asked for a recommendation; I recommended all three, citing different audiences per surface (cross-cutting agents / SF tooling readers / RevOps planning sessions). Cost: ~3 lines per surface.

User accepted. All 3 cross-links were added. Each serves a distinct discovery vector that the others can't:

- **CLAUDE.md ADR list** — every session loads CLAUDE.md, so any agent doing SF-adjacent work has the framework in scope from session boot
- **Integration doc** (`salesforce.md`) — anyone reading SF tooling docs (the framework's primary readers) sees the cross-link inline
- **Originating plan back-ref** (`**Resolved by:** ADR-009`) — future RevOps planning sessions revisiting the master plan see the ADR as the resolution of the open question, not an orphan

ADR-007 has 2 of these surfaces (CLAUDE.md ADR list + indirect via plan). ADR-008 has 1 (CLAUDE.md only). ADR-009 is the **first clean instance** of all 3.

### Alternatives considered

1. **All 3 surfaces** — Chosen. Each surface reaches a different audience; marginal cost is small.

2. **CLAUDE.md only** — Rejected. Highest reach but anyone working in salesforce.md or the master plan would have to know to grep ADRs for relevance.

3. **Integration doc + originating plan, skip CLAUDE.md** — Rejected. Misses cross-cutting agents who don't open salesforce.md but do load CLAUDE.md every session.

4. **CLAUDE.md + integration doc, skip plan back-ref** — Considered. The plan back-ref's incremental value is in resolving the "Decide" question that originally filed the issue. Without it, future RevOps planning sees an open decision question that's actually closed. Plan back-ref earns its line.

### Rule derived

For ADRs that serve a specific integration domain (SF, dbt, marketing tooling, etc.), use the **3-surface pattern**:

1. CLAUDE.md `## Architecture Decisions` list — for cross-cutting reach
2. Integration/SOT doc — for the audience that lives in the domain
3. Back-reference from the originating plan or design doc with `**Resolved by:** ADR-NNN` — for plan readers and to prevent the original question from looking unresolved

Marginal cost is ~3 lines total per ADR. The defense against orphaning compounds across years.

### Promotion note

1st clean instance of the 3-surface pattern (ADR-007 had 2/3, ADR-008 had 1/3). Promote to pattern-application 8/10 on 2nd instance (next ADR that follows all 3). At 4th instance across distinct ADRs, consider architecture-9 promotion with a CLAUDE.md gotcha entry encoding the rule.

## Task 3 — Pre-prune CLAUDE.md guardrail-buffer drops require alternate-discovery grep before deletion

**Category:** pattern-choice
**Confidence:** 6/10
**Tags:** pattern-choice, claude-md-prune, alternate-discovery-check, guardrail-buffer, anti-orphan

### Decision

Adding the ADR-009 entry pushed CLAUDE.md from 100 lines (exactly at the C2 guardrail target) to 101 lines (1 line over the advisory threshold). The check-guardrails.sh advisory is a warn, not a fail. Two paths to resolve: (a) accept the advisory, or (b) drop another existing line to hold the budget.

User had earlier offered to drop the `[Context-Skill Standard]` entry from the ADR list (the only non-ADR entry — design doc, not a decision record). I ran the check-guardrails advisory once with the +1 over budget and surfaced both paths. User chose to drop, but added the qualifier: **"yeah go for #1 if you really think that's ok."** That's not a green light — it's a request for verification.

Before deletion I grepped: `grep -rl "BC-1966-context-skill-standard\|context-skill-standard\|Context-Skill Standard" --include="*.md" --include="*.json"`. Returned 11 alternate references: marketing plugin README, product-marketing-context SKILL, decision-trace spec, brite-agent-platform PRD, workflow-spec, two plans, a precedent file, and the domain-plugin template. The CLAUDE.md mention was one of many — dropping it does not orphan the design doc; alternate paths cover every audience that would search for it.

Drop applied. CLAUDE.md back to 100 lines, C2 PASS.

### Alternatives considered

1. **Grep for alternates, drop only if ≥1 alternate path exists** — Chosen. Concrete safety check that protects against orphaning a doc just to satisfy a line-budget advisory.

2. **Drop without checking** — Rejected. CLAUDE.md is the highest-reach discovery surface in the repo. A line removed from there is materially harder to find again.

3. **Accept the +1 line advisory** — Considered. Defensible if no clean drop existed. But with 11 alternate references, the drop is the cleaner outcome.

4. **Drop a different ADR entry instead** — Rejected immediately. Every ADR entry is an active decision record; the design doc entry was the only non-decision item in the list.

### Rule derived

**Before pruning a CLAUDE.md entry to clear a guardrail-buffer advisory, grep the repo for alternate references to the same doc.** If `≥1` alternate path exists, the drop is safe; if zero alternates, accept the advisory or relocate the doc-pointer elsewhere before pruning.

Companion to the existing CLAUDE.md "every line is load-bearing" intuition: load-bearing-ness is a function of *uniqueness*, not just *presence*. A line that uniquely surfaces information is load-bearing; a line that duplicates a discovery already available elsewhere is removable.

### Promotion note

1st instance. Promote to pattern-application 7/10 on 2nd CLAUDE.md prune that follows the same grep-first protocol. Worth encoding as a soft rule in `best-practices-audit` skill if pattern recurs — the audit already flags CLAUDE.md size; could optionally suggest the alternate-discovery check before recommending which line to drop.
