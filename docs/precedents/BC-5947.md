## Task 1 — Plan-time reconciliation table when issue text predates dependency landings

**Category:** pattern-application
**Confidence:** 7/10
**Tags:** pattern-application, plan-doc, issue-text-staleness, reconciliation-table, brainstorm-output
**Precedent Referenced:** None — novel for this repo. Adjacent to `memory/feedback_atomic_issues_for_agents.md` (atomic-issue contract) and BC-5945 § 1's "issue prescription pressure-tested" framing.

### Decision

The BC-5947 issue body was authored 2026-04-22 — **before** BC-5945 § 1 reframed the MCP-cap policy from "exception" to "advisory-with-measurement", **before** BC-5946 verified the actual marketing `.mcp.json` shape, and **before** the BC-5551 gotcha clarified that `${user_config.*}` substitution was tested broken for HTTP and was unverified-but-suspect for stdio. By the time BC-5947 reached planning, **5 distinct prescriptions in the issue text had become stale** against ground truth:

| Issue Pass | Issue prescription | Ground truth at plan time | Plan resolution |
|---|---|---|---|
| Pass 1 | "existing 5 entries → 8" | Marketing `.mcp.json` had only `salesforce`. EB user-level. github/enrichment unregistered. | 1 → 4 |
| Pass 2 | "7 new userConfig entries, all sensitive: true" + ANTHROPIC_API_KEY | No userConfig. ${user_config.*} HTTP-broken, stdio unverified-but-suspect per BC-5551. | Pattern A (no userConfig); ANTHROPIC_API_KEY in setup command (CLI runtime concern) |
| Pass 4 | "Add new MCP-cap-exception bullet" | CLAUDE.md:94 already correct per BC-5945 § 1 | No edit — verify only |
| Pass 5 | Cross-validate `allowed-tools` against the 3 servers | BC-5832 not yet shipped | Pass 5 cross-validation note in plan |
| Verify #1 | "existing 5 entries untouched" | Only 1 existing entry | "existing 1 entry untouched" |

The decision was to **lead the plan doc with an explicit "Reconciliation: issue text vs ground truth" table** as the first section after Goal, listing every issue prescription that diverges from ground truth, with the plan's resolution. The reconciliation became a load-bearing artifact: it fed the brainstorm question to the user (Pattern A vs B vs C), the PR description's "5 deltas" section, and the Linear issue comment summarizing the divergences.

### Alternatives considered

1. **Treat issue text as authoritative; execute Pass 1–5 verbatim.** Reject the policy reframe (BC-5945) on the grounds that the issue body owns the source of truth. **Rejected.** Would have shipped 7 unused userConfig entries (substitution-broken per BC-5551), a duplicate CLAUDE.md Gotcha bullet (overwriting BC-5945 § 1's correct text), and a wrong server count that would have failed the BC-5945 § 1 measurement step. The downstream BC-5832 skill would also inherit the wrong allowed-tools surface count.

2. **Silently revise as you execute; mention divergences only in commit messages.** Catch the 5 deltas during execution but resolve in-flight without surfacing to the user. **Rejected.** The issue's Linear-side description stays stale; future readers (including the BC-5832 author) inherit a misleading source of truth. The BC-5945 brainstorm explicitly used the same pressure-test pattern (3 of 5 issue defaults revised, 2 stood) and produced a research artifact — BC-5947 mirrors the shape on a smaller scale.

3. **Lead the plan with a reconciliation table (this option).** Accepted. The brainstorm question to the user (Pattern A vs B vs C) presupposes shared awareness of the deltas; the reconciliation table makes that awareness explicit. Single source of truth (the plan doc); commit messages, PR body, and Linear comment all derive from it.

### Rule derived

**When a Linear issue body predates a known policy/dependency landing that reframes its prescriptions, the plan doc MUST lead with a Reconciliation section before the Tasks section.** The reconciliation lists each stale prescription, the ground truth, and the plan's resolution. Brainstorm questions to the user reference the table by row. PR descriptions and Linear comments derive their "delta" sections from the same table. Issue-body description stays untouched (audit trail); the plan owns the live truth.

### Promotion note

**Watch for a 2nd instance.** The pattern is most useful for issues authored ahead of dependency chains where research/design issues land between authoring and execution (BC-5945 → BC-5946 → BC-5947 was a 3-stage chain over 4 days). If a similar staleness chain produces another reconciliation-table plan in the next 60 days, this becomes a pattern-application architecture-7 candidate for the issue-creator skill (suggested location: a paragraph in `plugins/workflows/skills/writing-plans/SKILL.md` requiring authors to check issue-vs-ground-truth at plan time).

## Task 2 — Vendor MCP package-name claims need empirical verification (npm + vendor docs) before registration

**Category:** bug-resolution
**Confidence:** 8/10
**Tags:** bug-resolution, integration-guide, vendor-package-name, npm-verification, factual-drift, sibling-of-task-3-bc5946
**Precedent Referenced:** BC-5946 task-3 (architecture-8 promotion candidate — "integration-guide claims must grep against the wrapper code"). Sibling pattern (different surface).

### Decision

Both upstream `Revgrowth1/tam-map@9f5c72e74b/.mcp.json` and the BC-5946 Brite-authored `plugins/marketing/tools/integrations/spider-cloud.md` registered Spider's MCP as `@spider-cloud/spider-mcp`. **That npm package does not exist.** The real package per [Spider docs](https://spider.cloud/docs/integrations/mcp) is `spider-cloud-mcp` (unscoped, v2.1.1 at write time). Brainstorm pre-execution check (`npm view @spider-cloud/spider-mcp` returned 404; `npm search` for variants returned only `@spider-cloud/spider-client`) caught it before the issue's Pass 1 prescription would have shipped a registration to a non-existent package.

The decision was to **add a pre-registration `npm view` step to the plan's Task 1 for any new MCP server entry that names an external package**, and to fix the typo at the source (the integration guide). Tool inventory in `spider-cloud.md` was also corrected from 2 speculative tools (the BC-5946 author's guess) to 22 canonical tools (8 core + 5 AI + 9 browser, per docs).

### Alternatives considered

1. **Trust upstream tam-map's `.mcp.json`.** Upstream is the original tam-map authors; they should know the package name. **Rejected.** Empirically false — upstream had the same typo, and they have a `Last verified` date that wouldn't have caught the dead package because npm doesn't 404 immediately on missing packages in their workflow (they may have used a private mirror). Authority of upstream is a heuristic, not a guarantee.

2. **Discover at runtime.** Ship the `.mcp.json` with the wrong name; let the first user to invoke `/marketing:setup-tam-map` Phase 6 hit the `npx -y @spider-cloud/spider-mcp` fail and report. **Rejected.** Cascades through BC-5832 (tam-mapping skill compiles `allowed-tools: mcp__plugin_marketing_spider__*`) and the marketing plugin's version cache (BC-6000) — by the time the typo is reported, multiple downstream artifacts depend on the wrong name.

3. **Add `npm view` pre-step to plan + fix the integration guide (this option).** Accepted. `npm view <pkg> name version` either prints the package or 404s; the cost is one bash call per new external MCP. Catch is cheap, miss cost is high.

### Rule derived

**Before registering any external MCP package in `.mcp.json`, run `npm view <pkg> name version` (or the equivalent registry probe for non-npm packages) AND grep-confirm the package name against the vendor's own MCP docs.** Both checks must pass before the plan moves to execution. If the integration guide for that vendor exists in `plugins/marketing/tools/integrations/`, also re-verify the guide's Registration JSON snippet during the same step — Brite's prior speculative authorship is a known failure mode (BC-5946 task-3 task class).

### Promotion note

**Architecture-8 promotion candidate — extends BC-5946 task-3's surface from "wrapper source" to "vendor source of truth."** This is the sibling pattern: BC-5946 task-3 covers `Auth` / `Tool inventory` / `Registration` claims for **wrapper-backed MCPs** (where the JS wrapper is the source of truth). This trace covers vendor **package-name** claims for **native MCPs** (where vendor docs + npm registry are the source of truth). Same architectural rule: integration-guide claims need empirical verification against the most authoritative source for that claim's surface. Suggested location: `docs/guides/skill-tool-integration-pattern.md` § PR checklist, the same 8th item proposed by BC-5946 task-3, expanded to: "Grep every guide claim against the backing source — wrapper code for wrapper-backed MCPs, npm registry + vendor docs for native MCPs." Single rule, two surfaces. **At next recurrence on either surface, promote.**

## Task 3 — Pattern A (plugin-scoped stdio + OS env) vs Pattern C (userConfig substitution) when stdio path is unverified-but-suspect

**Category:** pattern-choice
**Confidence:** 7/10
**Tags:** pattern-choice, mcp-registration, substitution-pattern, gotcha-application, plugin-scope-vs-user-scope
**Precedent Referenced:** BC-5551 (gotcha_http_mcp_substitution_broken — HTTP-substitution proven broken; stdio path "all proven broken" but only HTTP empirically tested), BC-5535 (Salesforce stdio + plugin-scope, no env substitution at all — local-auth store), `plugins/marketing/tools/integrations/spider-cloud.md` § Registration ("env-var substitution into stdio server `env` maps works today" — Brite-authored claim).

### Decision

For 3 stdio MCPs (Spider native + AI Ark wrapper + Discolike wrapper), three viable substitution patterns existed:

- **Pattern A** — plugin-scoped stdio with `env: {KEY: "${KEY}"}` against OS env vars (user puts exports in `~/.zshrc`)
- **Pattern B** — user-level registration in root `.mcp.json` (gitignored), the existing Email Bison precedent
- **Pattern C** — plugin-scoped stdio with `env: {KEY: "${user_config.KEY}"}` + `userConfig.KEY: { sensitive: true }` in `plugin.json`

The BC-5551 gotcha proved Pattern C broken **for HTTP headers**. The same gotcha says "all proven broken in BC-5551" including stdio wrappers, but **only HTTP was empirically tested in BC-5551**. The BC-5946 spider-cloud.md (Brite-authored) explicitly states stdio env-var substitution works. Conflicting signal.

The decision was **Pattern A** — accept the spider-cloud.md hearsay-positive claim as the working hypothesis, ship plugin-scoped stdio + OS env vars + a guided `setup-tam-map.md` command for `~/.zshrc` exports. No userConfig at all in `plugin.json`. ANTHROPIC_API_KEY (needed by `tier_and_segment.py` CLI for fit-scoring, not by any MCP) goes in the same `~/.zshrc` block — not a plugin userConfig concern.

### Alternatives considered

1. **Pattern B** — user-level registration like Email Bison. **Rejected.** Worst trade for plugin distribution: every dev edits root `.mcp.json` manually; no commit-tracked plugin shipping; the marketing plugin's own `.mcp.json` would carry only `salesforce` even after this PR ships. Email Bison adopted this only because HTTP headers forced the workaround; stdio doesn't have that constraint.

2. **Pattern C** — userConfig substitution. **Rejected.** Cleanest UX if it works (Claude Code prompts user once, stores in OS keychain, substitutes at runtime). Risk: if BC-5551's "all proven broken" claim covers stdio too, the plugin appears installed but every MCP fails to authenticate at runtime — silent failure mode. The cost of empirical verification (a separate spike issue: register a test stdio MCP plugin-scope with userConfig substitution, observe whether the env reaches the spawned process) was deemed too high for inline this PR. Filed mentally as a follow-up.

3. **Pattern A — plugin-scoped stdio + OS env** (this option). Accepted. Distributes via the plugin's own `.mcp.json` (commit-tracked, multi-dev). Setup command provides a single touch-point for new devs. If stdio userConfig substitution is later confirmed working, migration to Pattern C is a single `.mcp.json` + `plugin.json` edit per server — low future-cost.

### Rule derived

**When choosing a stdio MCP substitution pattern in a Brite plugin, default to Pattern A (plugin-scoped + `env: {KEY: "${KEY}"}` against OS env vars + a guided setup command for `~/.zshrc` exports) unless empirical evidence proves Pattern C (userConfig substitution) works for stdio.** The Brite gotcha doc's "all proven broken" wording covers HTTP empirically; stdio coverage is hearsay-positive (per spider-cloud.md) but unverified. Pattern A is the proven path; Pattern C is the better UX-with-risk path. The migration cost from A → C is low (per-server JSON edit), so prefer A → C migration over C → A retreat.

### Promotion note

**Watch for an empirical Pattern C verification.** If a future session runs the BC-5551 spike for stdio specifically (register a throwaway plugin-scope stdio MCP with `userConfig` substitution, observe whether the spawned process's `env` block receives the substituted value), the result either: (a) **Pattern C works for stdio** → all future plugin-scope stdio MCPs use Pattern C, this trace becomes "applied during the unverified-stdio era", and `gotcha_http_mcp_substitution_broken.md` gets a clarifying amendment; (b) **Pattern C broken for stdio too** → this trace becomes the canonical justification for Pattern A as the standing rule. Either outcome promotes — Pattern A is the **interim** decision; the empirical check is the missing input.
