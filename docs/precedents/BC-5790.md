## Decision

First-of-N Phase 2 RevOps orchestration command (`/revops:deploy-sandbox`) establishes the 6-phase shape for BC-5791 and BC-5792 to inherit: Pre-flight → Dry-run → Deploy → Tests → Manual verification → Completion, with `AskUserQuestion` gates between every **mutating** phase. Gate rule is explicit in both the file body and the Rules section: mutating phases only (enumerated as Phases 2, 3). Phase 4 (Apex tests) is deliberately soft-gated — tests may fail without halting because the deploy has already landed and the user may want to inspect the failing state in the sandbox UI.

## Key alternatives considered

1. **Merge Phase 1.2 (default-org check) with Phase 1.3 (alias confirm)** — Initial draft had a separate `sf config get target-org` check that halted on unset default. Simplify-pass (cross-agent convergence, conf 8 + 9) flagged it as dead logic: every `sf` invocation pins `--target-org brite-sandbox`, so the default-org state doesn't affect execution. **Deleted.** Phase 2's dry-run surfaces real auth failures naturally.
2. **Use `result.success === true` AND `status === 0` for dry-run success** — Initial draft used both. Simplify-pass flagged `result.success` is not always present on dry-run responses; canonical stable field is top-level `status`. **Swapped to `status === 0` only.**
3. **Gate Phase 4 Apex-test failures with `AskUserQuestion`** — Code-reviewer flagged the asymmetry vs. Phases 2/3 (P2, conf 7). Validation subagent dismissed: top-of-file rule scopes gates to **mutating** phases; Phase 5 is manual browser inspection (non-mutating); halting after deploy landed adds no safety and defeats the documented "deliberately debug a failing test in the sandbox UI" use case.
4. **Assert `isSandbox === true` on the resolved alias** — Security-reviewer flagged confused-deputy risk if `brite-sandbox` alias reassigned to prod (P3, conf 7). Validation subagent dismissed: `sf org display --json` does **not** return an `isSandbox` field — the proposed fix is factually unimplementable. Existing Phase 1.2 + Phase 2 gates already mitigate local alias-reassignment risk.

## Rule derived

**For first-of-N orchestration commands in a new plugin subtree, lock the template in the first PR.** Phases, gate policy (which phases are mutating), success-parse shape (top-level `status`, not nested `result.*`), and halt-vs-soft-warn branches all set precedent for siblings. Changing them mid-series means either reworking already-shipped commands (see BC-5795 revert-reship) or accepting drift. The first-of-N writer pays the design cost; siblings inherit.

**Sub-rule (from this session):** the gate-vs-soft-warn decision must be explicit in the file body. State **which phases are mutating** in the Rules section (e.g., "Every mutating phase (2, 3) is preceded by..."). Reviewers and future siblings can check template compliance without reading the entire flow. Without this line, Phase 4's soft-warn looks like an oversight rather than policy — the validator needed to re-derive it from the top-of-file rule.

## How to apply

- **When:** writing any `/revops:*` Phase 2 command (BC-5791, BC-5792) or any first-of-N orchestration command in a new plugin subtree.
- **Template inheritance:** Phase shape (Narrate → step → parse-or-halt → AskUserQuestion gate → Narrate-done) is durable across BC-5790/5791/5792. Halt-on-dry-run-fail is durable. `--target-org` pinning is durable. Soft-warn on post-deploy diagnostic failures (like Phase 4 tests) is specific to sandbox — **BC-5791 prod-deploy should hard-gate** post-deploy verification.
- **Simplify-pass signal:** two different simplify agents flagging the same file:line with conf ≥ 8 = strong signal. Apply without Opus validation; save tokens.
- **Factual-error-catch:** validation subagents for CLI-related findings must independently verify field shapes. Don't trust "add this field check" without confirming the field exists.
