## Task 1 — Sibling-paragraph mirroring as fallback-adoption strategy (5th instance)

**Category:** architecture
**Confidence:** 9/10 (up from BC-5870 task-1's 8/10 at 4th instance — promotion to architecture-9 confirmed)
**Tags:** architecture, sibling-paragraph-mirror, fallback-pattern, fifth-instance, bc-5866-extension, cadence-skill
**Precedent Referenced:** BC-5870 task-1 (4th instance, arch-9 candidate); BC-5866 (gate-respect class-bug origin); BC-5871/5870/5869 (Phase 1 spec-extension siblings)

### Decision

When introducing a new conditional default ("fallback") to a skill section that already contains an accepted conditional default for a sibling question/condition, **mirror the existing paragraph's structure verbatim**: same trigger framing (`When state.X.length == 0 AND state.Y is empty`), same render-switch sentence (`<question>'s (Recommended) default switches from <old> to <new>`), same state-log line (`Logged under state.projects[i].skip_log as {question, reason}`), and same trailing parenthetical precedent reference (`(Closes BC-XXXX — codifies the W<NN> attempt-2 path as spec-compliant per <doc> § <N> <name> row, rather than rendering a "<departure>" annotation.)`). The mirror is the unit of pattern adoption.

### Surface in this session

BC-5900 added a "No-signal SQ1 fallback" prose paragraph to `plugins/cadence/skills/sprint-scoping/SKILL.md`. The existing "Scope candidate injection from enricher" SQ2-empty fallback (closes BC-5867) was 6 lines above. The new paragraph was authored as a structural mirror — same five sentence templates, same field names, same parenthetical-citation convention. Diff-triage verdict was TRIVIAL on first pass (no new pattern to evaluate).

### Pattern

**A mirror is denser-than-an-ADR pattern enforcement.** When N=1 the precedent is descriptive. When N=2 it's a pattern. When N=3-4 it's a class. At N=5 the structural mirror itself becomes load-bearing — consumer code that reads one fallback also reads the other, lint forbidden-phrase patterns designed against the mirror's prose now extend coverage to all instances, and any departure becomes a code smell because the contrast against the established mirror is visible at-a-glance. The decision is no longer "should I add this fallback?" but "does my fallback mirror the established sibling exactly?".

### Applies when

- Adding any new conditional-default fallback to a skill section that already has ≥1 accepted conditional default
- Authoring follow-up Phase 2 sprint-scoping fallbacks (BC-5901 ritual-close-out is the immediate next instance)
- By extension: any cadence skill where § 2.3-style adaptivity rules grow a sibling

### Follow-ups

- BC-5901 must apply this mirror to its ritual-close-out SQ2–5 fallback (3rd cadence-skill instance counting BC-5867 + BC-5900)
- If a 6th instance ships in a future cadence skill (linear-housekeeping § 4 mutation-skip rules, narrative-writer voice-guard fallbacks), promote this precedent from arch-9 to **arch-10 invariant** and codify in the cadence/CLAUDE.md "Mirror sibling fallback paragraphs verbatim" bullet
- Lint `lint_cadence_gates.py` could grow a cross-paragraph structure check that fails if a "fallback" prose paragraph diverges from its established sibling — defer until a 6th surface justifies the regex

## Task 2 — Forward-pointer parenthetical bridges declarative spec to conditional override

**Category:** pattern-choice
**Confidence:** 7/10 (new pattern; first instance — high confidence because the failure mode is concrete and recurrent)
**Tags:** pattern-choice, forward-pointer, spec-bridge, declarative-vs-conditional, drift-prevention, cadence-spec
**Precedent Referenced:** none (new pattern; informally co-applied with BC-5870 / BC-5871 § 1.6 reconciliation rendering)

### Decision

When a § 2.3-style adaptivity row introduces a conditional override on top of a § 2.2-style declarative default, **also touch the § 2.2 declarative line with a forward-pointer parenthetical** in the form `*(or "<new default>" when <condition> — see § 2.3 <row name> row)*`. The parenthetical lives inline in the declarative spec's "Default:" sentence, before the "Escape:" clause. Without this bridge, a future reader sees an unconditional default in § 2.2 and a conditional override in § 2.3, can legitimately argue the spec is internally inconsistent, and may file it as a P2 ("spec-strict conflict — § 2.2 says X, § 2.3 says Y").

### Surface in this session

BC-5900's § 2.3 6th-row addition forced the question. § 2.2 Q1 read: *"Default: agent proposes from top-priority carry-over + top-priority backlog candidates. Escape: custom sentence, or mark project parked."* — strictly unconditional. The new § 2.3 row introduced a conditional override. I added the parenthetical directly: *"Default: agent proposes from top-priority carry-over + top-priority backlog candidates *(or 'Owner picks next track — free-text' when both are empty — see § 2.3 no-signal row)*. Escape: ..."*. Plan called it out explicitly to prevent the future-reader-files-P2 failure mode that BC-5900 itself was an instance of (§ 2.2 Q1 strict-default → AC #1 breach when no signal exists → P2 → spec-codification fix).

### Pattern

**The bridge is the same shape as BC-5870/BC-5871's § 1.6 rendering rule** — both are "the declarative rule has a conditional override; surface the override at the declarative site so a reader can't reach the wrong conclusion from the declarative site alone." The pattern compresses to: *every § 2.3-style adaptivity row that overrides a § 2.2-style default also touches the § 2.2 line with a parenthetical pointer.*

### Applies when

- Adding any new § 2.3-style row to `docs/designs/cadence-orchestration.md` that overrides a § 2.2 default
- By extension: any spec doc with a "general rule" section + an "exceptions/overrides" section (where the general-rule section is read more often)
- BC-5901's ritual-close-out SQ2–5 row will need 4 forward-pointer parentheticals (one per Q2/Q3/Q4/Q5) — making the recipe mechanical at first sibling

### Follow-ups

- BC-5901 is the validation case — if the recipe holds for 4 simultaneous Q-row touches, promote confidence to 8/10 and add to cadence/CLAUDE.md gotchas
- If an instance in a non-cadence spec doc applies (workflows or marketing skill specs grow a § X.3-style overrides table), promote to architecture-7
