## Task 1 — Honor the brainstorm escape-hatch even when a recommended option is in the gate

**Category:** pattern-application
**Confidence:** 7/10
**Tags:** pattern-application, gate-respect, skill-invocation-surface, brainstorm-escape, cadence-plugin
**Precedent Referenced:** BC-5866 (gate-respect contract, original), BC-5864-5865 (1st instance at spec-cascade surface), BC-5872 (2nd instance at `### subsection` surface), BC-5923/5929/5930 (persona-title surface, batched / sub-type-split variants)

### Decision

When an orchestrator presents an `AskUserQuestion` gate that offers **an option to invoke a heavier skill** (e.g. A/B/C + "Run a full brainstorm instead"), and the user picks the heavier option, run the heavier skill end-to-end even when the orchestrator has already synthesized enough to recommend a lighter path. The escape hatch is a gate pick like any other — the user authorization governs which skill runs, not just what that skill does inside.

Specific instance this session: brainstorming Phase 2 presented 4 options (Option A / Option B / Option C / Run full brainstorm). Issue description already named A as recommended with complete arithmetic. User picked "full brainstorm". Orchestrator launched `workflows:brainstorming` via Skill, ran all four phases (context gather, precedent search, Socratic, design doc, approval), produced `docs/designs/bc-5869-phase-1-synthesis-cap-scale.md`, and only then moved to planning. The A/B/C recommendation in the issue body did NOT shortcut the brainstorm.

### Alternatives considered

1. **Treat the escape hatch as advisory when a recommendation is already strong.** If the orchestrator has already laid out the options with a clear recommendation, the "full brainstorm" option can be treated as a formality — skip it and proceed to plan. **Rejected.** This is exactly the silent-self-downgrade failure BC-5866 codifies. The user picks govern; orchestrator judgment about option-strength does not.

2. **Ask a clarifying question before honoring the pick.** "You picked full brainstorm — are you sure? The issue already recommends A with arithmetic." **Rejected.** Re-prompting with orchestrator opinion embedded is a different kind of downgrade — it pressures the user toward the lighter path. If a new gate is needed, it should be neutral, not leading. But in this case no new gate was needed — the pick was unambiguous.

3. **Run a compressed brainstorm.** Do the Socratic pass but skip precedent search and the design doc. **Rejected.** The brainstorming skill's phases are its contract; running a subset silently converts it to a non-skill. If a compressed variant is useful, it should be a separate skill with its own name and gate.

### Rule derived

**An option inside a gate that triggers a heavier skill invocation is a gate pick governed by the same contract as any other pick.** Orchestrator synthesis in the pre-gate render (recommendations, arithmetic, etc.) does not grant license to shortcut the heavier skill after the user picks it. Applies at every surface where skill-shape is user-selectable, not just gate-outcome within a fixed skill.

### Promotion note

**Architecture-9 promotion candidate at a later instance.** This is the 3rd distinct surface-class for BC-5866 (surfaces so far: spec-cascade self-downgrade · `###` subsection cascade · persona-title directive substitution · **skill-invocation-shape escape hatch**). If a 4th novel surface appears in a future session (e.g. gate-picked tool-registration changes, gate-picked model-tier changes), the BC-5866 contract crosses the architecture-9 threshold and promotes to `skills/_shared/gate-respect.md` as a surface-agnostic rule rather than a per-surface application pattern.

## Task 2 — Explain before re-asking when the user signals mid-gate confusion

**Category:** pattern-choice
**Confidence:** 7/10
**Tags:** pattern-choice, brainstorming-skill, mid-gate-confusion, explain-before-options, ux
**Precedent Referenced:** None — novel pattern. Adjacent to `memory/feedback_thorough_audits.md` (thorough by default) and `memory/feedback_more_checkins_for_infra_issues.md` (add check-ins for complex surfaces).

### Decision

When a user replies to a multi-option `AskUserQuestion` with a confusion signal (text like "help me understand this more", "im not really sure how this fits", "explain this first"), do NOT:
- re-present the same options
- ask a narrower clarifying question
- switch to a different set of options

Instead, write a **plain-English context expansion** covering:
1. What the feature is (concrete description of where the thing lives, who reads it, when)
2. Where the current constraint came from (origin, when-written-under-what-assumption)
3. What went wrong (the specific evidence that triggered this session)
4. What each option actually means in concrete terms (one paragraph per option, not just labels)
5. The deeper question the options are proxying for

THEN ask one simpler, concrete question that pins the decision to the user's actual experience rather than to abstract criteria.

Specific instance this session: Socratic discovery Phase 2 asked two questions (cap function + collapse acceptability). User answered both with "help me understand this more". Orchestrator wrote a 5-section explainer covering the feature, the cap origin, W17 evidence, option semantics, and the "what is the cap proxying for" meta-question. Then asked a single follow-up grounded in the user's last-week experience ("When you read the Phase 1 synthesis at Gate #1 this past week, what was your actual experience?"). User answered cleanly and the design fell out.

### Alternatives considered

1. **Ask narrower questions.** Break each option into sub-questions (does zero-activity matter? is 370 words readable? would you use pagination?). **Rejected.** User's confusion signal was "I don't understand the frame", not "I understand the frame but need to pick inside it". Narrower questions inside an unclear frame still leave the frame unclear.

2. **Present more options.** Maybe A/B/C missed an obvious fourth — add D/E/F to see if one resonates. **Rejected.** More options rarely resolve confusion; they compound it. If the problem is that the planner doesn't know which optimization target matters, adding options-per-target multiplies the question surface.

3. **Drop back to a free-text prompt.** "In your own words, what are you trying to optimize for here?" **Rejected.** Free-text puts the synthesis burden on the user. The orchestrator has context (issue description, dogfood notes, feedback rules) — it should present that context plainly and let the user react.

### Rule derived

**A confusion signal mid-gate is a context failure, not a choice failure.** The fix is prose context (what is this, where did it come from, what do the options mean), not more questions or more options. Follow with ONE question grounded in observable experience, not abstract criteria.

### Observation

The follow-up question that worked asked about the user's experience *last week* with *the specific synthesis*. It mapped option space to experiential signal. That kind of question is generalizable: when abstract criteria-based questions fail, anchor to the user's most-recent concrete encounter with the thing under decision.

When named options fail to satisfy stated concerns, hybrids should be in the Socratic toolkit — not just as combinations but as structural composites.
