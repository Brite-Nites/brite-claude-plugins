**Category:** pattern-choice

## Decision

After six consecutive Phase 3 siblings applying the same template (BC-5793 → BC-5794 → BC-5795 → BC-5796 → BC-5797 → BC-5798), the template is ratified beyond "proving" itself. Ship every remaining Phase 3 sibling mechanically with zero Plan-gate re-derivation per BC-5794, treat pre-merge `/workflows:review` as a mandatory gate per BC-5796, apply the five-check factual-anchor recipe per BC-5797, **and extend the recipe's second check (bullet-count verification) to include entity-canon-adjacent mislabeling detection**: any claim about "N custom/standard objects" must be cross-verified against the handbook's standard-vs-custom tagging (e.g., `Location` marked `(FSL standard)` cannot be folded into a "five custom" count).

Template variant B placement (Brite sections BEFORE `## When This Skill Owns the Task`) chosen without re-litigation — now majority 5-of-6 siblings.

Pre-merge `/workflows:review` (thorough, 4 agents: code, security, performance, cdr-compliance) surfaced 0 P1, 0 P2, 5 P3 above confidence threshold (8 below threshold filtered). The **simplify pass caught 4 content-correctness bugs before review agents dispatched**, including one novel class: the §Brite Context intro claimed "five custom extensions" listing `Territory__c`, `Location` (tagged `(FSL standard)` in the same sentence), `Lifecycle_Stage_History__c`, `AccountContactRelation`, `In_App_Checklist_Settings__c`. Only 3 of the 5 are custom; `Location` is a standard FSL object and `AccountContactRelation` is a standard Salesforce object. The simplify-quality agent caught the contradiction between "five custom" and the "(FSL standard)" tag on `Location` — within-same-sentence internal inconsistency that BC-5797's five-check recipe would not have caught directly (checks 1-5 verify citations + bullet counts + regex, not entity-canon consistency).

Independent review-agent verification added value in two places:
1. **Rule 8 TYPEOF preference.** Performance-reviewer flagged Rule 8's "`TYPEOF Who WHEN Contact THEN AccountId END` **or** a separate query by `WhoId`" as listing alternatives without performance ranking. TYPEOF is 1 query; separate-query is 2 queries. Reframed as ranked preference (TYPEOF preferred; separate-query as fallback when field-set or polymorphic-branch constraints don't fit). Not a factual error — a teaching-quality issue that would have produced slower agent-written code if shipped.
2. **Rule 12 citation tag.** Code-reviewer noted that Rule 12 (`_(§Apex & Automation line 196)_`) lacked the `BC-5609` tag though §Brite Context bundled Rules 11-12 under BC-5609. One-word append brought citation consistency.

## Alternatives Considered

1. **Skip `/workflows:review` entirely — template is proven across 5 siblings.** Rejected. BC-5796's prescription and BC-5797's reinforcement are unambiguous: pre-merge review IS the compound-engineering instrument that made 4 content-correctness fixes land pre-commit on BC-5798. Skipping would test whether 6-sibling streak is enough to drop the discipline. That test's value is low — the "five custom extensions" class bug would have shipped as a merged P1 factual error (exactly the BC-5795 revert+reship class) without simplify pass catching it.

2. **Accept the diff-triage TRIVIAL verdict (BC-5823/5824 pattern).** Considered. The Haiku triage agent correctly verdicted TRIVIAL by shape (markdown-only, no code) — matches BC-5823/BC-5824 precedent. The user gate-selected thorough at the review-mode pivot, explicitly citing BC-5796/5797 reasoning. Per `feedback_honor_user_gate_selection.md`, the orchestrator honored the selection and ran thorough. Value demonstrated: 4 pre-merge simplify fixes + 2 review fixes = 6 fixes that TRIVIAL would have shipped unreviewed.

3. **Run `/workflows:review` thorough (chosen).** Applied. 6 pre-merge fixes landed in 2 commits (aed0ecd + 91918e5). Cost: ~3 minutes of reviewer turns + ~5 minutes of simplify turns. Benefit: no BC-5795-class factual error reached commit. Specifically the entity-canon-adjacent "five custom extensions" mislabeling would have been hard to catch post-merge (it reads plausibly to anyone who hasn't opened `brite-salesforce/force-app/main/default/objects/`).

**Reusable beyond this case.** The factual-anchor recipe gains a sixth sub-check under "bullet-count verification":

1. **Line-range citation** — every rule cites a specific source line in `brite-salesforce/CLAUDE.md` (BC-5793-5797).
2. **Bullet-count verification** — `gh api | sed -n 'A,Bp' | grep -c "^- \*\*"` to confirm the actual bullet count before making "~N gotchas" claims (BC-5796).
   - **2a. Entity-canon mislabeling check (new, BC-5798).** Any claim about "N custom/standard objects" must be cross-verified against the handbook's standard-vs-custom tagging in the same or adjacent sentence. If a tag like `(FSL standard)` or `(standard)` appears on a listed item, exclude it from a "custom" count. Within-sentence internal inconsistency (e.g., "five custom: …, `Location` (FSL standard), …") is the signature.
3. **Canonical path verification** — every file path named in rule text exists in `brite-salesforce` main (BC-5793-5797).
4. **Live Linear verification for issue-ID citations** — `get_issue` during Explore for every `BC-NNNN` in rule text (BC-5797).
5. **Verify-matrix regex pre-check** — run every grep pattern in the issue-body verify matrix against the drafted SKILL.md before Execute completes (BC-5797).
