## Task 2 — Defer-with-guardrail shape for unverified spec-vs-reality unknowns

**Date:** 2026-04-29
**Category:** pattern-choice
**Confidence:** 7/10
**Tags:** pattern-choice, defer-with-guardrail, verification-side-effects, spec-vs-reality, downstream-issue-update

### Decision

When brainstorming a spec-fix and an unverified API/render-engine behavior surfaces with 3 options (test-now, fix-without-evidence, defer), the right shape is **defer-with-guardrail**: defer the test to the next already-planned live-walk + add an explicit verification hypothesis (with test procedure + outcome tree + spinoff-trigger criteria) to that downstream issue's body via `mcp__linear__save_issue`. The deferral is honest only if the guardrail is locked in — naked deferral without the downstream issue update is just procrastination.

For BC-6299, this materialized as adding R-2a (case-sensitivity) and R-2b (empty-value render) hypothesis rows to BC-6308 (round-3 dogfood) with: (1) explicit test procedure using `/test-email`, (2) decision tree for each possible outcome, (3) BC-5870 verification-side-effects callout (file spinoff, don't absorb fix), (4) AC checkbox in BC-6308's verification section, (5) source cross-ref to BC-6299 design doc for rationale.

### Inputs

- BC-6299 brainstorm surfaced 2 unverified EB render-engine behaviors (case-sensitivity Sx-3, empty-value behavior derived from Sx-2 chain)
- EB API probe (search_api_spec) confirmed no pure preview endpoint exists; only `/test-email` SMTP send (~15-20 min setup + sender-reputation cost)
- BC-6308 already-planned round-3 live-walk explicitly designed to surface render-time behaviors
- BC-5870 task-2 verification-side-effects pattern (don't absorb verification-discovered fixes into verifier's PR; file siblings)
- User explicit pushback on naked deferral: "otherwise wouldnt our dogfooding round just fall into the same loop?"

### Alternatives Considered

1. **Defer + add R-2a/R-2b guardrail to BC-6308 + commit to BC-5870 spinoff rule** *(chosen)* — pays zero live-test cost in this PR; guarantees the verification surfaces at the next planned live-walk; converts a "we don't know" into "we will know by date X with documented decision tree." The user's pushback is honored because the guardrail makes the loop self-closing rather than self-perpetuating.
2. **Test-now via `/test-email` setup** — rejected after probing EB API: would cost 15-20 min wall-clock + a real SMTP send + sender-reputation budget for evidence that round-3 will surface naturally as a side-effect of work it has to do anyway. Marginal-value-of-testing-now is low when the natural surface point is already scheduled.
3. **Lowercase the artifact convention now** (resolve case-sensitivity by making code match EB's storage) — rejected: 14-skill blast radius across marketing plugin on an unverified premise. If render is case-insensitive (EB normalizes both sides), the convention churn was wasted; if render IS case-sensitive, the spinoff post-round-3 still has to do the same work but with real evidence justifying it.
4. **Naked deferral (note in spec, no BC-6308 update)** — rejected; the user's pushback specifically named this failure mode. Without a guardrail, round-3 could quietly skip the spot-check and we'd loop again.

### Outcome

- **Files changed:** `plugins/marketing/commands/launch-campaign.md` (Phase 3 step 7 flag), `plugins/marketing/tools/integrations/email-bison.md` (Sx-3 bullet flagging unverified render behavior + BC-6308 reference); BC-6308 issue body augmented out-of-band via Linear MCP with R-2a/R-2b hypotheses
- **Tests:** N/A (verification deferred to BC-6308 round-3 by design)
- **Approved by:** user (explicit "okay im fine with the testing approach for the next dogfood round" after cost-benefit walkthrough)

### Precedent Referenced

BC-5870 task-2 (verification-side-effects — don't absorb fixes into verifier's PR); none in `docs/precedents/INDEX.md` for the defer-with-guardrail shape itself — first-time precedent.

1st instance — not eligible for org-level promotion until 2nd instance confirms reusability. Watch for: any future spec-fix where an unverified API/render behavior surfaces and the verifier issue is already planned. Likely 2nd-instance candidates: any of BC-6301/6302/6303/6304/6307 if their brainstorm uncovers a similar render-time unknown.
