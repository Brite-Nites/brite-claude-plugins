## Task 1 — Decision memo can explicitly supersede a prior memo's "Alternatives Considered" section

**Date:** 2026-05-05
**Category:** pattern-choice
**Confidence:** 7/10
**Tags:** decision-memo, supersession, alternatives-considered, institutional-memory, reversal

### Decision

When a new architectural decision adopts an alternative that an earlier memo explicitly rejected, the new memo must (a) cite the prior memo's section by name, (b) quote the rejection rationale verbatim, and (c) explain why each rationale-point no longer holds. Don't restate the prior decision as if the alternative was never considered. The supersession block is the institutional artifact that lets future-self trust the reversal wasn't oversight.

### Inputs

- BC-6514 chose the multiplicative ESP × email-type model as default
- BC-6307's design memo at `docs/designs/BC-6307-phase-2-email-type-segmentation.md` Alternatives Considered #2 explicitly rejected this model: "Augment ESP × email-type → up to 9 buckets. Rejected — combinatorial explosion on small lists; most segments empty in practice."
- Two material changes invalidate the BC-6307 rejection: (1) F12 empty-bucket prune logic (already shipped) handles the "most segments empty" concern automatically; (2) operator preference is now explicitly stated, removing the "theoretical-overkill" framing
- Without the supersession block, a future reader encountering both memos would see contradictory direction with no traceable reversal

### Alternatives Considered

1. **Explicit supersession block citing prior memo by section name + verbatim rejection quote** *(chosen)* — written into BC-6514 memo's "Supersedes BC-6307 Alternatives Considered #2" section. Two reasons that rejection no longer holds enumerated inline. Future reader follows the chain: BC-6307 rejected for reasons X, Y; BC-6514 reverses because X resolved by F12 prune (shipped), Y resolved by operator-stated preference (new input).
2. **Silent reversal — write BC-6514 as if no prior position existed** — rejected. Future reader sees two memos with opposite direction and no bridge between them; loses institutional memory of why the reversal happened. Encourages future-self to re-litigate the same question.
3. **Update BC-6307 memo in place to reflect new direction** — rejected. BC-6307's design was correct *for that issue's scope* (email-type pre-filter without ESP × email-type axis). Editing BC-6307 to retroactively justify the multiplicative model rewrites history and obscures that BC-6307 actually shipped a different design that worked correctly.

### Outcome

- **Files changed:** `docs/designs/BC-6514-segmentation-axis-decision.md` (123 lines, includes the supersession block)
- **Tests:** `/workflows:review` triage verdict TRIVIAL (docs-only); no executable changes
- **Approved by:** auto-verified during `/workflows:ship` Step 4

### Precedent Referenced

None — first time encountering the explicit cross-memo supersession pattern. Closest analogue is the per-issue precedent traces that reference earlier traces (e.g., BC-6298 task-2 cites BC-6306), but those are session-pattern traces, not architectural memos. This is design-memo-to-design-memo supersession with rationale traceability.

### Promotion candidate

Watch for 2nd instance. Future architectural decisions in the marketing or revops plugins are likely to occasionally reverse earlier rejected alternatives (e.g., a Salesforce-side decision might later reverse based on Spring '26 platform changes; a marketing tooling choice might reverse based on a tool deprecating). At 2nd application, the explicit supersession block becomes a generalizable convention worth codifying — likely as a CLAUDE.md gotcha or `docs/decisions/` ADR meta-rule: *"Architectural decisions that reverse a prior memo's rejected alternative must include an explicit `## Supersedes <prior-memo> § <section>` block with verbatim rejection quote + per-rationale rebuttal."*

## Task 2 — Distinguish escape-hatch flags from opt-into-rejected-model flags when scoping opt-out surface

**Date:** 2026-05-05
**Category:** pattern-choice
**Confidence:** 7/10
**Tags:** flag-design, escape-hatch, opt-out, default-trust, surface-area

### Decision

When an operator wants belt-and-suspenders insurance flags for an architectural default they've just chosen, distinguish two flag classes: (a) escape-hatches that handle materially different work (e.g., "this is a tiny test launch, give me one campaign"), which preserve the default's spirit; (b) opt-out flags that let operators bypass the default into a model that was explicitly rejected as default, which silently re-enable the rejected option. Recommend keeping (a), dropping (b). Recommend, don't decide — present the tradeoff in plain language and let the operator make the call.

### Inputs

- BC-6514 settled multiplicative as default; three opt-out flags were on the table: `--no-host-lookup` (drop both axes → 1 campaign), `--no-segment` (drop ESP, keep email-type-only → the rejected model), and a hypothetical `--no-segment-email-type` (drop email-type, keep ESP-only → also rejected as default)
- Operator initial framing: "as long as the default is segmenting by both, I dont actually hate that" (the three-flag belt-and-suspenders option)
- F12 empty-bucket prune already handles the "small CSV produces empty cells" case automatically — no flag needed to address that concern
- Operator deferred to my recommendation when offered with reasoning ("if you recommend keeping just no host lookup, then i am fine with that")

### Alternatives Considered

1. **Distinguish escape-hatch vs opt-into-rejected-model; recommend keeping only the escape-hatch** *(chosen)* — `--no-host-lookup` kept (the "I have a 30-lead test list, 9 campaigns would be silly" case is materially different work, not a different segmentation philosophy). `--no-segment` dropped (would let operators silently bypass the multiplicative call into a rejected model). Net surface area: 1 flag, not 3. Insurance for unforeseen-scenario shrinks but is bounded by F12's automatic empty-cell handling.
2. **Keep all three opt-out flags as belt-and-suspenders insurance** — rejected as recommendation but presented as defensible alternative. Cost: more spec text, more eval scenarios, more JSON-shape variations downstream skills must handle, two flags exist mostly to second-guess the default. Benefit: insurance for scenarios the operator hasn't thought of yet.
3. **Drop all opt-out flags — multiplicative or nothing** — rejected. The "tiny test launch" case is real and not covered by F12 prune (a 30-lead list gives 9 small campaigns, not zero campaigns). `--no-host-lookup` is genuinely useful; killing it forces operators to hand-build campaigns outside the command for tiny tests.

### Outcome

- **Files changed:** `docs/designs/BC-6514-segmentation-axis-decision.md` "Opt-out flag set" section captures the call (1 retained, 1 dropped, naming)
- **Tests:** N/A (decision-only memo)
- **Approved by:** operator deferred to recommendation after plain-language tradeoff presentation

### Precedent Referenced

None — first time encountering the escape-hatch-vs-opt-into-rejected-model split as an explicit decision frame. Closest analogue is `feedback_user_delegation_scope.md` (operator delegates in-scope execution but not project-level architecture decisions) — once the architectural call lands, opt-out flags are part of the architectural surface and warrant the same scrutiny as the default itself.

### Promotion candidate

Watch for 2nd instance. The pattern likely recurs whenever an architectural default is settled and the discussion turns to opt-outs (segmentation models, retry policies, validation strictness, etc.). At 2nd application, codify as a CLAUDE.md or `docs/decisions/` rule: *"Opt-out flags must be classified as either (a) escape-hatch for different-work cases or (b) opt-into-rejected-model. Default to recommending (a) only."*
