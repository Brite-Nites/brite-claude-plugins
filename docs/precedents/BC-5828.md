# BC-5828: Plan-inherited factual-anchor drift is a distinct subtype; live-read referenced file bodies at Plan gate

**Date:** 2026-04-21
**Category:** pattern-choice
**Confidence:** 9/10

## Decision

Extend the BC-5797 factual-anchor recipe with check #6: at the Plan gate, for any referenced file the skill will cite by content (not just by path), read the referenced file's relevant section and cross-check against the issue body's claims about it. The Plan-inherited drift class is distinct from prior factual-anchor classes (BC-5793 line-range, BC-5794 canonical-path, BC-5796 bullet-count, BC-5797 Linear-citation + verify-matrix regex) because the drift source is the issue body or sibling plan — the SKILL.md faithfully inherits whatever the plan said, and the plan faithfully inherits whatever the issue said, even when the reference file has quietly moved on.

## Context

BC-5828 shipped a net-new marketing skill `plugins/marketing/skills/creative-angles/SKILL.md` (394 lines, 9-section template). The issue body §Brite differential named three Brite-entity tables as the skill's differentiator: "Entertainment Venues, Landscape/Hardscape Contractors, HOAs/Property Management." Those names came from the original Revgrowth 06 upstream scoping + pre-swap handbook mapping. The plan (`docs/plans/BC-5828-plan.md`) inherited those names into Task 6 scope. The executing-plans subagent inherited them into SKILL.md §3 Deep Mode Step 4, §4 Brite-entity additions, §6 Flow 2 Step 4, and §7 Rubric score-10 row.

The actual `plugins/marketing/references/hidden-signals-library.md` §§11–13 had been swapped on 2026-04-20 to **Municipalities / HOAs / Universities** — the three handbook-Active verticals with ship-ready ICP + persona docs. The library itself carries an explicit provenance note at line 148 documenting the swap and reasoning.

Four downstream code paths now silently drifted from the ground-truth reference file, and the built-in `reference-file-name-anchor` eval scenario didn't catch it — that eval asserts on the 5 forcing-function names, not the industry-table names.

`/workflows:review` caught it: code-reviewer P1 [conf 10/10], confirmed by independent Opus verifier, four-site grep-fix committed as `21a7208`. Clean resolution in ~3 minutes once flagged.

The crucial observation: the plan authoring process (writing-plans skill) read the reference files in Phase 1 context loading but did not cross-check the issue body's claims against the reference file bodies. The writing-plans skill's BC-5797 prompt rule said "Ground-truth every forcing function name against `creative-thinking-models.md`" — that covered forcing-function drift but not the broader class.

## Alternatives Considered

1. **Extend the factual-anchor recipe to check #6 (chosen).** At Plan gate, for each referenced file the skill will cite by content, read the referenced section and cross-check against the issue body. Cost: 1–2 extra Reads during planning, trivial. Benefit: catches the whole class pre-SKILL-draft. Confidence high because the review pass caught exactly this class at P1, and the diff-fix was mechanical once flagged.

2. **Extend the eval coverage (partial).** Add an eval like `reference-table-name-anchor` that asserts the skill body's vertical list matches the library's §11–§13. Would catch this at eval-run time. Rejected as primary fix because it catches the bug too late (post-SKILL-draft) and doesn't generalize — every type of "claim about a reference file" would need a bespoke assertion. Worth adding as a secondary defense but the Plan-gate check is upstream.

3. **Add a reference-file TOC cache.** Extract a short "current-as-of-YYYY-MM-DD" summary into each reference file's frontmatter so the plan-gate cross-check is a single-line read. Rejected for now as over-engineered for a 2–3-file skill suite. Revisit if the library count grows past ~10 and drift becomes recurrent.

## Outcome

Delivered `plugins/marketing/skills/creative-angles/SKILL.md` (+394) + `evals/evals.json` (+134) + Consumers cross-links in 3 reference files + `docs/plans/BC-5828-plan.md` + 2 review-fix commits, shipped as PR #165. `./scripts/validate.sh` + `./scripts/check-guardrails.sh` both exit 0. 6 eval scenarios valid JSON.

**Reusable pattern — extended factual-anchor recipe (now 6 checks):**

1. **Line-range citation** (BC-5793) — every rule cites a specific source line.
2. **Bullet-count verification** (BC-5796) — confirm counts before "~N gotchas" claims.
3. **Canonical path verification** (BC-5793-5796) — every file path named exists.
4. **Live Linear verification for issue-ID citations** (BC-5797) — any `BC-NNNN` citation → `get_issue`.
5. **Verify-matrix regex pre-check** (BC-5797) — grep patterns in the verify matrix run before Execute completes.
6. **Plan-inherited drift check (new, BC-5828)** — for any referenced file the skill will cite by content, read the referenced section at Plan gate and cross-check against the issue body's claims about it. Specifically: if the reference file has a provenance/changelog note (like hidden-signals-library.md's "user swapped on 2026-04-20" at §148), that note is load-bearing — the issue body likely pre-dates it.

## Related Decisions (session)

### Batched subagent dispatch for sequential single-file edits

**Category:** scope-change
**Confidence:** 7/10

Chose to dispatch 4 subagents (voice-checkpoint / methodology / implementation / final) for 12 sequential tasks instead of the per-task dispatch the executing-plans skill defaults to. Reason: all 12 tasks edit the same file in strict order; there is no parallelism and no cross-task context-pollution risk because each task just appends to SKILL.md. Per-task dispatch would have re-read the in-progress file 12 times at ~500-line growth, adding ~5-10× overhead versus the single file-read-per-checkpoint pattern. Checkpoints were chosen to match natural "voice-locking" transitions per user pacing preference. Applicable when: (a) tasks are sequential-dependent file-append work, (b) content is primarily markdown/instructions rather than code needing fresh-context isolation. Not applicable when tasks touch multiple files or require fresh context to avoid prior-task bias.

### Centralized input-validation rule beats per-surface validation

**Category:** pattern-choice
**Confidence:** 8/10

Review surfaced 2 security P2s (SOQL interpolation + Write path traversal) at 4 different sites. Both stemmed from the same root: `{domain}` not validated before reaching tool surfaces. The fix was a single upfront validation rule in §2 ("every `{domain}` must match `^[a-z0-9.-]+$`; reject /, \\, .., quotes, semicolons, NUL, SOQL keywords") that gates Gate-3 Glob, §4 Write destinations, and §5 Workflow 4 SOQL interpolation. Alternative was 4 per-site validation blocks — rejected because (a) violates DRY, (b) drift risk when one site updates and others don't, (c) harder to review as a security surface. Apply when: a single tainted input flows through 3+ tool surfaces with the same validation requirements.

### Subagent stream-timeouts require pragmatic parent-agent recovery

**Category:** bug-resolution
**Confidence:** 6/10

Subagent D (final checkpoint) hit `API Error: Stream idle timeout` mid-response after writing §7 Rubric, §8 Anti-Slop, §9 Behavioral Tests, and evals.json but before the reference-file cross-links step. Parent agent recovered by grep-checking what landed, confirming which task items were complete vs pending, and completing the remaining work directly (3 `Edit` calls to add §Consumers sections). Lesson: subagent timeouts leave partial work, not corrupt work — the work committed up to the timeout point is valid. Parent-agent recovery protocol: (1) grep for the expected deliverables to confirm what landed, (2) validate any files the subagent wrote (e.g., `python3 -m json.tool` on evals.json), (3) complete remaining items directly without re-dispatching a fresh subagent for a small residual. Avoid re-spawning subagents for <10% remaining work — the dispatch overhead exceeds the remaining work.
