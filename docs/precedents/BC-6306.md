## Task 2 — Verify-IDs as second-pass gate beats per-campaign-loop pairing

**Date:** 2026-04-28
**Category:** pattern-choice
**Confidence:** 8/10
**Tags:** pattern-choice, partial-failure, idempotent-resume, two-pass-vs-loop, mcp-orchestration

### Decision

When a phase combines a creation step + a follow-up configuration step against a vendor API, prefer two-pass shape (create-all → verify-all → configure-all) over per-item-loop shape (create+configure per item) when partial-failure reasoning matters.

### Inputs

- launch-campaign Phase 5 (now: step 5 create-all → step 6 verify-IDs → step 7 PATCH-all → step 8 metadata)
- Initial design doc Key Decision #4 (preferred per-campaign loop)
- Phase 6 ATTACH LEADS shape (already two-pass) as comparison
- /workflows:review architecture-reviewer flagged the drift (conf 9)

### Alternatives Considered

1. **Two-pass: create → verify → configure** *(chosen)* — verify-IDs gate at step 6 lets create-failures short-circuit Phase 5 before any PATCH state writes. Collapses two interleaved partial-failure modes into one — you either have partial-create OR partial-PATCH, never both interleaved. Phase 6 ATTACH LEADS already uses this shape.
2. **Per-campaign create+configure loop** — initial design's preference. Pairs creation and configuration per item; rejected because the loop creates two interleaved partial-failure modes (some campaigns exist + are PATCHed, others don't exist; or all campaigns exist but some are unPATCHed) that are harder to reason about than the two-pass shape's single failure axis.

### Outcome

- **Files changed:** plugins/marketing/commands/launch-campaign.md (Phase 5 step ordering); docs/designs/bc-6306-launch-campaign-plain-text-default.md (Key Decision #4 reconciled to as-built)
- **Tests:** validate.sh 0 errors; review architecture confirmed shape
- **Approved by:** auto-verified + architecture-reviewer (conf 9)

### Precedent Referenced

BC-2707 (two-call MCP confirmation gate — verified `update_campaign` is NOT on gate list, single PATCH call per item). Phase 6 ATTACH LEADS pattern (already two-pass).

## Task 3 — Amend design-doc with revised rationale beats restructuring code when as-built is genuinely better

**Date:** 2026-04-28
**Category:** pattern-choice
**Confidence:** 9/10
**Tags:** pattern-choice, design-doc-drift, post-execution-reconciliation, review-feedback, escape-hatch

### Decision

When /workflows:review flags drift between design doc and implementation, and the as-built shape is defensible on its own merits, amend the design doc with the revised rationale rather than restructuring the implementation back to match the original design.

### Inputs

- Design doc Key Decision #4 v1: "PATCH inside per-campaign loop ... NOT a second pass"
- Architecture-reviewer finding (conf 9): implementation does the rejected alternative
- As-built shape (two-pass) genuinely better — see BC-6306 Task 2 above
- Spec adherence cost vs. restructure cost: amend = 3 lines edited in design doc; restructure = ~50 lines reordered in launch-campaign.md + downstream metadata updates + re-validation

### Alternatives Considered

1. **Amend design doc with revised rationale** *(chosen)* — cheaper edit, preserves the as-built shape that's actually better. Updates Key Decision #4 + Alternatives Considered + Scope Boundaries to reflect the as-built shape with explicit reasoning. The initial design's claim (per-campaign loop simplifies partial-failure reasoning) was wrong on closer look; the design doc captures that learning.
2. **Restructure Phase 5 to match original design** — strict adherence to the design-as-written. Rejected because the as-built shape is genuinely better (collapses two failure modes into one), and restructuring would re-introduce the worse shape just to match a doc that was written before the implementation discovered the verify-IDs-as-checkpoint advantage.
3. **Ship without reconciling** — leave design doc and implementation in disagreement. Rejected because future readers would derive different conclusions depending on which artifact they read; design docs are load-bearing in this org and silent drift erodes their value.
