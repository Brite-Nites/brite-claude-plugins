# BC-12276 — Retiring the hand-rolled secret broker: scope beats hardening, and the shell changed underneath

<a id="BC-12276-task-1"></a>

## Task 1 — A broker holding a broader credential than it dispenses cannot be hardened into safety

**Date:** 2026-07-31
**Category:** architecture
**Confidence:** 9/10
**Precedent Referenced:** [ADR-044](../decisions/044-secrets-manager-machine-account-broker.md), [ADR-010](../decisions/010-plugin-secret-config-canon.md), [BC-6905](BC-6905.md), [BC-6906](BC-6906.md)
**Tags:** architecture, credential-scope, secret-broker, blast-radius, review-rounds

### Decision

When a component must hold credential A in order to hand out credential B, and A
is strictly broader than B, **replace the component rather than harden it**. Count
the scope gap before spending review rounds on the implementation.

`bw-run.sh` held an unlocked Bitwarden vault session — the key to every secret
the developer could read — in order to fetch 11 vendor API keys. Every attack
surface that mattered traced back to that one inversion, not to any particular
line of the script.

### Inputs

- PR #565 tried to remove the `bw unlock` tax by letting the wrapper read the
  vault **master password** from the macOS Keychain and mint its own session.
- It ran **nine review rounds** and produced **eight distinct security findings**.
- **Five of the eight were introduced by the hardening itself**, not present in
  the original script. The trust-path check added in round 3 was the source of
  the round-5 finding; its own helpers (`ls`, `find`, `readlink`) were
  PATH-resolved, so the attacker it defended against could steer its verdict.
- Findings clustered on one theme: the wrapper had to authenticate as the human,
  so every check it performed was a check the human's own compromised environment
  could subvert.
- The replacement (`bws`, Bitwarden Secrets Manager) authenticates as a **machine
  account** scoped to two named projects. It cannot read anything else, and the
  token is expirable and revocable per machine.

### Why the rounds did not converge

Each round fixed a real finding and the next round found a new one in the fix.
That is the signature of hardening the wrong layer. The review process was
working correctly; it was being pointed at an implementation whose *premise*
guaranteed a supply of findings. Nine rounds is the cost of learning that
empirically rather than by counting scope at the start.

### Alternatives Considered

1. **Machine-account secrets CLI (`bws`)** *(chosen)* — the broker's credential
   becomes narrower than the vault: read-only, two named projects, revocable.
   The scope gap closes, so the class of finding closes with it. Cost: a new
   runtime dependency with no Homebrew formula, and a long-lived token in each
   developer's shell profile — accepted deliberately, because that token is
   scoped and revocable where a master password is neither.
2. **Keep hardening `bw-run.sh`** — rejected after round 9. Each fix was locally
   correct; the premise was not.
3. **OS keychain per secret** — rejected. Moves custody to the machine, loses
   central rotation, and still needs a broker.
4. **Per-teammate machine accounts** — rejected as over-engineered for the team
   size. Revisit if per-person audit trails are ever required.

### Why durable

The test is cheap and mechanical: name the credential the component *holds*, name
the credential it *dispenses*, and compare their scope. If holding is broader than
dispensing, findings will keep arriving no matter how carefully the code is
written — because the gap, not the code, is what an attacker is reaching for.

This applies well beyond secret brokers: CI jobs with org-wide tokens that deploy
one service, service accounts with table-level grants that read one column,
scripts that `sudo` for one file write.

Note the counter-case in the same lineage: `gbrain-team-broker.sh` (ADR-045)
survives as an in-repo broker precisely because it holds only what it dispenses.
The lesson is scope, not "no in-repo brokers."

## Task 2 — A broker swap can silently change which shell interprets your script

**Date:** 2026-07-31
**Category:** bug-resolution
**Confidence:** 9/10
**Precedent Referenced:** [ADR-044](../decisions/044-secrets-manager-machine-account-broker.md), [CONTRIBUTING.md § Plugin secret-config canon](../../CONTRIBUTING.md#plugin-secret-config-canon), [BC-12347](BC-12347.md) (same class: shell semantics invisible to review)
**Tags:** bug-resolution, posix-sh, dash, pipefail, cross-platform

### Decision

When migrating a command wrapper, treat **"which shell runs the body, and does it
still run one at all"** as a required check — separate from, and easier to miss
than, re-quoting the arguments.

`bws` joins the command argv with spaces and runs the result through `sh -c`. The
replaced `bw-run.sh` used `exec "$@"` and never shell-parsed anything. So the
migration changed a probe body from **bash** to **`/bin/sh`**, which is dash on
most Linux boxes.

### Inputs

- The Phase 3d four-provider verification probe in
  `plugins/marketing/commands/setup-tam-map.md` opened with `set -uo pipefail`.
- `pipefail` is not POSIX. dash rejects `-o pipefail`.
- `set` is a POSIX **special builtin**, so a failing `set` exits a non-interactive
  shell outright — the body died on line 1 and ran none of its four checks.
- Reproduced directly:

  ```
  $ readlink -f /bin/sh          →  /usr/bin/dash
  $ /bin/sh -c 'set -uo pipefail; echo REACHED'
  /bin/sh: 1: set: Illegal option -o pipefail     # rc=2, "REACHED" never prints
  ```

- The probe had previously been wrapped in an explicit `bash -c`, which the
  migration dropped as redundant. It was not redundant; it was load-bearing.
- **macOS hides this.** `/bin/sh` there is bash in POSIX mode, which accepts
  `pipefail`. Anyone verifying on a Mac sees a green board.

### Fix

Plain `set -u`. `pipefail` was never load-bearing here — every pipeline in the
body ends in `jq -e ... && echo 1 || echo 0`, so `&&` already tests jq's status.
Where bash really is needed, ask for it: `-- "exec bash -c '...'"`.

### Alternatives Considered

1. **Drop to `set -u`** *(chosen)* — one token, stays POSIX, keeps fail-on-unset
   so a missing injected secret still errors loudly. Verified by extracting the
   body from the doc and running it under `/bin/sh` with a stubbed `curl`: four
   checks green, exit 0.
2. **Re-wrap in `exec bash -c '...'`** — restores the old shell, but the body is
   already dense with nested single and escaped double quotes, so adding a
   quoting layer trades a known break for a fragile one.
3. **Require bash as a runtime dependency** — rejected. Nothing else in the
   command needs it.

### Why durable

Two things made this invisible to ordinary review. The failure is **silent and
total** — a probe that exits before its first assertion looks the same as one
that had nothing to report, and `set -x` shows nothing because the shell is gone
before tracing. And it is **platform-split**: correct on macOS, dead on Linux, so
a team on one platform can ship it and a teammate on the other inherits it.

The generalizable check when swapping any `run -- <cmd>` wrapper: does the new
tool `exec` the argv directly, or does it hand a joined string to a shell? If a
shell, **which** shell? Anything that ran under an explicit `bash -c` before the
swap needs re-checking, not just re-quoting.
