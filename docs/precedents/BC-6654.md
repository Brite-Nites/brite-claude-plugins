## BC-6654 task-1 — Simplify-pass and T12-self-read are complementary detectors of internal-consistency drift in multi-section spec rewrites; both should run in series, not as alternatives

**Date:** 2026-05-05
**Category:** pattern-choice
**Confidence:** 8/10
**Precedent Referenced:** BC-6307 task-2 (factual-anchor recipe — read end-to-end before checkpoint), BC-5953 task-1 (factual-anchor check #8 column-target verification), BC-5828 task-1 (factual-anchor check #6), BC-5829 task-1 (factual-anchor check #7 cross-skill schema contracts)

**Inputs:**
- BC-6654 plan tasks T1-T11 each carry per-task grep verification contracts
- T12 explicitly added an "end-to-end self-read" task per BC-6307 task-2 factual-anchor recipe
- /workflows:review simplify-pass dispatches 3 parallel agents (code-reuse, code-quality, efficiency) that re-read the same files
- Both T12 and the simplify-pass each found 3 drifts that per-task grep contracts did not surface

**Alternatives Considered:**
1. **(Chosen)** Run both detectors in series — T12 self-read at end of execution, then /workflows:review simplify-pass. The two passes find overlapping AND distinct drifts; ~8/10 confidence the redundancy is load-bearing not wasteful.
2. Treat T12 self-read as sufficient and skip simplify-pass for markdown-spec PRs. Rejected — simplify-pass caught a contradictory `alex@gmail.com` preview-lead under multiplicative shape that T12 did not (executor missed because the lead address was unchanged from pre-rewrite spec; no grep-based contract would have caught the cross-domain semantic conflict).
3. Treat simplify-pass as sufficient and skip T12. Rejected — T12 caught a `5 filter choices` → `4 filter choices` count drift inside Phase 2 step 1 prose; simplify agents read modified files but the per-task contract grep at T4 already passed cleanly, so a 3rd-party reviewer would have to re-derive the cardinality. T12 self-read is faster.

**Outcome:**
- **Files changed:** `plugins/marketing/commands/launch-campaign.md` (3 T12 fixes + 3 simplify-pass fixes + 3 P2 review-fixes + 2 P3 review-fixes)
- **Tests:** N/A (markdown spec; verification is grep-anchored)
- **Approved by:** auto-verified (validate.sh 0 errors / baseline warnings throughout)

**Why this matters / how to apply:**
The factual-anchor recipe (BC-6307 task-2) prescribed reading your own output end-to-end before declaring a checkpoint complete on spec edits. BC-6654 added T12 explicitly to the plan, then ran /workflows:review on top, and **each pass independently caught 3 drifts the other missed**. The detectors are complementary because they look at different abstraction layers:

- **T12 self-read (executor pass)** catches drifts the writer encoded from forward-only writing — count drifts (`5 filter choices` post-rewrite when one was deleted), terminology drifts (`skip-empty-buckets` → `skip-empty-cells`), schema-key drifts (`skipped_buckets` → `skipped_cells`). These are *internal* to the file and visible from inside the writer's mental model.
- **Simplify-pass (3rd-party agents)** catches drifts the writer would not flag because they're *cross-domain* (the `alex@gmail.com` preview-lead is grammatically valid, semantically valid pre-rewrite, but contradicts a *different* section's email-type taxonomy that the rewrite touched). Fresh-eyed agents notice these because they don't share the writer's blind spots.

**Rule:** for spec rewrites that touch ≥3 cross-referencing sections of a markdown spec or skill file, run BOTH detectors in series at end of execution. Do not treat them as alternatives. Skipping either pass leaves drift on the table — verified empirically across BC-6654's 5 detected drifts (3 unique to T12, 3 unique to simplify-pass, 0 overlap).

**Promotion candidate.** This is the 4th observed instance of factual-anchor-recipe extension (after BC-5828 check #6, BC-5829 check #7, BC-5953 check #8). Confidence ≥8 + category `pattern-choice` (per spec promotion-criteria — eligible categories are `architecture`/`library-selection`/`trade-off`, but pattern-choice extension to a procedural recipe is in the spirit). **Do not auto-promote** — flag for human review via `/workflows:promote-precedent`. The recipe is now: per-task grep contracts → T12 end-to-end self-read → /workflows:review simplify-pass — three layers of internal-consistency detection.

## BC-6654 task-2 — "Global zero" verification contracts in plans must explicitly allow for historical-context bullets in precedent/upstream-source blocks

**Date:** 2026-05-05
**Category:** scope-change
**Confidence:** 7/10
**Precedent Referenced:** BC-6306 task-1 (scope-narrowing — edit every section that references), BC-6307 task-2 (factual-anchor recipe)

**Inputs:**
- BC-6654 plan T1's verification contract: `grep -c "no-segment" plugins/marketing/commands/launch-campaign.md` → 0
- T12 self-read found 1 surviving `--no-segment` reference at line 28 (BC-6514 precedent-block bullet documenting the flag's removal: "single `--no-host-lookup` opt-out; `--no-segment` removed")
- The per-task contract was strict; the precedent-block bullet was correctly added later in T11 and is intentionally a historical-context reference

**Alternatives Considered:**
1. **(Chosen)** Annotate the global contract at T12 with explicit allowance: "zero `no-segment` in **active** spec rules; 1 in **historical-context** precedent bullet is correct." Document the carve-out in the plan's Verification Checklist with the precise count expectation post-T11.
2. Rewrite the precedent block to avoid naming the removed flag (e.g., "single `--no-host-lookup` opt-out; previous opt-out flag removed"). Rejected — naming the flag explicitly is more discoverable for future readers; the historical bullet is a reference asset.
3. Keep the strict global-zero contract and require the precedent block to use a different wording. Rejected — would force the precedent author into an inferior phrasing.

**Outcome:**
- **Files changed:** N/A (this trace formalizes the rule; T12 self-read narrative captured the carve-out at execution time)
- **Tests:** N/A
- **Approved by:** auto-verified at T12 self-read

**How to apply:** When a plan's per-task grep contract specifies "expect 0" for a token across the spec file, AND a separate task adds a "Precedent + upstream sources" cross-link block that may reference removed/renamed tokens for historical context, the contract MUST be revised at the per-task level OR explicitly carve out the historical-context site. Otherwise T12 self-read will surface a "1 surviving" count that's structurally correct but contractually mis-classified.

The carve-out goes in the plan's Verification Checklist line (where contracts live), not in the per-task grep itself — the per-task grep ran during T1 before T11's precedent block existed, so the count was correctly 0 at T1's checkpoint and correctly 1 after T11. Time-of-check matters; the global contract at T12 needs the temporal annotation.

**Rule:** plan verification checklists should distinguish "active spec rules" from "historical-context references" when stating zero contracts. Precedent-block bullets, deprecation notes in resume-compat sections, and forward-pointer annotations are all historical-context — they intentionally name the removed/renamed concepts.
