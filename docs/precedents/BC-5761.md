# BC-5761: Fix-review loops converge in 4-5 iterations; each fix introduces new spec surface

**Date:** 2026-04-20
**Category:** pattern-choice
**Confidence:** 8/10

## Decision

For non-trivial markdown-spec PRs (skill files defining LLM-instruction flows with state objects, MCP dispatch tables, and multi-group UX contracts), the fix-review loop converges in 4-5 iterations, not 1-2. Each round of fixes introduces new spec surface (new state fields, new edge-case handlers, new approval groups), which generates new review findings in the next iteration. Budget accordingly: expect iter 4 to re-introduce P1s from iter-3 fixes, iter 5 to converge with 0 P1 / 0 P2. Cap at iter 5 and ship.

## Context

BC-5761 implemented Phase 3 of `/cadence:weekly` — a ~390-line markdown skill defining Linear mutation batch execution with decision-path derivation, pre-flight idempotency, quality-gate re-runs, 3 pre-preview groups, 5 regular approval groups, and an audit log. Review was run 5 times in a loop:

| Iter | P1 | P2 | Pattern |
|---|---|---|---|
| 1 | 4→3 | 10→7 | Initial bugs: schema drift (ID vs name form), silent user-intent drops (CQ1=Park), missing allowed-tools |
| 2 | 0 | 2→1 | Refinements from iter-1 fixes: CQ3 parse routing through wrong gate check |
| 3 | 0 | 6 | More refinements: AC #3 group-count drift, _create_preflight_cache unwired, "Drop cancel" misleading wording, preview-vs-approve mismatch, raw-text sanitization, merge flow unvalidated |
| 4 | **4** | 2 | Iter-3 fixes introduced new P1s: placeholder-row has no pre-flight/execute handler, Re-enter wrong direction, merge one-question violation, Phase-0 cache dependency doesn't exist |
| 5 | 0 | 0 | Converged |

Key insight: **iter 4 surfaced MORE P1s than iter 2 or 3.** That's because my iter-3 edits (pending-cq3-reparse placeholder rows, _create_preflight_cache, merge validation claims) introduced new spec surface without updating the downstream sections that consume them. The architecture-reviewer catches this drift class specifically — it's the BC-5760 learning recurring at a within-skill-section level rather than across-phase level.

The loop converged only when all cross-section consistency was established: every state field in § 1 Inputs is used somewhere, every `result` enum value is set somewhere, every pre-flight rule matches a dispatch row, every AskUserQuestion follows one-question-at-a-time on infra-destructive paths.

## Alternatives Considered

1. **Ship after iter 1 review** (the "accept P2s as follow-ups" path). Rejected. Iter 1 found 4 P1s + 10 P2s — real bugs that would fail at runtime (e.g., the before/after schema only declared IDs but § 7.3 called `.cycleName`/`.stateName`; every mutation call would have failed). Shipping those is strictly worse than 5 fix commits.
2. **Strict single-iteration loop (fix what review finds, ship)**. Rejected. That's what iter 1 is; the pattern shows iter 2-3 finds genuine bugs introduced by iter-1 fixes (CQ3 routing through wrong check, schema drift from newly-added fields). Missing those makes the skill half-broken.
3. **Unbounded loop until 0 findings**. Rejected. Each iteration finds ~2-6 new findings from the fixes of the previous round. At iter 5 this had diminishing returns (only 1 cosmetic P3 in iter 5). An unbounded loop wouldn't terminate because markdown spec has infinite refinement surface.
4. **Cap at 5 iterations, ship with residuals documented** (chosen). 5 iterations captures all iter-1 real bugs (P1 + high-conf P2) plus the drift introduced by fixes (iter 2-4), and lands on convergence (iter 5). PR body documents the iteration history.

## Outcome

7 commits on the BC-5761 branch. Final state: 0 P1, 0 P2 per parallel architecture-reviewer + code-reviewer. PR #145 opened at https://github.com/Brite-Nites/brite-claude-plugins/pull/145.

**Reusable beyond this case.** Every future multi-section skill PR in the Cadence plugin (BC-5762 narrative) and in any plugin with LLM-instruction markdown should budget for 4-5 review iterations. The pattern per iteration:

- Iter 1: initial bugs + architecture issues
- Iter 2: drift from iter-1 fixes
- Iter 3: refinements
- Iter 4: drift from iter-3 fixes (watch for new P1s)
- Iter 5: convergence (≤1 P3)

Cost ~= 5× parallel review time. For a ~400-line skill, that's ~30-40 minutes of agent time per iteration, or ~3 hours total across the loop. Worth it for destructive-path skills (Linear batch mutations, SF deploys, any phase 3+ gate).

**Secondary learning — dual-form ID+name schema is required for Linear MCP skills.** Pre-flight reads (get_issue) return ID-form fields (cycleId, stateType, assigneeId); write calls (save_issue) take name-form (assignee, cycle, state). A mutation row's `before`/`after` must carry BOTH forms from derivation time, or the execute step will reference undefined fields. Declared in § 2.1 with explicit "Both ID-form and name-form populated at derivation time" paragraph.

**Tertiary learning — placeholder rows need explicit skip rules in every section that iterates state.mutations[].** When a spec introduces a "virtual" mutation (pending-cq3-reparse placeholder that displays in preview but isn't a real Linear write), every downstream consumer (§ 3 pre-flight, § 7.3 execute, § 8 resume) needs an explicit short-circuit. Missing even one = destructive write leak.

**Quaternary learning — feedback_one_question_at_a_time.md applies especially to infra-destructive paths.** Iter-3 § 6.1 Merge manually wrote "follow-up free-text AskUserQuestion collecting cycle + assignee + state + labels" (one AQ, 4 fields). Iter-4 caught this as P1. For infra paths (Linear batch writes, cross-project merges, cancel supersede), follow-ups collecting ≥2 fields must be sequential AQ calls.

**Strengthens** BC-5760 precedent (state-schema drift caught by review). Extends from cross-phase drift to within-skill drift between § 2.1 schema declaration and § 3/§ 7/§ 8 consumers.

**Precedent Referenced:** BC-5760 (state-schema drift). BC-5758 (superseded scope — applied here for AC #8's "7 mutation types" vs skill's 8 types; documented the label-change reserved type).
