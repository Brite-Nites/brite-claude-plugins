## task-1 — Precedent-fix scope extension: canon-level amendments when orchestrator faithfully echoes upstream Q-lock error

**Pattern type:** pattern-application (BC-6963 task-1 — extension to canon layer; 2nd surface of precedent-fix-scope concept, NEW extension axis)

**Context.** Iteration 1 of `/workflows:review thorough` on BC-6965 surfaced a P2 (conf 8) and a P3 (conf 8): (a) the per-sub-flow write count enumerated 4 items summing to 8 but stated `= 7 writes` — the orchestrator faithfully echoed Q47 sub-decision 2's lock text (memory:752) which itself has the arithmetic gap; (b) the L3 reviewer roster citation `per Q23 mod 2` referenced canon text (memory:515) listing `CEO/Story/Eng/QA/Docs`, but the canonical L3 roster across plugin CLAUDE.md + agent dispatch MATRIX + sibling commands is `Story/Eng/Design/QA/Docs` — CEO is L1/L2-only per `plan-ceo-reviewer: L1, L2` matrix rows. Both issues are upstream Q-lock typos that the orchestrator inherited via faithful-echo. BC-6963 task-1 covered sibling-orchestrator fixes (same plugin + line-identical + same downstream gate); this session extends the principle to the canon layer.

**Decision.** Apply Q23 amendment 1 + Q47 amendment 1 to `plugins/flow-architecture/docs/design-rationale/project_fda_plugin_interview.md` in the SAME PR as the orchestrator implementation, per BC-6955 task-3 source-of-truth precedent ("fix should be filed against the source-of-truth, not the derivative"). Rationale:
1. Without canon amendments, future orchestrators (`/flow:add-domain` BC-6964) would re-derive the same `= 7 writes` claim by faithful echo, perpetuating the gap.
2. The schema-discipline amendment pattern (Q21/Q24/Q29/Q31/Q41 amendments) already establishes the precedent for canon-level corrections; this session is the 6th application, 1st by /workflows:review fold-in (prior 5 were author-time catches).
3. Both errors are line-identical to their canon origins — fixing only the orchestrator would leave the canon as a future fail-mode source.
4. The Linear issue body still has `= 7 writes` text; we deliberately did NOT amend Linear (canon + orchestrator are the source-of-truth pair; the Linear issue body is a write-once derivative).

**Rejected alternatives:**
- Footnote-only fix in orchestrator: would leave canon broken; next orchestrator author would re-encounter the same arithmetic gap.
- File follow-up Linear issue for canon: would defer the fix and split the review trail across two PRs; the orchestrator and canon fixes are semantically coupled.
- Re-derive the count in orchestrator only: would diverge from Q47 sub-decision 2 text without an amendment audit trail — violates the schema-discipline amendment pattern.
- Amend the Linear issue body too: Linear issue bodies are derivative-write-once-at-Plan-time; amending mid-flight would conflate plan and design history. Deferred to a non-blocking Linear-side cleanup task.

**How to apply.** When `/workflows:review` surfaces a defect in artifact X (orchestrator, skill, agent) that is a faithful-echo of an upstream Q-lock typo or arithmetic gap, file a canon amendment in the same PR if:
(a) the orchestrator and canon share the originating Q-lock (single source-of-truth lineage),
(b) the schema-discipline amendment pattern is already established for that Q-lock-family (Q21/Q24/Q29/Q31/Q41 amendment precedent applies),
(c) fixing only the derivative would leave a future-orchestrator fail-mode (line-identical drift in sibling orchestrators not yet written).
If any of (a)/(b)/(c) is violated — e.g., the upstream Q-lock has no amendment precedent for its family — file a follow-up issue.

## task-2 — Multi-correction canon amendment in a single Q<N> amendment <M> entry

**Pattern type:** pattern-choice (NEW — 1st surface; extension of schema-discipline amendment pattern)

**Confidence:** 8/10

**Context.** Q47 amendment 1 needed to correct TWO independent errors in the Q47 lock:
1. Q47 sub-decision 2's arithmetic gap (`= 7 writes` total vs enumerated items summing to 8).
2. Q47 sub-decision 5's `memory:70` citation typo for Q13.4 (line 70 is Q12 start; Q13.4 is at memory:88).

The schema-discipline amendment pattern (precedent: Q21 amendment 1, Q24 amendment 1, Q29 amendment 1, Q31 amendments 1+2, Q41 amendment 1) historically covered one correction per amendment. The question: file one Q47 amendment 1 covering both corrections, or two separate amendments (Q47 amendment 1 + Q47 amendment 2)?

**Decision.** Single multi-correction amendment. Q47 amendment 1 explicitly covers both corrections with two clearly-delineated paragraphs, each citing its caught-by source (P2 conf 8 arithmetic + P3 conf 9 citation typo). Rationale:
1. Both errors share the same originating Q-lock (Q47).
2. Both errors share the same catch source (BC-6965 /workflows:review iteration 1).
3. Both errors share the same fix mechanism (canon amendment with audit trail).
4. Two separate amendments would over-fragment the audit trail; readers cross-referencing Q47 would jump between two siblings for what is semantically one set of corrections.
5. The schema-discipline pattern requires "original text preserved" — Q47 sub-decision 2 original AND Q47 sub-decision 5 original are both preserved verbatim, satisfying the pattern.

**Rejected alternatives:**
- Two separate amendments (Q47 amendment 1 + Q47 amendment 2): would atomize the audit trail across two entries that share a catch event. Worse for future readers.
- One amendment covering only the arithmetic correction + a separate document for the citation typo: would scatter the corrections across the codebase.
- Roll up both into a Q47 sub-decision rewrite: would lose the "original text preserved" discipline that the amendment pattern depends on.

**How to apply.** When two or more corrections to the same Q-lock are surfaced in the same catch event (same review session, same caught-by source, same fix mechanism), file ONE multi-correction amendment with:
- Explicit amendment-number ("Q<N> amendment <M>") as if for a single correction.
- Two (or more) clearly-delineated correction paragraphs inside the amendment body.
- Each correction paragraph names its catch source (P-level + confidence + reviewer).
- Original text for EACH affected sub-decision preserved verbatim in the canon body (above the amendment).
- A "second correction in this amendment" or similar transitional phrase between corrections.
If the corrections originate from different catch events (different review sessions, different caught-by sources), file separate amendments — the multi-correction shape is for a single semantic catch.

**Telemetry watch.** Track multi-correction amendments separately from single-correction amendments. After 3 multi-correction surfaces, consider amending the schema-discipline amendment pattern itself to canonize the multi-correction shape. Joint promotion candidate with BC-6965 task-1 (both are amendment-pattern extensions).

## task-5 — Iterative review-loop convergence with self-introduced defect class

**Pattern type:** pattern-choice (NEW — 1st surface)

**Confidence:** 8/10

**Context.** User invoked `/workflows:review` then said: "use sequential-thinking and ultrathink to solve all p1, p2, and p3. then run another review and do that in a loop until no issues return." This instructs the assistant to iteratively fold in findings + re-review until convergence — distinct from the standard one-shot review pattern.

**Decision.** Run 3 iterations:
- **Iter 1**: standard `/workflows:review thorough` — 1 P2 + 5 P3 + 5 simplify + 2 filtered.
- **Iter 2**: fold-in all 13 findings (including filtered for thoroughness) + 2 canon amendments. Re-run all 4 review agents. Surfaced 1 new P3 conf 9 (citation typo in the fold-in's NEW content).
- **Iter 3**: fix the iter-2 finding + re-run all 4 review agents. All clean. Loop terminates.

**Why 3 iterations not 2.** Iteration 2's fold-in introduced a defect of its own (the malformed citation in the new Q23 mod 2 reference paragraph). The 2-iteration convergence assumed for one-shot review is insufficient when the fold-in body is non-trivial. The 3-iteration shape — iter 1 surfaces, iter 2 fixes + may introduce new, iter 3 verifies clean — is the realistic minimum for "loop until no issues return" when fold-in is substantive.

**Rejected alternatives:**
- 2-iteration convergence: would have shipped with the L317 malformed citation. The iter-2 fold-in self-introduced defect is a real class.
- Block fold-in until each finding is independently verified pre-edit: would atomize the fold-in pass per BC-6958 task-3 (single coherent fold-in commit is the established pattern); slows by 5-10x with no obvious quality benefit.
- 4+ iterations: iter 3 cleanly converged; running iter 4 would be sunk cost. Stop at first clean iteration.

**How to apply.** When the user requests "loop until clean" or equivalent, plan for 3 iterations as the convergence floor:
- Iter 1: review.
- Iter 2: fold-in + re-review. EXPECT 0-2 new findings introduced by fold-in itself (citation drift in new paragraphs, schema drift in new code paths, etc.). These are real, not false positives.
- Iter 3: fix iter-2 issues + re-review. If clean, terminate. If new issues, continue (rare).
- Cap at 5 iterations. If not converged by iter 5, escalate to user with the finding-introduction trend (each iter should reduce the count; a flat or growing count means the fold-in pattern is wrong, not the codebase).

Budget telemetry: this session ran 4 review agents × 3 iterations = 12 review-agent invocations + 3 simplify agents × 1 iteration = 3 simplify-agent invocations + 2 canon amendments + 11 orchestrator edits + 1 citation fix. Token cost ≈ 4-5x a single-shot review.

**Telemetry watch.** Track iteration count to convergence per session. If most "loop until clean" sessions terminate at iter 3, the pattern is durable. If iter 5+ becomes common, the fold-in or review-agent quality is degrading. Promotion threshold: 3 surfaces of 3-iteration convergence (this is the 1st).
