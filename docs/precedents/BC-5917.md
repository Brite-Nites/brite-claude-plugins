# BC-5917: Frontmatter convention for Brite-originated reference files

**Date:** 2026-04-22
**Category:** pattern-choice
**Confidence:** 6/10

## Decision

For reference files under `plugins/marketing/references/` that are **Brite-originated** (not ported from `Revgrowth1/ai-gtm-workflows` or any other upstream), use frontmatter of the shape:

```yaml
---
source: <citation of external authorities the content paraphrases, semicolon-separated>
license: Brite-originated; <short paraphrase/attribution note>
---
```

Do NOT include:
- `upstream_path:` — reserved for Revgrowth-ported files that have a corresponding file in the upstream repo.
- `<!-- Adapted from Revgrowth1/ai-gtm-workflows@... -->` HTML attribution banner on line 1 — UPSTREAM.md reserves this for Revgrowth-adapted files.

Do NOT add the file to `plugins/marketing/references/UPSTREAM.md`'s per-file manifest — that table is scoped to Revgrowth ports. Brite-originated files belong in `README.md` only (§ Contents + § Expected consumers).

## Context

`offer-design-frameworks.md` was the first Brite-originated file added to `plugins/marketing/references/`. The three existing reference files (`creative-thinking-models.md`, `hidden-signals-library.md`, `shelf-life-patterns.md`) are all Revgrowth ports — two adapted with Brite-added sections, one verbatim. Their frontmatter all points at `source: Revgrowth1/ai-gtm-workflows@<sha>` plus `upstream_path: references/<filename>.md`.

For a non-upstream file, there is no upstream_path to point at. Two candidate conventions:

- **(a) No frontmatter at all** — simplest; breaks visual consistency with peers.
- **(b) Frontmatter naming the external-authority citations in `source:` + a `license:` declaration that content is Brite-paraphrased** — preserves the frontmatter slot for future tooling (a consumer that wants to know "what's this file based on?"), credits the source authorities, and sidesteps the missing-upstream-path problem by omitting the key.

Chose (b).

## Alternatives Considered

1. **No frontmatter** (Option a). Rejected — drops the metadata hook that peer files use. Any future tooling (e.g., a `references/` index builder, a citation checker, a freshness tracker) would need a special case for files with and without frontmatter.
2. **Frontmatter with `upstream_path: N/A` or `upstream_path: brite-originated`** — rejected. Dishonest about what the key means; future maintainers would see the key and go looking for a Revgrowth path that isn't there. Omitting the key is clearer than spoofing it.
3. **Add to UPSTREAM.md manifest** with a "Brite-originated" row — rejected. UPSTREAM.md's whole purpose is tracking a specific upstream (Revgrowth) at a pinned SHA. Adding a non-upstream row dilutes that contract.

## Outcome

Delivered `plugins/marketing/references/offer-design-frameworks.md` with the chosen frontmatter shape. `plugins/marketing/references/README.md` cross-linked in § Contents and § Expected consumers; UPSTREAM.md untouched. `validate.sh` passed (baseline 0 errors / 16 warnings preserved); `check-guardrails.sh` 0 violations. `/workflows:review` triage: TRIVIAL (pure markdown content, 0 runtime code). Merged as PR #175.

**Reusable beyond this case.** The pattern applies to every future Brite-originated reference file, including:

- BC-5918 (`experiential-lighting-vendor-landscape.md` — Brite vendor research, no upstream).
- Any Brite-originated playbook, taxonomy, or framework file that paraphrases external authorities.

**Secondary observation.** The issue body for BC-5917 explicitly said _"Add frontmatter (if convention used in peer references) — check existing files first."_ That single instruction — "if convention used" rather than "match convention" — is what opened the door to designing a Brite-originated variant instead of forcing a Revgrowth-port frontmatter shape onto a non-upstream file. Worth preserving this hedge in future roadmap issues that produce first-of-kind artifacts.

**Tertiary observation.** The convention decision was load-bearing for the next roadmap issue (BC-5918). If BC-5918 had shipped first with a different (or no) frontmatter shape, the two Brite-originated files would have diverged and a future retrofit PR would have been needed. Ordering BC-5917 before BC-5918 in the roadmap was the right call for this reason — R-1 and R-2 are parallel in the roadmap dependency graph but sequencing them serially let R-1 set the convention.
