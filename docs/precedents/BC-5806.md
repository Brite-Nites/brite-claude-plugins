## Task 1 — Simplify-pass `${dir%/*}` catch on a 30-line bash file: small files have non-trivial perf surfaces too

**Category:** pattern-application
**Confidence:** 7/10
**Tags:** pattern-application, simplify-pass, bash-perf, hot-path-hook, claim-grounding

### Decision

The first commit of BC-5806 (`3fbe73a`) had a 30-line bash probe that walked `$PWD` up using `parent="$(dirname "$dir")"` — one subshell + one `dirname` exec per loop iteration. The simplify-pass efficiency agent flagged this at **P2 [8/10]**: "Replace with pure parameter expansion: `parent="${dir%/*}"; [ -z "$parent" ] && parent="/"`. Eliminates all forks; loop becomes pure builtins."

I applied the fix (commit `50be366`). Measured non-SF cwd cost dropped from **7ms → 3ms** (~57% reduction). For a hook that fires on every Claude Code session start, this is a real win, not noise.

The pre-fix timing was already inside the spec budget (T6 <10ms). It would have been easy to dismiss the finding as "already passing perf tests, why bother." The reason to apply it anyway: the budget is a *floor*, not a *target*. A hook on the session-boot hot path should be cheaper than required so future additions don't push past the limit.

### Alternatives considered

1. **Apply the fix during simplify pass** — Chosen. The finding was P2 confidence 8/10, behavior-preserving, and addressed a real fork-per-iteration cost. Auto-fix in simplify is the right gate.

2. **Defer to "we already pass T6, ship as-is"** — Rejected. Performance budgets are boundaries, not goals. Below-budget code with known inefficiencies accumulates dead weight in hot paths.

3. **Replace with `cd "$dir/.."` chain** — Considered but rejected. `cd ..` resolves symlinks and changes the shell's cwd as a side effect (matters less here since we exit immediately, but lexical walk via string ops is cleaner and faster).

### Rule derived

**Small bash files on hot paths can still hide material perf bugs.** A 30-line probe is not "trivial enough to skip the simplify pass" — fork-per-iteration costs are linear in path depth, and the hot-path multiplier (every session boot) makes them visible at the millisecond scale. Run the simplify pass even on tiny scripts; trust ≥7/10 efficiency findings on hot-path code.

This sibling-extends BC-5928 task-1 ("mechanical ports have a factual-correctness surface that simplify catches but brainstorm/plan cannot") from *factual claims in skill bodies* to *micro-perf claims in shell scripts*. Same shape: simplify is the discovery surface for a quality dimension that brainstorm and plan don't evaluate.

### Promotion note

This is the **2nd surface** for the "simplify pass catches a quality dimension brainstorm/plan miss" pattern (1st: BC-5928 factual drift in skill body; 2nd: BC-5806 micro-perf in hot-path shell). At the 3rd surface (any further "simplify catches X that brainstorm/plan can't") promote to architecture-9 as a unified "simplify is the cross-cutting quality gate" rule. Adjacent claim-grounding patterns: BC-5946 task-3 (integration-guide claims must grep wrapper source), BC-5901 task-3 (simplify catches cross-site shape-claim drift), BC-5928 task-1 (factual drift in mechanical ports). The cluster is converging.

## Task 2 — A single code-reviewer P3 stylistic finding can be a probe for cross-cutting user preference

**Category:** pattern-choice
**Confidence:** 7/10
**Tags:** pattern-choice, review-validation, user-preference-discovery, feedback-memory, gate-as-probe

### Decision

The code-reviewer flagged a single P3 [7/10]: "Banner uses leading 🔧 which collides visually with workflows plugin's `🔧 Brite Session Context` SessionStart banner. Two consecutive 🔧 banners on session start in brite-salesforce." Fix would be a one-character emoji swap.

Step 6 validation CONFIRMED the finding. At Step 7's user-decision gate, I offered three glyph alternatives (🧰 toolbox, ⚡ lightning, 🛠️ hammer-and-wrench) plus a "ship as-is" option.

User reply: **"I don't want to use emojis at all."**

The finding wasn't really about emojis — it was a probe that surfaced a cross-cutting user preference (no emojis in any generated content). The fix scope expanded from "swap one glyph in this banner" to "drop the emoji from this banner AND save the no-emojis-anywhere preference as a feedback memory."

Saved as `feedback_no_emojis_in_generated_content.md`. The feedback memory is generalizable to all future banners, scripts, docs, commit messages, PR bodies, etc., even when an issue spec or upstream template includes an emoji.

### Alternatives considered

1. **Treat the P3 as scoped to BC-5806; ship the toolbox emoji per the gate selection** — Rejected. User explicitly chose "no emojis at all" as the gate response; honoring that requires updating preference at the user level, not just this one banner. Ignoring the broader signal would have left the same friction on the next emoji-bearing PR.

2. **Skip the user-gate question entirely; auto-apply emoji swap in Step 7 as a "obvious P3 fix"** — Rejected. P3s are user's-call per spec; the gate exists precisely so that a stylistic preference can be probed before locking it in. Auto-applying would have shipped a still-unwanted emoji and lost the cross-cutting signal.

3. **Save the preference as a CLAUDE.md gotcha instead of a feedback memory** — Rejected. The existing system-wide instruction ("only use emojis if the user explicitly requests it") covers the project-level rule. The feedback memory captures THIS user's stricter bar ("no emojis ever, even when the issue spec includes one") — that's user-scoped, not project-scoped, so it belongs in user-side memory.

### Rule derived

**A code-reviewer P3 about a stylistic detail (emoji choice, formatting glyph, naming flavor) can be a high-leverage probe for cross-cutting user preference.** When validation confirms the finding, present it as a user-decision gate even if the surface fix is trivial. The user's response may generalize beyond this PR; if it does, save as a feedback memory and apply forward.

Procedure:
1. Step 6 validation confirms a stylistic P3.
2. Step 7 gate offers 2-3 fix options + "ship as-is."
3. If the user response is broader than the offered options ("none of those" / "I want X always"), treat it as a probe-success.
4. Apply the local fix in this PR.
5. Save the cross-cutting preference as a feedback memory at the user level (not CLAUDE.md, which is project-level).

### Promotion note

First instance. The mechanism is generalizable — any stylistic P3 (formatting, naming, glyph) can be a probe — but the data is N=1. If a future session surfaces a similar pattern (P3 → user gate → cross-cutting preference probe → feedback memory), promote to pattern-application 8/10. The probe-as-gate framing also extends BC-5869 task-2 ("explain-before-options UX pattern") in the inverse direction: instead of giving context before asking, here a narrow ask surfaced unexpected breadth in the user's reply.

## Task 3 — BC-5947 reconciliation-table pattern reaches 2nd instance: issue-vs-ground-truth drift codified at top of plan doc

**Category:** pattern-application
**Confidence:** 7/10
**Tags:** pattern-application, reconciliation-table, issue-drift, plan-front-matter, deferred-decision

### Decision

The BC-5806 issue body (authored 2026-04-19) directed the banner to advertise `brite-deploy, brite-permissions, brite-apex, brite-metadata, brite-soql`. By 2026-04-26, those skill names did not exist — Phase 3 customization decided to keep upstream `sf-*` filenames (master-plan §13: "Skill renaming `sf-*` → `brite-*` deferred").

Substituting `brite-*` would have advertised non-existent skills. Substituting `sf-*` was the only correct option, but it's a departure from the issue spec. I applied the BC-5947 task-1 pattern: a **one-row reconciliation table** at the top of the plan doc, captured in plan §"Issue-vs-ground-truth reconciliation," with a grep-verifiable resolution column.

Captured table (verbatim from `docs/plans/BC-5806-plan.md`):

| # | Spec text | Ground truth (2026-04-26) | Resolution |
|---|---|---|---|
| 1 | Banner names `brite-deploy, brite-permissions, brite-apex, brite-metadata, brite-soql` | Skills are still `sf-*` — renaming deferred per master-plan §13 + Phase 3 customization issues kept the upstream `sf-*` filenames. `ls plugins/revops/skills/` confirms 14 directories all prefixed `sf-`. | Banner uses `sf-*` names verbatim. Substituting `brite-*` would advertise non-existent skills. |

### Alternatives considered

1. **One-row reconciliation table at top of plan** — Chosen. Matches BC-5947 precedent shape (5 rows there, 1 here). Same documentation contract: issue text quoted verbatim, ground truth dated, resolution explicit and grep-verifiable.

2. **Note the departure inline in the relevant Decision section, no separate table** — Rejected. The reconciliation table is meant to be the *first* thing a reviewer reads after the goal. Burying the departure inside D3 (Banner text) makes it discoverable only by readers who care about banner specifics, not by reviewers checking "did the implementation match the issue?"

3. **File a Linear comment asking the issue-author to amend the spec, then proceed only after amendment** — Rejected. The user is the issue-author; a Linear roundtrip for a 5-skill name list is overhead that the reconciliation-table pattern already solves cleanly.

### Rule derived

**When an issue body's spec has drifted from project ground truth between authorship and execution, codify the delta in a reconciliation table at the top of the plan doc.** Each row has three columns: spec text (verbatim), ground truth (dated), resolution (with rationale). The table is the first section after the goal so reviewers see departures immediately.

Triggers for adding a reconciliation row:
- Issue spec names a file/skill/symbol that doesn't exist (renamed, deferred, deleted).
- Issue spec assumes a dependency state that has since changed (version bumped, library replaced).
- Issue spec was authored before a deciding research note or master-plan amendment.

### Promotion note

This is the **2nd instance** of the reconciliation-table pattern (1st: BC-5947 tam-map MCP registration, 5 rows; 2nd: BC-5806, 1 row). At the 3rd instance, promote to pattern-application 8/10. At the 4th instance across distinct surfaces (plan-front-matter for code change AND any other artifact like SKILL.md or doc), promote to architecture-9.

The rule is also the dual of BC-5870 task-2 / BC-5871 task-2 ("verification-as-discovery surface"): both pattern-classes acknowledge that issue text is a snapshot, not a contract — the reconciliation table is the codification at plan-time, the verification-as-discovery is the codification at execute-time.
