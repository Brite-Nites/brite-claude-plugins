## Task 1 — Augment an existing template when the verify requirement adds constraints the template doesn't cover

**Category:** pattern-choice
**Confidence:** 7/10
**Tags:** pattern-choice, integration-guide, template-augmentation, grep-target, section-shape
**Precedent Referenced:** BC-5793 (first-of-N locks shared convention; update in same PR — considered and rejected for scope reasons; see Alternatives)

### Decision

`plugins/marketing/tools/integrations/_template.md` canonicalizes a 9-H2-section shape (Purpose → Consumed by → Auth → Registration → Tool inventory → Rate limits and quotas → Known gotchas → Related skills → Last verified). BC-5946's Verify #6 required that each new integration guide contain 6 exact grep-target H2 headers — `Auth`, `Rate limits`, `Cost`, `Failure modes`, `Retry`, `Brite usage` — and only 1 of the 6 (`Auth`) landed verbatim in the template. The decision was to **augment every new guide to 12 sections** (9 template + 3 new: `Cost`, `Retry`, `Brite usage`) with 2 renames (`Rate limits and quotas` → `Rate limits`; `Known gotchas` → `Failure modes`), rather than sub-sectioning under template H2s or updating the template first.

### Alternatives considered

1. **Sub-section under template H2s.** Keep the 9 template H2s untouched; nest `### Cost`, `### Retry`, `### Brite usage` as H3s inside `Registration` / `Known gotchas` / `Related skills`. **Rejected.** The grep target is `^## Cost$` (H2, per the issue spec); H3s wouldn't match. And sub-sectioning `Auth` under template's `Auth` H2 would duplicate it.

2. **Update `_template.md` to the 12-section shape in the same PR.** Evolve the template so future guides follow the expanded canon, and touch the 2 existing guides (`email-bison.md`, `salesforce.md`) for consistency. **Rejected for scope reasons.** BC-5946 is atomically scoped (per `memory/feedback_atomic_issues_for_agents.md`) as a pure port — template canonicalization + back-migrating 2 unrelated guides is a separate piece of work. Flagged as follow-up in the plan's `Risks + mitigations` table. This option is where BC-5793's "first-of-N locks the shared convention" precedent would apply, but BC-5946 is the 3rd integration-guide round (not the 1st), and the existing template was already well-established.

3. **Augment only the new guides (this option).** Accepted. All 7 new guides share the 12-section shape; the template stays on 9 and drifts one step from the canonical form. Drift cost is minimal (any future author who reads both will notice the pattern extension in the guides themselves); drift is flagged in this plan for future closure.

### Rule derived

**When Verify contracts add structural constraints a canonical template doesn't cover, augment the leaf artifact rather than the template when the template is out of scope.** Preserve every template section verbatim (or with minimal renames that match domain vocabulary) and add new H2s adjacent to their closest template peer. Log the drift explicitly in the plan's Risks section so template-canonicalization remains a live follow-up.

### Promotion note

**Not a candidate for promotion.** This is a narrow tactical decision about template scope vs. atomic-issue scope, specific to the integration-guide layer. Would promote only if the "template drift accumulates over N ports" pattern became structural — e.g., if BC-5947 + BC-6005 + another port each augmented differently, producing genuine template divergence.

## Task 2 — Non-applicable template sections become populated-with-adjacent-value instead of bare `N/A`

**Category:** pattern-choice
**Confidence:** 7/10
**Tags:** pattern-choice, integration-guide, non-mcp-provider, cli-surface, template-section-adaptation
**Precedent Referenced:** None — novel for this repo. Adjacent to `docs/guides/skill-tool-integration-pattern.md` § "What goes where" (the 12-row table establishing which concerns belong in integration guides vs. skills).

### Decision

4 of the 7 providers shipped by BC-5946 (IcyPeas, BlitzAPI, Prospeo, MillionVerifier) have no MCP server — they're called directly from Python waterfall scripts (`enrich_waterfall.py`, `verify_smtp.py`, `icypeas_client.py`). The template's `_template.md` golden-rule blockquote says: "A section that genuinely does not apply stays in the file marked `N/A — <one-line reason>`". `Registration` and `Tool inventory` both technically don't apply to non-MCP providers — there's no `.mcp.json` snippet, no `mcp__plugin_marketing_<server>__*` tools.

The decision was to **populate those sections with analogous, adjacent-value content** instead of bare `N/A`:

- `Registration` for non-MCP guides ← `.env.example` entry for the required API key + the exact Python CLI invocation + a "skills shell out to the Python client via `Bash(python:*)` rather than inventing a bespoke HTTP path" directive.
- `Tool inventory` for non-MCP guides ← renamed in-place to `CLI surface` (with a one-sentence note justifying the rename) + a Python function signature table + the raw HTTP endpoint internals for skills that wrap without the client.

### Alternatives considered

1. **Bare `N/A — called from scripts/tam-map/<client>.py, no MCP server`.** Template golden rule followed literally. **Rejected.** Loses genuinely useful surface-area documentation (env var name, CLI invocation, function signatures) that skill authors and MCP-promotion auditors both need. The golden rule assumes "does not apply" = "no useful content exists"; here "does not apply" = "the usual content doesn't apply, but adjacent content is load-bearing."

2. **Split into two template shapes.** Author an `_template-mcp.md` and `_template-cli.md` and require guides to pick. **Rejected.** Doubles the canonical-form surface and introduces a pick-the-right-template gate that the current single-template + per-section adaptation pattern avoids. Revisit if 3+ non-MCP guides ship in a future port round and the adaptations diverge meaningfully.

3. **Populate with adjacent value (this option).** Accepted. Every new guide preserves template section shape + grep targets; non-applicable sections carry documented alternatives; no template split.

### Rule derived

**When a template section is titled for the majority case but a minority case has adjacent load-bearing content, populate with the adjacent content rather than marking `N/A`.** The template shape is a contract to readers about what information to expect in what position; silent-skip-with-`N/A` breaks the shape-as-contract more than a minority-case adaptation does. When adapting: cover the adjacent content + a one-sentence note distinguishing this instance from the majority case. Flag `promotion candidate` status explicitly so MCP-wrapping follow-up is visible.

### Promotion note

**Watch for a 2nd instance.** If BC-5947 or a sibling port ships another CLI-only provider with analogous adaptation, the pattern crosses from local decision → architecture-7 candidate, and `_template.md` should grow a "Non-MCP variant" subsection documenting the adjacent-value shape. If the pattern stays singleton (BC-5946 is the only multi-non-MCP-provider port), leave as-is.

## Task 3 — Integration-guide claims must grep against the wrapper code, not author-memory

**Category:** bug-resolution
**Confidence:** 8/10
**Tags:** bug-resolution, integration-guide, wrapper-code, factual-drift, review-p1, architecture-promotion-candidate
**Precedent Referenced:** None — novel pattern-class this repo, but adjacent to `memory/feedback_atomic_issues_for_agents.md` (atomic-issues must specify exact paths) and `docs/guides/skill-tool-integration-pattern.md` § Last verified (explicitly dated freshness marker).

### Decision

Initial authorship of `ai-ark.md` and `discolike.md` populated `## Auth` and `## Tool inventory` sections from the **upstream README + vendor-signup pages** (Brite-level domain knowledge) rather than from the ported wrapper code itself (`aiark-mcp.js`, `discolike-mcp.js`). The review pipeline's code-reviewer surfaced 4 P1 findings — all factual drift between guide claims and actual wrapper behavior:

- `discolike.md` claimed `Authorization: Bearer` auth — wrapper uses `x-discolike-key` custom header (would 401).
- `discolike.md` listed tools `find_lookalikes` / `get_similarity` — wrapper registers `discolike_search` / `discolike_lookalike` (skill's `allowed-tools: mcp__plugin_marketing_discolike__find_lookalikes` would fail silently).
- `ai-ark.md` listed tools `search_companies` / `get_company` — wrapper registers `aiark_search` / `aiark_similarity` / `aiark_enrich`.
- `ai-ark.md` omitted the upstream wrapper's explicit `!! VERIFY BEFORE USING !!` warning (`aiark-mcp.js` lines 14-22) that endpoint paths + field names are "conventional guesses" pending `docs.ai-ark.com/reference` validation.

All 4 were independently CONFIRMED by Step 6 validators reading the JS wrappers directly.

The fix: rewrite the `## Auth` + `## Tool inventory` sections in both guides from the JS wrapper source of truth. The 5 guides that were already author-from-wrapper (`icypeas.md`, `blitz-api.md`, `prospeo.md`, `millionverifier.md`, and `spider-cloud.md`) all passed review without factual P1s.

### Alternatives considered

1. **Treat drift as a normal review outcome and keep the workflow.** Review catches it; all 4 got fixed before ship. **Rejected as a going-forward posture.** The review burn (4 Opus validators + 4 Edit + 1 recommit) is larger than the authorship burn would have been if every claim were grep-checked against the wrapper at write time. The fix is cheap; the miss cascades through BC-5947 (MCP registration) and BC-5832 (tam-mapping skill) if it slips through, because both will compile against the guide's claimed surface.

2. **Author the guide in the same file as the wrapper (JSDoc-to-guide generation).** Generate `ai-ark.md` Tool inventory from the wrapper's `ListToolsRequestSchema` handler automatically. **Deferred.** Worth a follow-up issue if tool-inventory drift recurs; not appropriate for the port scope of BC-5946.

3. **Add a pre-ship grep check (this option).** Accepted as the rule. Before committing any integration guide's `Auth` + `Tool inventory` + `Registration` sections, grep the target wrapper source (`.js` for MCP, `.py` for CLI surface) for each claim and confirm match. Specifically: `grep -E "(Authorization:|x-.*-key|Bearer)" <wrapper>` for auth; `grep -E "name:\s*\"(\w+)\"" <wrapper>` for MCP tool registrations; `def (\w+)\(` for Python function surface.

### Rule derived

**When authoring integration guides alongside ported wrapper code, the wrapper source is the source of truth — not upstream README, vendor docs, or author memory.** Any claim in `Auth` / `Tool inventory` / `Registration` / `Rate limits` that has a code-side analog must grep-match the wrapper before the guide commits. Guides for providers without a wrapper (vendor-native MCPs like `spider-cloud`) can cite upstream docs with a `## Last verified` date + explicit "not yet live-tested" caveat.

### Promotion note

**Architecture-8 promotion candidate at next recurrence.** If BC-5947 or any future integration-guide PR has a review P1 traced to guide-vs-wrapper factual drift, the pattern promotes to an architecture rule (suggested location: `docs/guides/skill-tool-integration-pattern.md` § PR checklist, adding an 8th item: "Grep every guide claim against the backing wrapper code before merge"). The rule is content-layer-agnostic (applies to any port where a connectivity-layer doc is authored next to the connectivity implementation), so it reads cleanly as a repo-wide architectural constraint rather than a per-issue lesson.
