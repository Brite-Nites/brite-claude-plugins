## BC-6780 task-1 — Orchestrator must independently re-trace runtime when review agents echo orchestrator's design vocabulary back

**Confidence:** 8/10

**Category:** pattern-choice (review-validation discipline)

**Tags:** factual-anchor-recipe, review-validation, vocabulary-capture, false-analogy-extension, sequential-thinking

**Decision:** When a review agent uses the orchestrator's own design-rationale vocabulary back at it ("load-bearing", "vendor-API quirk at boundary", "single edit-target"), pattern-matching on the shared framing short-circuits independent runtime re-tracing. The orchestrator must explicitly run the runtime path through sequential-thinking (or equivalent independent verification) before classifying agent-surfaced findings as "real" — particularly for P2+ findings that propose follow-up issues or scope expansion.

**Why:** This session, I asked architecture-reviewer to evaluate BC-6780 with framing that included "load-bearing convention" and "vendor-API quirk at the API boundary" — vocabulary I'd just used in my own sequential-thinking design analysis. The agent reflected the framing back in P2 #1 ("the load-bearing convention 'UPPERCASE everywhere in artifact'") and I accepted the finding at face value, recommending a follow-up issue. User pushed back — "use sequential-thinking and confirm we need these changes" — and the re-trace showed the convention is actually purely aesthetic at runtime (the agent's `.lower()` translation at the API boundary is what's load-bearing; whether the artifact is uniform UPPERCASE or mixed is style, not function). I would have filed an unnecessary Linear issue.

This extends BC-5830 task-2 / BC-5953 task-2 false-analogy class to a more specific sub-pattern: shared design vocabulary between briefing prompt and finding output is a confidence-amplifier that bypasses independent verification. The fix is to require an explicit re-trace step when finding-language echoes briefing-language for high-severity findings.

**How to apply:** Before accepting an agent-surfaced P2+ finding as "real" and recommending follow-up action, scan the finding for shared vocabulary with the orchestrator's own framing. If shared vocabulary is present, run the finding's claimed runtime impact through sequential-thinking (or a direct read-and-trace) BEFORE classifying. Independent verification cannot be optional for findings that mirror briefing language. Trigger threshold: any P2+ finding using ≥2 distinct phrases from the orchestrator's prior design analysis. Architecture/security/performance reviewers are particularly susceptible because they're prompted with rich context.

**Precedent referenced:** BC-5830 task-2 (review-validation: live-verify cited precedent), BC-5953 task-2 (false-analogy class), BC-6300 task-1 (user-delegation: file decisions, not unilateral PR expansion). Extension of false-analogy class into vocabulary-capture sub-pattern. Promotion-eligible if 3rd surface emerges.

## BC-6780 task-2 — Subagent worktree-path permission flakiness; agents that succeed route via `git show` from main repo

**Confidence:** 7/10

**Category:** bug-resolution (infrastructure workaround)

**Tags:** subagent-dispatch, worktree-permission, infrastructure-flakiness, git-show-fallback, BC-6307-extension

**Decision:** When dispatched subagents (general-purpose, workflows:code-reviewer, etc.) need to read changes living in a sibling worktree path (`/Users/.../brite-claude-plugins-bc-NNNN/`), expect ~50% of agents to fail with `Bash`/`Read` permission denial on the worktree path. Agents that succeed do so by reading committed content via `git show <branch>:file` from the main repo's path, not by accessing the worktree directly. Brief subagents to attempt `git show` first when worktree-direct access is denied.

**Why:** This session: 2 of 3 simplify-pass agents and 2 of 4 review agents hit `permission denied` on the worktree path despite repeated attempts. The 1 simplify + 2 review agents that succeeded both reported reading via `git show` from `/Users/.../brite-claude-plugins/` (the main repo, not the sibling worktree). This is consistent with the harness sandbox restricting subagent file access to the orchestrator's cwd subtree — and worktrees as siblings live OUTSIDE that subtree. Triggered the BC-6307 task-4 pivot rule (≥2 infrastructure failures → direct parent self-validation).

The ~50% success rate is suspicious — same agent type, same path, different outcomes between dispatches in the same session. May be a state-dependent permission resolution. Either way, the `git show` path is reliable when committed.

**How to apply:** When dispatching subagents that need to read uncommitted worktree content, first commit the changes so they're reachable via `git show <branch>:file` from main repo, THEN dispatch. For agents that may run before commit, brief them with: "If `Read` on the worktree path is denied, fall back to `git show <branch>:file` from `/Users/.../brite-claude-plugins/` (the main repo)." If ≥2 agents fail at infrastructure layer despite the briefing, pivot to direct parent self-validation per BC-6307 task-4 — don't waste cycles re-dispatching.

**Precedent referenced:** BC-6307 task-4 (≥2 infrastructure timeouts → pivot to parent self-validation). This is the 2nd-instance application of the pivot rule with a new failure mode (permission denial vs. timeout). Promotion-eligible if 3rd surface emerges.

## BC-6780 task-3 — Simplify-pass + T12 self-read complementary-detector confirmed at 5th instance; F2 caught loop-invariance the orchestrator missed

**Confidence:** 8/10

**Category:** pattern-application (factual-anchor-recipe extension)

**Tags:** factual-anchor-recipe, simplify-pass, t12-self-read, complementary-detection, loop-invariance, multi-section-rewrite

**Decision:** Simplify-pass and T12-self-read are confirmed complementary detectors of internal-consistency drift in multi-section spec rewrites at the 5th instance. Always run both in series during /workflows:review on multi-section spec PRs; neither alone is sufficient.

**Why:** This session, simplify-pass F2 (conf 8/10) caught that my pre-send guard was inside the per-chunk loop while its predicate (regex check on `custom_variables[].name`) was loop-invariant — names come from the artifact, not per-chunk lead values. Hoisting it pre-loop also corrected my own commit message's stated "mirrors BC-6548 Phase 1 step 5" claim, which was technically false at per-chunk scope (BC-6548 fires once pre-loop). T12 self-read caught the stale `line 364` cross-reference in Phase 3 step 2 — distinct issue, distinct file location, neither detector would have caught the other's finding. This is the 5th observed application of BC-6654 task-1 (4 instances → promotion-eligible threshold passed).

Distinct surfaces:
- Simplify-pass: detects loop-invariance, prose duplication, redundant computation patterns. Reads via parallel agents; cross-cuts the diff structurally.
- T12 self-read: detects step-renumbering breakage, stale ordinals, cross-reference rot. Reads sequentially; cross-cuts the diff narratively.

Both run on the same diff but find disjoint classes of drift. Together they're a multi-section-rewrite contract.

**How to apply:** Promotion-eligible to factual-anchor recipe check #11 (after #1-9 + BC-5806 task-1 + BC-6654 task-1's earlier observations). Recommend codifying as: "On any /workflows:review where the diff includes step-renumbering OR ≥2 spec sections were rewritten, run both detectors in series. Single-detector pass is insufficient for multi-section rewrites." Promote-via `/workflows:promote-precedent` when team is ready.

**Precedent referenced:** BC-6654 task-1 (4 instances, promotion-eligible). This session = 5th instance, ratifies promotion. Inherits factual-anchor-recipe lineage from BC-5797 onward.

## BC-6780 task-4 — One-line in-PR fix when (a) same file, (b) closes unifying topic, (c) trivial cost; otherwise defer to follow-up

**Confidence:** 6/10

**Category:** pattern-choice (scope-discipline judgment)

**Tags:** scope-discipline, in-pr-vs-follow-up, one-line-rule, unifying-topic, user-delegation-scope-refinement

**Decision:** When a review-surfaced finding is (a) one-line, (b) in the same file as the current PR's edits, AND (c) closes the unifying topic of the PR, apply in-PR. Defer to follow-up only when the finding requires (i) broader semantic change, (ii) cross-file edits, OR (iii) scope expansion the user hasn't agreed to.

**Why:** This session: Phase 3 step 3 case-insensitive match was a 1-line edit in the same file as BC-6780's Phase 4 changes. I initially classified as "follow-up" per user-delegation-scope memory (feedback_user_delegation_scope), but user pushed back ("just go ahead and fix the p3"). The 1-line cost made follow-up overhead disproportionate; the unifying topic (case-asymmetry across endpoints) was incomplete without it; and the same file was already under edit in the PR. Filing a separate issue would have created Linear-tracking overhead for what could be one word.

The user-delegation-scope memory says I shouldn't make project-level architecture/CLAUDE.md/ADR calls unilaterally — but a one-word case-sensitivity fix that completes the unifying topic of the current PR is below the threshold of "project-level decision." The memory should not be over-applied to make trivial in-scope cleanup feel out-of-scope.

**How to apply:** Ask explicitly when uncertain (one targeted question, not multi-select per feedback_jargon). The default for one-line / same-file / unifying-topic findings should lean toward "apply in-PR." Defer when the cost of getting it wrong (over-expansion, churn) exceeds the cost of an extra Linear issue. Refines feedback_user_delegation_scope: project-level decisions are out of bounds; one-line internal-consistency cleanups in the current PR's same file are not.

**Precedent referenced:** BC-6300 task-1 (user-delegation: 3rd-instance promotion declined; spinoff vs in-PR), BC-6298 task-1 (plan-gate scope-expansion when issue § Scope is strict subset). This refines the spectrum between them: at the trivial-cost end, in-PR is correct; at the broader-semantic end, follow-up is correct.
