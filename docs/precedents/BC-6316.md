## Trace 1 — pattern-choice — Path-B harmonization (use existing infrastructure when issue spec invents parallel)

**Confidence**: 8/10
**Tags**: path-b, harmonization, schema-discrepancy, existing-infrastructure, eval-harness
**Precedent Referenced**: 1st surface (NEW). Adjacent to BC-2717 task-1 reconciliation pattern (different shape — that's plan-vs-evidence; this is spec-vs-infrastructure).

### Decision

When an issue body specifies a new file path + new schema and notes the runner is "TBD or follow-up," investigate adjacent infrastructure before authoring. If a working harness already exists for the same problem class, harmonize with it (use existing schema/path) and record the deviation as a Linear comment + verify-table update. Don't invent parallel infrastructure to match the literal spec.

### Why

BC-6316 specified `plugins/revops/evals.json` with shape `{cases[].skill, expected: "fire"}` and a sweep runner labeled "TBD." Investigation found:

- The cited precedents (BC-5825, BC-5832 evals at `plugins/marketing/skills/<skill>/evals/evals.json`) are **behavioral-assertion** evals — testing skill *output*, no runner consumes them. Different problem class.
- `scripts/test-behavioral.sh` already reads `tests/fixtures/behavioral-registry-<plugin>.json` (schema: `test_cases[].prompt + expected_skill + ...`) — a working **skill-activation** harness introduced in BC-2462 specifically for this problem class.

The issue author conflated two patterns that share the file name `evals.json` but solve different problems. Path A (literal spec) would have required authoring a new schema + filing a "scope a sweep runner" follow-up. Path B (harmonize) inherited the runner immediately at zero schema cost.

### How to apply

When an issue spec invents a new file/schema/runner:

1. **Search the repo** for existing infrastructure in the same problem class (grep for related fixture/runner patterns, check `tests/fixtures/`, check the cited precedents for actual schema vs verbal label).
2. **Disambiguate problem class** — "behavioral-assertion" (output) vs "skill-activation" (routing) vs "integration-test" (end-to-end) vs "regression" — these often share file names but solve different problems.
3. **If existing infra fits**, harmonize. Record the deviation as a Linear comment with explicit "Path A would have done X / Path B did Y / why B is correct" rationale.
4. **Update the verify table** to reflect the actual files/commands used.
5. **If no existing infra fits**, follow the issue spec literally and accept the new-infrastructure cost.

### Counter-evidence to watch

If harmonization repeatedly violates the issue author's intent in ways the deviation comment doesn't catch (e.g., hidden semantic differences between the existing infra and what the spec asked for), the rule is too aggressive. In this case the deviation comment + verify-table update preserved auditability — no semantic loss observed.

### Promotion path

2nd surface → architecture-9. Adjacent observation: this is structurally similar to BC-2717 task-1 reconciliation table (plan-vs-execution-evidence) but operates at spec-vs-infrastructure layer instead of plan-vs-evidence. The two compose naturally — one says "reconcile plan with what you found at execute time," this one says "reconcile spec with what already exists in the repo."

## Trace 2 — pattern-choice — first-test-universal-failure-mode signals stop-the-sweep before confirmation cost

**Confidence**: 8/10
**Tags**: eval-sweep, fail-fast, infrastructure-bug, scope-down, follow-up-issue
**Precedent Referenced**: 1st surface (NEW)

### Decision

When the first test in a multi-test sweep fails on a universal mechanism (not content), stop the sweep immediately, diagnose root cause, scope a follow-up issue, and ship the authored half. Do NOT continue running remaining tests "to confirm" — the cost-to-signal ratio is wrong.

### Why

BC-6316 sweep ran R01-TP. It failed with `Expected skill 'sf-apex' to activate, but no activation banner found`. The error message named the mechanism (activation banner) not the content (sf-apex specifically). Diagnosis took ~5 minutes:

- Read `scripts/test-behavioral.sh:243` — `grep -Fqi "activated"` looking for stdout banner.
- Recognized the mechanism is obsolete in modern Claude Code (skill activation now happens via tool calls, not stdout banners).
- Concluded: every TP would fail for the same mechanism reason. Confirming this with 13 more failed TPs would cost ~$1.30 and ~10 min, yielding zero new signal.

Stopping after R01-TP saved ~$2.50 and ~15 min. Filed BC-6516 (runner fix) instead.

### How to apply

After the first test in a sweep fails:

1. **Read the error message** — does it name a *mechanism* (banner detection, regex, parser) or *content* (specific skill, specific assertion)?
2. **If mechanism** — universal failure mode is likely. Read the mechanism source (~5 min), confirm it's broken for all tests, stop the sweep.
3. **If content** — single-case issue. Continue the sweep; the next test may still pass.
4. **Don't continue "for confirmation"** when the mechanism is the issue. The sweep cost is real ($/$ × N) and yields no new signal.

### Counter-evidence to watch

If the "mechanism vs content" classification is ambiguous and stopping early misses real content failures, the rule is too aggressive. Mitigation: when in doubt, run 2-3 more tests of *different shapes* (e.g., different skills, different assertion types) to disambiguate before committing to the stop-the-sweep call. In this case all 28 cases had identical mechanism dependencies (banner detection), so the universal call was unambiguous.

### Promotion path

3rd surface → architecture-9. Adjacent to "fail-fast on infra issues, ship the authored half, scope follow-up" — this is the eval-sweep-specific instance of a more general pattern about distinguishing systemic-blocker vs content-issue at the first signal.

## Trace 3 — pattern-choice — TN-targets-sibling-skill encodes routing in both directions per case

**Confidence**: 7/10
**Tags**: skill-activation-eval, true-negative, sibling-collision, fixture-design
**Precedent Referenced**: 1st surface (NEW)

### Decision

For skill-activation eval TN cases, prefer `expected_skill: <sibling> + not_expected_skills: [<target>]` over `expected_skill: null`. The sibling-targeted form tests both directions of the routing decision in a single case (target doesn't fire AND sibling does fire), and provides richer signal for collision-boundary debugging.

### Why

BC-6316's 14 TN cases all use the sibling-targeted shape. Example R01-TN: testing that "How do I write Jest tests for the disqualified-lead LWC?" does NOT fire `sf-apex` (target) AND DOES fire `sf-lwc` (sibling). Compared to `expected_skill: null`:

- **Sibling form**: pass = both directions correct (negative for target + positive for sibling). Fail mode tells you which direction broke.
- **Null form**: pass = target didn't fire (single-direction signal). Doesn't validate that the right alternative fired — could fail silently if routing is broken in a different way (e.g., no skill fires at all).

The sibling form also makes the TN a *useful* test in isolation, not just a complement to the TP. Each TN doubles as a TP for the sibling skill, giving 14 free additional positive signals.

### How to apply

When authoring skill-activation eval TNs:

1. **Identify the sibling skill** that should fire instead — usually named in the target skill's `DO NOT TRIGGER` frontmatter section.
2. **Write the TN prompt** to fall squarely in the sibling's territory (not ambiguous middle-ground — that's a Phase-2 collision-edge case).
3. **Schema**: `expected_skill: "<sibling>"` + `not_expected_skills: ["<target>"]`.
4. **Avoid `expected_skill: null`** unless the prompt is genuinely inert (no skill should fire) — those are rare in a 14-skill plugin.

### Counter-evidence to watch

If sibling-targeted TNs over-pass (sibling routes to a third skill but neither target nor sibling fires), `not_expected_skills` catches the target-side failure but the sibling-side failure goes unflagged. Mitigation: pair sibling-targeted TNs with periodic Phase-2 multi-skill cases that explicitly enumerate `not_expected_skills` for the entire collision cluster.

### Promotion path

2nd surface → pattern-choice-9. Pattern is fixture-design-specific; less generalizable than Traces 1-2. Promote to skill-eval-authoring guide when 2-3 more skill-activation eval issues land.
