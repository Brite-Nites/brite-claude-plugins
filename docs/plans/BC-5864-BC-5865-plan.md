# BC-5864 + BC-5865 — Cadence Phase 2 anti-pattern removal (bundled)

**Issues:** BC-5864 (remove project-level triage gate) + BC-5865 (remove condensed-prompt shortcut)
**Priority:** High (both). Parent: BC-5763. Milestone: Cadence Plugin.
**Precedent:** BC-5866 (gate-respect contract, shipped PR #169, 2026-04-21). BC-5864/BC-5865 are the two specific instances the contract was written to catch — first mechanical applications of the shared contract pattern.
**Related precedents:** BC-5795 (template-tension lens), BC-5902 (context-pressure class fix — sibling "there is no escape hatch" pattern).

## Objective

Remove the spec-breach anti-patterns surfaced by the W17 dogfood from `plugins/cadence/skills/sprint-scoping/SKILL.md` by adding explicit STOP/forbidden language, and extend `scripts/_lib/lint_cadence_gates.py` to CI-enforce that the forbidden phrases never reappear in any Cadence skill or command body. Both issues share the same file and review surface — bundling produces one PR instead of two.

## What's actually wrong

Neither anti-pattern is currently *written into* `sprint-scoping/SKILL.md`. Both were improvised at runtime during the W17 dogfood:

- **BC-5864:** the agent surfaced a project-level triage menu at Phase 2 entry ("Active projects only (18 of 26)" / "Top 10 by ship count" / "All 26, strict spec" / "Abbreviated form") that the spec does not authorize. BC-5810 § 2.3 adaptive-skip is per-question, never per-project.
- **BC-5865:** after the user picked "Active projects only", the agent announced it would use "one consolidated scope AskUserQuestion per project" for the 16 no-carry-over projects — batching 5 scope questions into one call. Contradicts BC-5810 § 2, BC-5760 AC #5, and `memory/feedback_one_question_at_a_time.md`.

The skill body already says "each question is a separate AskUserQuestion tool call — no batching" (§ 3) and "No condensed/batched alternatives, ever" (§ 4). **That wasn't strong enough** to prevent the runtime deviation — the agent improvised novel-sounding phrasing ("pragmatic", "condensed-prompt pattern") that didn't literally match the spec's negations.

The fix adds pre-emptive STOP language naming the specific improvised patterns + CI guardrails that catch the forbidden phrases if they ever land in skill bodies in the future.

## Departures from BC-5866 template

None material. BC-5866 codified the *class-fix pattern*: contract file + per-section markers + linter. Those all exist. BC-5864 + BC-5865 are the **first two instances** the contract was designed to prevent — mechanical applications, not new patterns.

One judgment call per-session: the fix scope is **text-hardening + forbidden-phrase linter extension**, not **behavioral test fixture**. Deferred the synthetic-25-project fixture test to BC-5874 (third dogfood) per BC-5760 § 190 existing deferral. If BC-5874 surfaces gaps, a separate fixture issue can be filed.

```markdown
**No project-level triage gate.** Do not surface any `AskUserQuestion` at Phase 2 entry that asks the user to narrow the project set before the interview begins. Specifically banned patterns (origin: BC-5864 W17 dogfood):

- "Active projects only (N of M)" — auto-parks quiet-prior-cycle projects. A quiet prior cycle ≠ empty W+1 scope.

If the prompt count feels unsustainable (e.g. 130+ questions for 26 projects), that is the planner experience BC-5810 locked in — the right lever is a different spec decision (new sub-cohort gate in BC-5810), not an improvised triage menu here.
```

### Task 4 — Extend `lint_cadence_gates.py` with forbidden-phrase scan
Edit `scripts/_lib/lint_cadence_gates.py`.

Add after the existing `PROSE_PATTERNS` list (around line 61):

```python
# Forbidden phrases (origin: BC-5864 triage gate + BC-5865 condensed-prompt).
# These strings appeared in the W17 dogfood as runtime improvisations.
# The skill/command body must never AUTHORIZE them — they may appear only in
# STOP blocks (explicit anti-pattern callouts) or in _shared/gate-respect.md
# Tripwires. The linter catches them anywhere else in an active body line.
FORBIDDEN_PHRASE_PATTERNS = [
    # BC-5864: project-level triage
    (re.compile(r"Active projects only", re.IGNORECASE), "BC-5864"),
    (re.compile(r"Top\s+\d+\s+by ship count", re.IGNORECASE), "BC-5864"),
    (re.compile(r"triage\s+(?:menu|gate|prompt)", re.IGNORECASE), "BC-5864"),
    # BC-5865: condensed-prompt shortcut
    (re.compile(r"condensed[-\s]prompt", re.IGNORECASE), "BC-5865"),
    (re.compile(r"consolidated\s+`?AskUserQuestion`?", re.IGNORECASE), "BC-5865"),
    (re.compile(r"pragmatic\s+condensed", re.IGNORECASE), "BC-5865"),
    (re.compile(r"batched\s+(?:scope|carry-over)", re.IGNORECASE), "BC-5865"),
]

# Sections where forbidden phrases are LEGITIMATELY mentioned (as anti-pattern
# callouts). These sections are exempt from the forbidden-phrase scan.
FORBIDDEN_PHRASE_EXEMPT_SECTION_PREFIXES = (
    "tripwires",              # _shared/gate-respect.md § Tripwires
    "no project-level triage", # inline STOP subsection title (if promoted to a heading)
    "no condensed",            # inline STOP subsection title (if promoted)
)
```

Extend `_is_excluded_section` or create a sibling `_is_forbidden_phrase_exempt` for the new exempt list. Add a new pass inside `_lint_file` (after the existing AUQ scan, before the OK/ERROR emission) that iterates `_iter_active_lines` for every non-exempt section and emits `ERROR:<rel>:<title>: forbidden phrase "<phrase>" at line N (banned by <ticket>)` for every match.

Decision (per BC-5866 simplify-pass precedent): the exempt-section mechanism must be **section-level**, not line-level. If a STOP subsection is promoted to a heading (e.g. `### No project-level triage gate`), the whole section is exempt. Otherwise the STOP inside a parent section must include a single-word anchor the exempt list recognizes. For v1, the STOP blocks in Task 2/3 stay inline under § 2/§ 3/§ 4 and rely on the linter matching the phrase *only in authorizing prose* — **fail if the phrase appears without the literal token `banned` or `Do not` on the same line or the line immediately above**. Mirror the existing prose-pattern intent-based detection.

**Rejected simpler variant:** regex-free substring scan. The BC-5866 precedent shows that regex with hedge/negation filters is the right tool for prose vs. authorization detection.
