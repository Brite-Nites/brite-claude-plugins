# App-Type Quality Profiles

Profile modifiers that layer **on top of** the substance spine in `quality-rubric.md`. The spine is app-agnostic — every good story and journey doc shares its dimensions. A profile **re-weights** specific dimensions for the kind of application under review: it tightens what would otherwise pass, relaxes what doesn't apply, and names the defect each app type is most prone to. A profile never removes a spine dimension; the spine always runs.

Each profile is calibrated against shipped-app norms (the Mobbin corpus per app type) plus the one teardown witness named in the profile. Use the evidence to set granularity and interaction-pattern expectations — not to copy any UI.

## The classifier enum is the single source of truth for profile selection

Every profile's selection signal is keyed to the **closed enum** the app-classifier emits (`app-classifier-pattern.md` Phase 1, line 14):

> **`SaaS / CRM / ops / agency / marketplace / installation`**

These six values are the only `app category` signals a project can carry. **Every profile signal token below MUST be a member of this enum** — a signal line that names a value the classifier cannot produce (e.g., a bare `marketing`) is unmatchable and is a bug. If you find yourself reaching for a category outside the six, the fix is to amend the classifier enum in `app-classifier-pattern.md` *and* this file together, not to invent a token in one place.

Mapping of enum value → profile:

| `app category` | Profile |
|---|---|
| `ops` | A — internal-ops / workflow tool |
| `CRM` | A (when multi-actor admin) — see SaaS tie-break for the CRM-as-storefront edge |
| `installation` | A — internal-ops / workflow tool (field-execution variant; see Profile A) |
| `agency` | B — marketing-site |
| `marketplace` | C — b2b-ecommerce |
| `SaaS` | A, C, or D — **ambiguous by category alone; disambiguate by inventory tell** (see below) |

`SaaS` is the only category that maps to more than one profile. Resolve it by the inventory tell in this priority order:

1. **catalog → cart → order → invoice** present ⇒ **Profile C**.
2. **template × dimension generation plane** present ⇒ **Profile D**.
3. **actor-tiers + state-machine + audit** present ⇒ **Profile A**.

If two tells co-occur (e.g., a B2B ordering tool with admin roles), do **not** pick one globally — apply each profile **per-domain** (step 4 below) to the domains it actually covers. Bare `SaaS` is never a sufficient selector on its own; the inventory tell is the discriminator.

## How to apply

1. **Run the full spine.** Score every story dimension (D1–D11) or journey dimension (J1–J8) as written in `quality-rubric.md`. The spine is the floor for any app type. The spine's domain-conditional clauses (D3 / J1 / J6 "where the domain has permissions / a state machine / forks") mean the spine itself does **not** false-fail an app type that genuinely lacks those surfaces — a permission-free marketing form is not a D3 fail for missing a permission scenario; it re-aims per the profile.
2. **Select exactly one profile** by inferring the project's app type from `docs/product/intent.md` and the master flow inventory:
   - The intent doc's product framing and the `app category` captured by `app-classifier-pattern.md` are the primary signal — and that signal is always one of the six enum values above.
   - The inventory's domain shape is the tiebreaker — actor tiers + state machines + audit point to **internal-ops** (Profile A, including the `installation` field-ops variant); anonymous-visitor funnel to **marketing-site** (B); catalog → cart → order → invoice to **b2b-ecommerce** (C); a template × dimension page-generation matrix to **programmatic-seo** (D). For `SaaS`, use the SaaS tie-break priority above.
3. **Apply the matching profile's modifiers** to the dimensions it names. Where a profile and the spine disagree on a threshold, the profile wins for that app type. **The profile re-routes the spine BEFORE the spine verdict is finalized, not after** — score the spine, then let the profile adjust thresholds and re-aim edge classes, and the profile-adjusted verdict is the verdict of record. When a profile *tightens* a threshold and turns a spine pass into a fail (e.g., Profile A turning a spine D3 pass into a fail for missing the 2:1 boundary ratio), **report the profile verdict, not the spine pass, and cite the profile clause as the reason.** A reviewer must never publish the looser spine-first verdict for a dimension the active profile has tightened.
4. **If no profile cleanly matches, fall back to the spine alone** and note the absence. Do not force-fit — a project that is genuinely a hybrid (e.g., an internal-ops tool with a marketing landing page) applies each profile only to the domains it actually covers, not the whole inventory. Profiles are per-domain-applicable, not a global verdict.

### Granularity bands are anchored to STANDARD scale — shift by the classifier's `scale` signal

Each profile names an **absolute flow-count band** (A=8–15, B=3–6, C=6–10, D=4–8). **Every band is stated per-domain** and is the **expected range for a `standard`-scale domain** (the classifier's middle `scale` tier, 5–10 flows/domain). The classifier also emits a `scale` signal (`small ≤5 / standard 5-10 / heavy 10+`); use it to shift the band:

- **`small` scale:** shift the band *down*. Do **not** flag a `small`-scale domain as under-decomposed solely for falling below the profile's band floor — a correctly-small ops domain of 4 flows is not "under 6 = under-decomposed."
- **`heavy` scale:** shift the band *up*. A `heavy` domain legitimately exceeds the band ceiling without being over-decomposed; confirm over-decomposition by the sibling-title test (D9), not by the band alone.

The band is a calibration prior, not a hard gate: the D9 evidence test (fused actors per-doc; 5+ near-identical siblings across the inventory) is what actually fires the finding. Treat a band miss that the `scale` signal explains as expected, not a defect.

Inference is a judgment, not a lookup. State the app type you inferred, the enum value you matched, and the signal you used at the top of the review so the next reviewer can challenge it.

## Profile A — internal-ops / workflow tool (incl. installation / field-ops)

**App-classifier signal:** `ops` / `CRM` (multi-actor admin) / `installation`. (`SaaS` resolves here only via the SaaS tie-break: actor-tiers + state-machine + audit.) Inventory tell: 3–4 actor tiers, state machines, audit surfaces; for the `installation` variant, an appointment / survey / quote / install lifecycle with mobile field actors.

**What this type is.** Multi-actor administrative systems where named operators with real org responsibilities execute structured business processes (HR-ops, DAM, roster management, ops portals) — **and field-execution tools where the same structured process runs across an office tier and a mobile field tier** (home-services: a salesperson on a phone in a truck cab, an office_staff dispatcher at a desk, an installer on site; appointment → survey → quote → install lifecycle). The product *is* the process. State machines, permission boundaries, and audit trails are load-bearing product features, not infrastructure concerns. The `installation` business type — the core BriteBase / brite-supply field-ops shape — lives here: it is an internal-ops tool whose operators happen to work partly in the field, not a separate app class.

**Granularity band (per-domain, standard scale).** Split by **actor-tier × lifecycle moment** — one flow per distinct role (Employee, Manager, HR Admin, Auditor; or salesperson, office_staff, installer), one per meaningful state transition (submit → pending → approved → effective; provisioned → active → suspended → archived; scheduled → in_progress → completed | cancelled | no_show). Do not collapse flows sharing a UI surface if actors or system-state outcomes differ; do not split flows that differ only in data payload. Typical mature **standard-scale** domain: **8–15 flows** across 3–4 tiers. Under 6 *at standard scale* usually signals under-decomposed approval/permission lifecycle; over 20 usually signals over-decomposed shared pattern — but shift both thresholds by the `scale` signal (a `small` domain of 4–5 flows is fine; a `heavy` domain past 15 is expected). (Mobbin: WorkOS surfaces Audit Logs and Roles & Permissions as co-equal nav — separate sub-flows; Gusto's permission wizard groups capabilities by domain-category — each category is a meaningful sub-scope, not a detail variant.)

**Dimension modifiers.**
- **D3 / D9 (edge, grain)** held high: the permission / tenant / audit / atomicity scenario count must outnumber happy-path **at least 2:1** (computed over substantive scenarios only — NOT_BUILT placeholders never count toward the ratio). Required scenario classes: permission-boundary rejection (with exact error string when code-confirmed), tenant-boundary (org A cannot read/modify/enumerate org B), audit completeness (actor + verb + object + timestamp + old/new values), atomicity/partial-failure (mid-flight failure leaves a defined state), concurrent modification (deterministic outcome, no silent data loss), escalation/delegation boundary (no self-approval; no recall after approval begins). A pass that omits these scores **fail on D3** — and per "How to apply" step 3, that profile-tightened fail is the verdict of record, not the spine's looser pass. (Mobbin: Cloudflare's audit log carries a READ ONLY badge — immutability is a first-class contract; Sprout Social shows "0 of 1 required approvals" — approver count is testable, not ornament.)
- **D1 / D7 / D11 (story frame, persona).** Human-actor flows name the actor tier explicitly in the When clause. Approval-workflow flows are a middle ground: lead with the triggering actor's job story, then enumerate each state transition as one AC scenario — one story frame, multiple scenario rows, never a separate job story per transition. System flows (audit ingestion, permission-cache invalidation, deadline-escalation cron, SSO group sync) use the constraint-spec frame — "When I'm an automated process…" is the D11 failure. Personas are named operator types with org responsibility, operational posture (what they can delegate, what they cannot undo), and a trust boundary (see vs act-on vs configure); for the field-ops variant, device + posture is load-bearing (one-handed on a phone in the field vs desktop at the office). A generic "Admin user" copy-pasted across tiers is the D7 failure.
- **J2 / J6 (journey persona, decision points).** J2 must address per-role scope shapes in the same journey (own vs full access); J6 must include the tenant-isolation enforcement layer and the lifecycle state machine. A journey narrating a single role when multiple share a surface is incomplete.
- **J3 (journey phase narrative).** Pain points cluster at three moments: cross-system handoff (HRIS/IdP/ERP contract ambiguity; or, field-ops, the office→field→office handoff), approval-lifecycle ambiguity (actor doesn't know the current state of their submission), and audit reconstruction under pressure (log lacks detail or filter granularity). Rich journeys name these with root cause; thin journeys restate the flow inventory. (Mobbin: Deel's "Review pending items" ACTION NEEDED banner with deadline count, and Dropbox's inline old→new value diffs, anchor these pain-point sections.)

## Profile B — marketing-site

**App-classifier signal:** `agency` (public, no-auth). Inventory tell: anonymous-visitor funnel ending in a form submission to a CRM. (There is no `marketing` enum value — the classifier emits `agency` for this shape; never key this profile on a token outside the six-value enum.)

**What this type is.** Content is the product. No authenticated state, no multi-actor workflow, no transactional state machine. The user is anonymous throughout; the entire IA routes them toward one event — a form submission that enters a CRM record. Teardown witness: brite-labs-site.

**Granularity band (per-domain, standard scale).** **3–6 named surfaces** per domain — narrower than internal-ops, much narrower than programmatic-SEO. Typical shape: one hero/above-fold conversion surface (email capture + CTA + social proof in the same scroll band), one or two credibility surfaces (split by audience segment only when content shape genuinely differs — B2B exec quote vs consumer star-rating carousel), one pricing surface, one per-form conversion path. Over-decomposition risk is real for credibility/content (do not split per testimonial or per blog post unless the template differs). Under-decomposition risk is real for the conversion path — split the form surface from the post-submission confirmation state (what the user sees, what enters the CRM, what follow-up fires). (Mobbin: ClassPass combines a quote + logo grid on one screen — one flow; WSJ earns a separate case-study sub-flow per partner because each has a distinct narrative structure.)

**Dimension modifiers.**
- **D3 (edge coverage) re-routes.** No permissions or tenant atomicity to test — re-aim the negative/edge weight at: form validation states (each field: empty submit, invalid format, valid submit, server error — with the specific field and error string when code-confirmed), the CRM integration boundary (success → record created, duplicate email, required-field rejection, network failure/retry, and what the user observes in each), consent/compliance (opt-in checked vs unchecked, ToS required vs not, and the observable difference in what enters the CRM), and content accuracy (assert the specific claim — pricing tier names, feature list, logo set — matches the source of record). All counts are over substantive scenarios; "Form submits successfully" as the only scenario is the D3 failure. Permission-denied, tenant-boundary, audit-trail, and multi-actor scenarios should **not** appear — fabricating them signals an AC set copy-pasted from an internal-ops context. (The spine's D3 domain-conditional clause means a permission-free form is not a spine fail for lacking a permission scenario — it is scored against these re-routed classes.)
- **D11 (frame) carries extra weight — the most common defect here.** Human-actor surfaces (hero capture, pricing review, case-study reading, demo booking) use the job-story frame. Non-human/infra surfaces (SEO crawlability, sitemap generation, CSP enforcement, redirect rules, analytics firing, canonical-URL resolution) use the constraint-spec frame and still need AC-level precision (exact meta-tag values, sitemap include/exclude rules, CSP directives). "When I'm a search engine crawler, I want…" scores **1 on D11** regardless of the rest of the AC — the named brite-labs-site defect.
- **D7 (persona).** Personas are intent-and-channel segments, not demographics or session roles: "evaluator from a paid-search ad comparing three vendors, 10 minutes to decide, will leave if pricing isn't findable" vs "referred visitor who already trusts the brand, wants the fastest path to trial." Each carries a posture (intent urgency, skepticism, prior knowledge) and a tolerance profile, specific to the surface. A generic "marketing site visitor," or "Commercial buyer / Newsletter subscriber" copy-pasted across surfaces, is the D7 failure.
- **J3 / J4 (journey).** Marketing journeys are funnel-shaped: trace arrival channel → discovery → credibility → intent confirmation → conversion event, with named pain points and root cause at each phase gate (where visitors abandon and why — pricing ambiguity, form friction, social-proof mismatch, CTA/intent mismatch). Name the cross-surface handoffs owned by different disciplines (content / engineering form+CRM write / design / SEO). "Visitor lands on hero, then pricing, then form" is the J3 thin-journey failure — a flow index, not a journey.

## Profile C — b2b-ecommerce

**App-classifier signal:** `marketplace`. (`SaaS` resolves here only via the SaaS tie-break: catalog → cart → order → invoice present.) Inventory tell: catalog → cart → order → invoice → fulfillment, with account-scoped pricing and PO/net-terms paths.

**What this type is.** A transactional storefront where authenticated buyers place orders on behalf of organizations; physical or configurable goods, an ongoing account relationship. B2B layers quantity breaks, account-scoped pricing, PO/net-terms payment, multi-address shipping, and large-order approvals on top. Teardown witnesses: brite-supply-react (buyer storefront), brite-pim (catalog/spec data).

**Granularity band (per-domain, standard scale).** **6–10 flows** cover most storefronts. The PDP is one pattern parameterized by product type — decompose only when the interaction model diverges (configurable vs fixed-quantity vs subscription), not per product type. Cart-to-checkout is 2–3 flows by payment path (card vs PO/net-terms vs quote-request); account management is 2–3 (order history + reorder, address book, billing/invoices). Split on actor change (buyer vs approver vs guest), payment-path change, lifecycle-state change (active vs on-hold vs cancelled), or distinct discipline. Collapse near-identical entity pages with a "variant shape" note. (Mobbin: Faire's PDP handles case-quantity tiers, variants, delivery estimate, and returns as one screen; AWS's PO management is a genuine 2-step wizard — header vs line items — because trigger and data model differ.) Resist the PIM overfit signal: 8 product types do not need 8 PDP flows — the named teardown defect was 6 near-identical PIM entity sub-flows producing 30 children for one shared pattern (D9 over-decomposition, scored by the sibling-title test, not by the band).

**Dimension modifiers.**
- **D2 / D3 (testability, edge) amplified on transactional contracts.** Quantity-break pricing ACs name exact break points and computed totals ("selecting 24 units shows $360.00 ($15/unit)," not "price updates correctly"). Payment-path branching: card and PO/net-terms are distinct state machines, each with its own scenario set; an invoice-on-request path out of scope gets a NOT_BUILT or explicit handoff label (D4). Order-status lifecycle (draft → submitted → on-hold → confirmed → shipped → delivered, plus cancelled) must cover the on-hold state and its buyer-visible message. Reorder ("add all to cart") and CSV export are real B2B affordances that belong in ACs, not footnotes. Account-scoped data isolation (buyer A cannot see B's pricing, PO history, or addresses) is a **mandatory** tenant-boundary AC, not an optional edge. (Mobbin: Faire's "On hold — we're reviewing your order" status with an "Action required" tab; AWS PO line-item table with Bill-to/Ship-to and payment terms.)
- **Reduce relative to the spine default.** SEO/crawler/sitemap constraints apply to marketing-site, not authenticated storefronts — a single constraint-spec covers any public catalog page; do not thread SEO through transactional flow specs. Demographic persona detail (job title, company size) is context, not AC-driving.
- **D7 / D11 (persona, frame).** Personas are named role-bearers with procurement responsibility and job-cost pressure: procurement buyer (bulk orders, reorder cadence, needs price certainty before committing, low tolerance for ambiguous order status), finance reviewer/approver (reviews holds, validates against PO numbers, enters at order-history and invoice screens). A single "commercial buyer" on every flow including fulfillment and invoice is the D7 failure. System/infra flows (inventory sync, price-feed ingest, PIM indexing, order-state webhooks) use the constraint-spec frame; the PO/net-terms approval flow may mix a human job story with a system-validation constraint spec in one document, clearly labelled — "When I'm the price-feed ingestion job" is the D11 failure.
- **J3 (journey).** Phase-scoped pain points with root cause: catalog discovery (spec data missing/inconsistent across SKUs — PIM completeness, not UI), pricing certainty (displayed ≠ invoiced — contract data not surfaced at PDP), checkout path selection (PO-number capture and net-terms friction), order status + hold resolution (the highest drop-rate phase — "on hold" with no reason or remediation), post-order reconciliation (invoice-to-PO linkage, bulk reorder). Rich journeys name which phase has the highest drop and the spec change; thin journeys restate the inventory. (Mobbin: Faire's "Action required" tab is the pattern that resolves hold ambiguity; GoDaddy/Faire/Adobe all surface CSV export for reconciliation.)

## Profile D — programmatic-seo

**App-classifier signal:** `SaaS` / `agency` **with a generation plane** — resolved by the inventory tell (template × dimension generation matrix), never by a bare category. (For `SaaS`, this is the SaaS tie-break's "generation plane" branch.) Inventory tell: a template × dimension matrix generating large page sets, plus an operator admin plane.

**What this type is.** A system generating large page sets (tens to hundreds of thousands of URLs) from a template × dimension cross-product (`{service} in {location}`, `{attribute} + {entity-type}`). Two distinct user-facing planes: the **generation/admin plane** (operators configure templates, seed data, trigger runs) and the **rendered-output plane** (anonymous crawlers and searchers consume pages). Quality judgment covers both. The named teardown failure mode is FK-fragility: infrastructure wired to unstable semantic flow-IDs rather than stable contracts.

**Granularity band (per generation-domain, standard scale).** Split **per generation mechanism, not per page type.** The common over-decomposition trap is treating each matrix dimension as a flow (`/location-pages`, `/category-pages`, `/location-category-pages`). Split only at: different generation trigger (cron crawl vs operator seed vs feed ingest), different template contract (index/hub vs leaf/detail are genuinely different schema and link structures), different discipline owner (sitemap/robots = SEO-eng, content gating = editorial, schema markup = structured-data eng), or a confirmed not-built gap needing a stub. Do not split for "we have 12 city tiers" or "5 offer verticals" — those are parameter values. Typical well-decomposed platform, **per generation-domain at standard scale: 4–8 flows** (template engine, index hierarchy, leaf contract, sitemap/canonical infra, content quality gate, generation-run lifecycle, 1–2 NOT_BUILT stubs). (This band is per generation-domain, like every other profile's band — not a whole-platform cap; a platform with multiple generation domains carries the band once per domain.) (Mobbin: Fresha's service×city matrix, TripAdvisor's region-grouped index, ClassPass's city list, and Airbnb's long-tail index all share one template with parameter substitution — variation is in dimension set and depth, not distinct archetypes.)

**Dimension modifiers.**
- **D2 / D3 (testability, edge) elevated on the infra contract — pSEO legitimately carries larger AC sets.** Required: canonical/duplicate coverage (when two dimension combos resolve to the same semantic page — "New York" vs "NYC" — name the exact dedup rule and the `<link rel="canonical">` or redirect behavior), thin-content gate (name the threshold — word count, entity count, or schema-completeness score — not "adequate content"), generation-run failure modes (data feed missing / partial / malformed: halt, skip, or publish degraded — each a named AC), internal-link-graph integrity (index pages ARE the link graph — name the link-selection query: top-N by count, alphabetical, geo-proximity, and the fallback when N < minimum), and the sitemap/robots contract as constraint-spec ACs. Deprioritize RBAC/permission (generation plane has basic auth, output is public), tenant isolation (typically single-tenant), and session-state edges (no sessions on output).
- **D11 (frame) applied aggressively — pSEO has the highest proportion of infra/non-human flows.** Job-story frame for operators (configuring a template, reviewing a run, approving the quality gate) and for the searcher arriving at a leaf page. Constraint-spec frame for sitemap generation, canonical assignment, robots.txt, schema.org emission, crawl-budget controls (noindex/nofollow, rel=next/prev), run scheduling and idempotency, redirect-chain management, and automated content-threshold enforcement. Writing "When I'm a search engine crawler, I want a sitemap…" is the D11 failure — and the FK-fragility teardown defect is a direct consequence of mixing frames: treating URL-routing infra as a job story obscured the identifier-stability requirement that a constraint-spec "Given" surfaces naturally.
- **D4 / D7 (NOT_BUILT, persona).** NOT_BUILT stubs are especially load-bearing — the FK-fragility failure propagates silently when a planned dimension lacks even a stub; an absent stub is a spec gap with active risk, not "not yet written" (D4). (Stubs satisfy D4; they still do not count toward D3's substantive-scenario minimum per the spine's D3/D4 boundary.) Personas: the operator (named, role-specific — configures dimension sets, reviews runs, approves thresholds; their job is knowing a run completed cleanly with no duplicate/thin/broken pages reaching the index), the crawler (systematic traversal, crawl-budget sensitivity, schema correctness — not a job-story actor), and the anonymous searcher (intent-driven, high bounce tolerance unless above-fold relevance signals immediately). Writing "a user looking for [service] in [city]" as the persona for every leaf flow is a query description, not a behavioral persona — the D7 failure, acute here.
- **J1 / J3 (journey) split into two arcs kept separate.** The generation-lifecycle journey (operator-facing: feed arrives → template configured → run triggered → quality gate → published/held → sitemap updated → coverage verified) names root causes — feed latency (upstream dependency, not platform bug), gate false-positive rate (threshold miscalibration), run-idempotency failure (FK-fragile identifiers). The searcher-discovery journey (anonymous, organic: query intent → SERP listing → above-fold relevance → internal navigation → conversion) must cover the two highest-value moments — the SERP click-through signal (title/meta quality) and internal-link traversal (crawl efficiency + bounce reduction). A journey ending at "user lands on page" misses both. Thin journeys restate the matrix dimensions ("user can find Hair Salons in Melbourne, Sydney…") without naming why a searcher navigates deeper vs bounces (count badges, ratings, above-fold entity density tied to the template contract). (Mobbin: every mature pSEO platform renders a rich cross-link section — regional siblings, service siblings, related categories — as the primary exit path; the page IS the link graph.)
