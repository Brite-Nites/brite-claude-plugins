# Linear Writeback Pattern

Cross-cutting adaptation layer (Q46) for **post-scaffold ongoing Linear writes only**. Consumers call a single `linear_writeback(...)` function; this layer enforces idempotency markers, signature-based comment dedup, clobber-with-warning conflict resolution, and a canonical type registry that rejects unknown writeback types. Initial scaffolding (Q13) and legacy `## FDA migration` migration (Q14) stay direct — they precede this layer.

## Scope

**In scope (v1):**

- `/flow:ship` (Q53, pending) — `ship-summary` body section on parent + comments on completed children.
- `/flow:retro` (Q44, pending) — `retro-summary` comment on the completed milestone.
- `/flow:plan-{discipline}` (Q43, pending) — `plan-X-section` body section on the discipline child.

**Out of scope:**

- Q13 initial scaffold writes (direct via sub-skill).
- Q14 legacy `## FDA migration` section (direct via Q14 with `FDA-MIGRATION-*` HTML markers — the precursor pattern Q46 generalizes; Q14 stays as-is).
- Q13.3 fidelity-review body retries (Q13.3's inline pattern).

## Marker convention

Body-section idempotency uses generalized HTML-comment markers — hyphenated, kebab-case, lowercase — matching Q14.2's `FDA-MIGRATION-*` precedent (`:98`):

```
<!-- FDA-WRITEBACK-<type>-START -->
... content managed by /flow:<consumer> ...
<!-- FDA-WRITEBACK-<type>-END -->
```

Example: `<!-- FDA-WRITEBACK-ship-summary-START -->`. The `FDA-WRITEBACK-` namespace stays separate from `FDA-MIGRATION-` (no collision).

## v1 type registry

The canonical enum. Each entry is a kebab-case lowercase string. Adding a type requires editing this file **and** an amendment note in Q46's lock entry (mirrors Q31's amendment pattern).

- `ship-summary`
- `retro-summary`
- `plan-story-section`
- `plan-eng-section`
- `plan-design-section`
- `plan-qa-section`
- `plan-docs-section`
- `audit-concerns` (registered but UNUSED in v1 per Q38 deferred-decision resolution; reserved for v1.1 `--linear-surface` promotion)

Unknown-type writes are rejected with:

```
Unknown writeback type '<value>'. Valid types: <enum>. To add a new type,
amend Q46 + register at _shared/linear-writeback-pattern.md.
```

This forces deliberation on every new type and catches typos at the call site.

## Interface

Single function callable by consumers (verbatim from Q46 sub-decision 7, `:1041-1049`):

```
linear_writeback({
  issue_id: string,
  type: WritebackType,           // enum from this file
  surface: 'body' | 'comment',
  content: string,
  signature?: string,            // required for surface='comment'
  breadcrumb_path: string,
  warn_on_clobber?: boolean      // default true
}) → { result: 'created' | 'updated' | 'skipped', issue_url, warnings: string[] }
```

## Idempotency model

- **Body sections** — re-writing the same `<type>` on the same issue replaces only the content between the matching `START` / `END` markers; everything outside the markers is preserved verbatim.
- **Comments** — each Q46 comment opens with a signature line `_Generated by /flow:<skill> for <issue-id> on <ISO-8601>_`. On write, `list_comments` is matched against this signature; on hit, the existing comment is updated; on miss, a new comment is created and its ID is recorded in the breadcrumb's `linear_writeback_state.comment_ids[]` for cross-run resilience.

## Conflict resolution

Clobber-with-warning (per user lock 2026-05-07):

- Hand-edits **inside** markers are clobbered on re-run. A warning is emitted to stdout and persisted to `linear_writeback_state.warnings[]`: `"Detected user-edited content inside <type> markers on <issue-id>. Q46 will replace this content. To preserve user edits, move them outside the markers."`
- Hand-edits **outside** markers are preserved.
- Hand-edits to Q46-created comment bodies are clobbered on re-run (signature dedupes). User-created comments (no signature match) are never touched.

The framing is **machine-managed-region contract**: markers signal user-edits-out-of-bounds; clobber is loud (stdout + breadcrumb). This is best-effort, NOT a transactional lock — Linear MCP does not support that.

## Within-run throttle

Q46 checks `(issue_id, type, run_id)` against `linear_writeback_state.written_pairs[]` (Q31 amendment 2 schema slot) before each write; duplicate writes within the same run are rejected. Re-attempts with the same `(issue_id, type)` update the existing write rather than creating a new one. Cross-skill batching is a per-consumer concern, not a Q46 enforcement; see `plugin CLAUDE.md` (Q55) for the convention.

## Adding a new type

1. Edit this file's **v1 type registry** section to add the new kebab-case enum value.
2. Add an amendment note to Q46's lock entry (e.g. `Q46 amendment 1`) following the Q31 amendment audit-trail pattern.
3. Update consumer locks (Q43 / Q44 / Q53 / Q38) that need to emit or consume the new type.
